One-sided RDMA-Conscious Extendible Hashing for Disaggregated Memory

本文针对存算分离（Memory Disaggregation）架构下计算节点必须通过单边 RDMA 原语操作“弱算力”内存池的场景，解决了传统哈希索引在处理哈希冲突和并发控制时产生的大量网络往返（RTT）和远程原子锁开销问题。

问题

在存算分离架构中，计算池（Compute Pool）与内存池（Memory Pool）解耦。内存池通常由弱算力的 RNIC 或控制器管理，无法执行复杂的索引逻辑。这导致现有的“RDMA-Search-Friendly”哈希方案（如 Pilaf, FaRM, DrTM）面临严重失效：

  • 原有方案的不适应性：

    • IDU 请求无法卸载：传统方案中，Search 请求通过 RDMA READ 完成，但 Insert/Delete/Update (IDU) 请求通常发送给远端 CPU 执行。在存算分离架构下，由于内存池缺乏算力，IDU 请求必须由客户端通过单边 RDMA 动词（READ/WRITE/ATOMIC）直接实现。

    • 哈希冲突处理的高昂代价：

      • Pilaf (Cuckoo)：插入时若发生驱逐，需要计算 Cuckoo Path 并锁定路径上的所有桶。这涉及大量的 RDMA CAS（加锁）和 RDMA WRITE（移动数据），导致极高的插入延迟。

      • FaRM (Hopscotch)：寻找空槽需要线性探测（Linear Probe），在高负载下可能需要读取整个表。移动元素以保持邻域属性（Neighborhood）需要锁定多个桶并多次写入。

      • DrTM (Cluster)：插入需要遍历链表（每个桶一次 RDMA READ），添加溢出桶涉及复杂的内存分配和链表指针更新，同样产生大量 RDMA 操作。

  • 底层开销分析：

    • 网络往返（Network RTT）雪崩：由于单边 RDMA 操作无法在服务端组合逻辑，每一次指针追踪或数据移动都意味着一次完整的 RTT。

    • 远程原子锁开销：在本地内存中，锁的开销是纳秒级的；但在存算分离中，远程加锁必须使用 RDMA ATOMIC (CAS) 动词，其延迟是微秒级的。Cuckoo 或 Hopscotch 这种由于数据移动需要同时锁定多个位置的策略，会显著加剧锁竞争和延迟。

    • 扩展性调整（Resizing）困难：传统全表扩容（Full-table resizing）需要移动所有数据，代价不可接受。即便是可扩展哈希（Extendible hashing），每次访问都需要先读目录（Directory）再读桶，增加了一次额外的 RDMA READ。

Researcher’s Comment:

这里的问题本质在于逻辑操作的原子性与物理原语的原子性不匹配。在本地内存中，CPU 可以用一条指令或缓存行锁定来掩盖复杂的数据结构调整（如链表插入或 Cuckoo 踢出）。但在 RDMA 环境下，这些操作被“拆解”成了多次网络交互。Paper 敏锐地指出了“Data Movement”是性能杀手——因为移动意味着 Read-Modify-Write 循环，这在网络上是昂贵的。

解决方案 (The Solutions)

RACE Hashing 的核心在于设计了一种完全依赖单边 RDMA 且 最坏时间复杂度为常数 的索引结构，并配合乐观的客户端并发控制。

1. RAC (RDMA-Conscious) 子表结构设计

为了消除 IDU 操作中的数据移动和链表遍历，RACE 重新设计了哈希表结构：

  • 无数据移动（No Data Movement）：放弃了 Cuckoo 的踢出机制和 Hopscotch 的滑动机制，以此避免连锁的 RDMA WRITE。

  • 机制拆解：

    • 多路组相联（Associativity）：每个桶包含个槽位，允许单次 RDMA READ 读取多个条目。

    • 两次选择（Two Choices）：利用和计算两个独立的位置，写入负载较低的一个。权衡：作者指出虽然 3 个哈希函数能提供更好的负载均衡，但在存算分离下会增加一次 RDMA READ，因此选择了 2 个。

    • 溢出同构（Overflow Colocation）：将两个主桶（Main Bucket）和一个共享的溢出桶（Overflow Bucket）组成一个连续的 Bucket Group。利用 RDMA 的 Doorbell Batching 特性，客户端可以在一个 RTT 内并行读取这两个 Combined Buckets（主桶+溢出桶），从而在一个 RTT 内完成查找。

Researcher’s Comment:

这个设计非常聪明地利用了 Two Choices 理论来换取空间利用率，同时通过 Overflow Colocation 解决了 Two Choices 通常带来的多次随机访问问题。它把逻辑上不连续的溢出桶在物理上变得连续，从而利用 RDMA 对于连续内存读取（或 Scatter/Gather）的高效性。这是典型的软硬件协同设计（Co-design）。

2. 无锁远程并发控制 (Lock-free Remote Concurrency)

为了避免昂贵的远程锁，RACE 设计了基于 8字节原子操作的并发协议。

  • 8B Slot 设计：为了适配 RDMA CAS（仅支持 8 字节），桶中的每个 Slot 被压缩为 8 字节：Fingerprint (8 bit) + Length (8 bit) + Pointer (48 bit)。

  • KV 分离：完整的 KV 数据存储在哈希表之外，表内仅存指针。

  • 无锁操作流程：

    • Insert：并行读取两个 Combined Buckets 并在远端写入 KV 数据块 -> 寻找空槽 -> 使用 RDMA CAS 写入指针。若成功则结束；若失败（被抢占）则重试。

    • Delete/Update：通过 RDMA CAS 将 Slot 置空或更新指针。

    • 重复键检测：由于 RDMA CAS 仅保证 8 字节原子性，可能出现两个客户端同时插入相同 Key 到不同位置。解决方案是插入后**重读（Re-read）**桶，基于确定性规则（如最小桶号）保留一个，删除另一个。

Researcher’s Comment:

这里最精彩的 Trade-off 是指纹（Fingerprint）的使用。8 bit 的指纹虽然有误判率，但足以作为第一层过滤。更重要的是，它把元数据压缩到了 8 字节以内，使得由于缺乏 16 字节原子写（RDMA 目前的限制）而无法实现的“无锁指针交换”变得可能。虽然插入后的 Re-read 增加了一点开销，但相比于全局加锁，这是一个极佳的 Optimistic Concurrency Control (OCC) 实践。

3. 带有陈旧读的可扩展远程扩容 (Extendible Remote Resizing with Stale Reads)

为了解决可扩展哈希带来的额外目录查询开销。

  • 客户端目录缓存（Client Directory Cache）：客户端缓存目录副本（Directory），直接在本地计算目标子表地址，节省一次 RTT。

  • 陈旧读处理（Stale Reads Handling）：

    • 问题：当其他客户端触发扩容时，本地缓存可能过期，导致访问错误的子表。

    • 验证机制：在每个 Bucket 的 Header 中存储 Local Depth (LD) 和 Suffix。客户端读取桶时，对比 Header 中的 LD 和 Suffix 与自己缓存中的是否一致。

      • Case 1 (Match): 缓存有效，继续操作。

      • Case 2 (LD mismatch but Suffix match): 子表已分裂但目标 Key 仍留在该桶，数据有效（无需更新目录）。

      • Case 3 (Both mismatch): 访问错误，需重新拉取目录并重试。

  • 并发扩容：扩容操作仅锁定目录项（Directory Entry），不阻塞对正在迁移的子表的 Search/IDU 操作（通过严格的写入顺序保证一致性）。

Researcher’s Comment:

这一设计体现了**”Verify, don’t wait”** 的哲学。在分布式系统中，与其通过广播或租约（Lease）来强行同步所有客户端的视图（这非常慢），不如允许客户端持有旧视图，但在访问数据时进行懒惰验证（Lazy Validation）。Bucket Header 充当了 Version Number 的角色，以极小的空间代价（每个桶一个 Header）消除了昂贵的同步开销。

核心亮点 (Key Insights & Trade-offs)

  1. 常数级 RDMA 操作 (Constant RTTs)：

    RACE 的最大贡献在于将 Search/Insert/Update/Delete 的最坏情况网络开销限制在了常数级别（通常是 1-3 个 RTT）。相比之下，Pilaf 和 Hopscotch 在高负载下的 RTT 是不可控的。这对于尾延迟（Tail Latency）敏感的数据中心应用至关重要。

  2. 物理限制驱动的数据结构设计：

    文章的设计完全围绕 RDMA 的物理限制展开：

    • 因为 CAS 只有 8 字节设计了 Fp+Len+Ptr 的 Slot 结构。

    • 因为 READ 延迟高利用 Doorbell Batching 并行读取。

    • 因为 WRITE/ATOMIC 昂贵抛弃了 Cuckoo/Hopscotch 的重排机制，改用 Associativity + Two Choices。

  3. 乐观并发与客户端协同：

    RACE 将复杂性推给了客户端（Client-side logic）。内存池保持“dumb”状态，仅提供基本的内存读写。通过允许临时不一致（如重复插入、陈旧目录视图）并依靠后续的校验/修正逻辑（Re-read check, Header check）来保证最终正确性。这是一种典型的用**计算（客户端校验）换取网络带宽（减少同步消息）**的策略。
