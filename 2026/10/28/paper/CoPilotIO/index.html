CoPilotIO：让 CPU 充当 GPU I/O 的副驾驶

论文：CoPilotIO: CPU as a Co-pilot for GPU I/O to Free GPU Compute，Guanyi Chen、Qi Chen、Shu Yin、Jian Zhang，USENIX OSDI ’26（2026）。论文与会议信息。

TLDR： CoPilotIO 将 submission queue（SQ，提交队列）放在 GPU 显存、completion queue（CQ，完成队列）放在 CPU 固定内存，让 GPU 发起细粒度 I/O、CPU 核默认轮询 CQ；硬件 cuda::barrier 通知等待中的 warp（线程束），无锁 barrier-table 按 NVMe command ID 关联请求与 barrier。CQ 积压时，GPUAgent 与 CPUAgent 协同轮询。论文摘要报告，相比 BaM，I/O 引发的停顿最多减少 55.5%，饱和 GPU PCIe 带宽所需的 streaming multiprocessor（SM，流式多处理器）减少 50%；端到端结果中，Deep Learning Recommendation Model（DLRM，深度学习推荐模型）推理相对 BaM 提速 1.85 倍（85%）。详细扩展性实验另报告 24 个 SM 对比 BaM 和 AGILE 的 72 个以上，和摘要的 50% 口径并不完全吻合。

一、背景：显存限制与 GPU I/O 控制路径

GPU 工作集可能超过设备显存，应用需要从 SSD 按需读取数据。GPU I/O 因而同时要满足两个条件：请求由 GPU kernel（GPU 计算内核）按实际访问发起，避免把无关数据预加载到显存；I/O 过程又不能长期占用 GPU 计算资源。

GPU 的调度单位是 warp（线程束），论文所述每个 warp 含 32 条线程；多个 warp 在流式多处理器（SM）上交错执行。若 I/O 请求只能由发起请求的 warp 反复轮询完成状态，这个 warp 会持续占着调度机会，其他计算 warp 也可能因此延迟。GPU I/O 的控制路径放在哪里，既影响 I/O 吞吐，也影响计算可用的 SM 资源。

二、现状：CPU 与 GPU I/O 控制路径的取舍

CPU 主导的方案以 NVIDIA GPUDirect Storage（GDS）为例：SSD 可以通过 PCIe DMA 直接向 GPU 缓冲区传数据，但每条请求的控制操作仍经过 CPU 和 OS kernel。它不消耗 GPU 核做轮询，却难以用有限的 CPU 并行度和 kernel I/O 栈开销达到 GPU PCIe 带宽上限；GPU kernel 也不能直接发起真正按需的 I/O，应用通常要先把数据预加载到显存。

GPU 主导的方案以 BaM 为代表。GPU 线程直接构造 NVMe 命令、写 SQ、更新 doorbell 寄存器并轮询 CQ，从而让 GPU kernel 按需发起 I/O；但轮询 CQ 的线程会占据 GPU 执行和内存资源。AGILE 为轮询分配专用 SM 并支持异步 I/O，不过仍需 GPU 线程轮询软件锁标志，也会保留专用 SM。

论文的动机实验指出，GPU 主导轮询会形成三种停顿：

  • warp 内停顿（intra-warp stall）：发起 I/O 的 warp 轮询 CQ 时，即使后续计算与 I/O 返回数据无关，同一 warp 也不能越过轮询指令继续执行。
  • warp 间停顿（inter-warp stall）：轮询 warp 仍被调度器视为可运行，会占用 SM 的发射机会，延迟同一 SM 上的计算 warp。
  • SM 间停顿（inter-SM stall）：BaM 和 AGILE 将 SQ/CQ 放在 GPU 全局内存；应用访问显存与轮询 CQ 争用带宽，CQ 检测和 I/O 完成处理随之变慢。

GPU I/O 轮询引起的三类停顿（Figure 1: (a) Intra-warp stall: independent compute operation is stalled by I/O polling; (b) Inter-warp stall: compute warp is delayed from being scheduled as I/O polling warps keep occupying the GPU cores; (c) Inter-SM stall: I/O polling warps and regular application memory accesses contend for the global GPU memory.）

在 A100 上，论文指出 BaM 要用 80 多个 SM 才能使四块 SSD 的聚合带宽达到 PCIe 上限；AGILE 需要保留 32 个 SM 轮询。论文的 CPU 用户态对照使用 16 个 CPU 线程，在请求大于 16 KB 时可以达到单块 SSD 的带宽上限；小于 16 KB 时，CPU 并行度不足以提供设备所需的轮询速率。论文估计，若仅靠 CPU 轮询来使 GPU PCIe 链路达到带宽上限，需要专门分配 64 个以上 CPU 核。CPU 用户态轮询虽能绕过 OS kernel I/O 栈，却不能让 GPU 发起细粒度请求，也难以单独承担小 I/O 的高 IOPS（每秒 I/O 操作数）轮询。因此，目标是保留 GPU 发起请求的按需能力，同时把完成轮询从 GPU 移走，并在 CPU 并行度不足时仍维持带宽。

GPU 主导 I/O 的停顿测量（Figure 2: I/O Stall Analysis of the GPU-Centric Design.）

三、问题：跨 CPU–GPU 的 I/O 协调

如果把 SQ 和 CQ 都留在 GPU，GPU 可以快速提交命令，但 CQ 轮询继续造成三类停顿。如果把请求控制全部放在 CPU，GPU 又无法直接按需发起 I/O，小请求的轮询并行度也会受 CPU 核数限制。

因此系统要解决三件事：GPU 如何低开销提交 NVMe 请求；CPU 观察到完成后如何安全唤醒正确的 GPU warp；CPU 可用核心不足以及时处理 CQ 完成项时，如何增加轮询并行度，而不让所有 I/O warp 重新回到 GPU 上忙等。

四、方案：split SQ/CQ 与自适应 CPU–GPU 轮询

4.1 GPU 提交 SQ，CPU 轮询 CQ

CoPilotIO 将 NVMe SQ 放在 GPU 显存，将 CQ 放在 CPU 固定内存中。GPU 继续直接写 SQ 并提交命令；CPU 可以在用户态轮询 CPU 固定内存中的 CQ。GPU 也能通过 PCIe 对 CPU 固定内存做 zero-copy（零拷贝）读写，即直接访问这块固定内存而不显式复制到 GPU 显存。论文另做一组对照，只改变 CQ 所在位置，比较 GPU 轮询 CPU 固定内存（CPU DRAM）与 GPU 显存（GPU VRAM）的配置。在这条 GPU 轮询路径中，每条命令只读写约 4 B（例如 command ID 和 status 字段）。

论文的两个库分别承担请求侧和完成侧职责：GPU 端的 CoPilot-GPUIOLib 提供类似 POSIX 的 async_read、async_write 接口；CPU 端 CoPilot-CPUIOLib 用类似 SPDK 的用户态路径提交命令、轮询 CQ 和协调 DMA，不经过 OS kernel I/O 栈。

用户态 CPU I/O 轮询对比，以及 SQ/CQ 在 CPU DRAM 与 GPU VRAM 中的位置对带宽的影响（Figure 3: (a) User-space CPU I/O polling performance comparing GDS and BaM; (b) Impact of placing Completion Queue (CQ) and Submission Queue (SQ) in CPU DRAM versus GPU VRAM.）

4.2 cid 映射与 cuda::barrier 唤醒

GPU 发出请求时，CoPilot-GPUIOLib 为该请求分配 NVMe command ID（cid），创建对应的 cuda::barrier，并把 cid 与 barrier 的映射写入位于 CPU 固定内存的表。应用可在依赖 I/O 数据的计算前等待该 barrier；与忙等不同，硬件 barrier 会挂起等待中的 warp，让调度器继续运行其他就绪 warp。

CPUAgent 发现 CQ 完成项后读取 cid，查表取得 barrier 并将其触发。GPU warp 随后恢复执行依赖这次 I/O 的计算。发生 NVMe I/O 错误时，CPU 仍回收 cid 并触发 barrier，同时记录错误标记，由 GPU 端醒来后处理重试或向应用报告错误。平台不支持硬件 barrier 时，论文还给出由 CPU 通过 GDRCopy 向 GPU 显存写完成标记的备用路径。

CoPilotIO 的 I/O 提交、完成轮询与 GPU 通知流程（Figure 4: Design Overview of CoPilotIO. Application warps initiate I/O through CoPilot-GPUIOLib, after creating cuda::barrier and cid, 1 CoPilot-CPUIOLib submits the I/O requests to SQs and immediately returns control to the application. 2 CoPilot-GPUIOLib writes the cid and the cuda::barrier to barrier-table that resides on the CPU memory. 3 and 4 CPUAgent polls the CQ until it receives a CQ entry and extracts the cid. 5 and 6 CoPilot-CPUIOLib looks up the cuda::barrier using the cid. At the end, CoPilot-CPUIOLib uses 7 to notify the application warp on the GPU.）

论文使用无锁 barrier-table（屏障映射表）把 cid 映射到 barrier。NVMe cid 为 16 位；每项 cid 与 barrier 对应关系占 8 B。每个表按私有 warp 实例分配，GPU 端以 cid 为索引写入，CPU 端直接按 cid 读取，因此插入不需要在多个 warp 之间争用锁。按每块 SSD 配置 128 个 NVMe queue pair（队列对）、每队列深度 1024、共 4 块 SSD 计算，表的总空间为 8 B × 1024 × 128 × 4 = 4 MiB。

4.3 CQ 积压驱动的请求分流

CPU 核可以避免 GPU 轮询停顿，但小请求或 CPU 资源紧张时，CPUAgent 可能跟不上 CQ 完成速度。CoPilotIO 为每个 CQ 配置高、低两个迁移阈值，并按请求批次检查 CQ 待处理完成项数。GPUAgent 默认关闭；CPU 端发现 CQ 待处理完成项数超过高阈值后，将新请求绑定到 GPU 轮询的 CQ，并唤醒 GPUAgent。CQ 待处理完成项数降到低阈值以下后，系统停止向该队列加入新请求，GPUAgent 处理完队列中剩余项后关闭，后续请求回到 CPU 轮询队列。

CQ 始终位于 CPU 固定内存。CPUAgent 和 GPUAgent 各轮询独立 CQ，CPUAgent 不会因 GPUAgent 开启而关闭；改变的是新请求写入哪个 CQ，而不是把轮询线程在 CPU 和 GPU 间搬迁。GPUAgent 每个 SM 只启用一个轮询 warp，与应用 kernel 共用 SM；不轮询时可以睡眠，完全切回 CPU 后可以关闭。论文没有给出适用于所有负载的固定阈值数值，机制依据运行时队列积压调节。

CQ 积压触发 GPUAgent 协同轮询（Figure 5: CQ-based Adaptive Polling. At epoch N, CPUAgent is enabled by default to poll the CQ, while GPUAgent remains disabled. At epoch N + 1, CoPilotIO detects that the CQ is becoming overloaded and the CPU can no longer sustain high throughput, GPUAgent is activated to assist with polling.）

五、结果：停顿、带宽与应用性能

5.1 微基准与 PCIe 扩展性

评测平台为双路 Intel Xeon Gold 6530（每路 32 核）、256 GB DDR5；GPU 包括 NVIDIA A100 40 GB 和 H800 80 GB。软件环境为 Ubuntu 22.04.4、Linux 5.15.0、CUDA 12.4 和 NVIDIA 驱动 550.54.14。存储设备为 4 块 1 TB Samsung 990 Pro NVMe SSD，每块使用 PCIe 4.0 x4。论文报告的 PCIe 4.0 x16 链路带宽上限约为 25 GB/s。除特别注明外，正文并未把每项微基准结果逐一对应到 A100 或 H800；涉及 25 GB/s PCIe 4.0 x16 饱和的扩展性结果对应 A100 平台。

停顿微基准将随机 I/O 与 Fused Multiply-Add 计算放在同一 GPU 上。warp 内测试使用 32 个 warp，每个 warp 交错执行计算和随机读，并改变计算与 I/O 的比例；warp 间测试固定 4 个计算 warp，逐步增加 I/O warp；SM 间测试改变产生显存流量的竞争 SM 数量。对比对象为 BaM（同步 I/O）和 AGILE（异步 I/O）。摘要报告 CoPilotIO 相比 BaM 最多减少 55.5% 的 I/O 引发停顿；正文还报告 BaM 的 warp 内停顿可使独立计算吞吐下降最多 87%，轮询 warp 与计算 warp 共跑时，总执行时间最多达到计算 warp 单独运行的 1.71 倍。warp 间微基准中，正文报告 CoPilotIO 将该类停顿最多降低 18.6%。在 SM 间测试中，竞争 SM 超过 24 个后，BaM 和 AGILE 的 I/O 带宽随竞争增加最多下降 50.6%；CoPilotIO 在 0–54 个竞争 SM 的采样点上保持约 6.4–6.7 GB/s。论文没有逐项说明停顿微基准所用的 GPU 型号，也没有报告队列深度。55.5% 是论文摘要给出的整体验证结果，论文没有把该最大值限定到某一种停顿子项。

GDS 对比是单 SSD 随机读，使用 16 个 CPU 线程，测试请求大小为 4、64、128 和 256 KB。CoPilotIO 在这四种大小下的读带宽均高于 GDS。作者将其归因于 CoPilotIO 的用户态队列绕过 GDS 每请求经过 kernel I/O 栈的系统调用、缓冲区注册和 DMA 地址映射开销。该测试使用哪张 GPU 卡和队列深度均未报告。

GDS 与 CoPilotIO 的随机读带宽对比（Figure 8: Random read bandwidth: GDS vs. CoPilotIO.）

自适应轮询微基准模拟 IOPS 随时间变化的 AI 应用，对比 CPU-only 与 adaptive polling；该测试共使用 96 个 CQ。请求负载增加时，CPU 处理的 CQ 数下降，GPU 处理的数量上升。adaptive polling 的带宽约维持在 5.5–6.1 GB/s；CPU-only 曲线在过载区间降至约 3.2 GB/s。低负载时最多使用 16 个 CPU 轮询核；启用 CPU–GPU 协同轮询后降至 3–4 个，中等 I/O 负载下通常需要 4–8 个。论文未报告该微基准的队列深度、精确 IOPS 序列或对应 GPU 型号。

扩展性测试是在 4 块 SSD 上进行 8 KB 随机读，每个 SM 运行 16 个 warp，配置 108 个 NVMe queue pair、每队列深度 1024。CoPilotIO 用 24 个 SM 饱和 A100 的 PCIe 4.0 x16、约 25 GB/s 链路；论文正文称 BaM 和 AGILE 需要 72 个以上 SM。摘要另称 CoPilotIO 比 BaM 少用 50% 的 SM。按正文所列 24 对 72 以上计算，减少比例至少约为三分之二；在 75 个 SM 的采样点上，BaM 和 AGILE 仍未达到 25 GB/s。论文没有解释摘要的 50% 与正文详细数字为何不同。

5.2 GoFS、MoE 与 DLRM

CoPilotIO 集成到 GPU 文件系统 GoFS 后，使用 4 KB 随机读与 BaM 对比，性能最高提升 17.4%；代码改动少于 20 行。AGILE 不原生支持该测试，作者尝试扩展时遇到未说明原因的运行时错误，因此 GoFS 对比中没有 AGILE。该测试的队列深度和结果对应的 GPU 型号未在正文说明。

LLM 的 MoE（Mixture-of-Experts，混合专家模型）推理测试将 FlashMoE 的 expert 权重从 GPU 显存改为 SSD 按需加载。工作负载有 2,048 个 expert，hidden/intermediate dimension 均为 2,048，Top-2 routing、sequence length 8,192、capacity factor 1.0；每个 expert 的上下投影权重合计 32 MB、全部权重共 64 GB。I/O 配置为 108 个 NVMe queue pair、队列深度 128、I/O page 大小 64 KB，每个 expert 读取 512 个 I/O page，由一个 warp 的 32 条线程协作。32 次预热后，作者测量 32 次前向传播（forward pass）的平均延迟。CoPilotIO 相对 BaM 提速 1.44 倍；AGILE 不支持这种运行时访问模式，未纳入比较。

DLRM 使用 Criteo 1TB Click Logs，词表由最初三天数据构建，稠密矩阵乘法使用 cuBLAS。模型的 bottom MLP 为三个 512 单元全连接层，top MLP 为三个 1,024 单元全连接层，batch size 为 2,048，测量 10,000 次迭代的端到端推理时间。默认使用 2 GB clock 替换策略软件缓存、128 个 NVMe queue pair、每队列深度 256。以 BaM 归一化为 1，CoPilotIO 达到 1.85 倍，AGILE 为 1.41 倍；摘要所说应用性能最高提升 85% 对应这里的 DLRM 结果。论文分别报告了 A100 和 H800 测试平台，但没有在该段明确指出 DLRM 曲线对应哪张卡。
