论文：MoonBright: A GPU Memory Allocator with Device-Side Page Table Materialization and Deferred TLB Coherence，Yangyu Zhang、Lei Chen、Chunwei Xia、Shuaijiang Li、Shuoming Zhang、Zhicheng Li、Qianqi Sun、Jiawei Xiao、Ruiyuan Xu、Ao Chen、Guangli Li、Xiaobing Feng、Huimin Cui、Chenxi Wang、Jiacheng Zhao，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI ’26，2026 年 7 月 13–15 日，Seattle）。论文页面。

TLDR： GPU 上的细粒度分配仍经由 CPU 串行更新页表，并在映射复用时触发 TLB shootdown（由主机发起、使设备端旧地址转换失效并要求全局同步）。MoonBright 把页表映射到 GPU 可访问的线性视图，由 GPU kernel 批量构造页表项；CPU 仍负责地址范围校验、分配元数据和物理页分配。新映射在当前虚拟地址回收周期内使用从未用过的虚拟地址，因此常见分配路径没有同地址旧 TLB 项，不必执行 shootdown。2 MB 页的单次映射中，A100 上 CUDA Virtual Memory Management（VMM）约需 45 μs，MoonBright 需 2.6 μs；2 GB 映射分别为 36 ms 和 14 μs。单张 A100 的前缀复用推理实验中，Llama-2-7B 测试 4K–96K、Llama-3-8B 测试 4K–192K；相较 vAttention，两者 time to first token（TTFT，首 token 时延）在所测范围内最多分别约为基线的 1/8.2 和 1/2.9。4 张 A100 上 DenseNet 的峰值已分配显存占峰值预留显存的比例从 PyTorch 的 57.6% 提高到 97.7%。

一、背景：GPU 工作负载中的动态内存分配

GPU kernel 的执行时间已可缩短到数微秒，动态且细粒度的内存申请因而可能进入计算关键路径。GPU 已有硬件内存管理单元（memory management unit，MMU）处理地址转换，但当前运行时仍主要由主机 CPU 管理内存：分配、释放和重映射请求经驱动更新主机维护的权威页表，再传播到设备端页表；映射变化还需要维护设备 TLB 的一致性。

CUDA 提供几类设备内存接口。cudaMalloc 按固定流程预留连续虚拟地址、分配同等大小的物理内存、建立映射并设置访问权限，期间可能等待设备上的 kernel。cudaMallocAsync 从运行时内存池提供 stream-ordered 分配，缓存已有内存块以减少驱动调用，但请求受池块布局约束。CUDA Virtual Memory Management（VMM）则把虚拟地址预留、物理内存创建和映射拆开，允许按页建立任意映射；代价是当前 VMM 操作仍经过主机驱动控制路径。

TensorFlow 的 BFC（best-fit with coalescing）和 PyTorch caching allocator 等框架分配器也通过预分配内存池复用内存。它们减少了进入驱动的次数，却不能直接把离散的物理页重新映射成连续的虚拟区间。MoonBright 用 CUDA 说明接口与实现，论文指出相同设计限制也适用于 HIP/ROCm。

页表构建和传输占这三种分配大小下总延迟的约 80%–99%。瓶颈不只是 PCIe 传输：驱动还要校验地址范围、创建缺失的页表层级、编码叶子页表项并保护并发更新；这些本可并行处理的页表项，却由 CPU 在串行循环中逐项构建。

另一方面，池式分配器能缓存已映射内存，却不能合并池中的空洞。不同大小和生命周期的申请逐渐与池布局错位后，即使空闲物理页总量足够，也可能没有足够大的连续空闲块。若改用 VMM 把离散物理页重映射到连续虚拟地址，现有主机控制路径必须等待各 stream 的活动 kernel 结束，再更新页表并执行全局 TLB shootdown。硬件 flush 本身在 128 MB 分配的测量中为 6.3 μs；论文指出，重映射还要等活动 kernel 完成并排空设备，但没有单独报告这段全局等待的时长。

三、问题：映射延迟与 external fragmentation（外部碎片）

只靠内存池绕过映射延迟，会把外部碎片问题留在分配器层：池无法把非连续物理页拼成新的连续虚拟范围。直接使用 VMM 虽能灵活重映射，却因 CPU 串行构建页表及全局同步而太慢。因此，GPU 显存分配器需要同时处理两件事：将大量独立页表项的构建从 CPU 控制路径移出，并在保证地址转换正确的前提下避免常见映射上的 TLB shootdown。

MoonBright 的判断是，地址范围校验与分配元数据需要留在主机，但物理页到页表项的批量转换是数据并行工作，可以交由 GPU 处理。TLB 一致性则利用新映射使用新虚拟地址这一约束，避免常见路径复用可能留有旧转换的地址。

四、方案：设备端页表构建与延迟 TLB 一致性

4.1 线性化页表视图与 GPU 批量构建

GPU kernel 通常不能直接使用驱动的特权页表操作。

系统总览（Figure 1: MOONBRIGHT System Overview.）

MoonBright 在 CUDA context 初始化时，把硬件多级页表所在物理页映射到一段设备虚拟地址（virtual address，VA）中，构成 GPU Page Table（gPGT）视图。页表项（page-table entry，PTE）可通过线性数组定位：Base + VPN × sizeof(PTE)，其中 VPN 是虚拟页号（virtual page number）。CPU 和 GPU 都能据此计算页表项位置，不必逐项往返查询页表位置。

将硬件页表映射为 GPU 可访问的线性视图（Figure 2: Bootstrap. The hardware page table structures backing VA(user) are mapped to a specialized virtual address, VA(gPGT). This pointer allows CUDA kernels to treat the page table as an array.）

实现由六个原语组成：

  1. bootstrap 在创建 CUDA context 时建立 gPGT 线性视图。
  2. alloc_va 在主机上的红黑树中预留虚拟地址范围，并维护其有效、空闲等逻辑状态。
  3. alloc_pfn 从设备物理内存管理器申请物理页帧号（page frame number，PFN），并保存后续映射需要的布局元数据。NVIDIA 后端使用 GPU System Processor（GSP）相关分配路径；AMD 后端使用 buddy allocator。
  4. pgt_create 校验虚拟地址范围，为缺失的页目录申请物理页，再把目录指针写入 gPGT。
  5. pte_pop 把 PFN 列表放入 GPU 缓冲区，由 GPU kernel 并行组合物理地址和访问权限位，生成页表项（page-table entry，PTE）并写入目标页表位置。
  6. tlb_flush 由主机发起；取消映射、权限变化和重映射已有 VA 等可能留下同地址旧转换的操作需要调用。VA 环形缓冲区只在 VA epoch（虚拟地址回收周期）边界批量 flush 后才允许回收地址，不为每个待回收 VA 单独执行一次 flush。

pte_pop 是普通 GPU kernel，映射任务可按目标 stream 排序，也可与无依赖的计算重叠。论文的实现约 14.1 KLoC（约 1.41 万行代码），包含对 NVIDIA 和 AMD 开源驱动的内核态修改及用户态 runtime。

GPU 并行填充页表项（Figure 3: Workflow of the parallel PTE population kernel (pte_pop). MOONBRIGHT utilizes massively parallel GPU threads to dynamically synthesize Page Table Entries (PTEs) directly into the global GPU Page Table (gPGT).）

4.2 Always-Fresh VA 将 flush 推迟到地址回收

MoonBright 的 Always-Fresh VA 策略规定：在当前 VA epoch（虚拟地址回收周期）内，新映射只能使用此前没有使用过的虚拟地址范围。GPU TLB 不可能已有该同一地址的有效旧映射，因此安装新 PTE 时无需先失效旧项。首次访问会发生正常的 TLB miss 并读取新页表项。这种策略用一次局部地址转换代替常见路径上的设备级 shootdown。

NVIDIA 的翻译预取器可能对邻近的无效 VA 形成 negative caching。此类缓存记录的是地址当前未映射，不会把访问导向旧物理页；但预取窗口内的新映射可能触发 replayable fault（可重放故障），论文在评测中测量了这项性能影响。

虚拟地址空间有限，MoonBright 因此把 VA 管理成带延迟回收的环形缓冲区。释放的 VA 先进入 quarantine（暂不复用的隔离区），不立刻交给新映射；当环形缓冲区进入新的 epoch 时，系统等待可能引用旧 epoch 的 GPU 工作结束，执行一次批量 TLB flush，再允许回收的地址重新使用。相同 VA 的重映射和权限更新仍受支持，但需要同步，不属于无 flush 的快速路径。

论文用 Robson 的最坏分配分析估算 VA 空间需求，给出的公式为 M × (1 + 12 log₂ n)，其中 M 是物理内存大小，n 是物理内存与页大小之比。原文称 80 GB GPU、2 MB 页的估算值约为 693 GB；按 32 MB 边界对齐后，保守预算增至约 11 TB，低于原型提供的 128 TB 用户 VA 区域。但按原文公式和定义令 n = 80 GB / 2 MB = 40,960，直接计算约为 14.8 TB，与 693 GB 不符；再乘 16 倍也会超过 128 TB。笔记保留论文报告的 693 GB 和 11 TB，同时标出它们无法由文中所列公式复现，不把这组空间预算当作公式核验通过的结果。

4.3 基于映射原语实现分配、共享与整理

同步 Malloc 将上述原语串成分配流程。大申请依次取得 VA、物理页并创建页表后运行 pte_pop；若 VA 是新地址就跳过 flush，覆盖已有映射时才对该映射执行 tlb_flush。小对象使用 slab（把硬件页切分成固定大小对象的分配策略）在较大的硬件页内切分；论文举例的硬件页为 2 MB，用户申请可以小到 1 KB。

MallocAsync 在虚拟内存层提供 stream-ordered 分配，并采用两级路径。快速路径用 best-fit with coalescing（BFC）在用户态缓存池中分配和合并内存块；缓存耗尽或大申请到来时，慢速路径获取新 VA 和 PFN，再运行 pgt_create 与 pte_pop。释放到池中的块可供快速路径复用；将物理页交还系统时仍按同步取消映射路径处理。

当池中没有足够大的连续块、但离散空闲物理页的总量足够时，MoonBright 可以申请一个新的连续 VA，把多个不连续 PFN 映射进去。这个整理过程只更新页表，不搬动数据；它降低的是分配器层面的外部碎片。页粒度导致的 internal fragmentation（内部碎片）是另一项取舍，论文没有把它算作这里讨论的外部碎片。

VMM 风格接口把地址预留、物理页创建、映射和释放分别暴露出来，也提供 MemMapAsync。多个不同 VA 可别名到同一组物理页，无需复制数据，可用于前缀共享或 beam search（同时保留多个候选序列的搜索）状态分叉。映射新 VA 时可按 stream 异步执行；覆盖已有有效映射时仍插入一致性同步并执行 flush。

五、结果：映射延迟、分配器碎片与推理性能

5.1 低层映射与分配调用

实验平台包括 NVIDIA A100、H100 和 AMD MI210。NVIDIA 原型基于 open-gpu-kernel-modules driver 560.35.03；AMD 原型基于 ROCm 6.4.0。论文没有报告 GSP 固件版本。低层 VMM 对比采用平台最小 CUDA VMM 粒度 2 MB，映射范围从 2 MB 到 2 GB。

在 A100 单卡的 2 GB 映射实验中，CUDA VMM 延迟为 36 ms，MoonBright 为 14 μs；论文报告的加速幅度超过 2,500 倍。实验还在单节点上同时对 1、2、4 张 A100 发起映射；2 GB 请求下 CUDA VMM 延迟分别为 36、86、180 ms。论文称 MoonBright 延迟基本不随 GPU 数量增加，但没有给出各 GPU 数量下的具体延迟；4 GPU 结果比 CUDA VMM 快 12,700 倍。地址预留和物理页创建仍走主机驱动路径，论文称其延迟与 CUDA VMM 相近，但没有在正文列出具体值。取消映射按整个连续范围操作；论文称在 2 MB–2 GB 范围内 MoonBright 均快于 CUDA VMM，但正文没有给出这些点的具体延迟值。

5.2 训练碎片与 LLM 推理

训练碎片评测使用 4 张 NVIDIA A100，运行 PyTorch-based training stack，并比较 PyTorch caching allocator、GMLake 和 MoonBright。模型为 DenseNet、GPT-2、Llama-2-7B、Qwen1.5-MoE-A2.7B（Figure 7 中简写为 Qwen1.5-MoE）；配置组合包括基础设置（B）、重计算（R）、virtual pipeline（V）、ZeRO（Z）和 offload（O），并逐步增加 batch size 直到 out-of-memory。论文将 Memory Efficiency 定义为峰值已分配显存除以峰值预留显存，用作分配器层面碎片的诊断指标。

DenseNet 的 Memory Efficiency 从 PyTorch 的 57.6% 提高到 MoonBright 的 97.7%；GPT-2、Llama-2-7B 和 Qwen1.5-MoE 上，MoonBright 均至少达到 96.1%。在 Qwen1.5-MoE 的 Z+O+R 配置中，PyTorch 为 72.8%，MoonBright 为 97.8%。GMLake 采用 512 MB 映射粒度作为 CPU VMM 开销与粒度空隙之间的工程折中；论文称不规则分配下仍有剩余空隙，但没有给出该项的具体效率数字。

四个模型的训练内存效率（Figure 7: Training memory efficiency on four models across different allocators and optimization combinations: basic (B), recomputation (R), Virtual Pipeline (V), ZeRO (Z), and offload (O).）

LLM 推理比较使用单张 NVIDIA A100，以 vAttention 为基线，模型为 Llama-2-7B 和 Llama-3-8B。Figure 8 分别测量完整 prefill（处理输入 prompt 的阶段）的长上下文请求，以及复用 KV cache（缓存历史 token 对应的 key 和 value 张量）的 prefix caching（跨请求复用相同 prompt 前缀）请求。Llama-2-7B 的 prompt 或 prefix context 长度为 4K–96K；Llama-3-8B 为 4K–192K。图中 TTFT 归一化到 MoonBright，数值越低越好。在长上下文、无 prefix caching 的场景，MoonBright 最多快约 5%；论文援引的分析指出，在 192K 长度下计算约占执行时间的 85%，因此留给内存管理优化的空间有限。prefix caching 减少 prefill 计算后，CPU 驱动的 VMM 映射开销更明显；在 Llama-2-7B 的 4K–96K 和 Llama-3-8B 的 4K–192K 测试长度范围内，TTFT 最多分别约为 vAttention 的 1/8.2 和 1/2.9。论文正文没有指出这两个最大差异对应的具体长度。论文将两者收益差异归因于 Llama-3-8B 使用 grouped-query attention（GQA），KV heads 较少，KV cache 和需要重映射的缓存块也更少。
