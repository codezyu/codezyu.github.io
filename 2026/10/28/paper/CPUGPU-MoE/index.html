论文：Achieving Cloud-Grade SLOs for Local Mixture-of-Experts Inference through CPU–GPU Hybrid Design，Wenxin Wang、Yule Hou、Yu Ji、Peng Qu、Youhui Zhang，USENIX OSDI ’26（2026）。论文：USENIX PDF。

TLDR： 本地 MoE 推理受限于消费级 GPU 显存、CPU 侧专家计算效率和 PCIe 通信，长输入难以满足云端常用的 SLO（service-level objective；本文具体考察 30 秒 TTFT，即 time-to-first-token）参考线，decode（解码阶段）也难保持每请求 20 tokens/s。论文用 GPU 上的 stream-loading prefill（SLP，流式加载 prefill；prefill 为预填充阶段）和 SmallEP（针对小规模专家并行的论文专名），把 32K 输入的 prefill 控制在 30 秒内；双 RTX 5090 的 distributed stream-loading prefill（DSLP，分布式流式加载 prefill）吞吐逾 1,800 tokens/s，45K 输入也在 30 秒 TTFT 内完成。节点内再把 prefill 与 decode 分配到不同 GPU，并以共享权重和 dual-batch attention–MoE overlap（双 batch 的 attention 与 MoE 交错执行）减少互相干扰；AVX-512 FP8（8-bit floating-point）GEMV（matrix-vector multiplication，矩阵向量乘法）与细粒度 CPU 并行则提升 decode。评测正文报告，671B DeepSeek-R1 原始 FP8 版本的短输入单流 decode 为 21.5 tokens/s（未报告确切输入与生成长度），Q4_K_M 版本在 1K–8K 上下文下为 28 tokens/s（该段未报告 batch size 与生成长度）。

型号口径： 论文摘要把 28 和 21.5 tokens/s 分别写成 INT4（4-bit integer quantization）与 FP8 DeepSeek-V3；引言的贡献列表、评测设置、第 4.3、4.4 节正文及图注则将对应性能实验写为 671B DeepSeek-R1，而批量吞吐图和混合并发图的图例又标为 DeepSeek-V3。量化模型为 Q4_K_M；论文将它称为 INT4，但评测配置实际是 gate/up 使用 Q4_K、down 使用 Q6_K 的混合格式。下文按评测正文记录，并保留图例与正文的型号差异。质量评测另用 DeepSeek-V3.1 和 Kimi-K2-Instruct。

一、背景：本地 MoE 以主存容量换 GPU 显存

MoE（Mixture-of-Experts）模型由门控机制为每个 token 选择少量 expert 计算，因此总参数量可以很大，而单个 token 只访问其中一部分权重。论文用约 1 万亿参数、原始权重约 1 TB 的模型说明容量压力；论文另按每秒 20 次激活权重读取来估算现代 MoE 的带宽需求，约为 1 TB/s。这个带宽估算基于每 token 实际激活的权重，不是由总参数量直接换算。多路 CPU 的 DDR5 主存可以提供大容量和较高总带宽，论文给出的 DDR5 与 HBM（high-bandwidth memory）价格估计分别约为 3 美元/GB 和 30 美元/GB。

模型权重容量与激活权重带宽需求（Figure 1: Models’ memory demands and device comparison. Model memory capacity reflects parameter size at original weight dtype; memory bandwidth reflects activated weight accesses under a 20 tokens/second service-level objective (i.e., 20 serial activated-weight reads per second). Devices shown include NVIDIA GeForce RTX, NVIDIA Tesla data center GPUs, and AMD EPYC CPUs.）

这种资源结构适合 CPU–GPU 混合推理：CPU 主存保存大部分 MoE 权重，GPU 负责计算密集的 attention（注意力计算）等部分。云端系统依靠多 GPU 和高速互连处理高并发；本地部署通常只有少量 GPU、显存有限、互连以 PCIe 为主，而且请求并发较低。小 batch 下的稀疏激活减少了每步读取的 expert 权重，却也让 CPU 侧 decode 更容易受内存带宽效率影响。

二、现有本地推理的四个服务差距

现有系统通常按计算强度（arithmetic intensity）划分工作：attention 和 shared experts 放在 GPU，routed experts 放在 CPU。KTransformers 通过量化、改路由、Intel Advanced Matrix Extensions（AMX）CPU 指令和 NUMA 编排改善本地 MoE 推理。论文不同位置引用的 decode 结果分别约为 16 和 22 tokens/s，未解释两者的配置差异；另报告 prefill 最高约 500 tokens/s。DeepSeek-V3 INT4 的 8K 输入约需 20 秒 TTFT，12K 及以上的时间超过 30 秒是估算值。作者根据 CPU 时间占比 74% 和每 token 激活的 20.4B MoE 参数，推算其有效内存带宽约 221 GB/s，约为所报告双路 Xeon DDR5 系统名义总带宽的一半。

论文把与云端服务质量的差距归为四类：本地系统依赖量化、蒸馏或改路由后的容量缩减模型；长 prefill 难达到 30 秒 TTFT；decode 低于每请求 20 tokens/s 的响应基线；prefill 与 decode 混跑、或同时 decode 多个请求时，并发会压低单请求性能。

CPU 承担 routed expert 计算时，prefill 的计算强度随输入变长而上升。论文指出，输入长度超过约 512 tokens 后，CPU 侧 MoE 计算会饱和并成为 TTFT 的主要部分；DeepSeek-V3 INT4 在 8K、16K、32K 输入上的 TTFT 约为 20 秒、40 秒（估算）和 100 秒（估算）。另一类权重卸载系统会预取权重到 GPU，但通常以小到中型模型的低延迟为目标，难以在大型 MoE 的长 prefill 中兼顾高吞吐。

多 GPU prefill 也受小规模 expert parallelism（EP，专家并行）和 PCIe 限制。论文用 context parallelism（CP）=2 的 zig-zag StripedAttention 将 token 分到两个 rank，各自计算本地因果 attention 后通过 ring Pass-KV 交换，再接 EP=2 的 gate、dispatch、expert compute 和 combine。

两卡 StripedAttention 与 EP 的执行流程（Figure 2: Example workflow: zigzag StripedAttention (Pass-KV, CP=2, left) followed by expert parallelism (EP=2, right). Tokens are split across two ranks; each rank attends locally (phase 1), performs one ring Pass-KV exchange, then completes attention (phase 2). Outputs then flow through MoE gating, dispatch/compute/combine, and weighted aggregation.）

单层、20K 输入的 microbenchmark 显示，标准 CP=2+EP=2 比单 GPU 顺序执行降低 21% 层延迟；但没有 GPU–GPU peer-to-peer（P2P）通信时，dispatch 与 combine 仍占层执行时间约 31%。若直接沿用面向大量 GPU 的 EP 通信方案，本地两卡之间的传输会成为主要开销。

20K 输入单层 prefill 的并行方案耗时（Figure 3: Top-down comparison of parallelism designs on a 20K-token prefill for a single decoder layer (one Attention + one MoE). Baseline: single-GPU sequential. CP2+EP2: StripedAttention (CP=2) with standard expert parallelism (EP=2). CP2+SmallEP2: StripedAttention with our optimized expert parallelism that reduces inter-GPU communication by roughly 50%.）

三、目标：本地节点对齐云端 SLO

论文把云服务的 30 秒 TTFT 作为长输入 prefill 目标，输入长度超过 12K 时尤其难满足；decode 的响应参考线是每请求至少 20 tokens/s。TPOT（time-per-output-token）描述 decode 阶段的单 token 时间，论文也用 tokens/s 表示 decode 吞吐。QoS（quality of service，服务质量）评测同时考察原始模型质量，以及 prefill 与 decode 共存时的 TTFT、TPOT 和整组请求完成时间。

这些是论文采用的云端 QoS 参考点，不是与某个云服务在同一硬件、同一模型和同一请求轨迹上的直接对测。并发章节报告平均 TTFT、平均 TPOT 与总完成时延，没有给出统一的尾延迟百分位 SLO。

四、方案：让传输、计算和并行方式适配本地节点

4.1 SLP 的权重流式加载与执行重叠

SLP（stream-loading prefill）把 prefill 放到 GPU 上执行，并将权重按 sub-layer 从 CPU 主存流式加载到 GPU 显存。loader、model、unloader 三个线程分别负责搬运权重、执行模块和释放已用显存；线程之间通过 CUDA event 和主机端 event 协调。权重传输因此可以与前一模块的计算重叠，unloader 则在模块执行完后回收对应显存。

DeepSeek-V3 的 expert 权重由 58 个 MoE 层、每层 256 个 experts、每个 expert 3 个 FP8 线性模块组成，共约 44.5K 个 tensor。为避免反复 cudaMalloc/cudaFree，SLP 用跨层共享的 experts ring buffer 管理它们。短输入、传输占主导时，ring buffer 长度设为一层的 expert 数，以增加预加载距离并利用主机到 GPU 的带宽；输入超过约 50K 后，计算和中间 tensor 占用成为主要约束，buffer 缩为长度 2 的 ping-pong 结构。SLP 不要求改路由或把原始 FP8 模型再量化。

SLP 的三线程权重加载流水线（Figure 5: Stream-loading prefill pipeline with three concurrent threads. The loader (left, green) loads weights for modules (attn & exp.i) and sets ON events. The model thread (center, blue) wait ON events, executes modules and set OFF events. The unloader (right, gray) wait OFF events then unloads weights to free GPU memory. Arrows indicate event signaling and dependency ordering. Dark red boxes indicates weights that are managed by experts ring buffer.）

4.2 SmallEP 降低小规模 EP 的通信量

DSLP（distributed stream-loading prefill）把 SLP 扩展到多 GPU，结合 context parallelism（CP）和 expert parallelism（EP）。attention 使用 zig-zag StripedAttention；expert 计算则用 SmallEP，针对本地常见的小 EP 规模重新安排 token 交换。

标准 EP 先按 gate 结果排序，再用 All-to-All dispatch 把 token 发给负责相应 experts 的 GPU。SmallEP 改为先 All-Gather 全部 token，让每个 rank 本地执行 gate 和排序，再只保留分配给本地 experts 的 token；expert 计算完成后，各 rank 先做 partial weighted sum，再交换约为 [N, D] 的部分结果并完成归约。这样会重复执行 gate 和排序，但把每条链路的 All-Gather 流量固定为 N·D，并把 All-to-All 限制在部分归约后的 N·D tensor。标准 EP 每对 rank 的通信量约为 N·A·D/S；当 EP size S 不大于每 token 激活的 expert 数 A 时，SmallEP 可降低峰值链路带宽需求。

标准 EP 与 SmallEP 的通信流程（Figure 6: Workflow comparison between standard expert parallel and SmallEP optimization under an EP size=2 configuration. N is the number of tokens on all devices, D is hidden size.）

在 20K 输入的单层 microbenchmark 中，SmallEP 比标准 EP 再降低 18% 层延迟；作者报告通信量约减少 50%。路由偏斜在小 EP 场景下也较容易被每张卡上的大量 experts 平均，但本地 gate 和排序会重复计算。

4.3 节点内分离 prefill/decode 并重叠计算

节点内 prefill–decode 分离把一张 GPU 留给 prefill，另一张 GPU 处理 decode 或分块 prefill。进程间通过共享同一份常驻模型权重和 experts ring buffer 实现 zero-copy（复用同一权重副本而不复制权重）协作，避免在 DRAM（dynamic random-access memory）中保留重复权重副本；权重仍需经 PCIe 5.0 x16 在 CPU 与 GPU 之间传输。短于 2K tokens 的输入采用 chunked prefill（分段预填充，即把输入分段处理）；较长输入若近 5 分钟内没有 decode 请求，就派给 DSLP 追求吞吐，否则使用分离式 SLP 降低对 decode 的干扰。prefill 按先到先服务，decode 动态组 batch，目标 batch size 为 6。

CPU–GPU 混合推理中，attention 在 GPU、MoE 在 CPU 顺序执行。单层 attention 约需 350 µs，MoE 约需 450 µs，另一处理器会在这段时间空闲。dual-batch attention–MoE overlap 用两个线程和两条 CUDA stream 交错处理 batch A、B 的 GPU attention 与 CPU MoE。GPU 独占的 embedding 和 lmhead 同步开销低于 5 ms，相比 61 层约 50 ms/token 的主要执行时间较小。

双 batch attention–MoE 并行（Figure 7: Dual-batch attention-MoE parallelism scheme for simultaneous inference of two batches A and B. "embed" stands for input token embedding linear layer; "lmhead" stands for output language model head linear layer.）

4.4 CPU 的 AVX-512 FP8 GEMV 与细粒度并行

GPU 的 FP8 路径直接读取 FP8 权重与 scale，将 activation 转为 FP8 后执行带 FP32（32-bit floating point）累加的 GEMM（matrix–matrix multiplication，矩阵乘法）；CPU 侧既有路径则先把 FP8 权重和 scale 转为 BF16（16-bit brain floating point）再做矩阵乘法，使这部分权重占用翻倍并增加内存流量。CPU 没有 GPU 式的原生 FP8 运算单元。

GPU 与 CPU 的 FP8 GEMM 数据路径（Figure 4: FP8 GEMM execution on GPU versus CPU. “S” denotes per-tensor or per-block scale factors. On CPU, FP8 weights and scales are dequantized to BF16 prior to GEMM; the dequantization and doubled memory footprint are highlighted by the red box.）

CPU 的标准 FP8–BF16 dot-product kernel 先将 FP8 权重展开为 FP32，再调整 scale inverse 和 exponent bias，转成 BF16 后执行 BF16 点积。该路径需要 15 条以上的向量指令；受 FP32 寄存器密度影响，估算延迟约 36 cycles，每 16 个元素的迭代吞吐约 12 cycles。

AVX-512 基线 FP8–BF16 点积路径（Figure 8: Baseline FP8-BF16 dot-product kernel in AVX512.）

论文针对 MoE decode 的矩阵向量乘法（GEMV）实现 AVX-512 FP8 kernel：对 E4M3FN（1 位符号、4 位指数、3 位尾数）权重作整数位操作并直接展开为 BF16，将 BF16 activation 载入 __m512bh，用 vdpbf16ps 点积并由 FP32 累加器累加，最后做 post-scaling。这样减少热路径中的 FP32 中间展开和缩放操作，但累加仍使用 FP32，也不必先把整份 FP8 权重上转换为 BF16 后再写回主存。论文称这条路径支持 native CPU FP8 inference；这里的 native 指保留 FP8 权重格式并由 CPU kernel 处理，不表示 CPU 有专用 FP8 算术单元。优化设计将每条 512-bit 向量可处理的元素从 16 个 FP32 增至 32 个 BF16，估算延迟约 27 cycles、每 32 个元素的迭代吞吐约 4.96 cycles；双路平台上测得 815 GB/s 带宽。

FP8–BF16 点积的 post-scaling kernel（Figure 9: Our post-scaling kernel of FP8-BF16 dot product.）

论文称权重格式为 E4M3FN，列出 1/4/3 位字段，并写作「without NaNs」，但未展开 FN。Open Compute Project（OCP）的 8-bit Floating Point（OFP8）规范 对 E4M3 的定义是没有 Infinity 编码、但有两种 NaN 编码；这与论文的「without NaNs」说法不一致。这里保留论文的格式名和位宽，不沿用其无 NaN 描述。

kernel 再按 M 轴 tiling、K 轴 scale block 和 SIMD（single instruction, multiple data）dot product 三层组织；scale block 通常覆盖 128 个元素，每块累加完成后再应用一次 scale。相较于先前的 post-scaling kernel，这一层次设计将缩放乘法减少 4 倍，并把带宽提高到 947 GB/s。作者还报告，该 GEMV kernel 相对 PyTorch BF16 参考实现的逐元素 L1 差异第 95 百分位为 0.0017。

FP8 GEMV kernel 的层次结构（Figure 10: Hierarchical structure of the FP8 GEMV kernel. Computation is organized into Tiling along the M-axis, Scale-Block iteration along the K-axis (128 elements per block), and SIMD Dot-Prods that pipeline accumulations within each block. A single scale factor is loaded per block and applied after all accumulations, reducing scaling overhead and sustaining high bandwidth.）

CPU 并行方面，每个 expert 的 gate 与 up projection 可以并行，随后同步进入 down projection。

MoE expert 的计算依赖（Figure 11: MoE expert compute graph: each expert has gate, up, and down projections. Gate and up can run concurrently; their outputs synchronize before down. N is batch size (N=1 for single-request inference).）

系统把输出维度 M 切成 m 段；图示中的 8 个激活 expert 因而形成 m×8 个独立任务。per-expert barrier 负责同步 gate/up 与 down projection，取代粗粒度全局同步；系统还把 gate/up 的 activation combine 融入第一阶段。对 Q4_K_M 量化路径，gate/up 权重使用 Q4_K，down 使用 Q6_K；系统把 hidden type、Q8_K、FP32 和 BF16 间的转换融合进相邻 projection，减少 kernel launch 和同步。

NUMA 节点内 gate/up 的任务划分（Figure 12: Task partitioning of gate/up on a NUMA node. Output dim M is sliced into m segments per expert, yielding m×8 independent tasks (8 activated experts). Each thread runs a vectorized FP8–BF16 kernel. Red borders mark per-expert barriers that satisfy dependencies for down projection while minimizing synchronization.）

五、评测结果：吞吐、质量和并发边界

5.1 测试平台与长输入 prefill

主评测平台有两颗 AMD EPYC 9355、24 条内存通道上的 24 根 48 GB DDR5-6400 内存条，总主存 1.15 TB，理论总带宽 1,228 GB/s；GPU 为两张 NVIDIA RTX 5090，每张 32 GB GDDR。论文还列出最高 419 FP8 TFLOPS（FP32 accumulation），但没有说明这是单卡还是双卡的算力。两卡配置通过 PCIe 连接。除特别说明外，本文系统与 KTransformers 的实验都在该平台运行；部分 KTransformers prefill 结果取自其公开数据，平台不同。

prefill 主评测使用原始 FP8 DeepSeek-R1 和 Kimi-K2。SLP 的 prefill 吞吐最高约 1,200 tokens/s，支持 32K 输入在 30 秒 TTFT 内完成；两张 RTX 5090 上的 DSLP 超过 1,800 tokens/s，可在 30 秒内处理 45K 输入。20K–32K 输入时，SLP 比 CPU AVX 基线快一个数量级以上、比估算的 KTransformers AMX 结果快 2.8 倍；DSLP 吞吐为 SLP 的 1.64 倍。KTransformers 的长输入 prefill 结果在 8K 之后是按 AVX 测量值线性外推；其乐观上界则假设 attention 和 MoE 都随长度线性增长，因此这些长输入比较包含估算值。

不同输入长度下的 prefill 吞吐（Figure 13: Prefill throughput (tokens/s) for different configurations. We compare CPU AVX baseline (FP8), KTransformers (KT) AMX (INT4), Stream-Loading Prefill (SLP, FP8), and 2-GPU Distributed SLP (DSLP, FP8). KT AMX values for prefill lengths >8K are shown as estimates: “estimated” is obtained by linearly scaling the AVX baseline based on the ratio observed at ≤8K tokens. “estimated, upper” is an optimistic projection of the measured KT AMX results by assuming both attention time and MoE time scale linearly with prefill length.）

TTFT 评测覆盖 256–64K 输入。短于或等于 4K 时，SLP/DSLP 的权重传输与启动成本抵消了吞吐优势；系统因此在 4K 及以下使用 AVX prefill，较长输入切到 SLP/DSLP。4K–32K 区间内，SLP 和 DSLP 的 TTFT 低于 30 秒。prefill 吞吐测试没有给出生成多个输出 token 的长度；TTFT 指标只计到首 token。

KT AMX results beyond 8K tokens are shown as estimates.）

5.2 推理性能、并发与模型质量

在 671B DeepSeek-R1 的原始 FP8 版本上，单流 decode 在短输入下为 21.5 tokens/s，输入上下文到 32K 时约为 20 tokens/s；原始 FP8 的 1T 参数 Kimi-K2 单流吞吐为 22.4 tokens/s。decode 吞吐测试按上下文长度比较，但该段没有说明固定生成 token 数。

FP8 模型的单流与双流 decode 吞吐（Figure 15: Decode throughput of the full-precision FP8 DeepSeek-R1 671B and Kimi-K2 1T model under single-stream and dual-stream execution across varying context lengths.）

batch size 为 2、4、6 时，系统总吞吐分别达到 batch 1 的 1.56、1.58、1.61 倍；批量吞吐测试标注 batch 1、2 的总吞吐为 21.51 和 33.66 tokens/s。batch size 2 时每请求 16.8 tokens/s，比单流低 21.7%；32K 上下文下总吞吐为 31.1 tokens/s，即每请求约 16 tokens/s。该 batch 对比的正文和图注按本文 FP8 DeepSeek-R1 与 KTransformers Q4_K_M DeepSeek-R1 说明，但图例写作 DeepSeek-V3。

不同 batch size 下的 decode 吞吐（Figure 16: Decode throughput comparison of our engine running DeepSeek-R1 FP8 versus KTransformers (KT) running Q4_K_M (INT4) across batch sizes of 1, 2, 4, and 6. Bars are normalized to each engine’s batch size 1 result; absolute system throughputs (tokens/s) are annotated. Red markers report our throughput gains relative to batch size 1.）

Q4_K_M DeepSeek-R1 671B 的对比覆盖 1K–128K 上下文，量化模型需要 404 GB 主存。本文系统在 1K–8K 上下文达到 28 tokens/s，128K 时为 19 tokens/s；对照中的 KTransformers 在 1K–8K 约 22 tokens/s，128K 约 15 tokens/s，ik_llama.cpp 在 1K–8K 约 14 tokens/s。论文将 Q4_K_M 标作 INT4 对照，但其存储并非所有 projection 都是 4 bit：gate/up 为 Q4_K，down 为 Q6_K。该 decode 结果段没有另行注明 batch size 和生成 token 数。

Q4_K_M DeepSeek-R1 的长上下文 decode 速度（Figure 17: Decode speed comparison including Q4_K_M quantized DeepSeek-R1 671B model. IK: ik_llama.cpp; llama: llama.cpp.）

并发 microbenchmark 中，每种请求单独运行约 20 秒；KTransformers 的 prefill 输入设为 4K，本文系统设为 24K，以抵消两者 prefill 吞吐差异。两种引擎分别使用 INT4/Q4_K_M DeepSeek-R1 和原始 FP8 DeepSeek-R1；prefill 请求没有共享前缀，只生成少量 token（论文未给出准确长度），decode 请求使用 10-token 输入并生成 480 个 token。请求同时到达，比较 1 个 prefill（1P）、1 个 decode（1D）、1P+1D、2D 和 1P+2D。论文报告平均 TTFT、平均 TPOT 和全部请求完成时间。并发测量中，本文系统在 1P、1P+1D、1P+2D 下的 TTFT 分别为 23.8、24.0、28.2 秒；1P+2D 相对单独 1P 增加约 18.5%，正文取整为 18%。摘要所说并发 latency increase 小于 15% 不能外推到所有负载，文中没有明确指出摘要边界对应哪个并发组合。所有并发组合中，本文系统的 TPOT 至多达到 1D 基线的 1.54 倍，KTransformers 至多为 2.45 倍；整组请求总完成时延最坏时分别为各自基线的 1.67 倍和 2.53 倍。

双 batch overlap 的系统吞吐提升约 50%，而 batch size 2 的单请求吞吐仍下降 21.7%。因此 50% 指 aggregate throughput 的增加，不代表并发后每个请求仍保持单流速度。

端到端质量用 Exact Match 比较发布模型报告：DeepSeek-V3.1 的 MMLU-Redux 为 91.00（官方 91.8），MMLU-Pro 为 83.41（官方 83.7）；Kimi-K2-Instruct 分别为 91.53（官方 92.7）和 80.00（官方 81.1）。差距约 0.3–1.17 个百分点。论文没有在质量评测段注明精度或量化格式；作者认为结果差异可能来自生成配置的小幅差异，未观察到系统性能力损失。这组质量评测的模型版本与前述 decode 性能实验不同。

作者对较低端平台的讨论是基于测量结果作出的预期，而不是额外硬件上的完整验证：batch size 通常为 1–4，CPU 侧 MoE 计算约占总 decode 时间的 60%，双 batch 时 CPU 带宽压力更高。参与 MoE 计算的 skinny GEMM（形状较窄的矩阵乘法）算术强度约为 batch size 的两倍，低于 CPU 约 50 FLOPs/byte 的计算/内存比；因此作者预期低端 CPU 的 decode 吞吐主要随可用 DRAM 带宽近似线性变化。若 GPU 显存无法容纳覆盖单层全部 experts 的 ring buffer（DeepSeek-V3 与 Kimi-K2 需要约 11.3–16.9 GB；两卡分摊时每卡约 5.6–8.5 GB），例如 16K 的中等长度 prefill，其传输/计算重叠可能变差、TTFT 可能上升；超过 50K 的长 prefill 则更受 GPU 计算能力限制。
