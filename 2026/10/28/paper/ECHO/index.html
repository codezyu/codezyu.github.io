ECHO：长上下文 LLM 服务中的 KV cache offloading

论文：ECHO: Efficient KV Cache Offloading with Lossless Prefetching for Serving Native Sparse Attention LLMs，Guangda Liu、Wenhao Chen、Chengwei Li、Zhenyu Ning（Shanghai Jiao Tong University），Jing Lin、Yiwu Yao（Huawei），Quan Chen、Shixuan Sun、Jieru Zhao（Shanghai Jiao Tong University），Minyi Guo（Guizhou University and Shanghai Jiao Tong University），OSDI ’26（2026）。USENIX PDF。

本文用 KV cache 指历史 token 对应的 key 和 value 张量缓存；KV cache offloading（KV cache 卸载）指将这部分数据从 GPU HBM 移至主机 DRAM；native sparse attention（原生稀疏注意力）指训练时采用稀疏注意力的模型类别，本文实际评测使用 DeepSeek-V3.2 的训练时稀疏注意力实现；lossless prefetching（无损预取）提前搬运候选 KV，但不改变精确 top-k 选择，未预取的选中项仍会正式回取。

TLDR： serving native sparse attention LLM 时，稀疏计算仍要保存随上下文线性增长的 KV cache，模型权重和 indexer K cache 会挤压 GPU HBM 中可供并发请求使用的空间。ECHO 把 KV cache 放在主机 DRAM，并以 CUDA Graph 可执行的固定长度元数据管理 GPU 缓存；它根据 index score（索引分数）的可预测性，在 decoding（逐 token 解码）中做 intra-query prefetching（query 内预取），在 prefill（输入预填充）中做 inter-query prefetching（query 间预取），精确 top-k 完成后仍会回取所有缺失项，因此预取不改变选中 token 集合。论文摘要称长上下文生成吞吐最高提高 2.1×；§6.2 报告的对应结果是，在 8×NVIDIA H20、DeepSeek-V3.2-Exp、InfiniteBench 80K–100K 输入、固定输出 256 token、全部请求同时到达且全部可用 GPU HBM 用于 KV pool 的条件下，ECHO 比 SGLang 高 2.15×，比 vLLM 高 4.1×。

一、背景：稀疏注意力的缓存成本

自回归 LLM 在 prefill（处理输入上下文并生成首 token）阶段计算整段输入的 key、value 张量；进入 decoding（逐 token 解码）后，只需为新 token 计算一次，再与历史张量一起做注意力。KV cache 保存这些历史 key、value 张量，避免重复计算。长上下文让注意力计算成本按上下文长度平方增长；稀疏注意力只对 indexer 选出的 top-k token 计算注意力，可减少计算量和访问的 KV 数量，却不会缩小已保存的 KV cache。

ECHO 面向 DeepSeek-V3.2 的 DSA（DeepSeek Sparse Attention）。DSA 是训练时稀疏注意力：轻量 indexer 为历史 token 计算 index score，再选择分数最高的 token 参与 MLA（multi-head latent attention）计算。DeepSeek-V3.2 的 indexer 使用 64 个 head、维度 128；MLA 使用 128 个 head、压缩维度 512。indexer 的 query 和 key 使用 FP8（8-bit floating-point）格式，分数由各 head 的加权 ReLU 点积相加得到。由于稀疏注意力还要保存 indexer 的 K cache，模型的 MLA KV cache 与 indexer K cache 都随上下文增长。

论文用两组部署说明 HBM 预算：4-bit AWQ 的 DeepSeek-V3.2 部署在 8 张 96 GB H20 上，FP8 版本部署在 8 张 141 GB H200 上，模型参数都占用了 60% 以上的 HBM。MLA KV cache 不能通过 tensor parallelism（TP）切分，实际由 data parallelism（DP）worker 分别承担；论文估计每个 worker 分别容纳约 511K 和 655K token。对 8×H200 上的 FP8 配置，约 100K token 的请求最多只能并发 6 个。运行时元数据还会继续减少可用于 KV cache 的空间。

DeepSeek-V3.2 在 H20 与 H200 上的 HBM 使用量；MLA KV cache 与 indexer K cache 随 token 数增长（Figure 1: GPU HBM usage of DeepSeek-V3.2 (AWQ) on 8×H20 (96GB) and DeepSeek-V3.2 (FP8) on 8×H200 (141GB). Space for MLA KV cache and indexer K cache increases linearly with the number of tokens.）

HBM 限制也会放大稀疏 kernel 的硬件利用率问题。H20 上的 FlashMLA dense kernel 在 batch size 为 8 时，64K 上下文已能充分利用硬件；稀疏 kernel 的不连续访存使它需要更大的 batch 才能饱和。8×H20 上的 DeepSeek-V3.2 AWQ 配置只能为 MLA 留出约 511K token，最多容纳 8 个 64K 请求，对应的稀疏 kernel 利用率为 53%。

FlashMLA 稠密与稀疏 kernel 的硬件利用率（Figure 2: Hardware utilization in TFLOPS of the sparse and dense FlashMLA kernels across different batch sizes.）

二、现状：图执行与预取瓶颈

现有 KV cache 卸载有两类。Strata 等 request-level 方法把已完成请求的整份 KV cache 留在主机内存，请求到达时再整体载入 GPU；它不在推理过程中逐 token 淘汰或回取，因而不能缓解运行时 HBM 占用。ArkVale、InfiniGen、FreeKV 和 CLO 等 token-level 方法按稀疏选择动态淘汰和回取，但论文列出的系统不支持真实 serving 框架中的 continuous batching 或多 GPU 推理；InfiniGen、FreeKV、CLO 的预取依赖近似分数，会额外造成精度损失。SparseServe 集成了动态卸载，但不支持 graph execution，也没有预取。

serving 框架在 decoding 中依靠 CUDA Graph 捕获并重放计算，降低 kernel launch 开销。动态缓存管理若使用 CPU 控制、动态切片或变长 tensor，就会打断 graph。论文测得，在 DeepSeek-V3.1 的 dense attention（稠密注意力）上，CUDA Graph 相对 eager execution 将生成吞吐提高 1.2×；在 DeepSeek-V3.2 的 sparse attention（稀疏注意力）上提高 1.5×。对 300K token 的 KV pool，SGLang allocator 一次 allocate 加 free 约需 12 µs；ECHO 的 graph-friendly allocator 需要 6–8 µs。更重要的是，SGLang allocator 的 CPU 控制使 decoding 路径无法留在单一 graph 中。

CUDA Graph 对 dense/sparse attention 吞吐的影响，以及 SGLang 与 graph-friendly allocator 的分配和释放时延（Figure 3: (a) Normalized generation throughput of DeepSeek-V3.1 (dense attention) and DeepSeek-V3.2 (sparse attention) under eager and graph execution. (b) Allocation and free latency of the SGLang allocator and our graph-friendly allocator across different sizes.）

回取还受主机与 GPU 之间的带宽限制：PCIe 等互连带宽通常比 GPU HBM 低一至两个数量级。若 indexer 计算能与回取同时进行，传输延迟就有机会被计算覆盖；但在精确 top-k 完成前，系统尚不知道最终选中的 token。H20 上的 profiling 显示，随着上下文接近 100K、GPU pool 命中率达到 90%，indexer 计算时间可以超过 MLA KV cache recall（主机到 GPU 的 KV 回取）时间。

不同上下文长度下的 indexer 计算时延与不同命中率下的回取时延（Figure 4: Latency of indexer computation across different context lengths, and latency of recall across different hit rates, profiled using DeepSeek-V3.2 on NVIDIA H20 GPU.）

三、问题：容量限制与 top-k 依赖

ECHO 要同时解决两项问题。第一，动态淘汰、回取和新 token 分配发生在每一层 decoding 中；缓存状态若由 CPU 更新或通过变长 tensor 表达，就会破坏 CUDA Graph，管理与 launch 开销会抵消卸载收益。第二，稀疏 indexer 只有算完所有候选 token 的 index score 才能确定 top-k；等结果完整后才回取，无法与 indexer 计算重叠。利用历史相似度提前猜选中 token 虽能隐藏一部分传输，却会改变真正参与 attention 的 token 集合并损害精度。

因此，缓存管理必须用可捕获的 GPU 操作维护动态状态；预取则只能提前搬运候选 KV，不能代替精确 top-k，也不能因漏掉候选而跳过之后的正式回取。

四、方案：图内缓存与无损预取

4.1 固定元数据的缓存管理

ECHO 在每个 DP attention worker 上维护主机 KV pool 和 GPU KV pool。主机 pool 按模型管理，保存请求完整的 KV cache；GPU pool 按 layer 管理，缓存稀疏注意力最近选中的 token。indexer K cache 常驻 GPU。prefill 节点不执行动态卸载：请求的 KV cache 在 prefill 后传到主机内存，再由 decoding 节点按需回取。这种 PD disaggregation（prefill–decode 分离）避免 prefill 阶段的大量 token 选择与主机传输挤占 decoding 的 GPU pool 和 PCIe 带宽。

ECHO 的服务架构与数据流（Figure 5: Overview of the ECHO design.）

缓存管理器把状态保存在 GPU 上预分配的固定长度 tensor 中：GPUTokenFree 标记空槽，GPUTokenPriority 记录淘汰优先级，GPUIndicesBuffer 暂存操作选出的槽位，GPUTokenToHost 与 HostTokenToGPU 维护两侧映射。长度固定是为了避免 CUDA Graph 中不能动态创建或改变长度的 tensor。allocate（分配）并行读取空闲位，以 atomicAdd 为成功分配的线程分配槽位；free（释放）先保护本轮已选中的 token，再以并行 argtopk 找到优先级最低的槽并更新映射。淘汰时只改元数据，因为完整 KV 已在生成时写入主机 pool。回取操作根据 HostTokenToGPU 找出缺失 token，准备 GPU 槽并由 GPU kernel 直接访问主机内存传输 KV。以上操作都可在 decoding graph 中执行。

ECHO graph-friendly cache manager 的元数据与并行更新操作（Figure 6: The metadata and update operations in the graph-friendly cache manager of ECHO.）

若主机 pool 有 N_H 个 token、GPU pool 有 N_G 个 token，论文估算元数据占用为 4N_H + 13N_G byte。取 N_H=2M、N_G=200K 时，每层约 10 MB；DeepSeek-V3.2 合计约 610 MB。ECHO 基于 SGLang 实现，管理元数据使用 PyTorch tensor，parallel update 使用自定义 Triton kernel。

4.2 阈值预测与无损预取

Decoding 的 intra-query prefetching。 DSA 每个 decoding step 选择 index score 最高的 k 个 token，论文评测使用 k=2048。ECHO 观察到，第 k 高的 index score 在相邻 step 之间具有数值可预测性：它用 α=0.5 的 exponential moving average（EMA，指数移动平均）预测下一 step 的阈值，并在 indexer 计算期间预取当前分数高于该阈值的 token。预测阈值低于实际阈值时，候选数可能超过 k；ECHO 用全局计数器限制预取量。预取集合不作为最终选择，indexer 完成后仍按精确 top-k 计算 attention，并对尚未驻留的选中 token 执行回取，因此 EMA 误差不会造成 KV 缺失或 attention 精度下降。

对 20K-token ShareGPT 请求的监测表明，第 3 和第 50 层的第 2048 高分能被 EMA 跟随；超过预测阈值的候选数在多数 decoding step 接近 2048。候选过多会拖慢 indexer，因此系统仍需限制预取量；这项上限控制的是提前搬运量，不改变正式 top-k。

DeepSeek-V3.2 第 3 和第 50 层的第 2048 高 index score 与 EMA 预测（Figure 7: The 2048-th highest index scores in layers 3 and 50 of DeepSeek-V3.2 and prediction using EMA with α = 0.5 during decoding.）

DeepSeek-V3.2 第 3 和第 50 层超过预测阈值的候选 token 数（Figure 8: The number of candidate tokens for prefetching in layers 3 and 50 of DeepSeek-V3.2. The blue line uses 0 as the prediction, while the yellow line uses EMA with α = 0.5.）

Prefill 的 inter-query prefetching。 prefill 把 query 切成多个 block 顺序处理。计算完 block i 的分数后，ECHO 可以在计算 block i+1 的同时预取 block i 的候选 KV。精确 top-k 本身会拖慢 indexer，因此预取阶段使用近似 top-k：将 score 减去由前一 chunk 末尾 query 的 EMA 预测出的阈值，再按最高 8 位放入 256 个 histogram bin，优先预取高分 bin 中的 token。阈值平移缩小决定选取边界的 threshold bin，降低近似 top-k 的不确定范围。最终 attention 仍使用精确选择；未预取但被选中的 KV 仍会回取。

分数平移前后 prefill 近似 top-k 的边界 bin 大小（Figure 9: Threshold bin sizes of prefill chunks when computing approximate top-k with and without score shifts, profiled using DeepSeek-V3.2. The boxes and whiskers show the distribution of threshold bin sizes for tokens in the corresponding prefill chunk.）

融合 kernel 与流水线。 ECHO 将 prefetch 融入 DeepGEMM 的 indexer kernel，并用 warp specialization 和 software pipelining 分配工作。decoding kernel 由 Tensor Memory Accelerator（TMA）warps 载入 indexer K block、general matrix multiplication（GEMM）warps 计算 index score、prefetch warps 识别候选并回取；shared memory 和异步 barrier 让三类工作重叠。prefill kernel 按 query block 和 K block 分层循环，在下一 query block 计算期间处理前一 block 的 histogram 与预取。这样，互连传输可以与 GPU 上的 indexer 计算重叠。

decoding 阶段融合 intra-query prefetching kernel 的数据流与时间线（Figure 10: Data flow and timeline of the fused intra-query prefetching kernel for decoding.）

prefill 阶段融合 inter-query prefetching kernel 的数据流与时间线（Figure 11: Data flow and timeline of the fused inter-query prefetching kernel for prefill.）

五、结果：吞吐增益与延迟开销

5.1 长上下文吞吐

评测节点包含 8 张 NVIDIA H20（每张 96 GB HBM），通过 64 GB/s PCIe Gen5 连接主机；CPU 为 224 核 Intel Xeon Platinum 8480+，主机 DRAM 为 1.5 TB。软件使用 CUDA 12.9、PyTorch 2.8、SGLang 0.5.4 和 vLLM 0.11.1；所有框架都启用 decoding CUDA Graph，chunked prefill 大小为 2048。ECHO 和 SGLang 对 attention 使用 DP8、对 Mixture-of-Experts（MoE）使用 TP8；vLLM 因不支持 DP+TP 组合而对 attention 和 MoE 都使用 TP8。ECHO 的主机 KV pool 为 1.8M token，约占 1000 GB。

原始 FP8 DeepSeek-V3.2 无法装入 8×H20，因此评测使用 4-bit AWQ 的 DeepSeek-V3.2-Exp；indexer 与第 0、1、2、60 层保持未量化以保留精度。长上下文 workload 从 InfiniteBench 取 318 个 80K–100K token 请求，总输入约 26M token。最大吞吐实验将输出长度固定为 256 token，并把请求率设为 Inf，即同时提交所有请求。论文将 effective batch size（有效 batch 大小）定义为每个 decoding step 实际处理的活动请求平均数；它会随系统能否把 KV cache 放入 GPU pool 或主机 pool 而变化，不是预先固定的 batch size。

全部 GPU HBM 用于 KV pool 时，ECHO 在 Inf 请求率下相对 SGLang 的生成吞吐为 2.15×，相对 vLLM 为 4.1×；这对应摘要中的 2.1× 结论，但摘要没有展开上述实验条件。SGLang 的 325K-token GPU pool 每张 GPU 只能同时容纳约 3–4 个 80K–100K 请求，跨 DP worker 的 effective batch size 约 30；vLLM 的 TP 配置因重复保存 MLA KV cache，8 张 GPU 合计只有 180K-token pool，effective batch size 约 1.5。ECHO 的 1.8M-token 主机 pool 支撑更大的 effective batch size。这里的 2.15× 是固定输出 256 token、Inf 请求率下与 SGLang 的比较，不应与其他 pool 容量下的数字混用。

全部可用 GPU HBM 下的 InfiniteBench 生成吞吐；图(a) Inf 请求率下有效 batch size 为 ECHO/SGLang/vLLM 102/28/1.5，图(b) 为 73/19/1.5（Figure 12: Generation throughput on InfiniteBench under varying request rates on 8×H20, with each system configured to use all available GPU HBM. Annotated numbers denote the effective batch size.）

GPU KV pool 受限时，ECHO 与 SGLang 都设为 200K token，Inf 请求率下 ECHO 的吞吐优势是 3.10×。将所有系统的 GPU pool 限制为 110K token 后，ECHO 相对 SGLang 的优势最高为 4.12×。这两组均将输出限制为 256 token；容量越紧，SGLang 和 vLLM 的 effective batch 越受 GPU pool 限制，而 ECHO 可把更多活动请求的完整 KV 留在主机内存。

GPU pool 受限时的 InfiniteBench 生成吞吐；图(a) 200K 池 Inf 请求率有效 batch size 为 ECHO/SGLang 106/12，图(b) 110K 池为 ECHO/SGLang/vLLM 102/7/1.0（Figure 13: Generation throughput on InfiniteBench under constrained GPU HBM capacity, with output length limited to 256 tokens. Annotated numbers denote effective batch size.）

InfiniteBench 单任务且不限制输出长度时，ECHO 在 Code.Debug、En.MC、En.QA 的 output throughput 分别比 SGLang 高 27.07%、2.83%、7.11%，在 Code.Run 低 1.74%。各任务只有 75、160、31、42 个请求，未能让所有 DP worker 饱和；输出长度偏斜也会让少数长请求主导运行时间，因此不能把这组单任务结果直接等同于固定输出长度的最大吞吐测试。

InfiniteBench 各任务的生成吞吐与输出长度分布（Figure 14: Per-task generation throughput on InfiniteBench without capping output length. The histograms below each task show the corresponding output-length distribution.）

5.2 延迟开销与预取收益

ShareGPT 延迟实验随机抽取 100 个短上下文请求，在 mixed PD 部署下比较 ECHO 和 SGLang。ECHO 的平均 TTFT（time to first token）最多增加 7.9%；ITL（inter-token latency）增加 2.7%–27.8%，其中请求率 0.3 及以上为 2.7%–7.7%。端到端延迟在请求率 0.1–0.2 时增加 15.9%–19.2%，请求率 0.3 及以上最多增加 7.2%，0.5 至 Inf 时低于 4.6%。ECHO 更适合以吞吐为目标的长上下文负载；卸载仍需承担 prefill 备份、逐层缓存管理和 KV 传输开销。

ShareGPT 上 ECHO 与 SGLang 的平均 TTFT、ITL 和端到端时延（Figure 15: Mean TTFT, ITL, and end-to-end latency of ECHO and SGLang on the ShareGPT dataset.）

在 Inf 请求率下，ECHO 每个 decoding step 的全层分配、释放、回取和新生成 KV cache 卸载分别耗时 0.167 ms、0.572 ms、0.145 ms 和 0.261 ms，合计 1.15 ms，占全层 decoding latency 的 0.28%。全层 decoding latency 比 SGLang 高 2.8%；其中 graph replay 增加 5.9 ms，主要来自 CPU launch 与 metadata 开销。

ECHO 与 SGLang 的 prefill/decode 时延分解及 ECHO 的逐层卸载开销（Figure 16: Latency breakdown of ECHO and SGLang. (a) Per-layer prefill latency. (b) All-layer decoding latency, decomposed into graph replay and kernel execution. (c) All-layer offloading overhead of ECHO in one decoding step, including allocate, free, recall, and KV cache offload.）

InfiniteBench 上大多数层的 GPU pool 命中率为 0.97–0.99，第 12 层为 0.95，第 17 层为 0.88；高命中率减少了需要跨 PCIe 回取的 KV 数量。

InfiniteBench 上 DeepSeek-V3.2 AWQ 各层的 GPU pool 命中率（Figure 17: Per-layer GPU pool hit rates of DeepSeek-V3.2 (AWQ) on InfiniteBench, averaged across decoding steps.）

命中率为 0.5 和 0.9 的 decoding 微基准中，intra-query prefetching 将 indexer 加精确回取的总延迟最高分别降低 1.29× 和 1.51×；命中率为 0.9 时，回取延迟几乎可完全被 indexer 计算覆盖。命中率为 0.97 时改进较小，因为多数选中 token 已在 GPU pool。

不同命中率和上下文长度下开启/关闭 intra-query prefetching 的时延对比（Figure 18: Latency comparison between disabling and enabling intra-query prefetching.）

完整 InfiniteBench 测试中，启用 intra-query prefetching 使生成吞吐最高提高 4%；高 GPU pool 命中率和 MoE 计算占比限制了端到端收益。

启用或关闭 intra-query prefetching 时的端到端生成吞吐（Figure 19: End-to-end generation throughput comparison between disabling and enabling intra-query prefetching.）

prefill 的 inter-query prefetching 微基准最高改善 1.1×。每个 query token 独立选择 k 个 token，因此一个 prefill chunk 选中的 token 数量上界为 query token 数 × k；相比 decoding，prefill 的回取量更大，预取可降低的延迟有限。论文没有为 inter-query prefetching 单独做端到端吞吐消融：§6.2 的 PD 测试使用预先计算好的 KV cache；微基准还假设不同 query 的 top-k token 随机分布，未计入真实负载中相邻 query 可能共享选中 token 所带来的收益。
