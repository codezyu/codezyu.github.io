DGC：把 concurrent marking（并发标记）卸载到外部服务

论文：Shaving the Peaks: Taming Tail Latency for Managed Workloads via Disaggregated Garbage Collection，Hongtao Lyu、Yuhan Li、Mingyu Wu，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI 2026）。USENIX 论文页

论文将这套架构称为 disaggregated GC（DGC）。GC（garbage collection）仍由运行时协调；运行时保留周期触发和最终收尾，DGC 将并发 GC 的 marking 阶段（扫描对象引用并标记存活对象）交给外部服务处理。

TLDR： 多租户环境中的并发 GC 会周期性启动标记线程，与应用线程争用受限的 CPU。DGC 将 marking 从应用运行时卸载到共享服务；DGC-RDMA（跨机模式使用 RDMA，Remote Direct Memory Access）按 region（JVM 管理堆时使用的区域）取数，并配合 SATB（Snapshot-at-the-Beginning）逻辑快照与写屏障覆盖应用并发修改的引用，全局 GC 编排器则错开多个 JVM（Java virtual machine，用于运行 Java 程序的虚拟机）周期。在 OpenJDK 17 的 SPECjbb2015 评测中，基线与 DGC 使用相同物理核预算；DGC-SHM（同机共享内存模式）的 critical-jOPS（满足 service-level objective（SLO）时的最高请求速率）比 Shenandoah 高 24.0%。在 Shenandoah 的 critical-jOPS（10,356 req/s）处，DGC-SHM 和 DGC-RDMA 的 P99（99th-percentile）延迟分别降低 64.4% 和 60.3%。

一、背景：资源受限 JVM 的并发标记成本

GC 自动追踪对象是否仍可达，并回收不再使用的内存。Tracing 算法从 GC roots（已知存活的根对象，例如栈上的引用）出发，沿对象引用遍历；收集器将已发现但尚未扫描的对象保存在工作队列中，逐步找出存活对象。Shenandoah、ZGC 等并发收集器允许应用线程（mutators）在 marking 期间继续运行，减少长时间的 stop-the-world（STW）暂停。并发执行没有消除标记工作：GC 线程仍要扫描对象图，只是与应用线程同时争用 CPU。

云平台把大量 JVM 部署为小型服务实例，并为每个实例限制 CPU 和内存。论文引用的 2024 年 JVM 监测报告显示，82.8% 的 JVM 使用 1 至 8 个核，76.2% 分配到的内存少于 4 GB。在这种预算下，运行时可用于后台 GC 的空闲 CPU 很少；GC 开始标记时，应用线程的 CPU 份额会随之下降。

静态增加或固定 GC 核数可以减轻 GC 与应用的直接争用，但这些核要按 marking 峰值配置，在 GC 不活跃时会闲置；动机实验的非 GC 阶段 CPU 利用率不足 55%。多给堆内存可以减少 GC 频率，却会占用本已紧张的内存预算。减少 GC 线程也没有解决问题：在 SPECjbb2015 PRESET、注入速率 6,819 req/s 下，2 个标记线程会出现 Out of Memory（OOM）；把线程数从 8 降到 4，GC 周期数从 45 增到 50（增加 11%），P50（第 50 百分位，即中位数）延迟增加 20%，P99 延迟在统计上没有变化。

这是因为并发收集器以每轮 marking 开始时的逻辑快照判断存活状态；周期内死亡的对象仍会被当作存活对象，即 floating garbage。减少线程拉长 marking 窗口后，更多短命对象会作为 floating garbage 留到下一轮，使每轮回收的内存变少，GC 反而更频繁。论文据此把目标定为：GC 需要时能够弹性获得 CPU，非 GC 阶段则不静态占用这些核。

三、问题：远端标记与多运行时调度

把 marking 移出应用运行时，首先要解决跨机器并发扫描的正确性和数据传输成本。远端标记线程看到的 heap（运行时管理对象的内存区域）可能是不同时间读取的 region 拼成的中间状态；如果等整份 heap 复制完成再开始扫描，数据搬运就会串行占据 GC 周期。操作系统级远程分页既不理解 JVM 的 region 分配行为，也无法利用堆内对象的局部性，论文认为这会引入频繁缺页和难以接受的开销。

第二个问题是共享服务的调度。为单个 JVM 固定一组远端核，会在该 JVM 不需要 GC 时浪费资源；把多个 JVM 接到同一个标记池，如果各自按本地启发式同时触发 GC，又会让标记任务彼此争用服务端核，重新造成延迟尖峰。服务必须同时安排 GC 的启动时刻和标记线程数，并保证每个运行时能在堆耗尽前完成回收。

四、方案：DGC 的外部标记与全局调度

4.1 DGC 架构与本机、远端标记流程

DGC 包含 Disaggregated Marking Engine（外部 marking 服务）和 Global GC Orchestrator（全局 GC 编排器）。接入服务的 JVM 只提供运行时级别的堆信息与 GC 事件，应用本身保持不变。对于同一物理机上的 JVM，DGC-SHM 通过共享内存（shared memory，SHM）读取 heap 和 GC 元数据；跨物理机时，DGC-RDMA 通过 RDMA 读取远端 heap。服务端是裁剪过的 OpenJDK JVM，复用 Shenandoah 的并发标记数据结构，包括工作窃取队列和 bitmap（按位记录对象状态的数据结构）。

基线运行时与 DGC 服务的部署对比（Figure 2: Overview of the baseline (left) and DGC (right).）

每轮 GC 先有一个 STW 阶段，由运行时记录 GC roots 并建立 SATB 快照。应用恢复运行后，运行时通过 RPC 通知服务端开始复制与 marking；服务端一边取得 heap 数据，一边扫描对象。它周期性读取 SATB 屏障缓冲区中的新根。扫描收敛后，存活 bitmap 返回运行时，运行时再进入一次 STW 阶段，处理尚未同步的 SATB roots，完成一致性收尾。

4.2 SATB 屏障与远端标记正确性

Snapshot-at-the-Beginning（SATB）在 GC 周期开始时建立逻辑快照。并发 marking 期间，若应用覆盖对象引用，SATB 写屏障会把被覆盖的旧引用记入缓冲区，因此标记器即使没能从当前 heap 视图看到这条边，仍会沿缓冲区找到快照时存活的对象。标记完成前不回收对象；正确性依赖 heap 遍历和屏障缓冲区共同覆盖快照中的引用，不要求任一来源单独完整。

DGC-RDMA 的本地 heap cache 初始为空，且可能容纳不下完整 heap。若标记线程发现某个引用指向尚未缓存的 region，它先把该引用放入 region 对应的 pending queue（待处理队列）；region 复制完成后，RDMA 控制线程汇总队列，并把引用交给一个 GC 线程处理，避免多个线程同时扫描同一 region、争写共享 bitmap。

论文用 A → B → C → D 说明这个过程：A 所在的 R1 已缓存，B、C、D 所在的 R2 尚未缓存。标记线程扫描 A 后先挂起 A → B；R2 复制期间，如果 mutator 覆盖了 B → C，SATB 屏障会保存旧边。R2 到达后，标记线程从 pending queue 扫描 B，再从屏障记录找到 C，最后继续到 D。因此，即使远端读取由不同时间的 region 组成，标记结果仍覆盖周期开始时的存活对象。

4.3 region 级 software paging 与 heap cache

DGC 不让操作系统按页换入远端 heap，而是在用户态实现 software paging，并以 JVM 的 region 作为缓存和地址转换粒度。论文使用 4 GB SPECjbb heap、默认 2 MB region 举例：对应的软件页表只有 4 KB，可放入测试机 48 KB 的 L1 数据缓存（L1d cache）。region 级取数利用运行时按 region 分配对象的局部性。论文引用既有研究称跨 region 引用通常有限，并据此认为整块取入可提高本地 cache 命中率；论文未报告这一提升幅度。初始化时，DGC 预注册固定大小的本地 heap cache，避免逐页注册 RDMA 内存。

每个 region 有一个 8 字节状态项：高位记录 NotCached、OnTrans、Cached 或 OnEvict，低位是可重入读锁计数。标记线程访问对象时先登记并确认 region 仍为 Cached；RDMA 控制线程只有在计数归零时才能切换状态或覆盖缓存内容，避免取数/驱逐中断对象扫描。

缓存替换按 region 的 hotness 排序。已缓存 region 的分数取其中已发现但尚未扫描对象（grey）的总大小；未缓存 region 则先按 pending 引用数和平均对象大小估算，取回后再校准。只有待取 region 的分数高于驱逐候选的设定倍数时才取入，以避免反复换入换出。开始 marking 前，DGC 还会先预取含 GC roots 的 region；预取窗口中标记线程保持休眠，因此全局 GC 编排器不会把空等时间算作已分配的 GC 核。

Java 对象的 Klass 元数据决定每类对象包含哪些引用。DGC 通过 OpenJDK 的 APPCDS（Application Class-Data Sharing）共享类信息，并在服务端以与运行时相同的虚拟地址加载 Klass 结构，避免逐对象地址转换。运行时新定义的类会通知 DGC；下一轮 GC 前，服务端通过 SHM 或单边 RDMA 读取新类元数据。

4.4 异构 JVM 的 GC 联合调度

每个接入 JVM 内的轻量 monitor 提供剩余堆空间、分配速率、存活对象大小和历史 marking 时长。全局 GC 编排器根据这些数据，为每轮任务决定 GC 触发时刻及标记线程数；目标是在不让 mutators 耗尽可用内存的前提下尽可能推迟 marking，从而减少 floating garbage。若任务临近堆耗尽期限，全局 GC 编排器可临时增加线程，但所有同时运行的标记线程总数不能超过服务池可用核数。

全局 GC 编排器将剩余可用内存除以分配速率估计最晚完成期限，并根据历史存活对象大小和按线程数拟合的线性模型估计 marking 时长。它使用 Google OR-Tools 的 CP-SAT 求解器为异构运行时联合排程；单实例场景通常约 5 ms，每 10 ms 根据最新指标重求解。12 个 backend 时，单次求解耗时为 11.1 ms，超过 10 ms 的更新周期；论文将这个时长与持续数百毫秒的 GC 任务比较，并认为仍足以完成排程。

运行时刚启动、缺少历史数据时，DGC 暂不接管，由 Shenandoah 按默认阈值执行本地 GC；负载突变使计划无法在堆耗尽前完成时，该轮也回退到本地 Shenandoah。若服务端不可达，正在进行的请求可能走 Shenandoah 的 degenerated GC（STW 回收路径）；SPECjbb 实验中这次暂停约 100 ms，后续周期则恢复为本地并发 GC。

五、结果：DGC 的延迟收益与资源成本

5.1 两节点集群上的宏基准评测

DGC 基于 OpenJDK HotSpot 17（jdk-17+35）的 Shenandoah 实现，共 10,383 行 C/C++ 代码，其中 946 行用于 DGC-SHM、3,601 行用于 DGC-RDMA、959 行用于 GC 调度，其余包括共享类信息、GC 集成、RPC 和 RDMA 支持。

评测在两台服务器组成的集群上进行，每台有两颗 Intel Xeon Gold 6430（每颗 32 个物理核）和 128 GB 内存；关闭超线程并固定为 performance 模式。每台服务器配一张通过 PCIe 4.0 ×16 接入的 200 Gbps Nvidia BlueField-3 DPU（data processing unit），作为 RDMA 网卡。Artifact Appendix 列出的操作系统为 Ubuntu 22.04 LTS。

主要基线是 Shenandoah 和 G1。每种负载先测出可运行的最小 heap，再以其 2 倍进行评测；DGC-RDMA 的主要结果不限制服务端本地 heap cache 大小，受限 cache 的结果另测。为保持 CPU 预算相同，基线给每个 JVM 分配 8 + c 个核；DGC 给每个应用 JVM 8 个核，并将 N × c 个核分给一个共享 DGC 服务。SPECjbb2015 和 HBase 取 c = 2，DaCapo 取 c = 4。主结果中的每种应用使用两个实例；SPECjbb 的各项结果以两个 backend 集群的汇总值计算。以 SPECjbb 的 N = 2、c = 2 为例，基线和 DGC 均使用 20 个物理核：前者为 2 × (8 + 2)，后者为 2 × 8 + 2 × 2。RDMA cache 子测试则明确为两个各 4 GB 的 heap。

在 SPECjbb2015 1.0.4 默认 HBIR_RT 模式下，critical-jOPS 表示符合延迟 SLO 时的最大请求速率。DGC-SHM 的 critical-jOPS 比 Shenandoah 高 24.0%、比 G1 高 36.8%；DGC-RDMA 比 DGC-SHM 低 8.6%，但仍比 Shenandoah 高 13.4%、比 G1 高 25.0%。在 Shenandoah 的 critical-jOPS（10,356 req/s）处，DGC-SHM 和 DGC-RDMA 的 P99 延迟分别降低 64.4% 和 60.3%。在 6,000–13,000 req/s 区间内，两种 DGC 的 P99 低于 Shenandoah；曲线右侧更高请求速率处，DGC 的 P99 更早发散。作者将这一差异归因于 DGC 应用 JVM 比基线少 2 个核。

HBase 2.5.11 使用两个 RegionServer 和 Yahoo! Cloud Serving Benchmark（YCSB）0.18.0 的两种混合负载：50% read + 50% update，以及 50% read + 50% insert。在 read-update 负载的峰值吞吐处，DGC-SHM 的 read、update P99 比较好的基线 G1 低 58.3%、40.3%；DGC-RDMA 分别低 53.8%、29.1%。在 read-insert 负载处，DGC-SHM 的 read、insert P99 比 Shenandoah 低 81.8%、55.7%，DGC-RDMA 分别低 41.4%、28.5%。G1 因频繁 STW full GC（全堆回收）无法达到与 Shenandoah、DGC 相近的峰值吞吐。

DaCapo 23.11-chopin 测试九个能报告逐请求延迟的负载：h2、tradesoap、tradebeans、lusearch、tomcat、spring、kafka、cassandra 和 jme。五个负载在 Shenandoah 可维持的最高速率处表现出明显差距：DGC-SHM 的 P99 在 h2、tradesoap、tradebeans 和 kafka 分别降低 88.6%、73.1%、92.8% 和 71.0%；lusearch 的差距达到四个数量级。论文报告其余 tomcat、spring、jme、cassandra 在所有测试速率下都没有明显的 DGC 与 Shenandoah 差距。论文将这四项归为低 GC 压力负载：cassandra 的工作集大多位于 heap 外，spring 和 tomcat 的 heap 工作集只有几十 MB，jme 在可达到的速率下很少触发 GC。G1 的年轻代暂停低于 1 ms，因此在 tradesoap、spring、cassandra 上优于 Shenandoah 和 DGC；对其余七项，G1 与两者的表现相近。

5.2 混合负载、RDMA 成本与扩展性

混合负载测试让多个 JVM 共用一个 DGC 服务。SPECjbb 与 HBase YCSB A 共置时，在 100% 目标负载下，DGC-SHM 将 SPECjbb P99 从 Shenandoah 的 142 ms 降到 46 ms（67.6%）；YCSB read 从 4.64 ms 降到 1.51 ms（67.5%），update 从 11.1 ms 降到 2.80 ms（74.8%）。DGC-RDMA 对应降低 51.5%、58.5% 和 75.9%。四个 DaCapo 负载共置时，lusearch 在 Shenandoah 下于 60% 混合负载达到 64 s P99，DGC-SHM 为 708 μs；100% 负载下，tradebeans 和 tradesoap 的 P99 分别降低 94.6% 和 66.1%。

共用 DGC 服务的混合负载 P99 延迟（Figure 7: Mixed-workload P99 latency under different load levels; each mix shares one DGC service. (a) SPECjbb + HBase mix, with HBase Read/Update sharing a y-axis. (b) DaCapo 4-app heterogeneous mix. Bands show (min, max) across 3 reps.）

作者用 SPECjbb2015 PRESET 模式、注入速率 10,356 req/s 单独评估 RDMA heap cache。每个运行时使用 4 GB heap，两个运行时之间严格轮换共享的 4 个 DGC 核，以免 GC 同时触发而把峰值 cache 内存加倍。最受限的 1/4 cache 配置仍比 Shenandoah 低 51.5% P99，RDMA 流量没有超过链路带宽。1/2 cache 配置在内存开销与传输量之间取得较好平衡：相对两个 4 GB heap，服务端额外配置 2 GB 本地 heap cache（25%），平均每轮 GC 传输 5.52 GB，相对 4 GB 全 heap 的数据量放大 37%。

扩展性测试将每个 SPECjbb backend 的负载设为 6,819 req/s，并随 backend 数量同比增加系统总负载。DGC-SHM 受限于单台 64 核服务器，最多测到 6 个 backend；7 个至少需要 70 核。到 6 个 backend 时，DGC-SHM 和 DGC-RDMA 相对 Shenandoah 的 P99 改善最高为 43.3% 和 50.9%。DGC-RDMA 测至 12 个 backend 后，收益开始下降，作者将其归因于 RDMA 网卡带宽成为瓶颈。

SPECjbb2015 PRESET 模式下的扩展性（Figure 9: Scalability test results on SPECjbb2015 PRESET.）

消融实验中，禁用数据复制与 marking 流水重叠的 DGC-noOPT 将 P99 从 81.5 ms 增至 87.0 ms（增加 6.7%），说明流水设计隐藏了大部分传输成本。移除全局 GC 编排器的 DGC-noCOOR 依赖 JVM 本地启发式，触发时间难以对齐，标记常在完成前耗尽可用堆并退回 degenerated GC；P99 达到 13,800 ± 7,132 ms，而完整 DGC 为 81.5 ± 1.1 ms。结果表明，远端标记的数据通路和跨 JVM 触发编排共同决定系统收益。
