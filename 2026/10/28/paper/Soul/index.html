Soul：以 cache coherence（缓存一致性）实现分离式内存同步

论文：Efficient and Scalable Synchronization via Generalized Cache Coherence，Yanpeng Yu、Seung-seob Lee、Lin Zhong、Anurag Khandelwal，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI 2026）。USENIX 论文页。

TLDR： 论文研究 disaggregated shared memory（计算与内存分离、但向应用提供一致共享内存视图的系统）中的锁；现有锁算法叠加在页级缓存一致性之上，会产生重复的跨节点通信。作者把同步视为缓存一致性在时间和空间上的泛化，并提出 Generalized Cache-Coherence Protocol（GCP）：wait queue（等待队列）让冲突请求等到当前持有者释放权限，variable-size cache line（可跟踪任意大小区域的缓存一致性单位）则让一致性状态覆盖任意大小的受保护数据。Soul 在 MIND 上实现 GCP，以用户态库提供 C 的 pthread_rwlock 与 Rust 的 std::sync::RwLock，不要求改应用源码，并保留 MIND 的 x86-TSO memory consistency model（内存一致性模型）。在 8 个计算刀片的 Yahoo! Cloud Serving Benchmark（YCSB）C 类（YCSB-C，100% 读）负载中，Soul 达到 37.1 Mops（每秒 3710 万次操作），较 Pthread、Cohort、MCS 和 Lock Service 高 2–3 个数量级；论文摘要将真实应用的总体性能提升概括为相较 state-of-the-art locks 高 1–2 个数量级。交换机侧元数据开销低于 8%。

一、背景：分离式内存中的缓存一致性

分离式内存把服务器资源拆成计算刀片和内存刀片，再通过高速网络连接。计算刀片保留本地 DRAM 作为缓存，远端内存按页调入；缓存一致性协议为分布在不同计算刀片上的应用线程提供统一、连贯的内存视图。本文讨论的 disaggregated shared memory 就是建立在分离式内存之上的这类共享内存系统。

论文以 MIND 为例。MIND 使用目录式 MSI 协议：目录记录每个 4 KB 页的持有者和权限，放在可编程交换机中；计算刀片上的 DRAM 缓存页数据。MSI 的三种权限是 Modified（M，单一持有者可读写）、Shared（S，可由多个持有者读取）和 Invalid（I，不在任何缓存中）。论文把 cache line 用作一致性协议跟踪的数据单位；在 MIND 中，它对应一个 4 KB 页。

缓存一致性维持 single-writer-multi-reader（SWMR）不变量：一个共享状态要么由单个写者独占，要么由多个读者共享。传统协议按单条指令授予权限；在多核或 NUMA 系统中，核间通信约为 20–100 ns，而分离式共享内存的跨刀片通信为 5–10 µs。后者的时延使每次额外的一致性往返都可能显著拖慢锁操作。

二、现状：分层锁产生冗余通信

常见可扩展锁建立在缓存一致性协议之上，并尽量减少获取锁时的缓存一致性事务。MCS 是队列式互斥锁，每个请求线程在私有 cache line 上等待；Pthread reader-writer lock（读写锁）使用集中式读者计数；Percpu 将读者计数分散到各核；Cohort reader-writer lock 利用内存层次结构，让锁在附近线程之间交接。这些设计在核间通信较快时能减少争用，但每次加锁、解锁和访问受保护数据仍可能触发跨刀片的缓存一致性事务。

在 MIND 上运行 Twitter key-value（KV）store 的 cluster 3、10、53 负载时，Cohort 锁的平均请求处理时延在一个计算刀片上低于 10 µs，扩展到 8 个刀片后超过 1 ms。论文称锁操作占处理时间的大部分，但没有在正文给出具体比例。论文引言还概括称，分层锁会使同步密集型真实应用的性能最多下降 1000 倍，并将其归因于以太网上重复的跨缓存一致性消息；该概括没有给出这项 1000 倍退化对应的具体负载、刀片数和比较基线。

MIND 上 Cohort 锁的端到端请求时延与同步时间占比（Figure 3: End-to-end request latency (left y-axis, log-scale) and %-age of time spent in synchronization (right y-axis) for the state-of-the-art Cohort lock [27] on Twitter KV store workloads [58] atop MIND [16], a disaggregated shared memory system.）

另一类方案绕过缓存一致性，使用独立的软件锁服务或可编程网络中的锁服务。论文将客户端/服务器式软件锁服务的时延定性描述为比缓存一致的内存访问高出多个数量级，但没有在此处给出固定比值。网络锁服务虽然能利用交换机加速，但交换机的处理和存储资源有限，也难以实现需要复杂缓存一致性逻辑的优化。两条路线都没有同时解决高时延通信和锁数据局部性问题。

三、问题：锁与协议的时空粒度不同

锁和缓存一致性都要维护 SWMR，但作用范围不同。缓存一致性协议只在固定大小的 cache line 上、按单条指令授予权限；锁则要求独占或共享权限覆盖整个临界区，也就是任意数量的指令。锁保护的数据还可能由多个分散区域组成，大小不固定，甚至暂时为空。

因此，单纯把锁算法叠在页级协议之上，会把锁状态与临界区数据分开处理，增加一致性通信；完全绕开一致性层，又无法直接复用其状态管理和数据局部性优化。论文要解决的问题，是如何在保留现有目录式一致性协议能力的同时，让锁权限和受保护共享状态按临界区的时间与空间范围协同工作。

分离式共享内存中的三种同步实现路径（Figure 1: Different approaches for realizing synchronization. Layered approaches (left) incur redundant coherence transactions while standalone approaches (middle) preclude key optimizations, both significantly degrading application performance over disaggregated memory’s slower inter-compute and compute-memory interconnects. Our approach (right) generalizes cache coherence for efficient locks.）

四、方案：GCP 在一致性层实现同步

论文把锁同步看作缓存一致性在时间和空间上的泛化，并据此提出 Generalized Cache-Coherence Protocol（GCP）。GCP 面向目录式缓存一致性协议，通过两个扩展处理锁的时间范围和受保护数据的空间范围；未参与锁的普通 cache line 仍按原协议工作。

分离式共享内存中的背景、分层锁开销与 GCP 设计（Figure 2: Background & motivation (§2) (a) Coherence example with a single cache line at address 0x0A, a cache directory, and two compute blades (§2.2). (b) Lock acquisition latency and # of coherence transactions for locks layered atop coherence on disaggregated memory for different reader-to-writer ratios (§2.2). (c) GCP generalizes existing coherence protocols to realize locks (§2.2).）

4.1 wait queue 的临界区权限管理

传统协议在收到权限请求后立即执行失效或降级，使新请求可以取得所需权限。GCP 遇到与当前持有权限冲突的请求时，将该请求放进 wait queue，等当前持有者显式释放后再处理；因此，持有者可在整个临界区内保持权限。GCP_acquire 异步申请权限，GCP_is_acquired 查询申请是否完成，GCP_release 标记临界区结束并触发队列处理。请求者等待时可以让调度器切换到其他线程。

队列只处理冲突请求。多个读者取得 Shared 权限不需要排队；Invalid 状态转为 Shared 或 Modified 时也没有旧持有者需要等待。若锁所在 cache line 被逐出，GCP 在目录中记录其仍处于锁定状态，避免逐出意外结束锁所有权；这也避免通过固定 pin 住所有锁页而耗尽缓存、导致死锁。

wait queue 延长缓存权限的持有时间（Figure 4: Temporal generalization with wait queues (§3.1).）

4.2 shared memory list 的一致性域管理

GCP 将空间扩展称为 variable-size cache line：目录中的一个地址 tag 不再只关联固定大小区域，而是在逻辑上指向 shared memory list（共享内存列表），列出多个 (base address, size) 区域；这些区域可以不连续、大小不同。申请锁后，协议把列表中的区域作为一个一致性域处理，在权限转移时一起移动或失效，使任意大小的共享状态可以跟随锁取得 SWMR 语义。

GCP_create 注册地址区域，GCP_destroy 解除注册并将其恢复为普通 cache line。一个列表中的区域不得与其他列表重叠；创建和销毁会广播到所有计算刀片与目录，并刷新相关 cache line。shared memory list 只负责把受保护数据合并到缓存一致性流量中，真正排队和执行锁语义的是 wait queue；没有列表时锁仍然正确，只是访问数据需要更多缓存一致性事务。

shared memory list 的空间泛化示例（Figure 5: Spatial generalization with shared memory lists (§3.2).）

4.3 GCP 的锁数据优化与正确性验证

把锁和受保护数据放在同一一致性域后，GCP 可以在一次缓存一致性事务中同时取得锁和数据，省去先取锁、再取数据的额外往返。锁和数据也能像普通缓存数据一样留在持有者本地，直到其他请求使其失效。GCP 锁是否公平取决于 wait queue 策略；采用 FIFO 等无饥饿策略时，排队请求最终都能被处理。

作者用 ProtoGen 为 MSI、MESI、MOSI 和 MOESI 四种目录式协议生成规格，再用 Murphi 检查所有可达状态下的互斥性和无死锁性质。为控制状态空间，模型将范围限制在一个地址、两个数据值、三个带私有缓存的计算刀片和一个目录；论文另以最多 8 个刀片、80 个核心的微基准做实现压力测试。协议正确性不等于应用不会发生嵌套锁死锁，这仍由应用负责。

4.4 Soul 的实现边界与锁接口

Soul 是 GCP 在 MIND 之上的端到端实现：计算刀片上的 DRAM 缓存控制器和内核维护锁相关状态，可编程交换机目录转发请求并记录 wait queue 持有者与版本。Soul 把队列放在当前写者所在的计算刀片，使写者释放锁后可在本地处理下一请求；目录只负责转发。队列转移用版本号确认已转发请求都已被处理，从而避免多个读者各自维护副本造成不一致。

Soul 在 MIND 上的 GCP 全系统实现（Figure 6: Soul is a full-system realization of GCP atop MIND (§4).）

Soul 中 wait queue 的三种持有位置（Figure 7: Wait queue holders under different cases in Soul (§4.1). Case (i): the wait queue does not exist without writers; Case (ii): the wait queue is at the current writer; Case (iii): the wait queue is at the next writer after the current readers.）

GCP 的改动限于缓存一致性层。Soul 不改变 MIND 的普通页行为，并保留其 x86-TSO 内存一致性模型；GCP 本身不要求某种特定内存模型。GCP 等待队列在 8 刀片设置下使计算刀片内核元数据开销低于 0.2%、交换机 ASIC（专用集成电路）开销低于 8%；shared memory list 在 MIND 每页增加 9 字节元数据，对计算刀片内核的额外开销不超过 0.3%。

Soul 用户态库提供两种标准 reader-writer lock（读写锁）接口：C 的 POSIX pthread_rwlock 和 Rust 的 std::sync::RwLock。应用改为链接 Soul 锁库即可，不必改锁调用源码。库先用传统软件锁协调同一计算刀片上的线程，再用 GCP 锁协调跨刀片访问；每次全局加锁最多复用本地锁 64 次，以保证无饥饿。等待 GCP 锁时可以自旋或让出 CPU，默认实现会睡眠，使调度器可以运行其他线程。

Soul 锁库的层级结构（Figure 8: Soul lock library’s hierarchical design (§4.3).）

Rust 的 RwLock 在初始化时能显式给出受保护对象，因此可将对象数据一并纳入 shared memory list。若临界区内改变对象占用的内存范围，当前实现必须先 GCP_destroy 再 GCP_create 更新列表，相关广播和缓存刷新会带来开销。锁管理器还把 GCP 页的分配限制在本地 DRAM 缓存容量的默认 6%；超出上限时退回基于缓存一致性的传统软件锁。它能回收进程崩溃时的资源，并借助 MIND 的交换机状态复制恢复交换机故障；计算刀片或内存刀片故障不在其可恢复范围内。当前库提供基本获取和释放接口，带超时、try-lock 和显式 abort 等 API 留待后续扩展。

五、结果：真实工作负载与 CXL 模拟

5.1 MIND 实机集群上的 Soul 性能评测

实机平台由 5 台服务器和一台 Tofino 可编程交换机组成。交换机为 32 端口、6.4 Tbps。1 台服务器运行内存刀片 VM，配有两颗 18 核 Intel Xeon、384 GB 内存和 4 张 100 Gbps Mellanox CX-5 网卡；另外 4 台服务器各配两颗 12 核 Intel Xeon 和 2 张 CX-5 网卡，并各运行两个计算刀片 VM（每个 socket 一个）。每个 VM 有 10 个应用核心、2 个 OS 核心和 512 MB DRAM。实验最多使用 8 个计算刀片。

评测包括细粒度加锁的 MIND-KVS 和粗粒度全局锁的 Kyoto Cabinet，每个计算刀片运行 10 个工作线程。MIND-KVS 使用 Twitter 的 cluster 3、10、53 轨迹，读写比依次为 99:1、50:50、89:11，并使用 YCSB A、B、C，读写比为 50:50、95:5、100:0。哈希桶按 4 KB 页对齐，并通过 Rust API 将桶数据与锁合并。Kyoto Cabinet 运行 TPC-C，在 1 个和 10 个 warehouse 的设置下测试高、低竞争。对照包括 MCS、Pthread、Percpu、Cohort，以及作者因兼容性问题自行重实现的 FissLock 逻辑 Lock Service。

在 8 个计算刀片的 YCSB-C（纯读）测试中，Soul 达到 37.1 Mops，较 Pthread、Cohort、MCS 和 Lock Service 高 2–3 个数量级。纯读时没有写者触发失效，Soul 可让多个刀片同时缓存热点锁及其数据。Percpu 在纯读测试中的吞吐接近 Soul；加入 1% 写操作的 Twitter cluster 3 后，论文报告 Percpu 吞吐下降，但没有在正文给出具体差值。论文还指出，cluster 10、cluster 53、YCSB-A 和 YCSB-B 等写入较多的负载未能在以太网上随计算刀片数扩展，并将原因归于较长的跨缓存时延，而非 GCP 机制本身的限制。

Soul 在 MIND-KVS 上的吞吐扩展（Figure 9: Soul throughput scaling for MIND-KVS w/ Twitter cluster 3, 10, 53, and YCSB A, B, C (§5.1). Y-axis is in log scale.）

Kyoto Cabinet 的 TPC-C 使用全局排他锁，事务串行；在 1 个和 10 个 warehouse 的设置下，论文报告 Soul 吞吐与 Cohort 和 Lock Service 处于可比水平。

Soul 在 Kyoto Cabinet TPC-C 上的吞吐扩展（Figure 10: Soul throughput scaling for Kyoto Cabinet w/ TPC-C (§5.1). Y-axis is in log scale.）

在每个刀片一条线程竞争同一把锁、访问 4 KB 共享数据的微基准中，论文测试纯写、50% 读、95% 读和 99% 读四种竞争比例。Soul 在 8 个刀片上的锁与数据平均获取时延为 100–200 µs，较 MCS、Pthread、Percpu 和 Cohort 中最快的分层锁低约一个数量级。Soul 对锁和数据只发起一次缓存一致性事务；Pthread 和 Percpu 的事务数随刀片数增长，MCS 的事务数保持固定，但高于 Soul 的一次事务。

Soul 的平均锁获取时延与缓存一致性事务数（Figure 11: Soul avg. latency & # cache-coherence transactions per lock acquisition (§5.2).）

在上述 MIND 锁与 4 KB 数据设置的消融实验中，作者分别关闭 combined data optimization（锁与数据合并获取）和 locality optimization（锁与数据的本地缓存）。关闭 locality optimization 后，锁与数据获取时延提高 1–2 个数量级；关闭 combined data optimization 后，获取数据需要额外一次网络往返。

5.2 SoulCXL 的模拟评测

作者用 gem5 和 SynchroTrace 评估 GCP 在 CXL 3.0（Compute Express Link 3.0）上的可行性，因为当时没有可用于该实验的商用硬件。模拟集群由 16 个各含 8 个核心的 CPU host 和一个 CXL Global Fabric Attached Memory Device（GFD）组成；每个核心有 64 KB 指令缓存、64 KB 数据缓存和 4 MB L2 cache，各级缓存均为 2 路组相联。GFD 包含 16 个 4 GB DRAM 节点，每个节点有 8 个 DDR4-2400 通道。模型采用两台 host 间 300 ns 的往返时延，这一设定取自既有研究且偏乐观，因此作者将模拟结果视为 GCP 收益的下界。

受硬件实现复杂度限制，SoulCXL 没有实现通用的 shared memory list，而是用单个连续区域表示受保护数据，并将区域限制为 64 B 的 2 的幂倍数。每个 variable-size cache line 用 4 bit 编码大小；普通 64 B cache line 的存储开销低于 0.6%。对 64 KB L1 cache 的面积估算中，新增位占 0.0004 mm²，总 cache 面积为 0.0613 mm²，新增部分低于 0.7%。

在 MIND-KVS 上，SoulCXL 相对最接近的对照方案，在 Twitter 轨迹上最高快 1.7 倍，在 YCSB 上最高快 2.0 倍。

SoulCXL 在 MIND-KVS 上的吞吐扩展（Figure 13: SoulCXL throughput scaling for MIND-KVS w/ Twitter cluster 3, 10, 53, and YCSB A, B, C (§6).）

Kyoto Cabinet 中，粗粒度全局锁无法使用锁与数据合并，而所有请求者都是写者，时间局部性优化也无收益，因此 SoulCXL 与 Lock Service 表现相近。

SoulCXL 在 Kyoto Cabinet TPC-C 上的吞吐扩展（Figure 14: SoulCXL throughput scaling for Kyoto Cabinet (§6).）

锁争用微基准还比较了不同 CPU host 数下的时延和缓存一致性事务数。CXL 模拟中的所有方案时延都低于 MIND 实机结果，但事务数更多；作者将此归因于较低的互连时延让线程更频繁地访问锁，从而增加争用。纯写和 50% 写者负载下，Lock Service 的时延与 SoulCXL 接近；读者占 95% 或 99% 时，SoulCXL 的局部性优化降低了时延。CXL 评测只验证了模拟中的设计方向；完整适配硬件一致性协议仍是后续工作。

SoulCXL 的平均获取时延与缓存一致性事务数（Figure 15: SoulCXL avg. latency & # cache-coherence transactions per lock acquire. Y-axis is in log scale.）

模拟中的锁与数据获取延迟分解也显示，锁与数据局部性可将获取时延降低 1–2 个数量级，合并获取数据可省去单独取数的一次往返。这些结果受 300 ns 模拟配置、SynchroTrace 重放和 SoulCXL 的连续区域限制约束，不能当作真实 CXL 硬件上的测量值。
