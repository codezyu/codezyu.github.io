论文：ACOS: Apple’s Geo-Distributed Object Store at Exabyte Scale，Benjamin Baron、Aline Bousquet、Eric Metens、Swapnil Pimpale、Nick Puz、Marc de Saint Sauveur、Varsha Muzumdar、Vinay Ari，USENIX FAST ’26（2026）。前三位作者是论文标注的主要作者。

TLDR： ACOS 1.0 在两个区域间复制完整对象，区域内使用 (20, 2, 2) Local Reconstruction Codes（LRC，局部重建码），整体复制因子为 2.40；ACOS 2.0 把对象切成四个等长数据段并异或生成一个校验段，分布到五个区域，整体复制因子降到 1.50。一个区域失效时，缺失段可由其余四段重建；两个或更多区域不可用时，需要访问这些失效区域数据的请求会失败。完成时延优化后的一个月线上测量比较了 1 MiB 和 10 MiB 两种代表性对象：2.0 的完整对象 PUT 时延与 1.0 相近，完整对象 GET 时延更高，约 50 ms 的差值对应区域间平均网络时延。Apple 对剩余数据的跨代迁移历时数年，涉及数艾字节且没有停机。

一、背景：ACOS 的服务负载与规模

Apple 的 iCloud、Apple TV、Apple Music、Maps 等服务每天被全球数亿用户使用。ACOS 是面向这些用户服务和内部平台的对象存储系统，生产运行超过十年，管理数艾字节对象、每天处理数十亿请求。对象大小从数十 KB 的元数据和缩略图，到数 GB 的视频不等；不同服务的读写和删除模式也不同。用户上传通常直接访问 ACOS，部分下载经由内容分发网络（Content Delivery Network，CDN），而 Points of Presence（PoPs，网络接入点）也会就近处理时延敏感内容。

媒体服务主要存储数 GB 的大文件，内容由 CDN 缓存、很少读取且不会删除；Maps 的地图和 3D 视图经 CDN 分发，因此很少下载、几乎不删除，分析工作负载则会频繁下载和删除。内部工作负载还包括分析、长期保存、法律和制造资料。论文指出，照片尤其是视频要求更高吞吐和更低时延，媒体服务的大文件会拆分后并发上传；生产 GET 也常用范围 GET，只返回对象的一部分。

二、现状：双区域 ACOS 1.0 的复制设计

ACOS 1.0 于 2013 年部署。一个 store 由两个位于不同地理区域的 stamp 组成；stamp 是部署在一个数据中心内的独立存储服务单元，包含计算与存储主机。两个 stamp 以 active-active 方式工作，均可接收客户端读写。系统向内部服务提供兼容 AWS S3 的 API；请求经过负载均衡器、请求处理器和限流器后，由存储层读写磁盘。协调器负责数据放置、节点健康检查、修复与垃圾回收，对象元数据保存在双区域部署的 Cassandra 中。

ACOS 1.0 的 stamp 组件布局（Figure 2: Stamp layout in ACOS.）

每个 stamp 的存储层连接 JBOD 磁盘阵列。对象数据以 blob 形式保存在 container 中；container 是容纳多个对象的大文件，大小为 4–32 GiB。请求处理器将对象按 256 KiB 数据块流式写入 container 集群。新集群先对 12 个数据 container 做五副本写入，达到容量后再 seal（封存）：删除数据副本，生成基于 LRC 的校验 container。(12, 2, 2) LRC 表示 12 个数据 container、2 个局部校验和 2 个全局校验，数据分成两个各含 6 个 container 的条带（stripe）。集群封存后不可再写。该配置在 86.15% 的失效组合中可恢复 4 个 container，其余情况下可恢复 3 个。为降低新对象的存储开销，后续 ACOS 1.0 将新数据改用 (20, 2, 2) LRC。

container 集群布局：(a) 12 个数据 container、每个五副本的复制集群；(b) 含 12 个数据 container 和 4 个校验 container 的封存集群（Figure 3: Container cluster layout in ACOS for (12, 2, 2) LRC codec layout.）

写入时，请求处理器把数据块送到集群的复制副本。副本通过基于 ZAB 的分布式事务日志传输数据，并用 Raft 选举 leader；达到副本 quorum（完成写入所需的副本数量）后，请求处理器保存对象位置等元数据，再向客户端完成请求。删除请求先在元数据中写入 tombstone（对象已删除的标记）；宽限期过后，协调器调度 compaction（重写有效数据并回收空间），跳过已删除对象，再重新计算 LRC 校验数据。

协调器持续创建可写集群，并将同一集群的 container 分散到不同磁盘、主机和机架。硬件故障被确认后，协调器等待 30 分钟再启动修复，以过滤主机重启或软件发布等暂时故障；修复过程在其他磁盘上重建缺失 container。数据损坏由两类周期性检查发现：元数据服务校验完整对象的 checksum（校验和），存储应用扫描磁盘 container 并校验其片段校验和。检测到损坏后立即修复。

区域间复制完整对象。对象在一个 stamp 写入后，存储应用异步扫描尚未复制的数据并写到另一个 stamp；复制完成后更新元数据。读取时先访问本地 container；失败或超时后发起降级读取，依次尝试局部和全局校验数据，最后再尝试从另一 stamp 取完整对象。每当处理器启动新的数据来源请求，已启动的来源仍继续运行；哪个来源先返回数据，就先将其流式传给客户端。跨区域两份完整副本与区域内 (20, 2, 2) LRC 组合后，整体复制因子为 2.40。

三、问题：固定 store 的成本与扩展边界

双区域完整复制与本地 LRC 提供了较高的故障恢复能力，但存储开销仍然较大。两个区域间完整对象复制的区域间复制因子为 2，乘以 (20, 2, 2) LRC 的本地复制因子 1.2，得到 2.40。若把校验信息跨更多区域编码，可以减少存储开销；代价是缺段重建需要访问远端区域，可能增加读取时延。

ACOS 1.0 的 store 容量彼此隔离。一个客户端资源跨越多个 store 时，需要管理多个 endpoint、凭据、容量预留和配额；退役旧 store 还要逐对象搬迁，并执行繁琐的配置与校验。元数据系统也遇到热点、LIST 性能、操作谓词支持和跨 stamp 一致性等限制，难以扩展为跨多个数据中心的统一存储系统。因此，ACOS 2.0 要同时降低每字节存储成本、提供统一入口，并在区域或硬件故障下维持数据可访问性。

四、方案：五区域 ACOS 2.0

4.1 五区域 XOR-5 编码

ACOS 2.0 延续 stamp 结构，将部署扩展为靠近客户端工作负载的五个区域；每个 stamp 可存储约 500 PiB 原始数据。它不再跨区域复制完整对象，而是将对象切成四个连续、等长的数据段，再对四段逐位异或（XOR），得到第五个校验段。五段分别写入五个区域。任一段缺失时，可用其余四段恢复；因此一个区域失效时仍可处理读写，而两个或更多区域不可用时，需要访问相应失效段的请求会返回错误。只涉及元数据、不需要读写对象数据的请求在这种降级状态下仍可处理。

ACOS 1.0 双区域 store 与 ACOS 2.0 五区域部署（Figure 4: ACOS 1.0 store with two regions and one stamp (left) and ACOS 2.0 multi-region deployment with five regions and several stamps per region (right).）

每段在所在 stamp 内仍由 (20, 2, 2) LRC 保护。其本地复制因子为 (20 + 2 + 2) / 20 = 1.2；五区域单校验段的区域间复制因子为 5 / 4 = 1.25；整体复制因子为两者相乘，即 1.50。PUT 请求必须携带对象长度，以便在分段前确定各段大小。客户端处理器收到请求后向五个区域发送数据；四段成功落盘即可确认 PUT，并继续尽力写入第五段。若第五段未及时写入，后台过程会异步重建。

ACOS 2.0 的 PUT 分段和校验流程（Figure 5: ACOS 2.0 PUT request. Once the client handler in stamp 3 receives an incoming PUT request from the client, it splits the full object into four equal size segments and computes an additional segment X such that xX = x1 ⊕ x2 ⊕ x3 ⊕ x4.）

多段对象的每个 part 独立分段，commit 元数据记录所有 part 的段位置。完整对象 GET 需要四个段来还原对象，默认读取四个数据段；由于 XOR-5 的任意四段都能恢复对象，按往返时延（round-trip time，RTT）选择读取来源时也可能选入校验段，再用 XOR 重建未读取的数据段。若某段不可用，同样由其余四段恢复。范围 GET 只读取覆盖请求范围的数据；若所需数据段失效，则从其余段读取相同偏移的数据来恢复这段范围。

4.2 ClassVI 元数据一致性

跨区域分段需要各地读取到最新对象位置。ACOS 2.0 的 ClassVI 是自建元数据系统，类似 BigTable，以 RocksDB 为本地存储引擎并部署在各区域。它用 Raft 保证行级读写强一致；为降低时延，也允许从本地区域的单个副本读取，因此这类读取本身是最终一致的。对象元数据记录各段所在的集群标识、container 索引和对象偏移。

4.3 统一入口与弹性扩展

ACOS 2.0 为客户端提供统一 DNS endpoint。权威 DNS 根据客户端所在区域返回较近的负载均衡器地址；当区域流量接近预设阈值时，安全机制会把超出部分路由到其他区域。部署级限流器在对象分段前保护整个部署，stamp 级限流器在分段后保护各 stamp 的存储资源，并控制客户端与异步复制流量。

每个区域按磁盘可用容量给 stamp 分配权重，PUT 处理器据此为各段选择目标 stamp。rebalancer（数据再平衡服务）在区域内将已封存的数据文件和校验 container 复制到新 stamp，避免重新写事务日志及重新执行 erasure coding（纠删编码）；它也用于 stamp 上下线以及平衡请求和存储占用。ACOS 2.0 中请求的任意四段都足以还原对象，因此处理器会选择 RTT 较低的四个区域；多数情况下会读取校验段并执行 XOR，以减少跨大陆传输。

五、结果：生产性能、可靠性与迁移

5.1 生产时延与故障恢复

性能评估基于 ACOS 1.0 和 2.0 的线上流量，覆盖所有主机的一个月测量。首字节时间（TTFB）从服务端收到 GET 请求计到开始发送响应首字节，包含元数据操作、磁盘首字节读取和网络传输；完整对象时延则计到最后一个字节发出。由于迁移过程中主要工作负载逐步转到 2.0，两代系统承载的客户端数据并不完全相同。

完整对象 GET/PUT 对比采用 1 MiB 和 10 MiB 两种代表性对象大小，测量在作者完成下述时延优化后进行。GET 的 TTFB 在两代系统中相近，2.0 略高；论文没有在正文给出这项差值。对象分布在多个区域，客户端位置和范围可能要求先读远端段。完整对象 GET 的 2.0 时延更高，论文观察到约 50 ms 的差值，对应两个区域间的平均网络时延。完整对象 PUT 时延被论文描述为相近，但没有报告具体差值；2.0 在服务端缓冲客户端数据后，可并行发送各段写请求。完整对象时延还可能受客户端接收或发送数据的速度及出口网络吞吐影响。

作者在迁移前针对 GET 路径做了三项时延优化，报告服务端时延最多降低 60%，客户端时延最多降低 87%：

  1. DNS 地理路由。 将请求路由到五个数据中心中较近的一个；如果该区域接近流量阈值，安全机制会把超出部分转到其他区域。论文还分别为低流量时延敏感请求和非时延敏感请求配置 endpoint，后者通过轮询分配区域流量。
  2. 元数据预取。 ClassVI 的本地副本不一致读在 p99.9 可于个位数毫秒内完成。请求处理器并行发起一致读和不一致读；不一致读返回后立即预取数据段，一致读完成后再比较元数据。两者相同时开始传输预取数据；论文在这一预取描述中报告约 0.001% 的请求发现元数据不同，此时丢弃预取结果并按一致读返回的位置重新读取。论文另在生产结果中报告，99.99995% 的请求只需不一致读即可取得元数据；没有解释这两个比例之间的关系，不能将它们作为互补比例合并计算。
  3. 优先读取低 RTT 的段。 五段中任意四段都能重建对象，处理器选择网络往返时延较低的四个区域。多数情况下会读取校验段并执行 XOR，增加少量 CPU 开销，以减少跨大陆网络传输。

时延优化后的线上请求指标（Figure 6: Key latency performance metrics measured after the latency improvements presented in Section 6.2.）

分段提高了 stamp 间的吞吐，也使原有负载均衡器成为瓶颈。ACOS 2.0 因此绕过负载均衡器进行 stamp 间通信；请求处理器需要自行实现健康检查和大量连接管理。改动后，客户端请求时延在 p50、p90、p95 分别降低 22%、32%、26%。

故障恢复增加的时延取决于恢复层级。跨区域段重建的计算开销在 p90 为 0.3 ms；不涉及 stamp failover（请求切换到另一 stamp）时，重建使完整对象 GET 时延增加约 10 ms。stamp failover 期间，处理器要访问更远区域，p60 以上的 GET 时延最多增加 50 ms。区域内 LRC 重建的计算开销在 p90 为 2 ms；使用封存数据和校验 container 的 degraded read（通过校验数据完成的降级读取），在 p50 以内使段读取时延增加约 30 ms，p50 以上则增加数百毫秒。读取优先尝试局部校验，等待 500 ms 后再尝试全局校验，因此全局校验路径主要影响 p75 以上的请求。

5.2 可靠性模型与数据迁移

论文以平均数据丢失时间（Mean Time to Data Loss，MTTDL）作为耐久性指标，并用 Markov 链状态模型比较区域内 LRC 和区域间 XOR 编码；模型按故障和修复引起的状态转移计算数据丢失时间。区域内模型假设 container 失效率独立同分布且服从指数分布，单个 container 的失效率参数取 λ = 0.02；原文未在此处单独标出 λ 的时间单位。论文称该参数较保守，并与 Backblaze 报告的 1.35% 平均磁盘年故障率及 ACOS 自身观测对比；它是模型参数，不是 ACOS 的实测失效率。区域间模型用区域内 MTTDL 推导失效率。检测、修复或复制速率统一取 ρ = 1/T，其中 T = 365.25 天；修复时间也按指数分布建模。模型聚焦封存集群，因为含临时数据的复制集群对结果影响可忽略；此外，模型假定跨机架放置使失效不相关，修复带宽不受跨机架网络限制。论文对 (12, 2, 2) 和 (20, 2, 2) LRC 均使用四个 container 失效可恢复的概率 p_d = 0.8615，其余情况下可恢复三个。

区域级 XOR-5 与本地 (20, 2, 2) LRC 的 MTTDL 模型（Figure 8: Top: Regional MTTDL Markov chain model of XOR-5 layout. Bottom: Local MTTDL model of (20, 2, 2) LRC codec. The initial state has a double circle and the data loss state has the label “DL”.）

可用性模型将单一区域目标设为 99.999%（five nines），并假设各区域故障独立。恰有一个区域不可用时，系统处于 degraded 状态；两个或更多区域不可用时，系统处于 unavailable 状态。令单区域可用率为 A_r、区域数为 N，则处于 degraded 状态的概率为 P_degraded = C(N, 1)(1 − A_r)A_r^(N − 1)；处于 unavailable 状态的概率为 P_unavailable = Σ_(k=2)^N C(N, k)(1 − A_r)^k A_r^(N − k)。整体复制因子计算为 RF = RFlocal × RFregional：含 k 个数据 container、l + r 个校验 container 的 LRC 本地复制因子为 (k + l + r) / k；跨 N 个区域使用单个 XOR 校验段时，区域间复制因子为 N / (N − 1)。表中的 XOR-3、XOR-4、XOR-5、XOR-6 分别表示总计 3、4、5、6 个区域，其中一个区域存放 XOR 校验段。

表中 availability 时间是按上述 99.999% 单区域目标计算的年度状态时长，不是线上测量值。增加区域数会继续降低 XOR 区域间复制因子，但也增加系统处于 degraded 或 unavailable 状态的模型时长。模型显示，ACOS 1.0 使用 (12, 2, 2) 时的 MTTDL 高于 ACOS 2.0 的 (20, 2, 2) 加 XOR-5 配置；论文将 11 nines 服务等级协议（service-level agreement，SLA）归于前者，没有明确声称后者也满足同一 SLA。Apple 根据工作负载、区域位置和成本，选择部署五区域 XOR-5。

部分客户自行管理迁移；论文所述五步流程针对 Apple 负责的多个 store 中剩余数据的大规模迁移。流程从客户端凭据、配置、限流和配额迁移开始；再在源 store 继续服务请求的同时异步搬迁对象，并在目标端按新布局分段；接着计算校验和、核对元数据以验证对象；已有对象迁移后，将请求代理到目标部署，同时继续搬迁和验证新写入或修改的对象；最后更新 DNS CNAME，将客户端 endpoint 切换到新部署。这项迁移耗时数年，涉及数艾字节数据，对客户端应用透明且没有停机；论文报告，迁移过程中任何时刻都能保证数据可用和正确。
