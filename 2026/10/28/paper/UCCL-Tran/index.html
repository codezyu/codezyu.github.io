论文：UCCL-Tran: An Extensible Software Transport Layer for GPU Networking，Yang Zhou、Zhongjie Chen、Ziming Mao、ChonLam Lao、Shuo Yang、Pravein Govindan Kannan、Xizhi Zhang、Jiaqi Gao、Yilong Zhao、Yongji Wu、Kaichao You、Fengyuan Ren、Zhiying Xu、Costin Raiciu、Ion Stoica，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI 2026），2026 年 7 月 13–15 日。论文：USENIX OSDI；实现：GitHub。

TLDR： Remote Direct Memory Access（RDMA，常见中文译法「远程直接内存访问」）网络接口卡（NIC）将 congestion control（CC，拥塞控制）、可靠性处理和路径选择固定在硬件中。论文将部分 ML 流量描述为 low flow entropy（低流熵）且 high traffic burstiness（高突发性）；当 RDMA 每条连接只有单一路径时，不同流可能经哈希落到同一路径，发生 flow collision（流冲突）。UCCL-Tran 将 NIC 的数据传输与主机 CPU 上的软件控制分开，并以多个 Queue Pair（QP，队列对）实现 multipath transport（多路径传输）。在 ConnectX-7 跨机架 fat-tree 测试床上，NVIDIA Collective Communications Library（NCCL）的 NCCL-tests 测得 1 MB all-to-all（全互发）总线带宽最高为 ConnectX-7 内置可靠连接传输（16 QPs/connection）的 4.54×；AMD 上 64-expert DeepSeek-V2-Lite 训练的吞吐较 Thor-2 基线提高 7.5%。

一、背景：GPU collective communication 流程

RDMA 允许网络接口卡（NIC）在 GPU 与网络之间直接搬运数据。NCCL 和 AMD 的 ROCm Communication Collectives Library（RCCL）为 GPU 应用提供 allreduce、allgather、reduce-scatter、all-to-all（全互发）等 collective communication（集合通信）操作。一次 allreduce 通常由 GPU kernel 执行本地规约，CPU 提交 RDMA 操作，NIC 把数据直接写入对端 GPU 的传输缓冲区，随后 GPU kernel 再将结果并入应用张量。

RDMA 接收端将数据写入 GPU 并执行规约（Figure 1: Collective communication over RDMA (receiver side). The receiver directly receives data into the GPU memory (e.g., GPUDirect [28]); the sender side works similarly except that it will additionally issue an RDMA write in step 2.）

RDMA 的 Queue Pair（QP，队列对）提供不同传输语义。Reliable Connection（RC）是一对一可靠连接，由 NIC 硬件处理丢包恢复和拥塞控制；Unreliable Connection（UC）仍是一对一，但不在 NIC 中执行这些可靠性和拥塞控制逻辑；Unreliable Datagram（UD）支持一对多数据报，每次操作最多发送一个 Maximum Transmission Unit（MTU，最大传输单元），不提供可靠性或拥塞控制，NIC 也不卸载分段和重组。NIC 对 RC、UC 的分段和重组卸载，是保持 GPU 数据传输效率的重要条件。

二、现状：RDMA NIC 固化传输控制

论文指出，ML 网络需求持续演进，而 RDMA NIC 硬件和固件的改动比软件更新更慢，应用因此难以及时替换拥塞控制、丢包恢复或路径选择算法。单台 GPU 服务器可配 8 张 400 Gbps NIC，合计 3.2 Tbps；在这种带宽下让主机 CPU 处理传输控制，是论文要解决的线速处理挑战。

流量形态也会让固定策略失效。论文称大规模模型训练的 all-to-all 具有 low flow entropy（低流熵）和 high traffic burstiness（高突发性），但没有给出 flow entropy 的计算式或量化值。论文还指出，RDMA NIC 每条连接只支持单一路径时，不同连接可能经 ECMP（Equal-Cost Multi-Path）哈希落到同一路径，产生流冲突。Meta 报告，DCQCN 不适合这类 LLM 训练流量，并选择关闭 NIC 拥塞控制、改由应用层调度；论文指出，不使用 NIC 拥塞控制会增加死锁、head-of-line blocking（HOL blocking，队头阻塞）和持续拥塞的风险。论文还提到，Alibaba 为应对训练中的流冲突采用 rail-optimized dual-plane 拓扑，并指出建设和维护成本较高；原文没有进一步解释该拓扑如何改变路径分配。

其他 ML 通信场景还需要接收端驱动的拥塞控制来应对 Mixture-of-Experts（MoE）流量 incast（多对一汇聚流量），需要 selective retransmission（选择性重传）来恢复丢包，也需要在不同厂商和代际的 NIC 之间统一传输行为。这些改动都受限于现有 NIC 的可编程能力。

三、问题：控制扩展与线速转发难兼得

论文要解决两个相连的问题。第一，如何在不改造现有 NIC 的情况下，把传输控制放到主机 CPU 上，同时保留 NIC 到 GPU 的直接数据传输。第二，如何让 CPU 软件处理足够快，不因拥塞控制、负载均衡和可靠性逻辑而限制 GPU 网络带宽。

multipath transport 能分散流冲突，却会增加乱序和丢包后的重组工作。硬件 NIC 受限于片上 static random-access memory（SRAM），可用于重排的缓冲状态有限；若 CPU 逐包处理，控制工作量会随包率增长。因此设计必须同时处理控制与数据的分工、乱序恢复，以及线速下的 CPU 处理能力。

四、方案：NIC 数据传输与 CPU 软件控制

4.1 传输路径与协议适配

UCCL-Tran 作为 NCCL/RCCL 的网络插件，位于 collective library 与 NIC 原语之间。论文把 GPU 数据实际经过的路径称为 data path，把拥塞控制、可靠性和路径选择称为 control path。UCCL-Tran 让 NIC 继续通过 GPUDirect 搬运 GPU 数据，让用户态 CPU 线程处理可扩展的传输控制。

单机 PCI Express（PCIe）拓扑中的 UCCL-Tran 架构与线程模型（Figure 2: Overview of UCCL-Tran extensible transport for GPU networking. We assume a common intra-server topology for GPU servers [23] where individual PCIe switches directly connect a few GPUs, NICs, and CPU, providing high-bandwidth data transfer among them.）

有 UC 时，UCCL-Tran 使用 RDMA write with immediate：数据 payload 从 GPU 内存直接发送，32 位 imm_data 携带 control header，由接收端 CPU 读取。NIC 负责数据分段和重组，控制头与 payload 在丢失和到达顺序上保持关联。Broadcom 等不支持 UC 的 NIC 使用关闭拥塞控制的 RC；这样保留 NIC 的可靠性处理，但软件不能替换其丢包恢复逻辑。

UC/RC 的 control header 与 data payload 分离（Figure 3: Leveraging RDMA write_with_imm to separate control header and data payload for UC/RC.）

对不能关闭内置拥塞控制的 AWS Elastic Fabric Adapter（EFA），UCCL-Tran 可用 UD。它通过 scatter-gather 在发送端合并 CPU 上的 control header 与 GPU payload，在接收端再按固定边界拆分。UD 每个操作只发一个 MTU，分段和接收端重排需要软件处理；UCCL-Tran 将乱序数据复制到 GPU 传输缓冲区，并把重排并入 collective kernel。对非 RDMA NIC，系统还实现了基于 UDP 和 AF_XDP 用户态快速数据包 I/O 接口的传输，但这条路径不具备 GPUDirect。

UD 的 scatter-gather 控制头与数据分离（Figure 4: Leveraging RDMA send/recv scatter-gather to separate control header and data payload for UD.）

4.2 multipath transport 与乱序恢复

UCCL-Tran 的 multipath transport 为每对 NIC 复用一组 QP。交换机通常依据源、目的 QP 编号做 ECMP 哈希；不同 QP 因而可以映射到不同网络路径。UC/RC 默认使用 256 个 QP，UD 则可用 16 个源 QP 与 16 个目的 QP 组合出最多 256 种路径。多条 GPU 连接共享这组 QP，控制 QP 数量增长。

发送端用 Power-of-Two sampling 比较候选路径的 round-trip time（RTT，往返时延），选择 RTT 较低的路径；拥塞控制再决定发送量和速率。UCCL-Tran 实现 CUBIC 和 Swift，load balancing（负载均衡）使用每条路径的 RTT，丢包作为补充拥塞信号。现有 NIC 通常不把 Explicit Congestion Notification（ECN，显式拥塞通知）标记和 packet trimming（交换机在拥塞时截短数据包的状态）交给主机软件，因此实现主要依据硬件时间戳得到 RTT，并在需要时依据丢包调整。

多路径传输中的路径选择、丢包和 NIC 内部调度都会造成乱序。UCCL-Tran 用序列号和 ACK（acknowledgment，确认）跟踪数据位置，在 GPU 内存中保存重排缓冲区；重复 ACK 可触发快速重传，超时则触发超时重传。对选择性重传，论文实现 selective acknowledgment（SACK，选择性确认）与 bitmap，避免硬件 go-back-N 把后续已到达的数据一并重传。

多条网络路径同时传输时的包乱序与接收端重排（Figure 5: Multipathing and handling packet reordering in UCCL-Tran.）

4.3 CPU 核上的软件传输效率

UCCL-Tran 的每个 engine thread 以 run-to-completion 方式处理发送、接收、发送节奏控制（pacing）、超时和重传，并用 Deficit Round Robin 在多个连接间分配处理时间。connection splitting（连接拆分）将单条连接分配给多个 engine thread；每个线程管理部分 QP 和独立的拥塞控制、负载均衡状态，应用侧再把消息派给负载较低的线程。

control coalescing（控制合并）将决策粒度设为 32 KB 数据块，而非每个网络包。这样既保留了按 RTT 调整的空间，也减少 CPU 逐包处理开销。UD 不具备 NIC 分段卸载时，UCCL-Tran 还把最多 32 个 send/recv verb 链接后一次提交，减少 memory-mapped I/O（MMIO，内存映射 I/O）写入。

4.4 传输协议的扩展接口

软件接口允许应用和 collective library 替换路径选择、发送节奏控制、拥塞控制、接收端 credit 和重传逻辑。论文实现了三类案例：用 packet spraying（把数据包分散到多条路径）和 per-path RTT 选择路径；用接收端驱动的 Edge-Queued Datagram Service（EQDS）向发送方分配 credit，处理 MoE incast；用 SACK 与 bitmap 实现选择性重传，提高丢包恢复效率。实现约 28.4K 行 C++，支持 NVIDIA、Broadcom、AWS EFA 和非 RDMA Elastic Network Adapter（ENA）；除 UD 路径需要少量 NCCL 接口扩展外，应用可通过现有 plugin 使用它。

EQDS 实现为每块 NIC 运行一条 pacer thread，维护重传、active、idle sender 队列，并用 UD QP 向发送端发送 credit。由于论文测试的 RDMA NIC 和交换机不提供 packet trimming，UCCL-Tran 用 timeout 与 Request-To-Send（RTS）请求替代该反馈。

UCCL-Tran 中的接收端驱动拥塞控制（Figure 16: Implementing receiver-driven CC under UCCL-Tran.）

5.2 应用性能与传输代价

DeepSeek-V2-Lite 的基础训练配置为 16B 参数、64 个 routed experts，在 AMD testbed 上通过 expert parallelism 运行，采用 AMD Primus 和 Megatron-LM backend。作者再将 routed expert 数扩为 128、缩为 32，连同 64-expert 配置评估不同场景。Figure 11a 以 Thor-2 为基线，32、64、128 个 experts 的吞吐分别提高 6.2%、7.5%、6.7%；最高值出现在 64-expert 配置。DeepSeek-V3 serving 则采用 trace-driven 仿真，以真实 trace 中的计算时间和 hidden-state 消息大小驱动 PyTorch/NCCL，在 EFA 上关闭 NVLink/SHM 后比较。相对 EFA SRD，prefill 时延从 157.2 ms 降到 138.9 ms，decoding 从 13.6 ms 降到 9.6 ms，对应 1.13× 和 1.42× 的时延加速比。这组 serving 结果来自仿真，不是数百 GPU 的在线部署测量。

应用性能评测：DeepSeek-V2-Lite 训练和 DeepSeek-V3 serving 仿真（Figure 11: Application performance evaluation.）

应用性能之外，论文还评估了接口对网络拥塞的处理能力。接收端驱动的 EQDS 在 CX_IB 上与 InfiniBand 内置拥塞控制比较。测试同时运行 15-to-1 incast 和 16-NIC permutation 流量，每条流发送 1 MB 消息、最多 4 条在途消息。EQDS 对 incast 的 P99/P99.9（第 99/99.9 百分位）flow completion time（FCT，流完成时间）分别降低 1.73×/1.72×；对 permutation 流量分别降低 4.50×/4.88×。接收端提前分配 credit，减少 incast 引起的队列积压和上游端口暂停。

incast 与 permutation 流量的 FCT 分布（Figure 12: Complementary CDF of FCT (Flow Completion Time) on CX_IB when co-locating 15-to-1 incast and permutation traffic.）

另一类扩展针对丢包恢复。选择性重传在 AMD testbed 的两 GPU/NIC 连接上测试：单 QP、16 条在途消息，消息大小 32 KB–1 MB，并注入 1/16384 至 1/256 的丢包率。评测指标是 goodput（有效吞吐），每种消息大小均设有无丢包基线。相对该基线，UCCL-Tran 在 1/16384、1/4096 丢包率下的 goodput 下降约 1%；在 1/1024、1/256 下下降 6%–30%。论文将其与先前工作报告的硬件 RDMA 恢复下降幅度 26%–42% 和 59%–76% 对照；这两组硬件结果来自已有文献，不是同一轮测量。

不同丢包率下的 goodput；RTO（retransmission timeout，重传超时）阈值约为数个 RTT（Figure 13: Goodput of UCCL-Tran under different packet drop ratios. UCCL-Tran implements selective retransmission with a dynamic RTO threshold (around several RTTs).）

这些扩展以更多 CPU 资源和较粗的控制粒度为代价。32 KB 的控制粒度让一个 CPU 核能够处理 400 Gbps 单向流量；双向满速需要两个核。论文在模拟的 1024 个 400G NIC、三层 fully-provisioned fat-tree permutation 场景中，每个 NIC 发送 64 MB 流量，理想完成时间为 1.28 ms。32 KB chunk 加 RTT 负载均衡使 sender-driven 传输完成时间比 4 KB chunk 加 ECN 高 17.9%；改用 16 KB 后差距为 4.1%，receiver-driven 方案的差距为 2.8%。实际训练中，UCCL-Tran 每台活动 NIC 额外使用约 2 个 CPU 核；Table 2 的 NCCL 基线平均为每个 400G NIC 2.3 核，NCCL+UCCL-Tran 为 4.3 核，论文另报告该训练增加 16 个 CPU 核。拥塞信号也受 NIC 可见信息限制，CPU 调度会引入抖动。CX_IB 上的 Table 4 将 1 GB 消息列为 heavy、1–64 KB 列为 light；heavy 下 all-to-all 的 CC decision P99 为 10.8 µs，ACK turnaround P99 为 36 µs，light 下两项 P99 均不超过 10 µs。

附录 C.5.2 测量 UD 接收端乱序重排的 GPU kernel 开销。测试在关闭 NVLink/SHM 的 EFA 上比较独立 copy kernel、融合到 collective kernel 的实现和跳过 memcpy 的对照；后者同时关闭了 NCCL-tests 的数据正确性检查。相对该对照，scattered memcpy 令 allreduce 总线带宽下降不到 8%，all-to-all 下降不到 5%；融合方案在小消息时延和大消息带宽上均优于单独启动 copy kernel。

附录 C.5.3 在 CX_IB 上用 pcm-pcie 测量 MMIO 事件与 CPU-NIC PCIe 流量。UCCL-Tran 每个 verb 搬运 32 KB，NCCL 常用的传输缓冲区默认是 128 KB，因此 UCCL-Tran 会提交更多 verb；额外 PCIe 流量主要来自 NIC 换入未缓存的 QP context。以 32 KB chunk、每块 NIC 60K 个 QP 为例，额外 PCIe 流量约 12 Gbps，占 PCI Express 5.0 ×16 单向 512 Gbps 容量的 2.3%，低于 2.5%；UC 比 RC 多一些流量，来自 CPU 上的软件可靠性处理。
