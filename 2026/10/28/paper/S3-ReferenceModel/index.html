用可执行 reference model（参考模型）检验 Amazon S3 API 行为

论文：High Fidelity Models for Large Scale Stateful Services (Operational Systems)，Nouraldin Jaber、Dongyun Jin、Bernhard Kragl、Enrico Magnago、Gustavo Petri、Thorsten Tarrach、Serdar Tasiran，均来自 Amazon Web Services（AWS）；20th USENIX Symposium on Operating Systems Design and Implementation（OSDI 2026，2026 年 7 月 13–15 日，Seattle）。USENIX 论文页。

TLDR： Amazon S3 要在长期演进和多种实现中维持 API 的可观察行为。论文把 model-based testing（基于模型的测试，MBT）与 predicate abstraction（谓词抽象）结合：用可执行 reference model 表达 API 行为，把请求参数和相关状态划分为有限的抽象场景，按场景生成状态与请求，再把被测服务的响应与模型允许的响应比较。这里的“覆盖所有输入和状态”指覆盖所选抽象谓词与测试配置定义的场景；单次持续集成与持续部署（CI/CD）验证受约三小时和约 432,000 个请求的预算限制，会选择特征组合并运行多个批次。论文报告三项 S3 开发工作共发现 372 项问题，其中 46 项被作者评为高严重度；原文未披露分级阈值。所有问题都在部署前处理。

一、背景：S3 API 在持续演进中保持行为兼容

论文摘要在 2026 年介绍 S3 时称，Amazon Simple Storage Service（Amazon S3）已有 20 年历史，托管超过 500 万亿个对象，平均每秒处理超过 2 亿次请求；同时，S3 API 必须持续适应新负载和用例，在保持 backward compatibility（向后兼容性）的同时维持其所称的 high-paced development environment（快速开发节奏）。论文没有量化这一节奏。文中没有注明这两项规模数据的统计截止日、请求速率的平均时间窗口，也没有说明对象计数是否包含对象版本、请求计数是否包含重试等边界。因此，这里只按论文给出的服务整体规模陈述引用，不把请求量解读为峰值或某种具体请求类型的数量。

AWS 中文用户指南将对象（object）定义为文件数据及描述该对象的元数据，并将 bucket 译为“存储桶”。这个术语定义不能推出摘要统计对象的计数方式。AWS 中文用户指南：上传对象

S3 提供 REST API，论文引言按其引用的 S3 文档称 S3 支持 96 个 API 操作。持续增加的功能、参数和存储桶配置使 API 行为不断扩展；例如，GetObject 有 21 个输入参数、36 个响应参数，此外还有对象内容。响应还会受对象是否存在、对象版本、存储桶版本控制和加密配置等状态影响。

客户依赖的不只是成功返回的数据。以 If-Unmodified-Since 为例，GetObject 会根据对象修改时间返回 200 OK 和对象内容，或返回 412 Precondition Failed；客户端可能对这两种结果采取不同处理。论文把在持续变更中保持这些可观察行为称为 API sameness 或 conformance（API 行为一致性）。S3 Express One Zone 在 2023 年推出时使用 directory bucket（目录存储桶）；它的大多数 API 与区域 S3 一致，但也有有意差异，例如 ListObjectsV2 的条目不排序。参考模型被用于验证兼容部分，并在需要时记录这些预期差异。

二、现状：手工测试难以覆盖请求与状态组合

传统单元测试和集成测试依赖开发者选定场景与断言。请求参数、参数间依赖和服务状态组合增长后，单个测试只能覆盖其中一部分；测试套件也难以给出可操作的覆盖度量。对 GetObject 而言，21 个输入参数与存储桶、对象及配置状态共同影响输出，简单枚举不可行。

把旧版本服务直接当作新版本的正确性对照也不总是可靠。相同请求可能允许多种响应，例如不同实现可以按不同顺序检查参数并返回不同的错误。若两个版本分别选择不同但都有效的响应，直接逐字比较会把合法差异报成回归；反过来，只比较状态码又可能漏掉客户实际依赖的响应行为。

三、问题：如何度量并核对可观察行为

具体请求值的空间可能无限，例如 bucket 和 key 名称可以是任意字符串；系统状态又由此前成功的 API 操作逐步形成。论文估算 GetObject 存在至少 10^25 个在输入和状态上有区别的场景。这个数字是按特征与类别计算的近似场景数，不是实际执行过的测试数，也不表示一次 CI/CD 运行遍历了全部场景。

验证因此需要同时解决两个问题：一是用可检查的模型说明哪些 API 响应有效，并保留不同实现都允许的行为；二是把请求参数和状态组合抽象为有限、可枚举且覆盖度可度量的场景，再在时间预算内生成可执行测试。本文将目标限定在 S3 API 的顺序行为：一致性保证由其他机制验证，不在本文范围内；测试按顺序执行单个操作，不检查并发历史。

四、方案：按抽象请求与状态生成一致性测试

4.1 可执行模型只描述外部可观察行为

reference model 是 API 的可执行行为规范：给定请求和模型状态，计算允许的响应并更新后续请求会观察到的状态。作者要把模型校验到足够准确，使它能作为 S3 API 的 de facto specification（事实规范），并为不同实现提供同一行为参照。论文以 Java 实现模型，按服务代码库常用的开发方式维护；模型通过 API 输入与输出进行黑盒建模，不依赖某个被测实现的内部结构，只保存会影响后续 API 响应的信息，例如对象的 ETag（后续条件请求所用的对象标记）、创建时间、标签和加密配置。

模型不把每个响应字段都假装成可预测值。请求 ID 等字段可能只用于日志，日期和 ETag 等字段则可能影响后续请求。工具把 System Under Test（被测系统，SUT）实际返回的相关值作为 prophecy（预言值）传给模型，使模型能用这些值继续计算和同步状态。模型对请求检查顺序可能不同的错误响应保留多个允许结果；验证器学习每个 SUT 对同一请求稳定采用的错误优先顺序，并检查后续运行是否改变。

这个模型只描述顺序执行时的功能行为：模型状态在内存中，不跨实例持久化；模型本身单线程，不反映延迟、吞吐等性能指标，也不区分黑盒下输入输出完全相同的内部状态，例如缓存状态。论文不验证并发一致性。

4.2 谓词把具体值归并为抽象场景

论文用 predicate abstraction（谓词抽象）将请求和状态映射到有限空间。它把 API 参数或状态条件称为 feature（特征），例如 bucket 名称、key 是否存在或存储桶是否启用版本控制；每个特征按会影响行为的条件划分为 category（类别）。对 bucket 名称，可以区分语法无效、语法有效但不存在、以及已存在等类别。每个类别由关于请求或模型状态的谓词表示，因此一个 input scenario（输入场景）就是这些谓词的一组真值赋值。

具体请求和状态映射到抽象输入场景（Figure 2: Request abstraction）

抽象不是简单地给每个字段各取一个样例。谓词可以联合请求字段与状态，例如 key_exists 同时依赖 bucket、key 及当前模型状态。若两个具体请求与状态在所选谓词下会产生不同的可观察输出，抽象就应把它们映射到不同场景；在同一场景中的具体值则可用代表值进行验证。

HTTP 条件请求字段在抽象模型中的类别示例（Figure 3: Abstraction example.）

论文用简化版 GetObject 说明场景约束：请求只含 bucket、key 和 checksumMode，抽象成 6 个布尔谓词后有 2^6 = 64 种赋值。对象不可能存在于无效或不存在的 bucket 中；缺少 checksumMode 时，该字段也不可能是非法值。把这些状态不变量加入后，只剩 21 个可实现的输入场景。这个例子展示了如何删除不可能的组合；它不是完整 S3 API 的规模。

4.3 API-planner 准备状态，验证器比较响应

生成测试时，工具先根据场景的状态谓词构造目标状态，再由 API-planner 规划从当前状态到目标状态所需的请求。若目标要求对象存在，planner 可能先用 CreateBucket 创建 bucket，再用 PutObject 写入对象；这些准备请求也逐条经过模型和 SUT 的响应检查。到达目标状态后，生成与场景类别相符的具体请求并执行。

模型、请求生成和响应验证的执行流程（Figure 1: Model-based testing flow.）

验证器逐项核对 SUT 与模型的完整响应，而非只比较状态码；若模型允许多种响应，SUT 返回其中任一项即可通过。响应不一致即报告 deviation（偏差）。偏差可能来自模型、实现，或两者，因此论文对发现项进行人工分析，不能仅凭一次差异就断定实现错误。若某个错误场景包含多个无效参数，工具还使用 first-error hypothesis（首错假设）：在服务遇到首个错误后即停止处理的条件下，错误数为 0 的场景覆盖成功行为，错误数为 1 的场景覆盖单项错误，错误数为 2 的场景用于检查错误校验顺序；在该假设下，错误数超过 2 的场景不会带来新的检查次序。作者使用这些 campaign（验证批次）检查 SUT 的参数校验顺序，并减少重复场景。

4.4 CI/CD 按可配置场景运行

实际 GetObject 的特征规模远大于简化例子。论文统计了 21 个请求特征和 16 个状态特征，共 37 个特征；这些特征分别划分为 102 个请求类别和 33 个状态类别，共 135 个类别。按错误数估算的抽象场景约为：0 个错误 10^12 个、1 个错误 10^14 个、2 个错误 10^15 个，任意错误数合计约 10^25 个。

因此，“覆盖所有抽象输入和状态”只对给定的谓词、状态不变量及验证批次配置成立。若配置包含某 API 的全部特征与类别，生成器可以枚举该抽象空间内的非矛盾场景；一次部署审批不会遍历全部特征的组合。论文按每个验证批次约 3 小时的预算运行多个批次并行，每批最多约 432,000 个请求。成功请求中每个特征平均约有 2.4 个类别，因此一个批次可覆盖约 15 个特征的成功场景组合。开发者根据改动选择相关特征，较长时间运行的任务轮换未覆盖的特征组合；团队也预先维护高相关特征组。比如 Ranges 组在论文设置下约需 212,400 个请求，约 1.5 小时。

这套工具接入 S3 的持续集成与持续部署（CI/CD）流程，在传统单元与集成测试之后运行；开发者也可在本地运行其中较小的测试子集。覆盖率是相对于模型定义的抽象空间和当次配置度量的，不代表每次代码变更都测试了所有 API 场景，也不等于证明了未建模的内部路径。

五、结果：在部署前发现并处理行为偏差

5.1 三项开发工作报告 372 项发现

论文汇总了工具在三项 S3 开发工作中的发现。每项发现都经过人工分析并评定严重度；原文没有给出高严重度的分级标准或阈值。作者称这些问题都在部署前得到修复。

开发工作发现项高严重度
S3 持续验证10924
S3 Express One Zone 上线前验证17112
S3 前端重写（S3 Refactor）9210
合计37246

S3 Express One Zone 的 171 项偏差在 2023 年上线前处理，其中 12 项为高严重度。S3 前端重写的 CI/CD 检查发现 92 项其他单元测试和集成测试未发现的问题，其中 10 项为高严重度。常规 S3 持续验证报告 109 项发现，其中 24 项为高严重度。三项工作的统计范围和时间背景各不相同；论文摘要据此概括工具已阻止超过 300 个潜在回归。

5.2 场景枚举减少重复请求

与 property-based testing（基于属性的测试，PBT）的比较中，随机生成器从加权分布采样请求。一次 28,457 个 GetObject 请求的运行只覆盖 9,040 个不同抽象场景，另外 19,417 个请求重复落入已覆盖场景。另一个只包含 bucket、key 和 range 三个特征、每项两个类别的配置共有 8 个非矛盾场景；PBT 在 10 次运行中平均需要 3,200 个请求才覆盖这 8 个场景，而系统枚举直接生成 8 个请求。

这些结果衡量的是在论文给定抽象和配置下减少重复输入的效果。它们不表示工具在一次运行中覆盖整个 S3 API 的全部具体请求、状态组合或内部实现路径。
