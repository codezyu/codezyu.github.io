Arctic: a practical lock-free adaptive radix tree

论文：Arctic: a practical lock-free adaptive radix tree，Newton Ni、Nicolas Garza、Jenny Stinehour、Michael Goppert、Michal Friedman、Emmett Witchel，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI ’26，2026）。论文页面。

TLDR： 高并发有序索引需要兼顾高吞吐、无锁（lock-free）进展保证和范围／前缀扫描。ARCTIC 重排自适应基数树（adaptive radix tree，ART）的边与节点元数据，用 128 位比较并交换（compare-and-swap，CAS）配合冻结后替换节点的协议实现原地更新，并提出按操作键近似保护可达对象的回收机制。点读和范围／前缀扫描均保证 wait-free（每个操作都有有限步完成上界）；扫描不具线性化语义，结果不对应扫描期间的单一瞬时状态。Yahoo! Cloud Serving Benchmark（YCSB）在 80 线程、7 种键分布下，相对 ART 的几何平均吞吐在 C（100% read）上为 1.3×、A（50% read、50% update）上为 7.7×。RocksDB、Turso 的插入型集成基准相对原有跳表（skiplist），吞吐最高分别提升 1.40×（2 线程）和 1.12×（8 线程）。

一、背景：有序索引的三项性质

索引位于请求处理的关键路径，需要在真实硬件上提供高吞吐和低尾时延。高并发场景还要求操作不被其他线程持有的锁阻塞；键值存储系统的日志结构合并树（log-structured merge-tree，LSM-tree）依赖范围扫描加速 compaction（层间数据归并），数据库则用它加速范围查询和仅索引计划（index-only plan）。因此，论文关注的索引需要兼顾性能、无锁进展保证和有序扫描。

前缀树（prefix tree）把键看成符号序列：节点将一个符号映射到边，边的子对象可以是另一个节点、值或空指针。按字典序组织的结构能高效执行范围扫描，但朴素前缀树每个符号都要经过一条边，长键会增加访问路径长度；固定大小的节点在键分布稀疏时也会浪费空间。基数树（radix tree）把多个共享符号压缩进同一条边；ART 再按子节点数量选择节点表示，减少树高和稀疏节点的空间开销。

前缀树经边压缩和节点压缩形成自适应基数树；右侧比较 ART 与 ARCTIC 的压缩边布局（Figure 1: The midddle panel shows the evolution of prefix trees, with fixed nodes and height, to radix trees, which compress shared symbols into edges, to adaptive radix trees, which compress nodes into smaller partial mappings. All three trees represent the map {acb = 1,acc = 2}. The right panel shows two physical layouts of a logical compressed edge: ART stores them in child node headers, while ARCTIC stores them alongside child pointers.）

ARCTIC 与其他前缀树实现一样，要求没有一个键是另一个键的前缀。定长整数键和 C 风格的空字符结尾字符串天然满足这个条件；其他变长键可以追加一个哨兵字节。

二、现状：ART 的并发更新代价

并发哈希表可以实现无锁访问，但不支持高效的有序范围扫描。skiplist 保持有序，却会因指针访问的缓存局部性较差，以及高层节点竞争而受到影响。B+ 树的高性能实现通常使用锁或乐观锁耦合；无锁 Bw-tree 则通过增量记录（delta record）和映射表增加间接访问。ART 提供缓存友好的有序索引，但现有并发实现依靠节点级锁。

ART 将压缩边上的键字节放在子节点头部。扩展一条边时，要分别修改父边和子节点头部；多个内存位置之间的状态转换需要锁来协调，节点级锁还会让同一节点上的不同边更新互相竞争。

这些结构变化称为结构修改操作（structural modification operation，SMO）：它们改变树的物理布局，但不改变逻辑映射。前缀树的基本 SMO 只有创建和删除节点；加入边压缩、节点压缩后，还需要扩展或压缩边、追加节点映射及替换节点。节点替换包括节点扩容、节点压缩、边压缩和删除，是更新协调的主要难点。

前缀树、边压缩和节点压缩各自涉及的结构修改操作（Figure 2: SMOs in prefix tree variants. Prefix trees (bottom) only have two SMOs: node creation and deletion. Edge compression (middle) requires two new SMOs to expand and compress edge bytes. Node compression (top) requires three new SMOs to append to node partial mappings and change the representation of a node. SMOs on the right side require unlinking (Figure 3); we refer to them collectively as node replacement SMOs.）

三、问题：多位置更新与安全回收

CAS 一次只能原子地比较并更新一个内存位置。若一个 SMO 必须同时改父边和子节点头部，单次 CAS 无法覆盖两处状态；拆成多次 CAS 又会暴露不一致的中间状态。若先复制节点、再替换父指针，其他线程可能在复制期间更新旧节点，而这些更新不会出现在新节点中。使用锁会失去无锁进展保证，额外的复制和指针间接层则会增加缓存与分配开销。

节点从树中摘除时还会留下并发读写竞态：已经取得旧节点指针的线程仍可能读取它，但写入已不可达节点的结果不会反映到树中。安全内存回收（safe memory reclamation，SMR）必须确认没有线程还会解引用旧节点，才能释放它。hazard pointers 通过逐指针公布精确保护对象，代价是每次访问都要发布和验证指针；epoch-based reclamation（EBR）按线程经过的静止期延迟回收，代价是一个停滞线程就可能阻止全局内存回收。

四、方案：ARCTIC 的无锁节点更新

4.1 元数据布局支持原子结构修改

ARCTIC 把压缩边上的键字节从子节点头部移到父边中。每条边占 16 字节，包含键字节、子对象指针及其类型信息；这样扩展边时可以先在本地构造新节点，再通过一次 128 位 CAS 发布新边。相较 ART 对父边和子节点头部分别加锁，这把跨位置更新收敛为单位置原子更新。

节点类型标记也放进父边，使包含 256 条边的 Node256 恰好占 4 KiB，不必跨页存放额外头部元数据；Node3 则恰好占一个 cache line（缓存行）。所有节点类型采用 2 的幂次大小。Node3 和 Node15 的头部可放入 16 字节 CAS；Node47 使用按键字节反向映射到边序号的数组，避免范围操作前排序。为并发追加映射，Node47 另存 last 字段；线程通过 helping 修复上次追加留下的不完整状态，再完成自己的追加，使两个 CAS 之间的中间状态对操作不可见。

ARCTIC 与 ART 从空树开始执行三次插入时的结构状态变化（Figure 4: Walkthrough showing a series of insertions in ARCTIC and ART, starting from empty trees. Each insertion requires a different SMO (except the first insertion, which ARCTIC handles without an SMO). Each data structure undergoes atomic transitions between globally visible states, both between rows, and from left to right within a row (separated by dashed lines). To save space, we merge ART’s locking and omit its unlocking.）

ARCTIC 的边和节点类型布局（Figure 5: The memory layout of ARCTIC’s edge and node types. The child of an edge is a union between a user value (if the value bit is set), null, or a node pointer with its type tag in the lower two bits, which are zero due to alignment. 4.2 freezing 协议协调节点替换

ARCTIC 的 freezing（冻结）协议将节点扩容、压缩、边压缩和删除统一为节点替换。替换线程先冻结旧节点，再根据冻结后的最终内容构造新节点，最后用一次 CAS 摘除旧节点并接入新节点。冻结过程逐一设置节点头部和各条边上的 frozen bit；只有所有可 CAS 位置都被冻结后，旧节点才不可变。更新线程只有在 frozen bit 未设置时才能 CAS，因此冻结完成后不会再有未复制的更新。

替换原因不能在冻结前固定：例如线程开始冻结一个满节点准备扩容，但冻结完成前其他线程可能已经删除了所有子项。ARCTIC 因而等冻结后再根据节点的不可变内容决定新节点形态。冻结具有幂等性，多个线程可以并行协助；若更新线程的 CAS 因节点冻结而失败，它会帮助完成节点替换，而不是等待发起替换的线程。即使原发起线程停滞，其他线程仍可推进。

ARCTIC 节点从本地状态转为全局可见，并经过冻结、摘除和回收（Figure 3: The life cycle of a node in ARCTIC. The top two states are local, meaning that there is at most one thread that can access the node. The bottom three states are global, meaning there may be any number of threads accessing the node. We use freezing to coordinate unlinking (§2.4); a frozen node may be reachable or unreachable. Our hazard key protocol (§3.9) determines when an unreachable node becomes safe to reclaim (§2.5).）

4.3 wait-free 遍历与非线性化扫描

遍历和读操作不需要等待冻结：普通遍历是 wait-free 的，沿根到叶前进且不回溯。范围扫描和前缀扫描也保证 wait-free，但不是线性化（non-linearizable）操作；它们按字典序至多观察每个键一次，并能观察到扫描开始前已插入、且直到扫描结束都未删除的范围内键。

4.4 hazard keys 近似保护可达指针

hazard keys 是一种安全内存回收方案。前缀树中，键为 k 的点操作只会访问节点前缀 p 是 k 前缀的对象。该方案利用这一关系：每个操作开始时只公布一次操作键；每个已从树中摘除、但仍可能被在途操作访问的 retired object（待回收对象）都附带其键前缀 p，当 p 是某个已公布操作键的前缀时，该对象暂不能回收。这样，逻辑操作键近似表示这次操作可能解引用的一组节点和值指针，无须像 hazard pointers 那样逐次发布指针。

操作键与前缀树路径相关联，并可在遍历后细化保护范围（Figure 6: On the left, we show a concrete example of how an operation’s key can be correlated with the structure of the tree; the two get operations in the top left will only access the nodes and values of their color. On the right, we show how a hazard key could be refined after traversal to a subtree for a scan operation, or a value for a point operation.）

这种近似保护的内存回收机制减少了逐指针访问开销，但每个待回收对象仍需与线程公布的 hazard keys 比较，成本随线程数增长。回收效率也取决于请求分布：低到中等倾斜时，停滞线程只保护其键路径上的一部分对象；高倾斜时，热门前缀可能长期保护大量对象，因此 hazard keys 不保证有界的未回收内存。

五、结果：并发性能与工程代价

5.1 YCSB、回收与优化评测

评测运行在 Chameleon 的 compute_icelake_r650 实例上，系统为 Ubuntu 22.04.5 和 Linux 5.15。机器有两颗 Intel Xeon Platinum 8380，主频 2.30 GHz、每颗 40 核、120 MiB LLC，配备 128 GiB DDR4-3200 DRAM。实验关闭超线程和 Turbo Boost，将 CPU governor 设为 performance，并把线程固定到核心；YCSB 评测将内存和核心在 NUMA 节点间均匀交错分布，线程数最高为 160，是 80 个物理核心的两倍。

7 种键分布的数据集规模分别为：139M 个 IPv4 地址，顺序与随机 64 位整数、Twitter ID 和 UUID 各 100M 个，114M 个 email，以及 38M 个 URL。每组运行 100M 次操作，采用默认 Zipfian 请求分布（倾斜系数 0.99），值为 8 字节整数。YCSB-A 是 50% read、50% update；YCSB-C 是 100% read；另有 95% read／5% update 的 YCSB-B、95% read／5% insert 的 YCSB-D，以及 95% scan／5% insert 的 YCSB-E。Load 为 100% insert。

在 80 线程下，对 7 种键分布取几何平均，ARCTIC 相对 ART 的吞吐在 YCSB-C 上为 1.3×，在 YCSB-A 上为 7.7×。ARCTIC 的更新只需 CAS 最终边，减少了共享状态竞争；论文测得 YCSB-A 平均每次操作 0.5 次缓存行竞争事件。线程数超过 80 后，ARCTIC 仍能维持吞吐，而部分依赖锁的基线出现退化。字符串键的读性能则会随键长增加而下降，因为树的访问深度随键长度线性增长。

不同键分布和 YCSB 工作负载下的吞吐及峰值内存（Figure 7: Throughput on YCSB workloads across different key distributions. Each row is a key distribution, and each column a YCSB workload. The right-most column indicates the peak memory usage (measured by mimalloc) after loading with 80 threads. For the throughput graphs, the shaded area indicates thread oversubscription. For the memory graphs, the shaded area indicates the baseline size of inserted keys and values, and the text indicates memory usage relative to this baseline.）

hazard keys 的回收实验使用 rand-u64 键和单独分配的 8 字节值，在 YCSB-A、YCSB-B 中比较 Zipfian 倾斜系数 0.99、1.1、1.2，以及 60、80、100 线程。系数为 0.99、线程数为 100 时，hazard keys 的每线程峰值未回收对象数比 crossbeam-epoch 和 seize 低 5.6×–19×；相对 crossbeam-epoch，YCSB-A 吞吐高 1.3%，YCSB-B 低 12%。在 80 线程、相同低倾斜分布下，hazard keys 的吞吐分别比 crossbeam-epoch 低 7.2% 和 6.3%。当倾斜增至 1.1 或 1.2，热门键前缀使更多对象持续处于保护状态，未回收对象数可能不受界限约束。

不同请求倾斜和线程数下的每线程峰值未回收对象数（Figure 9: Reclamation efficiency of safe memory reclamation (SMR) schemes on SMR-intensive YCSB workloads with rand-u64 keys and allocated 8-byte values, varying skewness (Zipfian constant) and thread count. At Zipf 0.99, 17% of requests hit the top 10 (of 100M) keys, increasing to 33% and 48% at Zipf 1.1 and Zipf 1.2, respectively.）

消融实验在 80 线程下逐项叠加优化。免维护遍历栈的 optimistic traversal（乐观遍历）只改善插入：顺序 64 位整数键提升 1.3×，随机 64 位整数键提升 1.2×。原生整数键支持减少遍历中的分支和指令；SIMD（single instruction, multiple data，单指令多数据）对随机整数键更有帮助，对由密集 Node256 构成的顺序整数键影响较小。范围扫描受内存带宽限制，这些优化带来的吞吐变化低于 1.05×。

Reads and scans use the default Zipf 0.99 skew from YCSB. baseline disables all optimizations; +path is optimistic traversal, which avoids maintaining a stack during insertion; +int is native integer support, as opposed to treating integer keys as byte arrays; and +simd uses SIMD for node header lookups and scans. 5.2 RocksDB 与 Turso 集成

RocksDB 的默认内存表（memtable）使用并发 skiplist。论文用 bulk-load（批量装载）基准插入 100M 条随机 20 字节键、400 字节值，并关闭预写日志（write-ahead logging，WAL）。Turso 是 SQLite 的 Rust 重写版，其多版本并发控制（multi-version concurrency control，MVCC）索引以两个无锁 skiplist 分别索引 16 字节行 ID（row ID）对应的行版本数据，以及 8 字节事务 ID（transaction ID）对应的事务元数据；论文把这两处 skiplist 换成 ARCTIC，并运行 multi-writer（多写线程）基准，事务性地插入 100K 批、每批 100 行，即 10M 行，每行包含一个顺序整数和一个短字符串。两项集成基准均为插入型，论文未给出混合读写配比；40% 和 12% 是这些写密集基准中的端到端吞吐提升。

RocksDB 的最大端到端吞吐提升出现在 2 线程，为 1.40×；Turso 的最大提升出现在 8 线程，为 1.12×。启用内部计时器和 perf 采样后，ARCTIC 在所有线程数下都减少了索引操作耗时；线程数较高时，其他系统瓶颈限制了端到端收益。

ARCTIC 的正确性依赖 128 位原子 CAS；论文还将 128 位原子 load 列为性能要求。论文摘要给出的相对 ART 内存开销比例随键分布变化：整数键为 0.97×–1.5×，字符串键为 0.19×–0.61×。
