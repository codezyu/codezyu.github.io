Rakaia：TCP 上的消息级 RPC 调度

  2026-10-28 2026-10-28 Created   2026-10-28 11:55:15 2026-10-28 11:55:15 Updated

论文：Rakaia: Scalable In-Kernel Scheduling for TCP-Based RPCs，Rui Yang、Konstantinos Prasopoulos、Edouard Bugnion，USENIX OSDI ’26（2026）。论文：USENIX OSDI ’26 页面。

TLDR： POSIX TCP 按连接提供有序字节流：同一连接中较慢的 RPC 会让后续请求等待，连接负载集中时则会有少数核心排队、其他核心空闲；这两种情况分别形成连接内和连接间 head-of-line blocking（HOL blocking，队头阻塞）。gRPC 等框架因此要在用户态解析消息、排队并在线程间分派。Rakaia 在内核 TCP 接收路径提取完整消息，以连接无关的消息 API 和每核队列实现 work-conserving（工作守恒：只要有待处理消息，就不让可运行的 worker 空闲）调度，并在发送路径用委派降低共享 TCP socket 的锁争用。论文报告：在 20 个硬件线程、100 µs 平均服务时间的双峰负载和 20 条连接下，Rakaia 约为 160 KQPS（千次请求/秒），Kernel Connection Multiplexor（KCM）约为 30 KQPS，吞吐最高约提升 5×；在平均服务时间 20 µs 的指数分布、5,000 条连接下，gRPC-Rakaia 的 SLO（service-level objective，服务级别目标）约束下吞吐量（throughput-under-SLO，即客户端测得的 P99（第 99 百分位）尾时延（tail latency）不超过 SLO 门限时的最大请求负载）相对 gRPC-Go 和 gRPC-C++ asynchronous API 分别最高提升 1.56× 和 2.69×。论文没有给出这些合成对比对应的数值门限，也没有报告请求和响应的字节大小。

一、背景：TCP 字节流与消息边界

RPC 承载数据中心应用之间的远程调用，TCP 凭借成熟的内核支持和可靠性仍是生产环境的事实标准传输协议。POSIX TCP socket 向用户态提供按连接排序的字节流，不保留应用消息的边界；TLS 握手和加解密也通常由网络栈或运行时处理。

连接粒度的处理会形成两种队头阻塞。连接内阻塞发生在同一连接上的请求被串行处理时：前一个 RPC 执行较慢，后续已到达的请求只能等它完成，无法由其他线程提前取走。连接间阻塞则来自按连接把工作固定分配给线程：某些连接请求集中到一个核心时，该核心排队，而其他核心可能空闲。前一种阻塞让连接内部的后续请求不能由其他线程接手，后一种阻塞直接造成线程间负载不均；两者都会抬高尾时延并限制吞吐。

HTTP/2 可以在一条 TCP 连接上多路复用 RPC stream，并允许响应乱序返回，消除协议层的一些串行约束；但服务端仍要从 TCP 字节流重建 HTTP/2 frame 和 RPC 消息，再把消息交给可并发执行的 worker。若这些工作都由用户态完成，消息解析、线程间通信和排队就进入请求路径。

另一条路线是绕过 TCP，使用 Homa 等自定义消息传输或 eRPC 等用户态网络栈。这些系统能直接以消息为调度单位，但通常要求定制客户端、非标准基础设施或专用硬件，增加了部署难度。Rakaia 要解决的问题是在保留 TCP 兼容性的同时，把消息级调度放到接收路径。

二、现状：连接调度粒度与实现开销

论文用三种队列模型说明调度粒度的影响：

  • 连接分区 FIFO（connection-partitioned FIFO，CP）：按 receive-side scaling（RSS，接收端缩放）将连接静态分给线程，线程间无需协调，但连接不能迁移；连接负载不均时会有空闲核心，且慢请求会阻塞同一连接的后续工作。
  • 连接共享 FIFO（connection-shared FIFO，CS）：所有线程可从共享连接池取连接，减轻连接间负载不均；处理某条连接时仍由一个线程独占，因此连接内阻塞仍在，也不是 work-conserving 调度。
  • 消息共享 FIFO（message-shared FIFO，MS）：先从连接流中提取消息，再放入共享消息队列，由任一空闲 worker 取走。它以消息而不是连接为调度单位，可以同时消除连接内和连接间的队头阻塞；代价是增加消息解析、队列和线程协调。

CP、CS 与 MS 的双线程排队模型（Figure 1: Three queuing models for two application threads: (a) connection-partitioned FIFO (CP), (b) connection-shared FIFO (CS), and (c) message-shared FIFO (MS)）

论文的离散事件模拟器使用开放环 Poisson 到达过程，并把系统实现开销设为零，以隔离排队模型本身的影响。请求服务时间分别服从确定值、均值为的指数分布，以及双峰分布：90% 的请求耗时为，10% 为。模拟在 20 核服务器上比较不同连接数和服务时间分布下的 P99 尾时延；正文没有列出各队列模型的精确时延数值。MS 以消息而非连接为调度单位，可以同时处理两类队头阻塞；直接用用户态全局队列实现则会付出线程和同步成本。

三种服务时间分布下的 P99 尾时延模拟结果（Figure 2: Simulation results for the 99th percentile tail latency for three service time distributions on a 20-core server.）

gRPC 通过专用 I/O 线程读取 TCP stream、重组 RPC 消息并放入 work queue（工作队列），再由 worker pool 执行。HTTP/2 提供了并发 stream，但这条用户态流水线仍需要线程间传递和同步。

KCM 是 Linux 既有的内核消息 API：它借助 strparser 在内核中识别消息边界，却仍按 TCP 连接分别调度。每条连接会为每个应用线程创建一个 KCM socket，线程只能从各连接自己的消息中取活，无法在所有连接间统一分派；socket 数量随线程数和连接数按增长。论文还指出，KCM 当时不支持 kernel TLS（kTLS）等传输安全配置。

gRPC、KCM 与 Rakaia 的 TCP 接收端架构（Figure 3: Three RPC-oriented architectures on top of TCP that aim to eliminate HOL blocking (receive side).）

三、问题：TCP 上的消息级调度

上述方案留下一个明确的设计要求：内核已经在处理每个到达的 TCP packet，应在这条接收路径上解析消息并决定由哪个 worker 处理，让消息尽早脱离连接归属。调度器既要在有待处理消息时利用空闲核心，也要避免单一全局队列成为争用点；API 还应让应用只收发完整消息，不再维护每条 TCP 连接对应的用户态 I/O 线程和队列。

同时，方案需要继续使用 Linux TCP/IP stack，保留 TCP 的可靠传输和既有协议兼容性，并能配合 kTLS。由于发送仍要经过原 TCP socket，同一连接被多个 worker 同时写入时也必须控制 socket 锁争用。

四、方案：Rakaia 的消息收发与调度

4.1 消息 API 与接收路径解析

Rakaia 是 Linux 内核中的消息处理层，不替换 TCP/IP stack。应用线程创建一个 Rakaia socket，通过 rakaia_attach() 把已有 TCP socket 和协议解析器关联起来；之后用 recvmsg() 收取完整消息，用 sendmsg() 发送完整消息。每个 worker 只需一个 Rakaia socket 来处理多条 TCP 连接。连接来源由内核保存在消息元数据中，用户态不需要维护逐连接的接收状态。

Rakaia 接收路径与发送路径总览（Figure 4: Overview of Rakaia’s design. In the receiving path, solid arrows show the chosen execution path, while faded arrows indicate unselected candidates under power-of-two choices. In the transmission path, 1–4 shows a thread sending messages along the fast path, while a–b illustrates a case where message sending is delegated.）

每条已关联的 TCP socket 上挂有一个 strparser 实例。对 Memcached 这类带长度字段的协议，解析器检查固定头部并读取 payload 长度；对 HTTP/2，论文把一个 RPC 映射到一条 stream，解析器读取每个 frame（帧）的 stream ID、长度、类型和标志，并按 stream ID 缓存 frame。携带 END_STREAM 的 frame 到达后，内核把该 stream 缓存的 frame 合并为一条完整消息并交给上层。论文没有进一步说明同一 stream 内多条 gRPC 应用消息如何分别交付。HTTP/2 的 PING、WINDOW_UPDATE 等控制 frame 也由内核处理，避免把这些传输控制工作送回应用运行时。

Memcached 与 HTTP/2 的消息解析（Figure 5: Parsing Memcached and HTTP/2. s1, s3, and s5 refer to stream with ID 1, 3, and 5. f1 and f2 refer to the first and second frames of a stream.）

4.2 Rakaia 队列调度与发送委派

Rakaia 在逻辑上提供一个共享消息队列，物理上则为每个 Rakaia socket 维护本地 FIFO 队列。新消息到达时，调度器使用 power-of-two choices（P2C）：随机选两个候选队列，把消息放入较短的一条；如果目标队列为空，就直接交给空闲 worker。worker 取空本地队列后，会根据非空队列位图选择队列窃取消息。这样，消息调度不再受原 TCP 连接归属限制，Rakaia 因而消除连接内和连接间的应用层消息队头阻塞；分布式本地队列同时避免所有入队操作争用单一全局队列。

发送时，Rakaia 先把完整消息放入对应 TCP socket 的虚拟发送队列。若另一线程已经负责该连接的发送，当前线程入队后即可返回；否则它设置发送标记、获取 TCP socket 锁，把暂存消息移入 TCP 发送队列并调用 tcp_push()。发送者持续检查暂存队列，直到队列为空再释放锁。委派让同一连接上的并发发送者共享一次锁持有过程，同时保留既有 TCP 发送路径。

实现基于 Linux 6.8，核心为约 3,000 行 C 代码的可动态加载内核模块；另需约 60 行内核补丁注册新的 socket 类型，不改变 TCP stack 的语义。Rakaia 支持 Memcached 和 HTTP/2 解析，并可通过 kTLS 处理加密连接。现有 kTLS 无法稳妥地在 softirq（软中断）中并发解密，因此 Rakaia 把接收解密交给 workqueue（内核工作队列）。

五、结果：合成与真实负载评测

5.1 KCM 与 gRPC 的合成评测

实验在 CloudLab xl170 节点上进行：每台机器有一颗 Intel Xeon E5-2640 v4（10 核、2.4 GHz），开启超线程；系统运行 Ubuntu LTS 24.04 和 Linux 6.8。服务端使用 20 个硬件线程，应用负载为 compute-bound（计算密集型）；gRPC-Go 的 POSIX 和 Rakaia 版本都配置 20 个 worker goroutine（Go 的轻量级执行单元）。Lancet 一次建立全部客户端连接，再按 Poisson 过程开放环发请求；论文在客户端收到响应时测量 P99 尾时延，并绘制相对于已达吞吐量的变化。合成实验的请求和响应字节数没有在论文中报告。

§5.2 的 KCM 对比和 §5.3 的 gRPC 对比没有写出 throughput-under-SLO 所用的数值门限。因此，这两组倍数无法对应到具体的 P99 阈值；本文不把其他工作负载的 SLO 数值移用到它们。

100 µs 平均服务时间的合成测试覆盖 20、80 和 5,000 条连接。双峰分布的长尾请求占 10%，耗时为均值的 5.5 倍。20 条连接、100 µs 双峰负载下，Rakaia 约达到 160 KQPS，而 KCM 约为 30 KQPS；论文称 KCM 只有 Rakaia 吞吐的 19%，并报告 Rakaia 相对 KCM 的 throughput-under-SLO 最高提升 5×。这里的约 160 KQPS 与 30 KQPS 是论文正文给出的近似值，不能据此反推没有报告的精确 SLO 门限。

100 µs 任务下三种服务时间分布的 P99 尾时延与吞吐（Figure 7: 99th percentile latency as a function of throughput for 100µs tasks. Top, middle, and bottom rows correspond to 20, 80, and 5,000 client connections, respectively.）

gRPC 的倍数来自另一组设置：实验使用均值 20 µs 的指数服务时间，在 80 和 5,000 条连接下比较 gRPC-Go v1.75.0 与 gRPC-C++ v1.78.1 的 POSIX 和 Rakaia 版本。gRPC-Go 在 80 条连接时，Rakaia 版本能承载的负载高 39%；连接增加至 5,000 后，POSIX 版本吞吐下降 11%，Rakaia 版本在 5,000 条连接下的 throughput-under-SLO 最高为 POSIX 版本的 1.56 倍。gRPC-C++ 的 asynchronous 和 callback API 在 80 条连接时分别提升 2× 和 2.33×；5,000 条连接时分别提升 2.69× 和 2.67×。所以 2.69× 对应 5,000 条连接下的 asynchronous API，不代表所有 C++ API 都是同一倍数。

gRPC-Go 与 gRPC-C++ 的性能对比（Figure 9: 99th percentile latency according to throughput for gRPC-POSIX and gRPC-Rakaia (Exponential (S̄ = 20µs)).）

在 170 KQPS、20 个硬件线程下，gRPC-Go POSIX 版本从 80 条连接扩展到 5,000 条时，goroutine 数由 1,077 增至 16,946；gRPC-Rakaia 版本分别为 29 和 33。5,000 条连接时，Rakaia 把 Go 调度器开销从 5.5% 降到 1.0%，把栈增长与管理开销从 12.3% 降到 0.1%；用户态 CPU 时间从 60.0% 降到 37.3%，内核时间从 32.2% 增到 34.0%。这与 Rakaia 把消息拆分和分派移入内核的设计相符。

启用 kTLS 时，100 µs 任务下 Rakaia-kTLS 约为 120–130 KQPS，TCP-CS-TLS 和 Worker Pool TLS 约为 130–140 KQPS；20 µs 任务下 Rakaia-kTLS 约为 320–340 KQPS，TCP-CS-TLS 约为 380 KQPS，Worker Pool TLS 约为 200–220 KQPS。论文将 kTLS 启用后的吞吐变化归因于接收端解密要通过 Linux workqueue 执行。

启用 TLS 时的 P99 尾时延与吞吐（Figure 10: 99th percentile latency as a function of throughput with TLS enabled for 100µs and 20µs tasks, respectively.）

5.2 真实服务评测与 TCP 边界

真实应用测试继续使用同一 CloudLab 平台。Silo 的 TPC-C 网络服务关闭了垃圾回收；论文称垃圾回收会使 P99 尾时延出现波动，但没有报告波动幅度。该测试也未实现 SQL 请求和响应的 marshalling（把结构化数据序列化并组装成网络消息）。在 500 µs 的 P99 尾时延 SLO 下，Rakaia 约达到 350 KQPS，TCP-CS-80 约为 309 KQPS，Worker Pool 约为 299 KQPS。gRPC-Go 驱动的 Silo 在 80 和 5,000 条连接下，Rakaia 版本相对 POSIX 版本的 throughput-under-SLO 分别为 1.25× 和 1.39×。

Silo 运行 TPC-C 的结果（Figure 11: Silo running TPC-C benchmark）

OpenTelemetry Collector 测试由客户端通过 gRPC-Go 发送 OpenTelemetry Protocol（OTLP）trace；每条前端 RPC 携带 10 个 span（trace 中的一段记录），Collector 默认每批 8,192 个 span，并设置 200 ms 超时。使用 no-op exporter 时，后端导出工作被移除；在 2 ms P99 SLO 下，gRPC-Rakaia 为 192 KQPS，POSIX 为 142 KQPS，提升 1.35×。使用 Jaeger 后端时，前端处理要与 batching、protobuf 序列化和导出并行；Rakaia 为 131 KQPS，POSIX 为 92 KQPS，提升 1.42×。Jaeger 导出路径仍走未修改的 gRPC client，因此该倍数反映 Collector 前端服务端路径的变化。

OpenTelemetry Collector 的传输性能对比（Figure 12: 99th percentile latency according to throughput for OpenTelemetry Collector with POSIX and Rakaia transports.）

Rakaia 消除的是 TCP 之上的消息级队头阻塞。它仍继承 TCP 按序交付的传输限制：某个 segment 丢失或乱序时，该连接要等重传后才能继续；TCP 的发送端拥塞控制也没有改变。kTLS 接收解密仍通过 workqueue 执行。
