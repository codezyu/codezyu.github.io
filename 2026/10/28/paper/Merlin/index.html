Merlin：基于细粒度访问模式刻画的自适应缓存淘汰算法

论文：Merlin: An Efficient Adaptive Cache Eviction Algorithm via Fine-Grained Characterization，Liujia Li、Jinhao Guo、Yi Fan、Jianyu Wu、Zhenlin Wang、Jie Zhang、Yuval Tamir、Xiaolin Wang、Yingwei Luo、Diyu Zhou，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI ’26，Seattle，2026 年 7 月 13–15 日）。论文：USENIX OSDI ’26 页面。

TLDR： 现有自适应 cache eviction（缓存淘汰）算法只覆盖少数典型 access pattern（访问模式）；Cacheus 在多种模式并存时切换两种基础策略，可能让它们相互干扰。Merlin 按对象进行 pattern characterization（访问模式刻画），同时衡量短期和长期 access locality（访问局部性），并用 cache 大小决定分类阈值；过滤、保留、复核和统计由不同队列及计数结构承担。在 11 个公开数据集的 5,423 条访问 trace 上，论文报告 Merlin 的 hit rate（请求命中率，即由 cache 提供服务的请求占比）整体优于基线；以工作集大小（working set size，WSS）的 10% 作为 cache 大小时，命中率相对 LRU（least recently used，最近最少使用）平均提高 10.4%。另一项 throughput（吞吐量）评测在 2 亿请求、200 万对象的混合访问 trace 上进行；32 线程下，Merlin 的吞吐比对比算法高 1.4–7.8 倍。

一、背景：变化的访问局部性

Web cache、内存 key-value store、操作系统 page cache 等系统都依赖淘汰策略，在 cache 空间不足时决定哪些对象留下、哪些对象移除。命中可以避免访问较慢的后端；策略要有效，就得让留在 cache 中的对象匹配 workload 的访问局部性。

论文把 page、block、key-value pair（KV pair）等缓存内容统称为 object。真实 workload 的访问模式既多样，也会随时间改变。同一条访问序列还可能混合不同模式，因此只按整段序列归类，或只针对一种模式优化，都可能漏掉值得保留的对象。

二、现状：自适应算法的分类

静态算法对所有访问应用固定规则。LRU（least recently used）、LFU（least frequently used）、FIFO（first-in first-out）等简单策略各自适合有限的一类访问模式。后续算法通过更细的排序指标或组合多个队列来改善跨 workload 表现。论文 Figure 3 用 3% WSS 的 cache 比较 8 个数据集和 8 个代表性算法；不计 Merlin 时，S3-FIFO 在 4 个数据集的 hit rate 最高，LIRS 在其余 4 个最高。Merlin 则在其中 5 个数据集最高，在另外 3 个接近最佳。

8 个真实数据集上各淘汰算法相对 LRU 的平均命中率提升；cache 大小为 WSS 的 3%（Figure 3: The average hit rate improvement over LRU for 8 representative eviction algorithms on 8 real-world datasets. The cache size is 3% of the working set size. The larger the value, the higher the hit rate, with a star showing the best algorithm (excluding Merlin). Merlin achieves the highest hit rate in 5 datasets, with close to the best performance in 3 datasets.）

自适应算法主要分两类。ARC（Adaptive Replacement Cache）和 CAR（Clock with Adaptive Replacement）属于按空间自适应：它们将 cache 划分为只访问过一次的 one-hit 部分和重复访问的 multi-hit 部分。新对象先进入 one-hit 部分；cache miss 时，算法检查 ghost 历史中是否有该对象，再扩大对应部分、缩小另一部分。CAR 的主要区别是用 FIFO 队列替代 LRU 链表。

Cacheus 属于按策略自适应。它将访问归入四种典型模式：LFU-friendly（少数对象被频繁访问）、LRU-friendly（最近访问过的对象很快会再被访问）、Churn（所有对象以相同概率反复访问）和 Scan（对象只访问一次）。Cacheus 在抗 scan 的 LRU 变体与抗 churn 的 LFU 变体之间按权重选择淘汰策略；若发现刚被淘汰的对象又被请求，就降低负责淘汰它的算法权重，并用机器学习控制权重变化速度。

三、问题：模式覆盖与算法干扰

作者分析了 11 个真实数据集，共 5,423 条 trace。为量化 workload 的变化，论文定义 object change rate，用来衡量相邻时间窗口间访问到的不同对象集合如何变化；定义句没有进一步说明该比例的分母。窗口长度取 trace 总长度的 1% 时，作者报告各数据集的 object change rate 都较高，最高约 45%；两个示例 trace 中，四种典型模式也会频繁切换。

现有算法的分类假设覆盖不了真实 workload 的混合模式。ARC 和 CAR 主要关注近期是否重复访问，因此容易忽略长期局部性：对象可能隔很久才被再次访问，但跨多个时期仍有较高访问频率。Cacheus 则假定不同基础算法能各自覆盖一部分模式；如果一个时间段同时含有多种模式，两种策略都可能做出差的淘汰决策，权重调整只会让系统在它们之间来回切换。

第三个问题是 cache 大小。相同访问序列在不同容量下可能需要不同策略，但现有自适应算法没有把 cache 大小纳入访问模式刻画，因此跨容量表现不稳。

四、方案：对象级模式刻画

4.1 对象级访问模式刻画

Merlin 的 object-level characterization（对象级模式刻画）满足四个要求：在对象级而非整段序列级工作；不把访问限制在固定的少数模式；同时反映短期与长期访问局部性；根据 cache 大小改变分类标准。

论文将访问序列划分为 epoch。假设对象大小均为 1，一个 epoch 包含 S 个不同对象的访问，S 为 cache 大小。每个对象有两个统计量：

  • hotness：对象在当前 epoch 内被访问的次数，用来表示短期局部性。
  • popularity：对象在此前各 epoch 中出现过的 epoch 数，不计当前 epoch，用来表示长期局部性。

Merlin 分别把当前按 hotness 排名第 S 的对象之 hotness 值、按 popularity 排名第 S 的对象之 popularity 值设为阈值。每个对象据此分到四类：hot-popular、hot-rare、cold-popular、cold-rare。对象类别的数量分布反映访问模式；随分布和容量改变阈值，Merlin 也随之调整各类对象的处理方式。

这套刻画可以区分近期访问频繁和跨 epoch 持续出现的对象。Figure 6 给出四个 epoch 的访问示例：在 Epoch 2 结束时，A 的 hotness 和 popularity 都是 1；到 Epoch 4 结束时，A 在当前 epoch 没有访问，hotness 为 0，但它在前面三个 epoch 都出现过，popularity 为 3。C 则因 Epoch 3、4 中频繁访问，从 hot-rare 变成 hot-popular。分类因此跟着访问历史变化，而不是把整段 workload 强行归入单一模式。实验中的变长对象实现还会按唯一访问对象的总大小推进 epoch，并按总大小匹配 cache 容量。

4.2 队列职责与对象流转

Merlin 的主体由 filter queue、core queue 和 staging queue 三个 FIFO 队列组成，另有只存元数据的 ghost queue，以及记录 popularity 的 popularity recorder。默认空间比例分别为 10%、85% 和 5%；ghost queue 保存与主 cache 中对象数量相当的元数据，popularity recorder 追踪过去 16 个 epoch。

组件职责
filter queue接收新对象并快速淘汰疑似 cold-rare 的对象；对误筛出的 hot 或 popular 对象，保留 ghost 元数据以便再次访问时复核。
core queue占主要 cache 空间，保留 hot 和／或 popular 对象；hot-popular 对象离开队列后可重新插入。
staging queue复核从 core 或 ghost 来的对象；若仍 hot 或 popular，就提升回 core，否则淘汰或放回 ghost。
ghost queue保存被淘汰对象的元数据，使再次访问的对象有机会恢复并完成一个 epoch 的 hotness 观察。
popularity recorder记录对象跨 epoch 的访问情况，供 popularity 阈值和分类使用。

Merlin 的主要组件与工作流（Figure 8: An overview of Merlin’s key components and workflow.）

新对象先进入 filter queue。若被筛为 cold-rare，Merlin 移除其数据，只留下 ghost 元数据；否则提升到 core。core 中较旧的对象转入 staging；staging 再检查它的访问类别，hot 或 popular 对象回到 core，cold-rare 对象才最终移除。对 ghost 中被重新访问的对象，Merlin 更新 hotness，再按类别放入 core 或 staging。

这些组件围绕一套统一的对象分类协作，不用若干互相竞争的基础算法拼出自适应策略。Merlin 借鉴 S3-FIFO 的 FIFO 队列设计，但按对象类别决定组件间流转，而不是仅凭固定访问次数处理对象。

4.3 计数结构与多核扩展

popularity recorder 使用 count-min sketch（分行哈希计数的近似结构），不必为每个对象保存一份名称和每个 epoch 的计数。对象到达时，多个哈希函数分别更新对应计数器；查询时取各行计数的最小值作为估计。Merlin 用一个 sketch 近似记录 16 个 epoch 的历史；每次对象到达都会增加全局计数，达到 16 倍 cache 大小时，Merlin 将全局计数清零并把 sketch 中的计数减半，以近似维护滑动历史窗口。

作者在 CacheLib 和 libCacheSim 中实现 Merlin，并为对比实验补充了 ARC、CAR 的实现。Merlin 用 hash table 索引 cache 对象；ghost 对象的 hash table 记录 fingerprint、hotness 和序列号，每项共 8 byte，并用序列号延迟清除失效记录。每个对象的主要元数据占 5 bit，包括 3-bit hotness counter、ghost 标记和 access 标记。以常见的 4 KB 对象估算，ghost queue 每对象额外占 8 byte，count-min sketch 在 1% false positive rate（假阳性率）时平均每对象占 1 byte，整体空间开销约为 cache 容量的 0.31%。

多核扩展性来自队列和状态更新方式：FIFO 队列不必像 LRU 链表那样在每次访问时锁住整条队列；其余状态更新使用原子操作，hash table 与 sketch 也支持并发访问。cache 大小若在运行中改变，会使阈值失效；论文实现假设容量固定，将动态容量适配留作后续工作。

五、结果：命中率与吞吐评估

5.1 命中率评测设置与结果

评测平台是双路、192 核 AMD EPYC 9965，运行 Debian 12 和 Linux 6.13.8；关闭超线程和 turbo boost。作者使用 11 个开源数据集，trace 覆盖 2008–2023 年，包含 block、object 和 key-value workload；Alibaba 与 Tencent CBS 按 tenant 拆分。数据集合计 338 billion requests、33 billion objects，论文还报告 11 PB traffic、1,837.2 TB data；对象大小范围从 1 byte 到 4 GB。评测覆盖固定大小和变长对象，总共运行 38.5 trillion requests，耗费约 1 million CPU hours。

命中率评测比较 16 个基线算法，并沿用各自默认配置：经典算法 LRU、LFU、FIFO、2Q；近期静态算法 S3-FIFO、LIRS、LHD、W-TinyLFU、GDSF、Hyperbolic、SIEVE；已有自适应算法 ARC、CAR、Cacheus、LeCaR；以及机器学习算法 GL-Cache。论文为清楚展示结果，只在图中列出表现较好的算法。命中率使用 libCacheSim 回放 trace；吞吐评测在 CacheLib 中运行；闪存友好度评测使用 libCacheSim 的扩展。

5.2 吞吐、闪存与敏感度

吞吐量不是在上述 5,423 条原始 trace 上逐条测得。作者依据真实 trace 中观察到的访问模式，生成一条由 Zipfian（Zipf 分布）、uniform（均匀分布）、repeated sequential（重复顺序访问）和 scan（扫描访问）四类分布组成的混合 trace，再随机打乱访问；合成 workload 有 200 million requests 和 2 million objects。实验在 CacheLib 中用 1–32 个线程回放，并在 cache miss 时模拟 10 µs 后端延迟。Figure 14 的吞吐轴单位标为 MQPS，论文未展开这个缩写；该图同时比较包含后端延迟和移除后端延迟两种设置，后者用于观察 cache 管理开销。32 线程时，Merlin 的吞吐比 Figure 14 中的对比算法高 1.4–7.8 倍；正文没有把区间端点分别对应到具体算法。作者另报告 Merlin 在不同线程数下的吞吐约为 S3-FIFO 的 1.4 倍，移除后端延迟时比 S3-FIFO 高 16%。论文的 7.3 节及 Figure 14 caption 没有说明该吞吐测试采用的 cache/WSS 比例。

敏感度实验显示，filter queue、staging queue 和 ghost queue 的容量在较宽范围内变化时，整体 hit rate 大多稳定；总体较好的配置是 filter 为 cache 的 10%、staging 为 5%、ghost 为 cache 中对象数的 100%。CloudPhysics 上，filter 和 staging 取 cache 的 5%–15% 时多数容量下稳定；超小 filter 配小 cache、或过大的 filter/staging 配大 cache 时会退化。Merlin 的 hotness epoch 长度固定为 cache 大小；ghost queue 决定被淘汰对象的元数据保留多久，因此作者通过改变 ghost queue 大小来近似测试 4–128 的 hotness 观察窗口。count-min sketch 的 false positive rate 则在 0.1%–5% 之间变化。约 8% 的 trace 对 epoch 窗口或 sketch 大小较敏感，hit-rate improvement over LRU 的变化超过 1%；CloudPhysics、Alibaba、Tencent CBS 中分别约有 25%、17%、5% 的 traces 落在这组敏感 workload 中。
