DPA-Store：在 BlueField-3 上实现有序 KV 存储

论文：DPA-Store: An Ordered Network Data Path Key-Value Store，Frederic Schimmelpfennig、Jan Sass、Reza Salkhordeh、Martin Kröning、Stefan Lankes、André Brinkmann，USENIX OSDI ’26（20th USENIX Symposium on Operating Systems Design and Implementation，2026 年 7 月 13—15 日，Seattle，论文集页码 1513—1530）。论文页面。

TLDR： 远程有序 KV 存储要支持范围查询，但 host 网络栈、network interface card（NIC）与 host 之间的数据往返、以及 DPA 侧内存容量限制了吞吐。DPA-Store 把 BlueField-3 的 Data Path Accelerators（DPAs）用于 User Datagram Protocol（UDP）请求处理：在 DPA 使用的 1 GiB DDR5 区域中遍历学习索引（根据 key 分布模型预测 key 位置的索引），叶节点再从 host-side 副本读取值；写入先留在 DPA 每个 leaf node 的 insert buffer，凑批后交给 host 更新结构，再把新节点复制回 DPA memory 并以原子指针切换接入树。论文报告，在 64-bit key/value 的 100 Gb/s 测试环境中，GET 达 33 MOPS（million operations per second，每秒百万次操作），读取 10 个相邻 key 的 RANGE 达 13 MOPS。论文称纯读时 host CPU 参与可忽略，但没有给出 CPU 利用率百分比；INSERT 最高只有 1.7 MOPS，受 host-to-DPA 回传路径限制。

一、背景：有序 KV 存储与 DPA

远程 key-value（KV）存储通常提供 GET、INSERT、UPDATE、DELETE，也可能提供 RANGE。GET 可以用哈希表实现；RANGE 要按 key 的顺序定位起点并继续扫描，因此通常依赖有序树或其他有序索引。

学习索引根据已排序 key 的分布训练分段线性模型，用模型预测目标 key 所在的位置，再扫描预测位置附近的一小段连续数据。它用少量模型计算换取较少的随机内存访问，适合访问延迟高、希望限制 cache-line 数量的存储层。

B+ 树与学习索引树的访问模式（Figure 1: Access patterns in B+ -trees vs. learned index trees.）

BlueField-3 SmartNIC 除网络功能外还提供片上 DPA subsystem。该 subsystem 有 16 个 1.8 GHz RISC-V 物理核心，每个核心运行 16 个硬件线程；256 个线程中有 189 个可供应用使用。DPA memory 是 BlueField-3 DDR5 中专供 DPA 使用的 1 GiB 区域。每个 DPA thread 有私有 L1 cache，并共享 1.5 MiB L2 与 3 MiB L3 cache。论文引用文献 [7] 报告，DPA memory 的平均访问时延约为 465 ns，约为标准 CPU 访问 host DRAM 的 5 倍。

BlueField-3 在 NIC mode 下的架构与 host DMA 路径（Figure 2: NVIDIA BlueField-3 architecture configured in NIC mode, allowing DMA access to host memory.）

二、现状：远程 KV 路径的取舍

Redis、Memcached 等 host-based KV 服务通常经由 socket 和 OS 网络栈处理请求，网络数据还要经过 SmartNIC 与 host 之间的 PCIe（Peripheral Component Interconnect Express）总线。Data Plane Development Kit（DPDK）可以绕开内核网络栈，但请求处理仍占用 host CPU。直接在 SmartNIC 上服务的 MICA、KV-Direct 等方案把路径移近网络，却使用 hash-based point lookup，不能处理范围查询。

另一种做法是在 field-programmable gate array（FPGA）SmartNIC 上遍历 host memory 中的树。Honeycomb 支持有序操作，但未缓存的 KV 会触发多次 DMA（direct memory access）往返。remote direct memory access（RDMA）KV 系统可以在 host memory 上实现树或学习索引，也支持范围操作；其中 Sherman、ROLEX 等方案依赖 client-side 的地址或索引缓存。client 要保存额外状态、参与索引访问和故障处理，系统扩展与一致性管理也随之复杂。

因此，DPA-Store 要同时保留有序读能力、减少 DPA 与 host 之间的访问，并让 client 不维护服务端索引状态。

三、问题：DPA 内存与 host 访问代价

DPA memory 容量只有 1 GiB，因此论文把较大容量的 values 放在 host-side tree replica 中；如果把树也放在 host memory，DPA 每层遍历都要经 PCIe 发起 DMA。论文引用文献 [7] 报告，DMA 访问 host memory 的平均时延约为 910 ns，DPA memory 访问约为 465 ns。论文没有在此处给出 [7] 的访问粒度、读写比例或测量方法；这组数值用于说明硬件访问代价，不是 DPA-Store 端到端吞吐测试的测量条件。

读路径需要让 DPA 就地定位有序 key，同时只在取叶节点数据时访问 host。写路径则有另一类工作：插入和删除可能改变叶节点、模型和父节点，训练与分裂比普通查询更重，适合交给 host 执行；但 DPA 线程仍要在更新期间持续读取一致的索引。系统还要避免把树遍历和索引维护状态转移给 client。

四、方案：DPA 遍历与 host 更新

4.1 DPA 上的学习索引遍历

client 通过 Ethernet 发送请求，每个 request 是一个 UDP packet。BlueField-3 的硬件包匹配规则按监听端口把请求直接放进指定 DPA thread 的接收路径；默认情况下，client 对 key 使用共享 hash，将同一 key 发往同一个 home traverser。DPA thread 从 NIC buffer 取请求，不经过 host 的 OS 网络栈。

DPA-Store 的 NIC 请求路径、叶级读取、批量写入和 host/DPA 更新（Figure 3: DPA-Store architecture: (I) Request packets are assigned on-path to a DPA traverser thread, which (II) walks a NIC-side learned index. (III) Values are fetched per DMA using leaf-level models, and (IV) inserts are placed in leaf-level insert buffers. (V) The host performs structural updates that are (VI) transactionally stitched back to the NIC without interrupting traversers.）

DPA memory 中的学习索引树保存遍历所需的模型、pivot key 和 child pointer。每个 inner node 分成 7 个 segment，每段用 piecewise-linear approximation（PLA）预测 child 位置。模型形式为 p(k) = a · k + b；遍历线程用预测位置附近的 key 做线性扫描，再读取下一层 pointer。DPA 不提供浮点运算，因此 slope 和 intercept 使用 fixed-point 运算；覆盖完整 64-bit key 空间时，计算中会暂时扩展到 128 bit。

NIC-side 节点与 leaf DMA 区域的内存布局（Figure 4: Layout of NIC-side nodes and leaf DMA regions.）

论文将 inner-node error bound 固定为 εinner = 4，将 leaf-node error bound 固定为 εleaf = 8。在这个设置下，inner-node 查询最多访问 2 条 DPA-memory cache-line，leaf key 扫描最多需要 3 次 DMA 访问。DPA memory 容量有限，因此 host-side replica 保存高容量的树数据与 key/value；DPA traverser 到达叶节点后，才通过 DMA 扫描 host-side key 并取回对应 value。

DPA traverser 到达 leaf node 后先检查 insert buffer；若其中没有请求的 KV，再根据模型预测位置扫描 host-side key 数组，找到 key 后以 DMA 读取 value。RANGE 从 kmin 所在叶节点开始，先扫描 insert buffer、收集查询范围内的值，再扫描 host-side key array；扫完一个叶节点后，DPA 以刚返回的最后一个 key 重新下降索引，定位 key 严格大于它的下一叶节点。论文说明每个 range response packet 最多携带 64 对 KV，以符合 1500-byte maximum transmission unit（MTU）；没有进一步说明超过 64 对时的分包处理。论文只交代 insert buffer 与 host leaf array 都会扫描并收集范围内的值，没有说明 buffer 中重复 key、更新或删除标记如何与 host-side 条目合并。

4.2 host patch 与 DPA stitch 更新

本节所说的 patch 是 host 接收满 buffer 后更新或重训树结构；stitch 是 DPA 侧复制新节点并切换树指针。每个 leaf node 在 DPA 侧有一个可容纳 16 对 KV 的 insert buffer。INSERT、UPDATE 和 DELETE 先追加到 buffer；写入用前后两个 atomic counter 标记，后续 GET 和 RANGE 会先查 buffer，因此已确认的更新立即可见。论文说明，DPA 将写请求追加到 buffer 后就向 client 返回确认；这次 append 是该写请求在 delivered-request history 中的 linearization point。

buffer 满后，负责该 buffer 的 traverser 通过 DMA 向 host 队列发送 patch request。host patcher 将操作与既有叶数据合并、排序并重训受影响的 subtree；必要时创建新的 leaf 和 inner node。更新 host tree 时，patcher 会锁住父节点，以便处理相邻 subtree 更新。

host-side patching 的结构更新步骤（Figure 6: Host-side patching protocol.）

DPA-side stitcher 按顺序应用 host 生成的更新：先用 COPY 把新节点和地址准备到 DPA memory，再发 CONNECT 命令，以一次 pointer swap 把更新后的 subtree 接到父节点。旧节点不原地改写，因此 traverser 可以继续读旧树；新指针切换后，epoch-based reclamation 会等所有 traverser 进入下一请求，再回收旧节点和 host-side DMA 地址。

stitch 应用期间 NIC tree 仍保持有效（Figure 7: The NIC-tree stays valid while stitches are applied.）

支持并行 stitch 的 tree 分区（Figure 8: Tree partitioning to allow concurrent stitches.）

这种 read-copy-update（RCU）式拼接让 DPA 树遍历保持 lock-free（遍历过程不获取锁）。UPDATE-only patch 不需要把新节点复制到 DPA；INSERT、DELETE 或需要重训、分裂的更新则需要更多 host-to-DPA stitch 工作。

4.3 DPA 热项缓存与接纳策略

每个 DPA traverser thread 都维护自己的 hot-entry cache：一个 256-bit、3-way Bloom filter 和按 cache-line 布局的 bucketed hash table。每线程缓存容量设为 96 项；176 个 traverser 合计可存 16,896 项。平均 Bloom false-positive rate 为 31%；误报只会多探测一条 cache-line，之后仍比较完整 key/value，不会返回错误值。

DPA 侧 hot-entry cache 结构（Figure 5: DPA-side hot-entry cache.）

GET 命中缓存时可省去树遍历和 host DMA。UPDATE、DELETE 会在响应前使对应 home-thread cache slot 失效；INSERT 不直接进入缓存，只有之后的 GET 才会接纳新 key，以免冷数据挤掉热点。

hot-entry cache 未命中时，DPA traverser 按 4.1 节的路径继续查 insert buffer、host-side key array 和 value。论文采用随机接纳策略时，在 α = 1 的负载下缓存命中率为 25%。作为随机接纳的替代方法，作者评估了每个 traverser 独立运行的 Space-Saving heavy-hitter 变体，用它决定哪些 GET key 进入 cache；在 α = 1.1 的专项测试中，该策略的命中率最高为 50%。作者报告，这一策略每个请求增加读写后，GET 总吞吐仍未超过随机接纳策略；论文没有给出该比较的具体吞吐差值，也没有单独报告随机策略在 α = 1.1 下的命中率。因此，25% 和 50% 不是同一负载下的命中率对比，也都不等于默认 α = 0.99 的命中率。

五、结果：查询吞吐和写入代价

5.1 GET、RANGE 吞吐与评测条件

在 100 Gb/s 主评测中，论文报告 GET 为 33 MOPS、RANGE 为 13 MOPS。评测分别包含 GET-only 和 RANGE-only 请求，不是混合读写比；每个 RANGE 查询 10 个相邻 key。MOPS 表示每秒百万次操作，计数的是请求操作。

主评测使用一台 server 和六台 client，通过 100 Gb/s Ethernet 与 Dell PowerSwitch S5232F 相连。server 配有 32-core AMD EPYC 9354P、128 GB DDR5 和 BlueField-3 B3140L；所有实验都把 BlueField-3 配置为 NIC mode，以允许 DPA DMA 访问 host，并关闭 ARM cores。每台 client 使用双路 AMD EPYC 7301（共 32 cores）和 Mellanox ConnectX-5；client 以 DPDK 发送请求。

评测使用 SOSD 的 key-distribution dataset suite，包括 synthetic 分布以及 Facebook、Amazon、Wikipedia、OpenStreetMap 的真实分布；论文将其标为 sparse、dense、dense4x、sparseBig、face、amzn、wiki 和 osmc。除非另有说明，每次实验先 bulk-load 25M 条 KV；key 和 value 都是 64-bit（各 8 bytes）。偏斜 key popularity 默认按 Zipf 分布取 α = 0.99，另有均匀访问测试。

GET-only 是 100% GET；专门的 RANGE-only 测试以 10 个相邻 key 为查询范围。论文也测试 100% INSERT、UPDATE，以及 Yahoo! Cloud Serving Benchmark（YCSB）A—F 的混合负载：

负载操作比例
YCSB-A50% GET、50% UPDATE
YCSB-B95% GET、5% UPDATE
YCSB-C100% GET
YCSB-D95% GET、5% INSERT
YCSB-E95% RANGE、5% INSERT
YCSB-F50% GET、50% read-modify-update

客户端共有 6 × 31 = 186 个线程。每线程 GET queue depth 设为 32，对应最多 5,952 个 in-flight requests；INSERT 和 RANGE 的 queue depth 设为 18。DPA 侧默认使用 176 个 traverser threads（占用 11 个物理核心）和 4 个 stitcher threads；host 侧默认使用 4 个 patcher threads。DPA-Store 使用无连接的 UDP，而不是 Transmission Control Protocol（TCP）等面向连接的传输协议；论文没有报告 TCP connection 数，只报告 client threads 与请求队列深度。

长时间运行的 throughput benchmark（如 GET）取 4 次运行平均，短测试（如新 key INSERT）取 8 次运行平均；latency 由所有 client 收集后合并。各 client 通过 Message Passing Interface（MPI）同步启动。论文报告 throughput 标准差低于 5%，latency 标准差低于 9%。read-only workload 不会发出 patch request；论文因此称 host CPU 参与可忽略，但没有报告 host CPU 利用率百分比。

5.2 内存、写入与 ROLEX 对照

在 50M 条记录的内存评测中，使用 εinner = 4、εleaf = 8 时，索引额外开销随 key 分布变化：wiki 为 23%（147 MB），sparse 为 32%（207 MB），osmc 为 74%（472 MB），face 为 104%（672 MB）。为控制 osmc 和 face 的 metadata footprint，论文把这两个数据集的两个 error bound 都提高到 16；此时内存分别降至 228 MB 和 332 MB，更大的扫描窗口则会影响查询性能。

论文用 B+ tree 作为 lookup baseline：树构建为 2 KiB、每节点 128 个 entry 的满节点，节点内使用从中间开始的二分查找；B+ tree 与学习索引都使用 176 个 traverser。一般的 εinner = 4、εleaf = 8 配置下，学习索引在 sparse、sparseBig 和 amzn 上的 throughput 更高；osmc 为控制 metadata footprint 使用 εinner = εleaf = 16，一次要扫描约 32 个 key，因此 B+ tree 的 raw throughput 更高，但论文报告其中位 latency 仍略高。论文没有在文字中给出这些图示比较的具体差值。作者还用内存访问模型估算：深度为 3 的树在 εinner = 4、εleaf = 8 时需约 6.47 μs；176 个 traverser、相关 cache-line 均未缓存时，理论上限为 27.2 MOPS。若 root node 的首批 cache-line 留在 DPA subsystem 的 shared L3 cache，模型给出的上限为 31.05 MOPS。该模型是近似估算，实测结果与之相近；论文在 GET traverser 的预取优化中报告吞吐提高 19%，但未在该处指定数据集和 key 分布。

学习索引与 B+ 树 traversal 对比（Figure 12: Comparing B+ -tree and learned DPA traversals.）

写入代价主要出现在 INSERT 引起的结构变化。论文在 sparse、amzn、osmc 上测试 UPDATE、INSERT 及与 GET 混合的比例；其中 UPDATE-only 最高达到 12.1 MOPS，INSERT-only 最高为 1.7 MOPS。正文没有将两个峰值分别归到具体数据集。50M 条 sparse 数据的 bulk load 平均耗时 1,643 ms，其中 1,605 ms 用于复制和处理 stitch requests；192 MB tree data 写入 DPA memory 的带宽为 120 MB/s。改用 NVIDIA FlexIO 让 host 直接 push stitch payload 后，论文称 host-to-DPA throughput 与原方案相近、没有更高；正文没有报告两者的具体差值。

不同 GET/UPDATE/INSERT 比例下的吞吐与 p50 时延（Figure 13: DPA-Store performance of UPDATEs and INSERTs.）

换用 BlueField-3 B3220 的测试中，B3220 有双通道 DPA memory 和两个网络端口，DPA 核心数量与 B3140L 相同。在偏斜 GET-only 负载下，B3220 达 48.5 MOPS，B3140L 为 39.9 MOPS；均匀 sparse 访问的吞吐则几乎相同。该项测试用另一块 B3220 的 DPA 程序发请求，并对 B3140L 取消 in-flight request 数量限制以饱和吞吐；client card 算力不足以测 response latency。它不同于主评测的客户端 queue-depth 配置，因此 39.9 MOPS 不应与摘要的 33 MOPS 当成同一条件下的结果。

B3140L 与 B3220 上的 GET 吞吐（Figure 14: GET throughput for different BlueField-3 models.）

与 ROLEX 对比时，论文沿用相同硬件和软件栈，并用 uniform key distribution 降低 hot-entry cache 的影响。DPA-Store 在 amzn、osmc 上的 YCSB-A，以及所有 RANGE-only 测试中吞吐更高；GET-only 时，它在 sparse 和 amzn 上领先，ROLEX 在 osmc 上更快。ROLEX 的 INSERT-only 吞吐更高，因为 client 可用 one-sided RDMA 将新项写入 server buffer，并把模型重训分散到 client；DPA-Store 则由 host-to-DPA 回传承担结构更新。论文对 Figure 15 的文字总结是，DPA-Store 在这些测试中的 latency 低于 ROLEX；正文未给各项对比的数值差或聚合加速比。

DPA-Store 与 ROLEX 在不同 YCSB 负载下的吞吐和时延（Figure 15: YCSB workloads on sparse, amzn, and osmc datasets. Each of the three subplots shows the throughput and latency for all workloads as 2D scatter. Connected points represent DPA-Store’s and ROLEX’s performance for the same workload.）

这组结果表明，DPA-Store 用 DPA memory 访问和 host-side batch update 维持了有序 GET/RANGE 数据路径，也把学习索引状态留在 SmartNIC 与 host；读吞吐受 DPA memory latency 约束，INSERT throughput 受 host-to-DPA 写路径约束。
