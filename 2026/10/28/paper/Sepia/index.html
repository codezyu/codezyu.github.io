Sepia：面向 DDIO 的颜色感知页分配器

论文：When DDIO Meets Page Coloring: Revisiting DDIO Performance with Sepia（DDIO 指 Intel 的 Data Direct I/O；page coloring 对应「页着色」），Changwoo Song、Sanghyun Kim、Jinhyeok Oh、Qizhe Cai、Joonsung Kim、Jaehyun Hwang，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI ’26，2026）。USENIX 论文页。

TLDR： Linux 网络栈的 DDIO miss 不只由可用缓存空间不足造成。39 MB 的最后一级高速缓存（last-level cache，LLC）由多个 slice（缓存分片）组成，每个 slice 又分成 set（缓存组）；Linux 默认页分配会让页面地址在 slice/set 间分布不均，使映射到同一组位置的缓存行互相挤占而出现 conflict miss，工作集总量低于 LLC 也可能发生。Sepia 用 page coloring 构造每核颜色均衡的页池，并配合缩小接收环与 TCP 接收缓冲区的工作集。在双路 Xeon Gold 6354、ConnectX-6 200 Gbps 网卡、9000B MTU（maximum transmission unit，最大传输单元）、最多 6 条流的 iperf 长连接和 write-hit regime（写命中场景）下，Sepia 以总 CPU 利用率折算约 3.5 个满载核达到链路饱和，默认 Linux 需要 6 核；LLC miss rate 约 0.4%，总吞吐/CPU 利用率约为 Linux 的 1.51×。按 violation ratio（slice/set 映射超限比例）低于 1% 时可容纳的最大工作集定义 effective LLC size，实用方案 Stride-1 将其从 Linux 的 18 MB 提高到 32 MB；理论上界 Tetris 达到 35 MB，对应提升 77.8% 和 94.4%。

一、背景：DDIO 的接收页生命周期

Intel 的 Data Direct I/O（DDIO）让网卡（NIC）通过 DMA 将接收数据写入 LLC，CPU 随后处理数据时便可能直接从 LLC 读取，而不必从内存重新取回。Linux 接收路径为每个接收队列（Rx queue）维护接收环（Rx ring）和页池（page pool）：网卡按 ring descriptor 把数据写入对应页面；softIRQ（软中断）将已 DMA 的页面交给 socket buffer（skb，Linux 内核中的 packet 表示），同时从 page pool 为 ring 补充页面；网络处理结束后，页面再回到 page pool。处理过程也包括 copy-to-user，因此同一批页面会被网卡和 CPU 先后访问。

Rx ring 与 page pool 中的页面生命周期（Figure 1: Page lifecycle with Rx ring and page pool (N=new pages, D=DMAed pages): (a) the NIC DMAs incoming packets into the corresponding ring-buffer pages; (b) the softIRQ handler allocates skbs, detaches the DMAed pages from the Rx ring, and hands them off to the skbs; (c) consumed ring entries are replenished with new pages from the page pool; (d) after network processing (including data copy), the pages are returned to the page pool for reuse. See §2 for more details.）

DDIO 写入已有 LLC cache line 时会原位更新，这称为 write hit（写命中）；若对应地址不在 LLC，DDIO 才在预留的 cache way（缓存路）中分配新 line，这称为 write miss（写未命中）。测试机的 LLC 每个 set 有 12 个 way，DDIO 默认预留其中 2 个。CPU 读取页面时，只有 read miss（读未命中）才会把数据带入 LLC，新 line 可按替换策略放入任意 way。因此，只要工作集留在 LLC，CPU 读入的页面即使不在 DDIO 预留 way 中，后续 DDIO 写入仍可能命中它。后文把页面工作集留在整个 LLC、DDIO 写入多命中已有 line 的场景称为 write-hit regime；工作集或流量压力使 DDIO 需要在有限预留区分配新 line 的场景称为 write-miss regime。

Ice Lake 采用分片式 LLC（sliced LLC）。地址的 set index（组索引）与 tag bits（标记位）一起输入 slice-hash（选择 slice 的哈希函数），决定访问哪个 slice；之后由 set index 选中该 slice 中的 set。论文对测试 CPU 反向分析得到 26 个 slice、每个 slice 2048 个 set、12-way associativity，总 LLC 为 39 MB。

Intel Ice Lake 的 LLC 架构与物理地址映射（Figure 2: LLC architecture and physical address mapping for Intel Ice Lake. When address 0xC0 is accessed, the slice hash (from the full set of tag and set bits) maps the address to a slice (e.g., slice 25). Given a set index of 3, the access targets the cache line in set 3 of slice 25. See §2 for more details.）

二、现状：容量之外还有 conflict miss

论文用两台直连的物理机测量接收侧网络栈：每台机器配双路 Intel Xeon Gold 6354（3.0 GHz，每路 18 核）、每核 1.25 MB L2、39 MB LLC、256 GB DRAM，以及 NVIDIA ConnectX-6 200 Gbps 网卡；系统为 Ubuntu 20.04、Linux kernel 6.6。实验打开 TCP Segmentation Offload（TSO）、Generic Receive Offload（GRO）、9000B Jumbo Frames、Dynamically-Tuned Interrupt Moderation（DIM）和 accelerated Receive Flow Steering（aRFS），关闭超线程、IOMMU（I/O memory management unit）与 irqbalance。iperf 产生长连接 TCP 流量，每条流固定在一个核上。论文把 throughput-per-core 定义为总吞吐除以总 CPU 利用率，用它表示一个满载核可提供的吞吐；packet-occupied memory 则统计尚未处理完成的入站包占用量。

默认配置下，ConnectX 的 multi-packet work queue element（MPWQE）每个包含 64 个页面。Rx ring 有 1024 个 entry、MTU 为 9000B 时，驱动为每个 ring 配置 64 个 WQE，即每核约 16 MB descriptor 页面。单流还需要约 6 MB 页面来补充已交给 skb 的 descriptor，工作集合计约 22 MB。测试机的 DDIO 预留区为 12-way LLC 中的 2-way，按 39 MB × 2 / 12 估算约 6.5 MB。

默认 Linux 下，长连接从 1 条增至 6 条时，throughput-per-core 下降约 46%，LLC miss rate 升至约 60.4%。单流的约 22 MB 工作集对应 0.9% LLC miss rate；把单流 Rx ring 扩到 2048 个 entry（32 MB），总工作集约 38 MB，仍略低于 39 MB LLC，但 LLC miss rate 升到 16.5%，吞吐下降 11%。这说明工作集总量没超过 LLC，并不能保证页面在各个 slice/set 中分布均匀。

DDIO 下的 leaky DMA 性能（Figure 3: Leaky DMA performance with DDIO. (Default setting) Traditionally, the leaky DMA problem has been attributed to cases where the volume of incoming packets exceeds the DDIO capacity, causing packets stored in DDIO-reserved cache ways to be evicted before processing completes. This results in reduced throughput-per-core and increased LLC miss rates. (Throttling setting) However, throttling incoming traffic to stay within the DDIO capacity is insufficient to fully resolve the issue. See §3.2 for more details.）

把 TCP receive buffer 调小以压低 packet-occupied memory，也没有消除 miss。在 throttling 配置下，1 流和 2 流的页面工作集分别约为 22 MB 和 38 MB，都在 LLC 总容量以内，LLC miss rate 却分别为 0.9% 和 18%；多流下 LLC miss rate 最高仍达 46.4%。当 packet-occupied memory 超过 DDIO 预留容量时，DDIO write miss 会增多，新 cache line 只能在有限的预留 way 中分配，容量压力仍然存在；即使总工作集能放入整个 LLC，页面映射偏斜也会引发 conflict miss。

DDIO write behavior 与工作集大小（Figure 4: DDIO write behavior. (a) Limiting the number of available LLC ways increases DDIO write misses even in the single-flow case, indicating that DDIO write hits drive low LLC miss rates. (b–c) The write-hit regime can collapse even with working sets near the LLC capacity, raising LLC miss rates. See §3.2 for more details.）

为估计这种映射偏斜，作者记录物理页面地址并计算各页面映射到每个 slice/set 的访问数。若某个 slice/set 的映射数超过 12-way associativity，就记作一次 violation；violation ratio 是超限的 slice/set 组合占比。约 22 MB 工作集的 violation ratio 为 1.97%，约 38 MB 时升到 39.3%。该比例反映潜在冲突，不等于逐次 LLC miss：论文无法以可接受的开销精确记录每次 CPU 访问与驱逐的时间关系；作者报告 violation ratio 与实测 LLC miss rate 相关。

22 MB 与 38 MB 工作集下的 violation ratio（Figure 5: Violation ratio comparison (22MB vs. 38MB). For given page footprints: (a) when per-slice/set access counts stay at or below the violation threshold (i.e., ≤associativity), accesses are safe (blue bars), so evictions are unlikely; (b) counts above this threshold are violations (orange bars), indicating potential conflict misses and LLC underutilization. See §3.3 for more details.）

三、问题：默认页分配忽略 LLC 映射

Linux buddy allocator 不按 LLC 的 set index 或 slice-hash 分配物理页，因此 page working set 在 slice/set 间分布不均。测试 CPU 有 26 个 slice，slice 数不是 2 的幂；slice-hash 的 modulo bias 使连续物理地址也不能在各个 slice 上完全均匀。若过多活跃 cache line 映射到同一个 slice/set 并超过其 associativity，缓存会驱逐其中的 line，后续访问可能 miss。

单纯扩大 DDIO 预留 way 无法解决 write-hit regime 中已经存在的映射冲突；只限制 packet-occupied memory 也无法均衡 Rx descriptor 页面。论文因此把 page coloring 用于 DDIO 接收路径：分配时控制物理页进入哪些 set，并利用连续物理页的 slice 分布来减少 conflict miss。它与缩小工作集、限制流量的容量控制互补。

四、方案：用 page coloring 构造每核页池

4.1 Stride-1 与 Tetris 的页面映射

在 4 KB 页粒度下，物理地址的低 12 位是 page offset；论文测得 set index 与 block offset 共占 17 位，因此 set index 的高 5 位可用于分组。作者将内存划成 32 个 page group，每组对应 64 个 set。页着色以 page group 为单位，让每组分到相同数量的页；随后在每组内按物理地址递增顺序分配，以利用连续地址经 slice-hash 后倾向分散到不同 slice 的性质。

page group 的地址划分（Figure 6: Page group allocation. The set index and block offset fields span 17 bits in total. Of these, 12 bits are used as the 4KB page offset. Thus, five upper set index bits remain available for page grouping, which we refer to as the page group offset. Accordingly, the 2048 LLC sets in the system can be partitioned into 32 page groups, each consisting of 64 sets. See §4.1 for more details.）

这个实用顺序称为 Stride-1。它能平衡 page group 和 set 使用，但 26-slice 的非 2 次幂映射仍会留下 slice 偏斜。作者另构造 Tetris：先提取每个 page group 中不同的 slice/set 映射模式，再组合成更均衡的分配块。Tetris 用来估算页面粒度下可达到的上界；它依赖预先固定的精确顺序，而真实系统中页面回收时机不一致，会打乱该顺序，因此不适合作为在线分配策略。

默认分配与 Stride-1 的页面分布（Figure 7: Memory allocation behavior. (a) The default Linux buddy allocator ignores set indexing, resulting in uneven page distribution across page groups and set-level imbalance. (b) Stride-1 enforces set balance by allocating an equal number of pages to each of the 32 page groups. See §4.1 for more details.）

Tetris block 的构造与映射分布（Figure 8: Construction of a Tetris Block. First, unique slice/set mapping patterns are extracted from the physical memory space for each page group (e.g., PG 0). Then, these patterns are assembled (i.e., Tetris) into a Tetris block to maximize the balance of the slice/set mapping. However, due to the finite number of unique patterns, violations inevitably occur in the mapping distribution.）

4.2 Sepia 的每核着色页池

Sepia 是论文实现的 color-aware page allocator（颜色感知页分配器）。Sepia Manager 将连续物理内存建模为二维页面数组：纵向是 LLC 决定的 32 个 page group，横向是每组可分配的页面；同一组页面共享相同的颜色。作者选择每核独立 page pool，使每个核都能从全部 32 个 page group 分配页面，不必按活跃核数在共享池内重新分配颜色。Manager 还跟踪各页是否已回收可用。

Sepia Manager 构造 per-core page pool（Figure 11: Sepia Manager constructs per-core page pools, which is the right design that reduces working-set reconstruction overhead. See §4.3 for more details.）

Sepia Allocator 按 page group 顺序轮转，优先取该组中最早可用的页面。若轮到的页面尚未回收，它改取同组下一张可用页，以保持颜色顺序；某组暂时没有可用页时先跳过。Sepia page pool 用尽后会向 Linux 默认分配器取页，之后仍优先管理和复用已着色页面；随着负载降低、着色页被回收，颜色分配可以恢复。

Sepia Allocator 的轮转页选择（Figure 12: Sepia Allocator selects pages one by one from each page-group index, choosing the earliest page within the group. The numbers inside the pool illustrate an example allocation order. When previously unavailable pages are recycled, they become eligible for selection in subsequent rounds. See §4.3 for more details.）

原型基于 Linux kernel 6.6 和 ConnectX 驱动，并通过 Sepia API 与驱动衔接。实现用 Contiguous Memory Allocator（CMA）预留连续物理内存：每核 16 MB，其中 4 MB 用于 Rx ring、12 MB 用于 descriptor replenishment；18 个 DDIO-enabled 核合计预留 288 MB。论文希望将接口推广到其他网络驱动，但当前原型集成在 ConnectX 驱动中。

五、结果：有效容量与网络吞吐

5.1 有效 LLC 容量的测量口径

论文用 violation ratio 评估不同分配顺序能容纳多大的 page working set，并把 violation ratio 仍低于 1% 时的最大工作集定义为 effective LLC size。这是由 slice/set 映射分布得到的有效工作集容量指标，不是直接把 LLC 硬件容量改大，也不是单独测得的 LLC miss rate。

在 write-hit regime 下，默认 Linux 的 effective LLC size 为 18 MB（39 MB 总 LLC 的 46.2%）；Stride-1 提高到 32 MB（82.1%），比 Linux 高 77.8%；Tetris 达到 35 MB（89.7%），比 Linux 高 94.4%。Tetris 在 35 MB 时 violation ratio 为 0.04%，超过 35 MB 后则升至 9.43%。因此 94.4% 是页面映射的理论上界；Sepia 实际采用 Stride-1。

不同工作集大小下的 effective LLC size（Figure 9: Evaluation of effective LLC capacity. Comparison of violation ratio across working set sizes. We define the effective LLC size as the working set size at which the violation ratio remains negligible (< 1%) (Default: 18MB, Stride-1: 32MB, Tetris: 35MB (0.04%, not shown)). See §4.2 for more details.）

只看两条 DDIO way 时，着色收益会变小：Stride-1 的有效 DDIO 容量约 3 MB，占 6.5 MB 预留区的 46.2%；Tetris 可达到 5.5 MB、即 84.6%。有限的 DDIO associativity 没有足够余量容忍 slice 分布不均，不能把全 LLC 的容量结果直接当作 DDIO 预留区的容量结果。

slice/set 分布与 effective DDIO capacity（Figure 10: Comparison of slice/set distributions. (a) The effective DDIO capacity of Stride-1 is limited to 3MB (not shown), where the violation ratio remains 0%. (b) Tetris extends the effective DDIO capacity up to 5.5MB while maintaining a 0% violation ratio through optimized slice/set mapping. See §4.2 for more details.）

5.2 200 Gbps 链路与应用评测

为同时减少 capacity miss（工作集超过当前有效容量时的 miss）和 conflict miss，最佳写命中配置将每核 Rx ring 缩到 4 MB（ring size 256），并把每核 TCP receive buffer 设为 4 MB。测试中的 DIM 最多合并 128 个包，9000B MTU 下约 1.1 MB，ring 大小也保证被消耗的 entry 能在下一批 DMA 到达前补齐。该组合把工作集限制在 Stride-1 的有效 LLC 容量内。

在该测试平台最多 6 条流的 iperf 长连接中，Sepia 用总 CPU 利用率折算约 3.5 个满载核即可打满链路，默认 Linux 需要 6 核，少用 2.5 核；LLC miss rate 约为 0.4%。throughput-per-core（总吞吐除以总 CPU 利用率）最高约为默认 Linux 的 1.51×。两项指标分别衡量链路饱和所需的 CPU 利用量和单位核吞吐。

write-hit regime 下的链路饱和结果（Figure 13: DDIO write-hit regime: Sepia’s benefits are maximized as both capacity and conflict misses are avoided. (a) Sepia achieves up to 1.51× improvement in terms of throughput-per-core, compared to Default, reaching the link saturation (200Gbps) using (b) 2.5 fewer cores than Default, (c) while keeping near-zero LLC miss rates (∼0.4%). See §6.1 for more details.）

这组工作集由每核 Rx descriptor pages 和 packet-occupied memory 构成；前者按 4 MB/核随核数线性增长，后者增至 3 核时约 7.8 MB，链路趋于饱和后逐渐下降。论文图中，Stride-1 的 32 MB effective LLC size 可容纳最多 7 核的页面工作集。

write-hit regime 下的 Sepia 工作集（Figure 14: Sepia’s working set trend (write-hit regime). Our color-aware allocation expands the effective LLC capacity from 18MB to 32MB, accommodating the page working sets of up to 7 cores.）

工作集超过有效 LLC 容量后，capacity miss 无法避免；8–18 流的 write-miss regime 中，Sepia LLC miss rate 从 1.5% 增至 16.4%，说明着色不能替代工作集容量控制。

write-miss regime 下的性能（Figure 15: DDIO write-miss regime: Sepia’s benefits shrink as capacity misses become unavoidable. (a) Even in this worst-case scenario, Sepia still improves throughput-per-core, and (b) reduces LLC miss rates compared to Default. See §6.1 for more details.）

消融实验区分了着色与工作集控制的作用。Stride-1 单独使用时，throughput-per-core 平均提高 8.62%，最高提高 11.4%。4 流时，默认配置、仅加 Stride-1、仅缩小 Rx ring、Sepia 的内存带宽分别为 31.29、30.01、16.59 和 0.96 GB/s；Ring Throttling 单独把工作集变小，Stride-1 则让缓存位置分布更均匀。二者结合后，1–4 流配置的吞吐最高提高 50.8%。

Sepia 的性能分解（Figure 16: Sepia performance breakdown. This result indicates that Sepia’s color-aware allocation (together with Ring Throttling) allows the network stack to utilize the LLC more efficiently during DDIO. See §6.2 for more details.）

页面回收时序会影响颜色顺序。作者用较大的 TCP receive buffer 造成 page pool 耗尽，Linux 默认分配器补入的未着色页在 4 流时占 pool 的 35%，伴随 3.5% LLC miss rate 和 55 Gbps 总吞吐；1 流静态设置的吞吐为 64 Gbps。流量在 1 流与 4 流之间每 20 秒切换时，throughput trace 随着着色页重新可用而回升。

突发负载下的 Sepia 性能（Figure 17: Sepia performance under bursty workloads. (a) Page-pool exhaustion can introduce non-colored pages from the default allocator, increasing LLC miss rates. (b) Sepia quickly recovers once enough colored pages become available. See §6.3 for more details.）

端到端评测也显示工作集较大时收益更明显。

SPDK（论文描述为高性能用户态存储栈）的 NVMe-over-TCP 测试采用 64 KB 和 128 KB block、queue depth 16，Sepia 平均带宽最高分别提高 26.7% 和 51.1%。

SPDK 的 NVMe-over-TCP 平均带宽（Figure 18: Evaluation results with SPDK. Sepia achieves up to 1.27× and 1.51× improvements in average bandwidth over the default Linux with 64KB and 128KB block sizes, respectively.）

Nginx 用 wrk 发送 HTTP POST，2 MB 与 4 MB 页面负载下，上传带宽最高分别提高 20% 和 27.1%。

Nginx 的平均吞吐（Figure 19: Evaluation results with Nginx. Sepia achieves up to 1.2× and 1.27× improvements in average throughput over default Linux with 2MB and 4MB web page sizes, respectively.）

Memcached 使用 4 个固定在 4 个核上的 worker，比较 4 KB、64 KB、512 KB 和 1 MB value；4 KB value 下性能与默认 Linux 相当，512 KB 和 1 MB 时平均带宽最高提高 22% 和 25.9%。

Memcached 不同 value size 下的平均带宽（Figure 20: Evaluation results with Memcached. For workloads with limited DDIO benefit (e.g., 4KB values), Sepia matches the performance of default Linux. As the value size increases to 512KB and 1MB, where DDIO efficiency becomes more important, Sepia improves average bandwidth by up to 1.26× over default Linux.）

原型的页面池依赖 CPU 的 set index 位宽和 slice-hash 行为；论文称测试过 Xeon Gold 6354（Ice Lake）和 Xeon 6526Y（Emerald Rapids），但详细的 200 Gbps 主评测使用 Gold 6354。未来 CPU 可能需要重新分析地址映射；当多核流量使工作集超过有效 LLC 容量时，Sepia 的冲突 miss 优化也不能替代容量控制。
