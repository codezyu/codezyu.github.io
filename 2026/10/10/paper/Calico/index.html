论文：Making Array-Based Translation Practical for Modern, High-Performance Buffer Management
arXiv 2604.00423v1（2026 年 4 月）
作者：Xinjing Zhou（MIT CSAIL）、Jinming Hu（sea-land.ai）、Andrew Pavlo（CMU）、Michael Stonebraker（MIT CSAIL）
代码：PostgreSQL v18 上约 2600 行 C，pgvector 约 600 行

TLDR： Calico 把 buffer pool 的页号到页框的地址转换表从哈希换成数组，文件内块号直接作下标。收益的大头在淘汰不碰页表映射：数组转换本身只有 1.59×，累计 3.15× 里其余来自页框用大页（1.35×）、乐观读与批量预取。不需要 TLB shootdown，2MB 大页与 4KB 细粒度淘汰得以共存。

一、数据库的地址转换

页号到页框的地址转换表

数据库把数据按固定大小的页存在 SSD 上，PostgreSQL 默认 8KB。内存装不下全部数据，只缓存一部分。

缓存的那部分叫 buffer pool。它按页大小切成一批槽位，每个槽位记作一个页框。

上层组件手里只有逻辑页号（PID），没有内存地址——PostgreSQL 里一个 block 就是一个 8KB 页，块号就是页号。B+tree 内部页里写的是子节点的块号；索引叶子里存的是 (块号, 页内偏移)；HNSW（向量检索用的近邻图索引）节点的邻居数组里也是块号。磁盘上的持久化格式不可能存内存地址——进程一退出地址就失效，而且一次崩溃恢复后所有地址都变了。

页号换地址这件事只能每次现做。表里记着「哪一页现在在哪个页框」：

frameID 是槽位号，加基址算出地址。

这一步落在每次页访问的路径上。一次全表扫描扫 5GB、8KB 一页，就是约 65 万次转换。

PID 在 PostgreSQL 里是五段拼成的 BufferTag：

前四项唯一确定一个文件。Relation 就是一张表，存的是 relfilenode——一个随机分配的对象标识符（OID）；表删掉后这个 OID 可以复用，中间留空洞。Fork 是同名文件的用途分支——main 是表数据，fsm 是空闲空间映射，vm 是可见性映射，各有独立的块号序列。最后一项 BlockNumber 是该文件内的第几块，从 0 连续分配。

一个页在内存里的位置不固定。同一页这次读进来落在页框 5，被淘汰后下次读进来可能落在页框 12。所以「哪一页在哪」不能靠推算，只能记下来。

四类访问模式的地址转换要求

论文把现代 buffer pool 的访问模式分成四类。

顺序扫描（SS） 走连续的块号，比如堆表全扫、partition-based 向量检索。要求转换保留空间局部性，让硬件预取器提前发出请求。

范围扫描（RS） 先一小段依赖查找（B+tree 定位），然后顺序扫叶子页或 posting list。前半段和后半段的要求不同。

点查（PL） 是 B+tree 从根到叶的下降，每次访问的页取决于上一层读出的块号，无法提前知道。要求单次转换延迟低。

图遍历（GT） 是 HNSW 这类近邻图搜索。访问一个节点要探测它的全部邻居，论文测的图每个节点 44 个随机邻居。这 44 个邻居页号全在当前节点数据里，一次就能拿到。要求转换能并行——44 次转换互相独立，应该同时在途。

顺序扫描依赖局部性，图遍历依赖并行性，点查要求单次转换足够快。Calico 得同时处理这几种访问模式。

二、地址转换的设计空间

哈希表是生产系统的主流做法。PostgreSQL、MySQL、Oracle、SQLite、WiredTiger 都用它。它保住了 DBMS 对淘汰和 I/O 的控制，也不需要改内核。代价在定位方式：算哈希、定位桶、比较键、解引用，这几步串行。而且哈希函数把相邻页号散到不同桶，顺序扫描时预取失效。

论文测的顺序扫描：std::unordered 4.38 QPS，absl::flat_hash 5.67 QPS。

OS 页表路线把转换交给 MMU（CPU 里的内存管理单元），代表是 vmcache。它 mmap 一段匿名虚拟内存，大小对应存储容量；页装入用 pread，淘汰用 madvise(MADV_DONTNEED)。已经驻留的页查表靠 TLB 硬件加速。但它有一处结构性限制：DBMS 需要 4–32KB 的细粒度淘汰，而 2MB 大页对 TLB 效率重要。转换状态在硬件页表里时，OS 无法从一个已映射的 2MB 页里单独淘汰一个 4KB 子页，只能整个 2MB 淘汰、拆分大页、或者失败。所以它要在 4KB（细粒度淘汰、高 TLB 压力）和 2MB（低 TLB 压力、高 I/O 放大）里二选一。另外 madvise 淘汰要失效其他核的 TLB 项，触发 TLB shootdown，64 线程下成为同步瓶颈。要改善这些得改内核（vmcache 的 exmap、Tabby 的 libdbos），这条路有部署障碍。

pointer swizzling 把数据结构里的引用字段从块号换成直接指针，命中时一次解引用，完全跳过转换。LeanStore、Umbra 走这条路。问题在淘汰：一个 frame 被换出后，所有指向它的指针都悬空，必须找到全部引用点改写回块号。一页被多处引用时（图的多父节点、B+tree 叶子链、二级索引回链）引用点数量不定。Umbra 的做法是限制所有 buffer-managed 结构必须组织成树，保证每页恰由一个 owning swip（swizzled pointer）引用——代价是叶子页不能有 sibling 指针。

predictive translation（PrediCache）保留哈希表，但给每个页按 hash(pid) mod poolSize 预分配一个 preferred frame。访问时同时发起哈希查找和读 preferred frame，靠 CPU 的乱序执行重叠，用分支预测器判断预测是否成立。它在 B+tree 点查上能追平数组（0.93 Mops/s），因为根到叶路径可预测。但底层仍是哈希表，顺序扫描的局部性恢复不了，论文测它 4.67 QPS，比 absl::flat_hash 的 5.67 还低。

论文的落点是：没有一条同时满足全部约束。哈希表有 DBMS 控制但扫描和图遍历弱；页表方案快，但淘汰粒度受限；swizzling 快但对数据结构侵入且难支持图。

三、页号空间的障碍

Calico 回到最朴素的转换形式：让页号自己作数组下标，表项里存的就是 frameID。不用算哈希，没有碰撞，相邻块号落在相邻表项，查表这一步就是一次 load。

这个想法不新。1984 年 Effelsberg 和 Haerder 写过，生产系统没采用，障碍在页号空间：16TB 存储按 4KB 切是 40 亿个页，每页一个 8 字节表项就是 32GB 内存，而 PostgreSQL 的页号还是五段拼成的，relation 段是随机 OID。要动的是页号本身——这种既稀疏又分层的编号没法直接作数组下标。

目标是把转换做到一次 load，同时保住 DBMS 对淘汰和 I/O 的控制、不改内核、数据结构不用配合改写。这三样正是前面四条路线各自丢掉的东西。

四、基于数组的地址转换

Figure 2：Calico 的总体结构——上层映射表把页号前缀解析到末级翻译数组，64 位表项编码 frame ID、version 与 latch state，帧内存用大页承载，空洞回收计数数组管翻译数组的冷区（Calico Buffer Manager Architecture）

层级地址转换与路径缓存

不做处理的话数组不可行。Calico 的判断是：页号里有一段是稠密的。

前缀 <Tablespace, Database, Relation, Fork> 稀疏——它唯一确定一个文件，取值是随机 OID。后缀 BlockNumber 稠密——它是文件内的第几块，从 0 连续。这两个性质不同，应该分开处理。

页号的后缀就是下标：用前缀查一张上层映射表，拿到「这个文件对应的数组」的指针；用后缀在那个数组里作下标。

多级转换把上层查找重新放回热路径，每次访问就不止一次下标了。每个线程用 thread_local 存一对「最近一次的前缀，对应的数组指针」，这就是路径缓存：每次访问先比对前缀，相同就跳过上层查找，热路径只剩一次下标。

上层映射表可以用哈希表、B+tree、Trie 或数组，论文列举了这几种。实验里 PostgreSQL 集成用哈希表：有了路径缓存，它不在热路径上。

Figure 3：层级翻译与路径缓存的四步——查路径缓存；未命中则用前缀经上层索引（radix tree、哈希表、B+-tree 或 trie）拿到末级翻译数组；用后缀直接下标；回写缓存（Step-by-Step Hierarchical Translation with Path Caching）

命中率取决于访问是否集中在一个文件内。B+tree 遍历整棵树在一个文件里，HNSW 索引也在一个 relation 里，顺序扫描同样。论文报 pgvector 的路径缓存命中率接近 100%。

按需的数组内存管理

数组长度等于该文件最大块号 + 1，正比于文件大小。1TB 的文件按 8KB 一页是 1.34 亿个表项，虚拟尺寸 1.07GB。虚拟地址可以按文件大小划，物理内存不该跟着走。

转换表项是 64 位原子字：

字段位数含义
Frame ID32页框槽位号。0 是 INVALID_FRAME，非法值
Version24版本号。排他解锁时自增；淘汰时随表项一起写回 0
Latch State8latch 状态：Evicted、Unlocked、Locked 等

约定：全 64 位为 0 表示这页不在内存。三段同时取特定值——Frame ID 段为 INVALID_FRAME、latch state 为 Evicted、version 为 0。

这个约定的作用是让「从没被访问过的表项」和「已被淘汰的表项」编码相同。系统不需要区分这两种状态。页被淘汰时把表项写回全零，就回到这个状态。

有了这个不变式，转换数组用 mmap 预留虚拟地址、靠 OS 的共享零页支撑就成立了：

  • 线程第一次读某表项 → 触发缺页 → OS 建立到共享零页的只读映射。读到的值是 0，按约定正好是「不在内存」。这一步不分配物理内存。
  • 线程第一次写某表项（装入新 frameID）→ 触发写缺页（copy-on-write，COW）→ OS 分配一个 4KB 物理页，把零页内容拷进去。

所以分配粒度是 4KB，一个物理页装 512 个表项。从没被写过的表项永远停在共享零页上。

如果全零是非法值，系统就必须给每个表项写一次初值——那等于给每个表项分配物理内存，数组退化成实体数组。这个约定是数组可行的前提，不是优化。

零页写时复制只解决「从没写过的表项」，不解决「写过又被淘汰」。

一个表项被写过，那 4KB 物理页就已经分配了。即使这页后来被淘汰、表项写回零，那块物理内存还占着。没有回收机制，数组物理内存会随「曾访问过的页」单调增长，而不是跟着工作集。

Calico 加了一个计数器数组 HPArray。每 512 个表项（一个 OS 页）配一个 32 位原子计数器，记这一组里还有几个有效表项。

  • 页装入（缺页）：该组计数器原子加 1。
  • 页淘汰：原子减 1。减完为 0，说明这一组 512 个表项全是「已淘汰」，这一整页可以归还给 OS。

归还用 madvise(group_base_addr, 4096, MADV_DONTNEED)。还的是地址转换表的元数据内存，不动页框内存。

512M 个表项配 1M 个计数器，占 4MB；如果组按 2MB 大页划分，只要 2048 个计数器。计数器里保留 1 位作锁。

淘汰路径的加锁次序：

先拿到元数据计数器的锁，才释放表项的锁。这样并发缺页必须等元数据锁才能给计数器加 1，避免把新 frameID 装进正在被回收的页。对应的，缺页处理程序里先自增计数器、再发布 frameID。

buffer pool 算法

排他 pin 用 CAS（compare-and-swap）把表项从 Unlocked 转到 Locked，成功就返回页框指针——拿到这个指针，页在持有期间不会被淘汰。表项无效则走缺页处理程序。

排他 unpin 是一次原子操作：置 Unlocked 并自增 version。

乐观读是读路径上不加锁的版本：

version 只在排他 unpin 时自增，所以校验通过就意味着读的整个窗口内这页没被写、没被换出。校验失败就丢弃刚读到的内容重试。

「先读后校验」能成立，靠的是页框内存的映射在淘汰和重装之间不变——读那一刻即使这页正在被换出，读到的地址仍然合法，只是内容可能过时。

五、地址转换的实现

图遍历的转换彼此独立，要的是同时在途。Calico 提供批量预取（group prefetch）接口，接受页号数组和页内偏移数组，分三个阶段：

  1. 对每个页号算出表项地址，发 CPU prefetch，把转换表项调入 cache。
  2. 遍历，驻留的按页内偏移发页框预取（frame prefetch）；未驻留的收进列表。
  3. 列表非空就批量提交异步 I/O。

前两阶段是 CPU prefetch 指令，效果是把 cache line 调入 CPU cache，不产生 I/O。第三阶段是 I/O 预取，把多个页从 SSD 读进页框内存。接口名 calico_prefetch_group 把 CPU prefetch 和 I/O 预取这两种做法混在一起了。

同时暴露两种并行：驻留时是 memory-level parallelism（多个独立 load 同时在途），未驻留时是 I/O-level parallelism（多个异步 I/O 一起提交）。

六、地址转换的实验评测

收益的来源

论文在 DEEP10M 上做内存内 HNSW 消融，逐步叠加。

步骤吞吐增量
基线（absl::flat_hash）3.1 kQPS—
+ 数组转换4.91.59×
+ 页框用 2MB 大页6.71.35×
+ 乐观读7.7—
+ group prefetch9.8—

累计 3.15×。

Figure 11：消融——数组下标贡献最大（1.59×），随后大页、乐观读、预取依次叠加，相对基线合计 3.15×（Ablation Study (HNSW DEEP10M, 0.88 Recall@10)）

第一，把大页用在紧凑的转换数组本身没有额外收益，起作用的是页框内存用大页，降低的是页框访问的 TLB 压力——顺序扫描的 DTLB（数据 TLB）miss 从 vmcache（4KB）的 1.25/页降到 0.002/页。第二，这个 1.35× 是 Calico 自己的内部增益，不是相对哈希表的优势——哈希表版 buffer pool 同样是 DBMS 管理，页框内存同样能上大页。

论文把数组的优势归为「去掉依赖链」和「更高缓存密度」两条。数据支持第三条：空间局部性。

去掉依赖链。 哈希每次转换要走「算哈希 → 定位桶 → 读桶 → 比较键 → 取 frameID」，步骤串行。数组是一次 load。图遍历最能体现：42.0s → 15.5s（2.7×）。收益随 fan-out 缩放——B+tree 点查 fan-out 低，只从 0.67 升到 0.93（1.4×）。

空间局部性。 相邻块号落相邻表项，硬件预取恢复。顺序扫描 LLC（末级缓存）miss 从 2.53/页降到 1.33/页，QPS 从 5.67 到 30.3（5.3×）。

缓存密度。 数组一项只存 8 字节 frameID，页号隐含在下标里；哈希表每项要存键和值（16+ 字节）并维持 0.5–0.9 的装载因子。随机场景下没有局部性可利用，但 B+tree 点查的 LLC 引用（Ref）仍从 21.2 降到 12.5。

去掉依赖链和缓存密度这两条互相加强：去掉依赖但密度低，并行发出的 load 多在 miss 上浪费；密度高但依赖还在，访问仍一次等一次。

收益的大头不在数组本身，在淘汰不碰页表映射：淘汰时只改数组里的 Frame ID、把表项清零，不动操作系统的页表。页框内存的虚拟地址到物理地址映射在淘汰和重装之间保持不变。

其一，CPU 里已有的 TLB 项仍然有效，没有「失效某个映射」这个动作，也就不需要 TLB shootdown；vmcache 的 madvise 淘汰做不到这一点。

其二，2MB 大页和 4KB 细粒度淘汰能同时存在。vmcache 做不到——已映射的 2MB 页里无法干净地淘汰一个 4KB 子页。

抽掉这一环，Calico 只能退成两种：vmcache（2MB），有大页但丢了细粒度淘汰；vmcache（4KB），保住淘汰但要承受 shootdown。而这两条退路在数据全部驻留内存的场景下已经追上或超过 Calico。

对照与条件

PrediCache（SIGMOD 2026）是 Leis 团队的工作，作者也是 vmcache 和 LeanStore 的作者。它反驳「哈希表 buffer pool 无法高性能」这个前提，做法是保留哈希表、靠 preferred frame 让 CPU 投机重叠转换延迟。内存内 TPC-C 192 线程，它比 vmcache 高 34%、比 LeanStore 高 19%。

它自己给出的超内存结论是：128GB 内存池下，「traditional 哈希表实现取得与 SSD 优化设计相当的性能」，理由是 I/O 是超内存负载里最大的开销，转换开销可以忽略。这和 Calico 的数据一致——Calico 在 2GB 内存池下，数组转换和乐观读都只有 1.04–1.09×，增益主要来自 group prefetch。

回到地址转换这一层，两者并排看（Calico 论文的微基准，硬件不同，倍数不可直接并列）：

场景CalicoPrediCache
顺序扫描 QPS30.34.67
随机扫描 QPS9.783.78
B+tree 点查 Mops/s0.930.93
图 BFS（5M 节点）15.5s28.5s

Calico 在扫描和图遍历上领先，点查持平。高并发下 PrediCache 更强：它用乐观 latch 把哈希表的 192 线程吞吐提高了 7.4×，内联首 slot 在 192 线程又提高 18.6%；而 Calico 的 TPC-C 128 线程只比 vmcache 高 9%，64 线程 HNSW 的 53.2K 还低于 vmcache 的 55.5K。

PrediCache 可能对 Calico 提出的三条批评，每一条都能从 Calico 的论文里找到依据：Calico 的哈希基线是 std::unordered / absl::flat_hash，换成优化过的哈希，这项差距会收窄；Calico 的内存开销在论文 Table 1 里自标为 O(#storage pages)，与 vmcache 同类，TPC-C 上终值是哈希表的 1.89×；超内存领先 vmcache 的那部分，主要来自 group prefetch 的 I/O 批处理，而预取与转换结构正交，可以照搬。

反过来，Calico 对 PrediCache 的批评也有依据：它每页仍要 23.5 次 LLC reference、7.55 次 LLC miss；它的哈希表要 2× buffer pool 大小才能让链短（装载因子 50%），且不还给 OS；它预测依赖准确度，数据集 3× buffer pool 时只有 3% 的页在 preferred 位置。

上面所有倍数的条件：单线程或 64/128 线程、数据在内存内或按指定内存池、基线是 std::unordered 和 absl::flat_hash、硬件是 m7a.8xlarge（AMD EPYC 9R14）或双路 EPYC 7513。硬件、线程数、基线强度三处变了，倍数都会动。

收益归到哪一处跟着设定走：数据全在内存时在淘汰不碰页表映射，内存装不下时转到 group prefetch 的 I/O 批处理。

超内存的对比：Calico 比 vmcache 高 2.11×、比 USearch 高 5.99×。USearch 用 mmap 同步缺页，内存压力下线程阻塞等 I/O，内存池给到 1.5GB 时只有 189–222 QPS。

Figure 5：超内存的向量检索——64 线程、不同内存预算，Calico 比 vmcache 高 2.11×、比 USearch 高 5.99×（Vector Search (Larger-than-Memory)）

OLTP 侧的对照（YCSB-C、TPC-C）：内存内单线程 LeanStore 1.02M ops/s、Calico 935K，LeanStore 高 9%。TPC-C 128 线程 LeanStore 1.66M、Calico 1.65M、vmcache 1.51M txn/s。超内存 YCSB-C 在 6GB 时 Calico 1.17M txns/s，是 vmcache/LeanStore 的 1.6×。

转换内存开销：TPC-C 16GB 内存池回收 86.2%（1379/1600MB），终值 221MB；YCSB-D（read-latest）回收 95.7%，终值 68MB，比 vmcache 少 46.9×。哈希表是常数开销，136MB（16GB 池）和 1088MB（128GB 池）；vmcache 随库大小线性增长。

Figure 10：翻译内存开销——hole-punching 让翻译空间正比于工作集；哈希表恒定，vmcache 随库大小线性增长（Translation Memory Overhead）

一个反例是论文自己写的：YCSB-C 只读加 Zipfian 分布让热键遍布整个键空间，分不出连续的全零组，回收失效，转换内存全程稳定在 1209MB，论文把这称为 worst case。所以「转换内存正比于工作集」应改成「正比于被触碰过的连续页号区间」，对访问分布的聚类性敏感。
