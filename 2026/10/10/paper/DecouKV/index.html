论文：Mitigating Resource Usage Dependency in Sorting-based KV Stores on Hybrid Storage Devices via Operation Decoupling
USENIX ATC ‘25（2025 年 7 月，波士顿）
作者：Qingyang Zhang、Yongkun Li（中国科学技术大学），Yubiao Pan（华侨大学），Haoting Tang（中国科学技术大学），Yinlong Xu（中国科学技术大学、安徽省高性能计算重点实验室）
开源：https://github.com/QingyangZ/DecouKV

TLDR： LSM-tree 的 flush 要生成元数据再写盘，资源耦合在一个操作内，操作容易受到资源限制，导致其余资源闲置。DecouKV 把排序拆成索引归并、数据刷写两类任务分别调度，插入吞吐 4.3 倍。

一、要解决的问题

LSM-tree 的 KV 存储（RocksDB 等）靠 flush 和 compaction 两类排序操作管理数据。论文把它们在混合存储上拖慢写性能的原因归为三个耦合。

操作内部同时消耗 CPU 和 I/O。 flush 的序列化阶段要生成 Bloom filter、index block 等元数据，属于 CPU 密集；随后的写盘属于 I/O 密集。compaction 的归并排序属于 CPU 密集，读数据、写数据属于 I/O 密集。

Figure 2：一次排序内部的资源交织——CPU 密集段和 I/O 密集段绑在同一个操作里（Intertwined resource consumption within an operation）

操作之间相互触发。 层容量阈值固定，L(i-1)→Li 的排序让 Li 超出阈值，就被动触发 Li→L(i+1)。系统没有机会按当前资源余量选择在哪个层、什么时机排序。

Figure 3：操作之间的依赖——Li 超出阈值就顶出 Li→L(i+1)（Interdependencies among operations）

操作之间抢占资源。 多个层的排序同时进行，争抢同一份 CPU 和 I/O，排序效率下降，写停顿增多。

混合存储（快设备为 NVMe SSD 或 PM（persistent memory，论文也称 NVM），慢设备为 SATA SSD 或 HDD）把这三条放大。论文实测：快设备上做 compaction，CPU 时间占 60% 以上，CPU 是瓶颈；慢设备上 CPU 占比不到 30%，I/O 带宽是瓶颈。另一组实验向 100GB 的库导入 100GB 更新数据，取 200 秒窗口观察——排序落在快设备上时 CPU 利用率 94%、磁盘 48%；排序落在慢设备上时磁盘 88%、CPU 21%。两种利用率此起彼伏，平均值低。

Figure 4：RocksDB 在混合设备上的资源利用率——(a) 排序各占多少 CPU 时间，(b) 200 秒窗口内的波动（Resource utilization of RocksDB on hybrid devices）

二、已有方案为什么不够

论文把相关工作分成两类，各取一个代表做实测。

固定式差异化管理（MatrixKV）。 它把 L0 从 SSD 搬到 NVM（持久内存），用矩阵容器（matrix container）管理。矩阵容器由两部分组成：一个 receiver 和一个 compactor。DRAM 里 flush 下来的每个 MemTable 序列化成一行（RowTable）追加进 receiver；receiver 涨到容量上限（约容器的 60%）且 compactor 是空的时，它整体原地变成 compactor，同时新建一个 receiver 继续接收。

compactor 按「列」做 compaction，一列就是一个 key 区间，例如 key 落在 c 到 e 之间的那部分数据。做 compaction 时，它从各行中取出该 key 区间的项，与 L1 里 key 范围重叠的少量 SSTable 归并排序，写回 SSD，然后释放该列占用的 NVM 空间，再轮到下一个 key 区间。之所以这样切：L0 内各 SSTable 的 key 范围互相重叠，L0→L1 原本是全对全合并，一次要搬整个 L0——论文实测单次超过 15GB，是 RocksDB 的 4.86 倍，写停顿就出在这里。切成 key 区间后，单次搬运量降到由放大因子和 SSTable 大小界定的范围，compaction 还能与接收并发进行，单次写停顿变短。代价是同一个 key 的多个版本散在多行里，读要靠 cross-row hint search 跨行定位。论文给出的结果是 P99 延迟比 RocksDB 低 5×、比 NoveLSM 低 1.9×，随机写吞吐高 3.6× 和 2.6×。

论文的实验显示，它的资源利用率波动相比 RocksDB 降下来，但仍超过 50%。论文的判断是：细粒度 compaction 降低了每次操作的 CPU 和 I/O 消耗，部分缓解了操作内的资源交织，但操作间的依赖问题仍然存在，管理策略与波动的资源需求也仍然错配。

表面调度（ADOC）。 ADOC 把 LSM 的各组件（MemTable、immutable MemTable、L0、各层，以及快慢设备）看成一条数据流，把「某个组件里的数据积压」认定为写停顿的直接原因。它的做法是监测各组件的积压情况，动态调整线程数和 batch size，来控制 flush 与 compaction 在哪些组件、以多快的速率执行，把积压的数据尽快处理掉。

论文称它为「表面调度」（superficial scheduling），指的是它调的只是排序操作的频率、时机和位置（以及线程数、批量），而每次排序仍然是「读 + 归并排序 + 写」——CPU 和 I/O 仍绑在同一个操作里，资源竞争与交织没有改变。

在混合存储上的实测暴露了这个局限：快设备出现积压时，ADOC 给快设备多派排序线程、减少慢设备的线程，多线程争抢 CPU 使得 CPU 利用率升到接近 100%，磁盘利用率反而下降，CPU 瓶颈更重；反过来说慢设备积压时，磁盘利用率高而 CPU 低，I/O 瓶颈更重。瓶颈在两种状态间大幅交替，波动比 RocksDB 更明显。

Figure 5：已有方案的利用率波动——(a) 固定式差异化管理，(b) 表面调度（Resource utilization fluctuations of existing solutions）

它有两处表现不差：纯写负载（load）下 DecouKV 相对它只提升 1.6×，说明它确实压低了写停顿的发生频率；value 过大或过小时资源需求失衡、解耦收益下降，此时论文说 ADOC「靠调度平滑数据流，表现仍然良好」。

两类方案都没有触及「排序操作本身同时消耗两种资源」这一点，所以论文选择解耦。

三、DecouKV 的做法：解耦、调度与弹性容量

3.1 索引与数据分离

索引放 DRAM，数据放快设备上的追加写文件。原来一次排序里的两类工作被拆开，成为互不重叠的两类任务：CPU 密集的索引归并（只在内存里做，不涉及磁盘 I/O），I/O 密集的数据追加与刷写（不做排序）。

Figure 6：DecouKV 总览（DecouKV overview）

IndexTable。 可合并的跳表，条目只有 key、8 字节文件号和 8 字节偏移，不存 value，同样的内存能装下更多条目。初始容量 max_index_size 的设计值为 8MB，评测里设为 16MB。写满后转为不可变并新建一个，查询按从新到旧穿过各个 IndexTable。写入是异步的，不等数据落到快设备就返回。

AOF（append-only file）。 value 无序追加在快设备上。快设备随机读性能足够好，去掉 Bloom filter 后读性能受影响有限，换来的是省掉生成 Bloom filter 的 CPU 和缓存它的内存。原来的 WAL 也去掉了，故障恢复直接用 AOF 重建索引。

索引归并。 两个 IndexTable 合成一个，全程在 DRAM 内，用 CAS 无锁的 Merging Index Set 支持多线程并行归并。

数据刷写。 按 data_flush_trigger_size 触发，顺序扫 IndexTable、从 AOF 取数据、写进慢设备上有序的 SSTable。这一步有少量 CPU 开销，但瓶颈在 I/O，仍算 I/O 密集型。

3.2 两个队列与自动调参

Index Merge Queue 管索引归并，Data Flush Queue 管数据刷写。用队列长度比值判断当前瓶颈（L_IMQ、L_DFQ 分别是 Index Merge Queue 和 Data Flush Queue 的长度）：Score_IM = L_IMQ / IMTN（index merge trigger num，触发索引归并的阈值）超过 1.5 判为 CPU 受限，Score_DF = L_DFQ / DFTS（即上面的 data_flush_trigger_size）超过 3 判为 I/O 受限。

判定之后调参：CPU 受限就加大 IMTN（容纳更多待归并索引、降低归并频率）或减小 DFTS（把工作量推向 I/O 侧）；I/O 受限则反向操作。IMTN 每轮增减 2，DFTS 每轮乘除 2，都有上限。两个方向同时受限时接受写停顿；队列 60 秒不拥塞则判定空闲，同时降低 IMTN、DFTS 和层容量。评测中 IMTN 的最大取值只到 4，IndexTable 数不超过 6。

Figure 10：任务调度的控制流（Control flow of task scheduling）

3.3 弹性容量，但只到某一层

慢设备上的高层（HL，high level）容量做成弹性：放宽放大因子（默认 10），层间容量比一放大，每层的容量上限跟着抬高，Li 不再轻易超出阈值，层间的被动触发链被削弱；再配合 DFTS 控制写入 HL0（高层的第一层）的文件大小。论文明确说明解耦的边界：高层仍然使用 leveled compaction。原因是内存有限、慢设备随机访问性能差，高层无法套用低层的解耦设计，只能用弹性容量缓解。

四、利用率、吞吐与尾延迟

4.1 配置

服务器 2×20 核 Xeon Gold 5218R、128GB DRAM，Ubuntu 20.04.6、内核 5.15。快设备 128GB Intel Optane DCPMM 加 NVMe SSD，慢设备 960GB Intel S4520 SATA SSD。MemTable 与 SSTable 都设 64MB，Bloom filter 10 bit/key，block cache 1GB，4 个工作核加 4 个后台 compaction 线程，直连 I/O，快设备容量限制为数据集的 10%。

对照 RocksDB 9.3.0、MatrixKV、ADOC，部分场景另与 PrismDB、SplitDB 比较。微基准为插入 100GB、更新 100GB、读取 100GB（最大扫描长度 100）；YCSB 为 100GB 库上 1 亿次操作，KV 1KB（24B key、1000B value），uniform 与 zipfian 各跑一遍。

4.2 利用率与吞吐

1500 秒窗口内的平均 CPU 利用率（insert）：RocksDB 41.9%、MatrixKV 48.8%、ADOC 46.9%、DecouKV 74.2%；插入的 CPU 利用率波动区间从 RocksDB 的 76.8 降到 DecouKV 的 29.2。磁盘利用率插入提升 17.6–31.6%，更新提升 8.0–19.9%。

Figure 11：1500 秒窗口内的实时 CPU 利用率，黑虚线是平均值（CPU utilization over a 1500-second period）

吞吐（以 RocksDB 为基准）：插入 4.3×、更新 4.6×、读取 1.2×、扫描 1.5×；相对 MatrixKV 和 ADOC，插入为 1.6× 和 2.2×，更新为 2.2× 和 2.1×。平均延迟比 RocksDB 低 76.0%（insert）、77.9%（update），比 MatrixKV 和 ADOC 低 38.7–56.9%。

4.4 YCSB 与消融

写密集负载（load、YCSB-A、YCSB-F）比 RocksDB 提升 2.3–4.9×，比 MatrixKV 和 ADOC 提升 1.5–3.4×；读密集和扫描密集（B、C、D、E）提升 1.2–2.3×。zipfian 偏斜下 PrismDB 在写密集场景表现突出（快设备上的 in-place 更新），DecouKV 整体仍领先。

消融分三档：只解耦（DecouKV-D）、加调度（DecouKV-DS）、再加弹性容量（完整版）。load 负载主要靠调度策略获益，YCSB-A 上弹性容量的贡献更明显。

Figure 15：三档版本的归一化吞吐（Normalized throughput of different DecouKV versions）

4.5 其他场景

  • 500GB 库（5 亿 KV）：load、YCSB-A、YCSB-F 比 RocksDB 提升 5.2×、2.8×、2.4×。
  • Nutanix 生产负载（57% 更新、41% 读、2% 扫描）：提升 1.3–2.0×。
  • 只在 NVMe 上部署：仍有 1.4–2.4× 提升。
  • 内存：YCSB-A 下总计约 3.2GB，IndexTable 占 0.7GB（约 23%），TableCache 1.4GB，低于 RocksDB 的 1.56GB。
  • 恢复：10GB 库崩溃恢复 8.12 秒，RocksDB 为 8.76 秒。

五、思考

QA

  • value 极端或核数少时，为什么增益消失／有限？ value 到 16KB 以上时 CPU 和 I/O 同时饱和，没有可用的资源碎片；核数 2 时受 CPU 资源限制，16 核时不再增长则受制于磁盘 I/O。

Figure 18：value 大小与核数的影响（Performance impact of varying value sizes/core counts）

局限点

  • 快设备容量是硬约束，写到超限就接受写停顿，停顿位置从慢设备移到快设备容量上；update 的 CPU 利用率波动区间仍有 60.7。
  • 索引仍在全内存，容量上限由 DRAM 决定；论文只给出 0.7GB / 100GB 数据集这一个点，未讨论 key 数超过内存时的行为。
  • 去掉 WAL 之后的持久性边界：一次写何时算持久、崩溃会丢多长的窗口，论文没有结论，只给了恢复耗时。
  • 调度参数是启发式的，论文只说这些取值在实验中表现最好，没有稳定性或长期漂移数据。
