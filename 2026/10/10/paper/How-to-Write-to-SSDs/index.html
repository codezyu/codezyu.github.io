论文：How to Write to SSDs
PVLDB Vol. 19, No. 7（2026），pp. 1469–1483
作者：Bohyun Lee（慕尼黑工业大学）、Tobias Ziegler（TigerBeetle）、Viktor Leis（慕尼黑工业大学）
开源：https://github.com/Leebohyum/ZLeanStore

TLDR： SSD 的写入单元是 4 KB 的 page，擦除单元是 superblock（4–8 GB），page 只能写一次，覆写前必须先把所在的擦除单元擦掉。擦除要搬走单元里还活着的 page，这就是 SSD 写放大的来源（1/(1−v)）。B+ 树原地覆写，数据库决定不了写在哪；page 的失效时刻只有数据库知道，SSD 要等这个 page 真被改写才知道它没用了。两端放大因此相乘到 4.7 倍。方案是先把写换成追加、让 page 有失效时刻，再按失效时刻把 page 聚进 zone，让一批 zone 的总量对齐 SSD 的擦除单元。论文称这是首次在量产 SSD 上把 SSD 写放大做到 1。

一、背景：SSD 的擦除单元与写放大来源

1.1 写按 page，擦除按 block

NAND 的最小读写单元是 page，通常在 4 KB 到 16 KB 之间。若干个 page 组成一个 block，block 是擦除单元（一般由 128 到 1024 个 page 组成）。NAND 还有两条性质：

  • 一个 page 只能写一次，擦除之后才能再写。写入是往浮栅里注入电子（位从 1 变 0），擦除是把浮栅里的电子移出，存储单元才回到可写的状态。写入和擦除的单元不一样，原因是两者依赖的共享结构不同：写入靠字线选中一个 page，page 上的存储单元共用一根字线，能按 page 做；擦除要在整个 block 共用的阱区上加高电压，没法只给其中一个 page 单独加压，只能按 block 整块来。
  • 所以覆写在物理上做不到。主机要求改写某处数据时，SSD 只能把新数据写到别的空 page，把旧的那个标记为失效。

以上都还是 NAND 颗粒内部的单元。到了 SSD 这一层，擦除单元从颗粒内的 block 抬到 superblock。

SSD 内部按 主控 → 通道 → die（芯片）→ plane → block → page 分层。一个 block 只落在某一个 die 的某一个 plane 上，单独操作它只能用上这一个 die、这一个 plane；把跨 die、跨 plane 的 block 捆成一排、一起写一起擦，多个 die、多个 plane 才能同时工作，把 SSD 内部的并行度用满。这一排就是论文里的 superblock，实测常见 4 到 8 GB，是 SSD 对外的写入分配单元，也是 SSD 的擦除单元。

主机能看到的只有逻辑块地址，或者 ZNS（Zoned Namespace）SSD 报出的 zone、FDP（Flexible Data Placement）SSD 报出的回收单元（Reclaim Unit，RU，也就是 SSD 内部用于回收的擦除单元）。superblock 有几个、同时开几个、怎么分配，全在 SSD 内部，主机看不到。

1.2 回收复制有效 page，产生写放大

写入推进时，同一个 superblock 里会混着两类 page：已经被新版本取代的失效 page，和仍然有效的 page。空闲空间不足时，SSD 要回收：挑一个 superblock，把它里面还有效的 page 搬到别处，然后把整个 superblock 擦掉，变回一个可用的空 superblock。

搬这部分有效 page，是主机从未要求过的额外写入。设被挑中的 superblock 里有效 page 占比为 v，写放大（WAF，write amplification factor）就等于 1/(1−v)。论文举的例子：一个 8 个 page 的 superblock 里 6 个 page 有效（v = 0.75），主机要写 2 个 page 新数据，SSD 先搬走 6 个 page 再擦，物理写入 6 + 2 = 8 个 page，除以逻辑的 2 个 page，WAF = 4。v 等于 0 时 WAF 取下限 1：一个 page 都不用搬，整个 superblock 直接擦除。

1.3 数据库与 SSD 的写放大相乘

论文要解决的问题是：数据库逻辑上写 1 字节，NAND 上实际落盘约 4.7 字节。这 4.7 由两层相乘而来。

数据库这层是 2.0。原地覆写有写到一半掉电的风险（page 比 SSD 的原子写粒度大，SSD 只保证 512 B 或 4 KiB 粒度的原子写），所以数据库在覆写前先把整个 page 另写一份做保护，发出去的写量翻倍。论文测到 MySQL 每个 4 KiB page 的写落盘 70.22 KiB，PostgreSQL 67.98 KiB，LeanStore 原地写 18.85 KiB。前两者里约一半是这笔保护开销，LeanStore 的 18.85 KiB ≈ 4 KiB × 4.72，正好是两层放大的乘积。

SSD 这层是 2.36。论文用 OCP（Open Compute Project）遥测读 PM9A3 上物理写与逻辑写的比值，跑到稳态得到这个数。2.0 × 2.36 = 4.72。

Figure 1：每写一个 page 落多少 flash 写，以及吞吐（Flash writes per single page write and throughput）

分开优化会互相抵消。论文举的例子是 LSM：加大 tier 尺寸能压低数据库端的写放大，但占掉更多空间，SSD 内部回收时擦到的有效 page 比例上升，总账反而变差。反过来只优化 SSD 端，数据库还是发两倍的写。所以论文把两层的乘积立成目标函数，并把这个目标交给数据库来优化——它知道写什么、何时写、写在哪，SSD 和文件系统看不到上层的语义。

这种放大的后果落在 SSD 的寿命上。实验用的 PM9A3 标称 1 DWPD（drive writes per day）能用五年，折成平均写速是 11 MiB/s（11 MiB/s × 86400 s ≈ 950 GB，也就是这块 SSD 的容量量级）。实验里的持续写速是 400 MiB/s，超了三十多倍，SSD 撑到一个半月就到寿命终点。

二、现状：原地写给不出失效时刻、写量翻倍

论文改的是 LeanStore，一个原地覆写的 B 树引擎。原地写里，page ID 直接对应 SSD 上固定的偏移，更新写回原处。这个结构带来两个后果：写模式（写在哪、按什么顺序）由 SSD 决定，数据库调不了；而且因为覆写有写撕裂（torn write）风险，必须靠 doublewrite 保恢复，数据库端的写量翻倍——也就是 1.3 里数据库那层 2.0 的来源。

Figure 2：原地写与追加写，在磁盘与 SSD 上的四种组合（In-place vs. out-of-place writes on disk and SSD）

page 位置固定，也让「page 的失效时刻」这件事无从表达。一个 page 被改了就是被改了，旧内容当场消失，没有版本，也就没有「什么时候失效」这个问题。

三、优化点：写入单元与擦除单元对不上

搬有效 page 的唯一成因是「同一个擦除单元里住着失效时刻不同的数据」，而 SSD 自己不知道失效时刻，只能按到达顺序往当前单元里填。所以论文要动的地方可以一句话说清：让写在一起的数据，将来一起失效。

目标是把两端的放大从相乘改成对齐：SSD 内部回收时不再搬有效 page，写放大落到下限 1；数据库端也不必再靠 doublewrite 保恢复，写量不再翻倍。

要动到这一点，两边各缺一样东西。主机侧要有一个能指定落点、按失效时刻分组的写入单元。数据库侧要能给出每个 page 的失效时刻，也就是上一节缺的那一样。

四、方案：把 page 的失效时刻接到 SSD 的擦除单元上

4.1 前置改造：从原地写到追加写

改造的第一步是把原地写换成追加写：page 刷出内存时整个 page 写到新位置，page ID 到物理位置变成一对多的映射，由地址转换表维护，旧版本留给 GC（garbage collection）处理。这一步顺带消除了 doublewrite，因为旧版本永远还在，新版本写坏了丢掉就行。数据库端的写量因此减半。

代价是：地址转换表常驻内存，论文实测最坏情况多占约 11 GB；旧版本在回收前占着空间；恢复方式从保护性副本改成 WAL 重放加 page header 时间戳；另外多出一个 GC 组件，原地写时 page 位置复用、旧版本自动消失，追加写不行。

有了版本，「page 的失效时刻」才成为一个可以估计的量。

4.2 前置改造：用 LSN 外推失效时刻

论文给 page header 加一个字段，记录这个 page 被持久化时的 LSN（log sequence number），另外保留最近 n 次的时间戳历史（n 约 4）。预测的方法是外推：取最近两次刷盘的 LSN 之差当作这个 page 的更新周期，从当前的 LSN 加过去。

用 LSN 而不是挂钟时间，是因为它跟写入量绑定。机器空转的时候 LSN 不动，负载高的时候涨得快，而 page 的更新频率本来就与写入量相关，用 LSN 间隔比用秒数更能反映 page 的实际节奏。

这个字段记的是刷盘时刻，不是每次逻辑修改的时刻。论文的场景里缓存开得很小（只装数据集的 5% 到 20%），page 频繁被换出，刷盘频率接近修改频率，这个近似可以接受。

还没有写历史的新 page，按 B 树索引 ID 分组兜底，同一个索引的 page 访问模式相似，等攒够历史再切回按失效时刻走。

这些信息全在 page header 里，跟着 page 内容走。物理位置变了、被回收搬到别处时，历史一并带过去，重启后从 SSD 上读回 page 就恢复了，不需要另外维护一份全局状态。

4.3 主机侧：单元大小、一批总量、单一批次

主机侧因此引入几个新名词。空间被划成一段段连续区间，叫 zone，数据顺序追加进去，每个 zone 有一个平均 EDT（expected deathtime，预期失效时刻）。一个 page 落盘时，挑平均 EDT 最接近的那个活跃 zone 写进去。正在接收追加写的 zone 叫 active zone，一批 active zone 构成一个 active group。规则是当前这组 zone 全部写满之后才开新的一组，所以任何时刻只有一个 active group；同时打开的 zone 数有上限，实验里是 16 个。

要构造出和 SSD 的擦除单元对应的写入单元，需要三个要素同时成立。

单元大小要对得上。 一个 zone 有多大、同时开几个，乘积要等于 SSD 的擦除单元大小或者它的整数倍。论文的原话是 max open zones × zone size 等于或整数倍于推断出的单元大小。三个量里 zone size 先定，单元大小由 SSD 报出来或测出来，剩下的 zone 数由除法反解。对 FDP SSD 还有两条附加约束：zone size 取 RU 的大小，同时打开的 zone 数不超过 RU 句柄的数量。

Figure 6：zone size 与单元大小对得上（Zone size matches）

Figure 7：zone size 比单元小（Zone size is smaller）

一批的总量要对得上。 一批就是一个 active group 从开始到全部写满产生的写入量。这个量等于 zone 数乘以 zone size，必须是单元大小的整数倍，否则这批数据会跨在单元边界上，边界处混进下一批。实验里的配置是 16 × 512 MiB = 8 GB，对上一个推断出来的 8 GB 单元。

同一时刻只有一批在写。 这条靠「当前组没写满不开新组」保证。多个批次并发写入时，它们的写会在 SSD 里交错，散到不同的单元上，这是论文讲的 multiplexing。

单元大小从哪来？分三种情况：

  • ZNS SSD，zone size 由 SSD 报出，精确。
  • FDP SSD，回收单元大小由 SSD 报出，精确。论文实测的一块 SSD 报 8,496 MB。
  • 普通 SSD，没有接口。论文的办法是二分：把 zone 从 1 GB 一路加到 128 GB，观测 SSD 写放大何时首次降到 1，用那个阈值作为单元大小的近似上界。实测六款 SSD 大多落在 4 到 8 GB。论文建议工程上直接把 zone size 取 32 GB 兜底，宁大勿小。

上界够用，是因为它只需要挡住一种失败：zone 比单元小的时候，一个单元会由好几个不同寿命的 zone 拼起来。只要尺寸不小于单元，这种拼装就不成立。

4.4 主机侧：挑平均 EDT 最接近的 zone（GDT，Grouping by Death Time）

挑的时候是「最接近」，不是「必须相等」——这是最近邻选择，只要候选集非空就一定选得出来，不会卡住。没有活跃 zone，或者系统认为该开新的，就从空闲列表开一个，前提是没超过上限。

active group 不是预先配好的批次容器，是写的过程中长出来的：page 按驱逐节奏一个个来，每个 page 就近挑一个 zone 塞进去，zone 写满就退场，组里全退场了组才结束。所以「一批 8 GB」是跑到组终结时的产物，是结果不是前置条件。

分组质量的代价在于：page 的 EDT 分布越散，越容易塞进一个其实不贴近它的 zone，把那个 zone 的平均 EDT 方差顶大，簇内的数据就不再一起失效。论文的压制手段有三项：zone 的平均 EDT 随写入在线更新，早期失配会被后续拉回来；没有写历史的 page 先按索引 ID 分组，把冷启动期的方差压下去；最后是补偿写，事后处理。

组内两个 zone 的失效速率不同时，回收只能失效一部分，单元里就留下部分有效 page；失效进度均衡时，即使写入跨 zone 交错，SSD 也能产出有效 page 比例为 0 的单元。所以对一批 zone 的要求不是 EDT 相同，是失效进度均衡。

Figure 9：失效频率均衡——B、D 同步失效（Balanced frequency）

4.5 SSD 侧：ZNS、FDP 与普通 SSD

ZNS SSD。 把 zone 直接交给数据库，数据库自己按 zone 做逐出和刷新，SSD 内部不再回收，这部分放大整个消失。顺带拿回 SSD 自己留着的 7% 到 28% 的预留空间（OP）。论文的实测里，同样填充率下 ZNS 比普通 SSD 的收益，主要来自这部分多出来的可用容量。

FDP SSD。 给每个 zone 配一个 placement ID（PlID），取 zone ID 对 RU 句柄数取模得出，SSD 按 PlID 做物理隔离，不同寿命的流不会混进同一个回收单元。有了这个，NoWA（No Write Amplification）就不必要了。论文实测数据库端写放大从 0.57 降到 0.54，吞吐从 541K 到 553K OPS。

普通 SSD。 用 NoWA 写模式：始终留一个全空的回收单元，让 SSD 内部回收永远不触发。做法是两条规则，延迟开新组（当前组没写满就不开新的），以及检测并修正写流之间的频率失衡。失衡时用补偿写（compensation write）把短命的 page 重写到别的组，让被腾出来的那个组能整组作废。补偿写发生在 SSD 到达最小空闲阈值之前，而且 GC 在挑回收对象前会先检查「发补偿写会不会抬高后续轮次的有效 page 比例」，会的话就换一个 zone。

论文承认这条路不是严密保证：SSD 可能重排写入，有同时开放 superblock 的数量上限，有坏块，有磨损均衡。补偿写是把一部分写放大从 SSD 搬到了数据库端，论文实测数据库端写放大从 0.59 到 0.60。实测六款 SSD 上，SSD 写放大都做到了 1。

4.6 分支：压缩与 page 打包

压缩和 page 打包不针对 SSD 的擦除单元，但它们直接减少落盘的字节数。做法是每个 page 单独压，按 4 KiB 对齐打包，保证压缩 page 不跨读边界。

论文实测压缩后体量落在原数据的 14% 到 49%（LZ4 和 ZSTD 两种算法），800 GB 的数据集压到 418 GB。四款企业级 SSD 上 4 KiB 都是读延迟最低的粒度，而 3,000 字节的压缩 page 跨 4 KiB 边界会带来约 1.19 倍的读放大，打包之后消除。

数据量变小还带来一个间接好处：空间压力小了，回收时能挑到的有效 page 比例更低。论文实测这一项把 SSD 内部回收时的有效 page 比例从 75% 压到 14%。

五、结果：写放大与吞吐

5.1 硬件与负载

硬件是八款企业级 TLC NVMe SSD（五家厂商，容量 3.76 到 7.68 TB），两台服务器（96 核 EPYC 9654P 配 360 GB 内存，64 核 Xeon Gold 6342 配 500 GB 内存），Ubuntu 24.04。负载是 YCSB-A（50% 读 50% 更新，zipf 0.8）和 TPC-C（15,000 仓），数据集铺到 SSD 容量的九成，缓存只给数据集的 5% 到 20%。对照组是 MySQL 和 PostgreSQL，主要对照是作者自己的 LeanStore。

SSD 写放大用 OCP 遥测读物理写字节数，除以数据库发出的写字节数。

5.2 总写放大从 4.72 降到 0.60

八款 SSD 上，每次操作的闪存写入量降到原来的六分之一到十分之一。吞吐提高 1.65 到 2.24 倍，TPC-C 上提高 2.45 倍、写入量降低 7.2 倍。

总写放大：800 GB 数据集从 4.72 降到 0.60（7.8 倍），160 GB 数据集从 2.33 降到 0.53。原地写模式下实测的 SSD 写放大分布在 1.93 到 6.86 之间，优化后落到 0.56 到 1.00。

5.4 CPU、命中率与元数据开销

CPU 开销增加约 5%（这部分含压缩、打包和回收，不单是查表）。缓存命中率基本没动，从 93.2% 降到 91.8%。元数据内存最坏情况多占约 11 GB（地址转换表按每个 page 一条算）。

六、思考

QA

  • NoWA 是严密保证吗？ 不是。SSD 可能重排写入、有同时开放 superblock 的数量上限、有坏块、有磨损均衡，某次写入未必落到预期的单元里。实测残余量小到可以忽略，但机制上是概率性的。
  • 普通 SSD 上拿到的单元大小准吗？ 只是近似上界。论文建议直接取 32 GB——取大了浪费一点空间，取小了会混。
  • 追加写要付出什么？ 两处：SSD 用到九成满时，朴素的追加写会把数据库端写放大顶到 4.06，得靠按失效时刻分组才降回来；地址转换表常驻内存，最坏多占约 11 GB，内存紧张时论文说可以只留活跃部分、其余落盘，但留给未来工作。

局限点

  • 共享的 SSD 没有处理。论文的实验是直连裸设备，不走文件系统，别的进程和文件系统的写都被排除了。SSD 被别的写者插入，主机侧的 zone 边界和 SSD 内部的单元边界就对不上。
  • 多写流的隔离在普通 SSD 上做不到严格。主机侧的 zone 隔离不等于 SSD 内部的单元隔离，普通 SSD 上没有 RU 句柄可用，只能靠限制同时活跃的组数和补偿写事后修正。
  • 活跃 zone 的上限固定（实验里 16），而 page 的失效时刻种类数没有上限。超过上限时，page 找不到失效时刻接近的 zone，只能塞进最近的，靠补偿写兜。
  • 组内失效均衡是要求，不是保证。补偿写只修某个 zone 失效进度落后，减不了种类数。
  • RAID 没有涉及。这套东西要求数据库直接管理 SSD，而且 SSD 要能报出或被测出单元大小。硬件 RAID 通常把这两个条件都挡住。
