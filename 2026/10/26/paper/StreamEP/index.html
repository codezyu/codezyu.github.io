StreamEP：移除 MoE 解码的集体通信屏障，应对慢链路与落后 GPU

论文：StreamEP: Straggler-Tolerant MoE Decoding without Communication Barriers，Yizhuo Liang、Shaoyu Wang（共同一作）、Jaeyong Song、Yanqi Zhou、Geon-Woo Kim、Guangrong He、Seo Jin Park，SOSP ’26（2026）。论文：DOI 10.1145/3830418.3843869。

TLDR： 专家并行（EP）的每层集体通信须等待最慢 GPU 或链路，使局部迟滞变成全局停顿。StreamEP 保留专家放置，改为按 token 到达异步推进；StreamInfer 用微队列和去碎片调度聚拢批次。在 16×L40S 与 16×A100（200 Gbps）集群上，吞吐最高较传统 EP 提升 1.7%；双向全链路干扰下，StreamInfer 吞吐近乎稳定而 EP 下降约 24%。

一、背景：MoE 解码与 EP

MoE（Mixture-of-Experts，混合专家）模型按 token 路由，每个 token 只激活少数 expert（专家网络）。模型参数规模可以超过单张 GPU 的显存，因此服务时要把不同 expert 分配到多张 GPU。专家并行（expert parallelism，EP）让每张 GPU 保存一部分 expert，token 按路由结果发送到持有目标 expert 的 GPU，再把计算结果送回原来的数据并行 rank。

解码时，GPU 需要从显存读取被激活 expert 的权重，token 批次的大小影响计算相对内存访问的强度。EP 能让各 GPU 对路由到本地的 token 执行完整 expert 矩阵运算，维持较高的算术强度；但每一层的 token 路由和结果返回都要跨 GPU 交换数据。

解码服务需要为活动请求保留键值缓存（KV cache），显存容量因此限制并发请求数。

一个 MoE Transformer 层包含 attention、router（路由器）和分布在多个 GPU 上的 expert。Router 为每个 token 选择 top-K 个 expert；dispatch 把 token 发送到目标 expert 所在 GPU，expert 计算完成后，combine 将结果送回 token 原属的 rank 并按 gating 权重合并。

MoE 层通过路由把 token 分发给不同 GPU 上的 expert，再合并计算结果（Figure 3: An MoE transformer layer: each token is routed to a subset of experts by a learned gating function. Expert parallelism distributes experts across devices; tokens are exchanged via barrier-style collectives before and after expert computation. Every device must wait at the barrier before executing the next layer.）

二、现状：EP 集体通信

传统 EP 在每个 MoE 层执行 dispatch 和 combine 集体通信：前者把 token 分发到目标 expert，后者把 expert 计算结果合并并送回原 token rank。实现通常使用 all-to-all，或先 all-gather、再 all-reduce。所有 GPU 都必须等待整批交换完成才能继续；论文把单条慢链路或进度落后的 GPU 称为 straggler，任一 straggler 都可能让其他 GPU 停在集体通信屏障上。

Barrier EP 中所有 GPU 等待慢链路；StreamEP 将 token 放入各自队列并独立调度（Figure 1: Barrier EP (a) vs. StreamEP (b), with identical expert placement and a straggling link on GPU 2 marked in pink. Red frames mark the module each GPU is currently executing. (a) Blocking Dispatch/Combine collectives run in lockstep, so every GPU stalls behind the straggler. (b) Outputs stream over async P2P into per-layer μ-queues, whose fill shows the tokens waiting in each. The scheduler on each GPU continuously picks a queue to drain and execute without waiting for the full batch.）

普通 GPU 集群还要应对异构和共享的通信路径：节点内可能混用 PCIe 与 NVLink，节点间网卡也可能由多张 GPU 共享；即使 expert 放置方案尽量平衡计算负载，不同 rank 对之间的待传 token 数仍可能不同，多租户网络上的短时拥塞也会改变链路速率。论文在一组 8 节点、16 GPU、每节点 200 Gbps RoCE（RDMA over Converged Ethernet，以太网上的 RDMA）的集群上测量 NCCL（NVIDIA Collective Communications Library，GPU 通信库）all-to-all 的首个、中位和最后 peer 消息到达时间。256 KB 到 1 MB 的消息对应 GPT-OSS-120B 在这套集群上产生的单 peer 消息大小。

NCCL all-to-all 中首个、中位和最后 peer 消息的到达时间（Figure 2: First peer, median, and last peer message arrival times inside an instrumented NCCL all-to-all collective on an 8-node, 16-GPU cluster with 200 Gbps RoCE on each node. More data is shown in §A. Sizes from 256 KB to 1 MB are about the per-peer message sizes GPT-OSS-120B generates in this cluster.）

现有优化尝试隐藏通信耗时，但仍保留每个微批次（micro-batch）的集体通信屏障。Two-batch overlapping（TBO）把一个批次拆成两个微批次，一批计算时另一批通信；tile 级内核融合则在更细粒度上交错传输与计算。两者都只能隐藏部分通信，慢传输仍会阻止当前批次继续推进。部分融合方案还依赖 Hopper GPU 或 NVLink 等硬件，难以覆盖使用 A100、L40S 和普通网络的集群。

TBO 在两个微批次之间交错通信与计算（Figure 11: Two-batch overlap execution flow that interleaves communication and computation across two micro-batches.）

三、问题：屏障与异步管理

3.1 集体屏障放大全局等待

在普通集群的异构或共享链路、rank 间流量偏斜和短时拥塞下，最慢参与者决定每层 dispatch/combine 的完成时刻，局部 straggler 因而阻塞所有 GPU。论文报告，这道集体通信屏障在这类集群上可占每个 MoE 层执行时间的最高 75%。解码并发受 KV cache 显存容量限制，不能靠无限扩大批次来摊薄等待；结果是每层吞吐都受最慢链路或设备牵制。

3.2 异步到达打乱层级执行

取消整批同步后，同一逻辑批次中的 token 会从不同 GPU、在不同时间到达，层级执行顺序也不再由全局边界确定。每张 GPU 必须独立识别 token 身份和目标层，再决定执行顺序；这种层级异步执行本身需要额外的状态管理。

3.3 批次碎片化和重组开销

同一逻辑批次被拆到多个层队列后，会形成许多小批次，降低每次执行的算术强度。简单调度策略也有两难：most-token-first-serve（MTFS）总选当前 token 最多的队列，仍会把工作散布到多层；first-layer-first-serve（FLFS）优先最早层，但高请求率下新请求可能持续获得优先处理，令已有请求无法推进并陷入 livelock（活锁）。与此同时，token 张量分散在 GPU 显存中，attention 需要各请求的 context length 和 KV page-table 索引，top-K expert 输出也可能分时到达。重组这些数据会产生主机与 GPU 间的元数据传输及 GPU 内存管理开销，paged attention 下尤其明显。

3.4 变长 P2P 与 NCCL 的匹配限制

异步调度下，任意 GPU 都可能随时向任意 peer 发送大小不同的 token 批次。NCCL 的点对点（P2P）接口要求发送端和接收端同时发起匹配操作，接收端还要预先知道源 rank 和 tensor 大小；消息目的地与尺寸都在运行时变化时，不能直接按常规方式启动传输。

四、方案：StreamInfer 实现 StreamEP

4.1 StreamEP 按到达推进

针对全局停顿，StreamEP 将每层 dispatch/combine 集体通信改为异步点对点转发，同时保留 EP 的 expert 放置方式。每张 GPU 收到部分 token 后即可执行当前可运行的 attention 或 expert 层，并在结果就绪后继续转发；慢链路只延迟经由它传输的 token，不再阻塞其他 GPU。

传统 EP 与 StreamEP 的单 rank 执行时间线（Figure 4: Demonstration of a single rank’s execution timeline for three consecutive layers under (a) barrier EP and (b) StreamEP.）

这改变了系统的推进粒度：GPU 不必等待完整批次，而是在部分 token 到达后就启动计算；计算期间陆续到达的 token 留在队列里，形成后续批次。算力成为瓶颈时，队列有时间积累更多 token；通信成为瓶颈时，GPU 可以用较小批次更早推进，减少集体通信屏障造成的等待。由于解码并发受键值缓存（KV cache）显存容量限制，单纯扩大批次并不可行，降低每步等待时间也有助于提高吞吐。

4.2 微队列和路由元数据

为管理异步到达的 token，StreamInfer 将控制面和数据面分开：全局协调器管理请求生命周期、attention 数据并行 rank 的负载均衡和集群状态；每张 GPU 运行一个 StreamEP engine，独立接收其他 GPU 的 token 并继续执行。token 张量始终留在 GPU 显存中并通过 NCCL 直传，CPU 只处理路由、队列和张量引用等元数据。

StreamInfer 由全局协调器和每 GPU 的 StreamEP engine 组成（Figure 5: System architecture of StreamInfer. Each GPU runs a StreamEP engine with μ-queues, a defragmenting scheduler, an executor, and a communicator. The global coordinator manages requests and load balancing across engines.）

每个 engine 为模型的每一层维护两个微队列（μ-queue）：一个存放等待 attention 的 token，一个存放等待 expert 计算的 token，因此共有 2L 个队列。token 的 RequestID 用来在异步到达和重排后识别请求；LayerID 记录目标层、attention 数据并行 rank 和 expert 编号。attention rank 在 token 生命周期内保持不变，让 token 回到持有其 KV cache 的 GPU；expert 编号在 router 完成选择前为空。

CPU 侧 token 元数据，以及 LayerID 中的目标层、attention rank 和 expert 编号（Figure 6: Token metadata tracked on the CPU. LayerID encodes the target layer as <layer#> | <attn. DP rank> | <expert#>.）

一个 token 在 engine 内经过五步：receptor（接收器）接收其他 GPU 发来的数据，并将 token 放进对应层的 attention 或 expert 微队列；GPU 空闲时由调度器选择一个队列；executor（执行器）把分散的张量 gather（聚集）成连续批次并启动 GPU 内核；最后 dispatcher（分发器）更新 token 的下一层目标并转发。若模型使用 top-K 路由，K 份 expert 输出可以先后到达；系统按 RequestID 和 LayerID 暂存部分结果，待 K 份都到齐后再合并。

token 在 StreamEP engine 内经过接收、排队、调度、批次重组、计算和转发（Figure 7: Token execution flow within a StreamEP engine (with request 37 as an example). 1 Receive dispatched tokens from other GPUs. 2 Stream to layer-specific μ-queues (attention or expert) based on LayerID. 3 Select the optimal task via the defragmenting scheduler. 4 Perform batch reformation and launch GPU kernels. 5 Relabel output tokens with next-layer destinations and forward.）

4.3 去碎片调度器聚拢批次

微队列能按目标层保存待执行 token，但不决定 GPU 空闲时先运行哪个队列。为避免批次继续碎片化、同时保证已有请求能前进，StreamInfer 使用去碎片调度器。

调度器给候选队列打分：当前队列深度加上沿后续执行链计算的加权队列量，并把最近若干步已经取走的 token 计入估计，以反映其他 GPU 上仍在途的 token。它沿活跃执行波前聚拢批次，同时暂缓远离波前的小碎片；这样既避免 MTFS 把执行散布到多层，也避免 FLFS 持续优先新请求导致活锁。

MTFS 将执行分散到多层，去碎片调度器则沿单一活跃波前聚拢批次（Figure 8: μ-queue depth over time under the two scheduling policies. (a) MTFS scatters tokens across many layers simultaneously, producing fragmented small-batch executions. (b) StreamInfer’s defragmenting scheduler keeps execution concentrated in a single frontier wave that sweeps the layers. For visibility, we only show a subset of layers.）

4.4 批次重组与开销隐藏

调度器选好队列后，executor 仍要解决数据不连续的问题。传统 EP 的集体通信按固定顺序交付整批 token，输入通常连续；异步到达的 StreamEP token 则分散在 GPU 显存中，启动计算前必须先 gather 成连续输入。attention 还要整理 context length 和 paged attention 的 KV page-table 索引。对于 top-K 路由，receptor 按 RequestID 和 LayerID 保存分时到达的 expert 输出；收到 K 份后，重组 kernel 再 gather 并按 gating 权重合并，减少逐 token 操作和 kernel launch。

批次重组会增加 CPU 元数据处理和 CPU/GPU 传输。StreamInfer 在 GPU 计算当前微批次时，让 CPU 调度并准备下一批，再用 GDRCopy 传递小块元数据；GPU 完成当前计算后即可运行下一批的重组与计算 kernel。attention 阶段 router 产生的 gating 索引和 expert 分配结果会复制回 CPU，供 dispatcher 设置 token 的下一目的地；这些后处理也与后续准备重叠。

GPU 计算当前微批次时，CPU 准备下一批并处理前序结果（Figure 9: Batch reformation overhead hiding. While the GPU computes μ-Batch i−1, the CPU schedules and prepares μ-Batch i, and GDRCopy transfers post-processing data for μ-Batch i−2 and metadata for μ-Batch i in parallel.）

4.5 两阶段 NCCL 点对点通信

为在普通 NCCL 上承接变长点对点消息，StreamInfer 把传输拆成两阶段。第一阶段由 CPU 消息队列发送源 rank、tensor 数量和各 tensor 大小，接收端据此分配 buffer；第二阶段由两端在专用 GPU stream 上启动 NCCL send/receive。启动后 CPU 继续处理下一条传输，接收端只在把数据交给 receptor 前与 GPU 同步，发送端则在回收 buffer、限制并发 send 时检查完成状态。独立的发送和接收线程避免分布式死锁；整个协议不依赖 IBGDA 或 NVSHMEM。

第一阶段交换元数据并分配 buffer，第二阶段通过 NCCL 传输 tensor（Figure 10: Two-phase communication protocol. Phase 1 exchanges lightweight metadata via the message queue on the CPU to coordinate buffer allocation. Phase 2 transfers tensor data via NCCL on the GPU.）

五、结果：吞吐与干扰

5.1 吞吐、并发与网络干扰

评测使用两个 16 GPU 集群：Sphere 有 8 台服务器，每台 2 张 L40S，节点内通过 PCIe 连接，两张 GPU 共享 200 Gbps RoCE 网卡；Delta 有 4 台服务器，每台 4 张 A100，节点内使用 NVLink，每台服务器配一张 200 Gbps Cray Slingshot 网卡。论文以 bfloat16（BF16）运行 GPT-OSS-120B 和 GLM-4.5-Air，在 ShareGPT 与 GSM8k 工作负载上评测，并与 SGLang 的 EP、pipeline parallelism（PP）× tensor parallelism（TP）、两副本 EP（EP×DP，每个副本使用半数 GPU）和 EP-TBO 比较。主吞吐结果取系统达到最大可持续并发后的峰值 60 秒窗口；由于被测 SGLang 配置不支持在 pre-Hopper GPU 上运行 TBO，EP-TBO 数字是按理想重叠上界投影的结果。

在 Sphere 上，StreamInfer 对 ShareGPT 和 GSM8k 分别达到 36K 和 40K tokens/s；传统 EP 为 21K 和 28K tokens/s，StreamInfer 分别快 1.7× 和 1.4×。相对理想投影的 EP-TBO，StreamInfer 仍分别快 1.4× 和 1.1×。在 Delta 上，StreamInfer 分别达到 25K 和 31K tokens/s，比 EP 快 1.3× 和 1.5×。Sphere 的 PCIe 与共享网卡让更多链路可能成为瓶颈；Delta 的节点内 NVLink 和较少的跨节点网卡跳数减轻了通信限制，因此两套集群的相对收益不同。

两个普通 GPU 集群上的解码吞吐对比，EP-TBO 的斜线部分为理想重叠投影（Figure 12: Decoding throughput comparison of StreamInfer on two resource-constrained clusters. For EP-TBO, the crosshatched segment represents the improvement attributed to projection.）

论文另作一组逐步提高请求到达率的吞吐—时延扫描，按 ShareGPT 和 GSM8k 分别报告结果（原文在该节未重述模型与集群配置）。EP 在两种工作负载上的吞吐约在 14K tokens/s 封顶；继续提高请求率会推高 token 间时延（inter-token latency，ITL）。StreamInfer 的吞吐前沿在 ShareGPT 达 26K、GSM8k 达 25K tokens/s。该扫描同时记录各请求率下的平均 ITL。

请求到达率变化时的吞吐与 ITL 工作点（Figure 13: Throughput–ITL trade-off experiments.）

对 GPT-OSS-120B 的 ShareGPT 工作负载，论文还改变在途请求数并比较 EP 与 StreamInfer 的吞吐；每个实验点均标出产生该点的请求到达率。

GPT-OSS-120B 在 ShareGPT 上的并发吞吐，各点标注对应请求到达率（Figure 14: Decoding throughput against concurrency, the number of requests in flight, for GPT-OSS-120B on ShareGPT. Each point is annotated with the offered request rate that produced it.）

StreamInfer 的固定调度与批次重组开销会随批次增大而更容易被摊薄。对 KV cache 占用较高的 GLM-4.5-Air，46 层完整模型并发较低，StreamInfer 的吞吐优势最高约 1.2×；把层数减半到 23 层以释放显存、将最大并发大致翻倍后，优势扩大到 ShareGPT 1.3×、GSM8k 1.4×。

GLM-4.5-Air 完整和减半层数模型的吞吐对比（Figure 15: Throughput of StreamInfer and SGLang EP on GLM-4.5-Air with full and halved layers on Sphere.）

网络干扰实验回放 AWS 集群带宽轨迹，中位带宽为 185.1 Gbps。干扰依次覆盖单条节点间链路、单链路双倍流量、所有链路和双向全链路，平均背景流量仅占总带宽的 7.5%。双向全链路干扰使 EP 吞吐下降约 24%；StreamInfer 在这些场景下的吞吐保持近乎稳定，因为慢链路只影响承载的 token，不再通过集体通信屏障拖慢所有 GPU。

AWS 带宽轨迹、干扰场景下的吞吐对比及吞吐—ITL 工作点（Figure 16: Network variability tolerance. (a) Bandwidth trace from an AWS cluster (median 185.1 Gbps) [35]. (b) Throughput comparison of SGLang EP and StreamInfer under progressively severe interference scenarios. (c) Throughput–ITL operating points under each scenario, showing that StreamInfer’s operating point remains tightly clustered while SGLang EP shifts toward lower throughput and higher ITL.）

消融实验以 MTFS 为基线；加入去碎片调度器后，吞吐提高 3.2×。在此基础上再加入批次重组优化和 CPU/GPU 重叠，吞吐进一步提高 4.5%。

去碎片调度及批次重组优化的消融结果（Figure 17: Ablation experiments of StreamInfer.）

5.2 端到端时间投影

端到端结果是根据一批共 5,000 个请求投影的：作者在 SGLang 将提示词预填充（prefill）产生的 KV cache 卸载到 Mooncake 外部 KV cache 服务时测量 prefill 用时，再用论文前文测得的解码吞吐估算总完成时间；原文未注明采用的具体吞吐测量点。ShareGPT 的输入/输出 token 数为 174/435，prefill 用时 12.4 秒，EP 与 StreamInfer 的总时间分别为 171 秒和 96 秒；GSM8k 的输入/输出 token 数为 137/287，prefill 用时 8.8 秒，总时间分别为 111 秒和 66 秒。StreamInfer 的投影时间分别约为 EP 的 0.56 倍和 0.59 倍，与论文概括的约 1.7× 加速相符。
