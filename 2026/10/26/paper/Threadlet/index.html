Threadlet：面向微秒级计算的硬件线程抽象

论文：Computation Is Fast, Use Threadlet! Efficient Threading for µs-Scale Computing via OS/Hardware Co-Design，Yiming Yao 等，SOSP 2026。DOI：10.1145/3830418.3843863。

TLDR： 微秒级负载中，分离线程模型四类开销为 0.60–1.52 µs。threadlet 将可调度执行单位交给硬件，让切换、调度和通知走硬件路径，同时保留操作系统策略。四核周期精确模拟中，LoomOS 键值存储吞吐较 Shinjuku、Linux 轮询和 Shenango 分别高 3.4、47、8.25 倍。

一、背景：微秒级负载中的线程需求

CPU、内存和 I/O 设备的性能提升，使更多工作负载的计算时长进入微秒级。数据中心网络要把请求派发给工作线程，并在长请求执行时优先处理短请求；请求稀少时，数据中心还会把尽力而为任务放在同一组核上。并发控制、微服务调度、系统调用和微内核进程间通信也依赖快速切换或唤醒。

论文评测的网络负载中，两类通知最高约每秒 90 万次；峰值时平均上下文切换间隔为 5.5 µs。

二、现状：分离线程模型及其替代方案

传统处理器把核暴露为计算资源，操作系统把带有完整状态的软件线程多路复用到核上。硬件看不到软件线程，因此切换线程需要保存、恢复寄存器，操作系统还要决定下一个运行者；线程间通知要经过内核状态更新和调度，设备到线程通知通常要经过中断处理。这形成上下文切换、调度、线程间通知和设备到线程通知四类开销。

论文在 Intel Xeon Silver 4216、Ubuntu 24.04.2 和 Linux 6.12.20 上测量这四类开销。上下文切换与调度微基准在一个核上运行 64 个线程，各空转 5 µs 后让出核；线程间通知测量等待锁线程的唤醒时间；设备到线程通知测量 Linux 网卡中断路径。四类延迟为 0.60–1.52 µs。

当前线程模型四类开销的分解；T-T 指线程间通知，D-T 指设备到线程通知（Figure 2: Overhead breakdown of the four inefficiencies in the current threading model.）

用户态线程和协程可以绕过内核调度。协作式切换减少了需要保存的状态，但依赖任务主动让出；不合作的任务可能饿死其他任务，阻塞操作和长任务还需改写异步路径或插入让出点。自定义用户态调度器也可缩短决策路径，却常采用较简单的策略，难以保留 Linux 默认的 EEVDF（Earliest Eligible Virtual Deadline First，最早合格虚拟截止期优先）中的历史 CPU 使用量、按权重公平分配和突发偏置。

轮询通过反复检查数据状态发现变化，延迟低但持续占用处理器；它通常要独占核才能保持及时，共享核时可能不如中断。先自旋再阻塞（spin-then-park）则依赖启发式规则，规则失准时会浪费 CPU。

已有硬件方案也没有覆盖全部开销。把线程状态换入内存仍要在寄存器与内存间搬运数据；扩大寄存器文件能增加硬件上下文，但会增加面积、功耗和访问延迟，而且只能容纳少量上下文；硬件调度器若固化策略，也难以适配目标负载以外的系统。

三、问题：切换、调度、规模与通知的约束

3.1 上下文切换与策略保真

在一个核上，基线的上下文切换为 0.60 µs，调度为 1.02 µs；Linux EEVDF 的线程描述符更新耗时 0.3 µs，红黑树访问和更新耗时 0.6 µs。微秒级请求可能需要抢占长任务，切换路径不能依赖任务自愿让出；同时，减少调度决策开销也不能把 Linux 的公平性语义简化为固定的 round-robin 或优先级规则。待解问题是缩短状态保存与调度决策，同时保留可抢占性和策略表达能力。

3.2 512 个线程的状态与排序成本

Google 数据中心平均每核运行 50 个线程，部分场景接近 500 个，因而 Loom 以每核支持 512 个 threadlet 为目标。若把所有完整上下文都放进寄存器文件，访问延迟和面积会随容量上升；若每次都比较 512 个 threadlet，调度逻辑的延迟、面积和功耗也会过高。

DeathStarBench 的测量显示，并发总数与可运行数并不相同：测试在四核上按泊松（Poisson）分布发送每秒 1 万个请求，每 100 µs 采样一次，并把观测到的最大线程数作为总线程数。平均可运行线程数占总线程数的 1.5%–1.9%，采样到的最大可运行线程数占 5.2%–15.4%。因此，问题是怎样支持 512 个线程，同时避免把每个上下文都放进快速寄存器路径或逐个全局比较。

寄存器文件访问代价与微服务线程活动；左图由 CACTI 存储结构建模工具估算（Figure 5: Left: Register file access latency and area vs. threadlet count, as reported by CACTI [52]. Each threadlet uses 32 general-purpose registers using 22 nm technology node. Right: Average and maximum numbers of runnable and total threads in DeathStar-Bench, running on 4 cores; we sample every 100 µs.）

3.3 通知延迟与处理器利用率

线程间通知和设备到线程通知经由内核状态更新、调度或中断路径；在 Linux 测试中，前者为 1.52 µs，后者为 1.46 µs。轮询可以快速发现数据，但独占核时无法同时服务其他任务，共享核时又会增加等待。问题是如何在设备 I/O 完成或线程间状态变化后及时唤醒对应线程，同时让阻塞线程释放的核可供其他任务使用。

四、方案：threadlet、Loom 与 LoomOS 协同

论文把软件线程在硬件中的可调度执行单位称为 threadlet；Loom 是支持该抽象的处理器架构，LoomOS 是基于 Loom 构建的操作系统。Loom 让硬件直接切换 threadlet、按其调度元数据选择下一线程，并通过缓存一致性事件唤醒对应 threadlet。操作系统负责创建和删除 threadlet、维护复杂调度策略和系统服务。

传统线程模型与 Loom 的对比（Figure 1: A comparison of conventional threading model and Loom.）

4.1 threadlet 执行上下文压缩

针对上下文切换的状态搬运，threadlet 保留所有通用寄存器，以及程序计数器（program counter，PC）、栈指针（stack pointer，SP）、页表基址寄存器（page table base register，PTBR）和特权级等关键控制状态。调度元数据只保留可运行或阻塞状态、优先级、截止期和时间片；这些字段选自 Linux 约 700 字节的线程调度结构。

浮点和向量寄存器、调试寄存器及性能计数器不属于 threadlet 的独立状态，而由同一核上的线程共享。线程使用这些状态时，先通过特权指令取得所有权，使用后再释放，由操作系统负责虚拟化。这样，已加载 threadlet 之间切换时可直接恢复寄存器文件中的状态，避免在寄存器和内存间搬运完整上下文。

4.2 三元组映射与调度快慢路径

为缩短调度决策又保留策略弹性，Loom 在可配置的调度周期（默认 32 个周期）以及当前 threadlet 让出、阻塞或结束时执行调度。每个 threadlet 携带优先级、截止期和时间片：硬件先选优先级最高者，同优先级时选截止期最早者；没有截止期时按轮转顺序选择。FIFO（先入先出）、轮转和最早截止期优先可以直接用这三个参数表达，硬件快路径因此不必运行完整的软件策略。

三元组不能独立表达所有复杂策略。Loom 用调度 threadlet 作为软件慢路径，在创建、唤醒等事件后把操作系统策略映射到三元组。Linux EEVDF 的虚拟运行时间和虚拟截止期用于计算 threadlet 参数，再交给硬件快路径选择；虚拟截止期和按权重分配的时间片都能映射到相应字段，因此 EEVDF 只需相对少量慢路径更新。若某策略与三元组不匹配，慢路径调用会更频繁，这是硬件快路径保留策略灵活性所付出的代价。

4.3 threadlet 排名与异步暂存机制

为每核支持 512 个 threadlet 而不把全部状态放进寄存器文件，Loom 只保存 8 个已加载状态，另设一个暂存位置保存已加载集合之外排名最高的 threadlet；其余上下文留在内存层级。

Loom 架构概览（Figure 4: An overview of Loom.）

控制器依据可运行状态、优先级、截止期和轮转指针距离排序，利用上节的调度语义预载最可能运行的 threadlet，而不是使用 LRU（least recently used，最近最少使用）策略。已加载集合通过比较选择树决定下一线程，最多两周期完成。暂存 threadlet 是第 9 名；当卸载线程晋升或已加载线程降级时，控制器先比较暂存项并异步交换，不让这次状态搬运阻塞已加载线程的执行和调度。

如果一个未加载 threadlet 晋升，控制器仍需从未加载集合中寻找最高排名者，再与暂存项比较；该扫描在后台执行。论文给出的例子中，64 个未加载 threadlet 的扫描耗时 128 个周期。这样，Loom 避免在常用调度路径上比较全部 512 个线程，扫描成本则由异步换入承担。

4.4 基于地址监控的内存通知机制

针对两类通知，threadlet 通过 tlet_monitor 登记待监视的内存地址，再通过 tlet_wait 让出核并阻塞。等待路径先检查标志、登记地址，再检查一次；论文指出，这两次检查处理 tlet_monitor 后、tlet_wait 前发生的写入，避免漏掉唤醒。

Loom 在每核地址监控表（address monitor table，MAT）记录地址及 threadlet 标识，并监听缓存一致性消息。其他线程或设备写入该地址所在缓存行时，失效消息会使 MAT 找到对应 threadlet 并唤醒它。网卡通过直接内存访问（direct memory access，DMA）更新接收队列描述符也能触发同一条路径。线程因此可以阻塞并让出核，不必持续轮询。

调度线程触发事件与内存通知接口；MWAIT/MONITOR 是 x86 的监视与等待指令（Figure 3: Left: Events that trigger the scheduling threadlet. Right: Pseudocode for threadlet’s memory notification interface. We note that this interface is similar to x86’s MWAIT/MONITOR.）

这条路径仍可能误唤醒：若被监视缓存行因替换而驱逐，Loom 也会唤醒对应 threadlet。论文按 SPEC CPU2017 的缓存流量估算，在 3 GHz、每周期指令数（instructions per cycle，IPC）为 1 的假设下，1 MiB 二级缓存约每 0.7 ms 被新数据填满一次；论文据此认为替换导致的误唤醒频率不高，对微秒级 threadlet 不频繁。

4.5 LoomOS 的系统路径集成

LoomOS 用专门指令创建、删除 threadlet，修改调度参数、改变可运行状态并登记监视地址。每核一个事件 threadlet 合并调度线程和传统中断处理线程；它始终保持最高优先级并驻留在寄存器文件中，占用 8 个已加载位置之一，其他用途可用其余 7 个位置。现代网卡使用地址监控快路径；不支持该机制的设备走事件 threadlet 的传统中断慢路径。

网络运行时由专用网络 threadlet 接收网卡队列并派发请求，工作 threadlet 通过共享内存和地址监控等待新请求。工作 threadlet 的优先级高于尽力而为任务，时间片为 5 µs；处理长请求期间，Loom 会在时间片耗尽时抢占当前工作 threadlet，让其他工作 threadlet 运行。没有请求时，阻塞中的工作 threadlet 已让出核，处理器可运行尽力而为任务。锁等待 threadlet 监视锁变量并阻塞；系统调用采用委派路径，由用户态和内核态 threadlet 经共享内存传递参数与结果，地址监控让等待方阻塞而非忙等，使 LoomOS 获得委派处理的收益而不浪费 CPU。

Loom 硬件没有跨核迁移 threadlet 的机制。LoomOS 仍按核负载、CPU 亲和性和硬件拓扑分配线程；若某核用完 512 个 threadlet 槽位，操作系统会在目标核创建新 threadlet、复制架构状态和调度参数，再删除原 threadlet。

五、结果：微基准与系统负载

论文在 Xilinx VCU118 上用周期精确 FireSim 模拟器评测 Loom。目标是四核、五级流水、顺序单发射 Rocket，配置 16 KB 一级指令和数据缓存、512 KB 共享二级缓存和 16 GB 动态随机存取存储器（DRAM）；Linux 对照版本为 6.6.0。Loom 也在现场可编程门阵列（FPGA）上实现原型。

5.1 微基准中的开销与扩展性

上下文切换测试在一个核上创建 8 个 Linux 线程或 LoomOS threadlet，各空转 10 µs 后让出核。LoomOS 用 17 个周期完成一次切换，Linux 为 728 个周期；已加载状态驻留寄存器文件，因此无需搬运上下文。在 8 个 threadlet 的 EEVDF 测试中，硬件选择耗时 20 个周期，调度 threadlet 的策略维护摊销为每次 72 个周期，总计 92 个周期，较 Linux 的 2,315 个周期低 25 倍。

线程间通知测试把等待者和发送者放在不同核，等待者监视地址；设备通知测试由网卡更新 DMA 完成位。线程间通知在 LoomOS、轮询和处理器间中断（inter-processor interrupt，IPI）下分别耗时 73、36 和 6,201 个周期；设备到线程通知在 LoomOS、轮询和设备中断下分别耗时 82、40 和 1,312 个周期。相较 IPI 和设备中断，LoomOS 两类通知最高分别快 84.9 倍和 16 倍。

上下文切换、调度与通知开销（Figure 7: Context switching, scheduling, and notification overhead. Lower is better.）

在 2、4、8 个 threadlet 的调度测试中，增加 threadlet 数量不改变 LoomOS 的硬件调度开销。8 个 threadlet 时，LoomOS 每秒完成 9.92 万次调度，是 Linux 的 1.34 倍，调度开销占比从 22% 降至 0.8%。

多线程调度结果（Figure 8: Results of multithreaded scheduling. Left: Overhead, lower is better; Right: Throughput, higher is better.）

晋升测试在单核上运行 32–512 个可运行 threadlet，进行 1,000 次随机排名提升；被提升的 threadlet 执行 0.5 µs 空转循环。512 个 threadlet 时，晋升到执行的平均延迟为 0.50 µs，p99（99 百分位）为 0.56 µs。唤醒测试重放 DeathStarBench 轨迹，同样在单核上放置 32–512 个 threadlet；每个 threadlet 空转 0.5 µs 后休眠，再按采集的唤醒间隔分布重放。512 个 threadlet 时，从唤醒到执行的平均延迟为 0.7 µs，p99 为 2.1 µs。

5.2 系统负载的收益与实现成本

网络评测使用四个核。LoomOS、Shinjuku 和 Shenango 各用一个核处理网络、三个核运行应用；LoomOS 每个应用核运行 8 个工作 threadlet，Shinjuku 和 Shenango 每个工作核运行一个线程；Linux 用 NAPI（网卡收包轮询机制）收包，NanoPU 用四个核运行应用并在硬件中处理网络。论文未在 NanoPU 丢包最多的负载上列出其结果。

工作负载包括双峰服务、重尾服务和简化自 LMDB（Lightning Memory-Mapped Database，内存映射数据库）的键值存储。双峰请求时长一半为 1 µs、一半为 100 µs；重尾负载 99.5% 为 1 µs，0.5% 为 100 µs；LMDB 负载含 99.5% GET（键查找）和 0.5% SCAN（范围扫描），SCAN 约比 GET 慢 1,000 倍。双峰负载下，LoomOS 的最大吞吐分别为 Shinjuku、Linux 轮询和 Shenango 的 1.3、1.5、1.3 倍；重尾负载为 3.5、53.1、6.5 倍；LMDB 负载的吞吐分别为 3.4、47.0、8.25 倍。53.1 倍对应合成重尾负载对 Linux 轮询；47 倍对应简化 LMDB 负载。

网络性能（Figure 10: Networking performance. Subfigures (a–c) compare LoomOS with networking baselines in different benchmarks. Subfigure (d) shows the networking scalability of LoomOS. NanoPU is omitted from workloads on which it loses most packets.）

将网络任务与每个核一个空转的尽力而为任务共置后，Linux 和 Shenango 的网络尾延迟随请求吞吐上升。在 p99 延迟为 10 µs 的点上，LoomOS 达到每秒 60 万个请求，同时保留尽力而为任务单独运行时 37% 的吞吐。

延迟敏感（LC）任务与尽力而为（BE）任务的共置性能（Figure 11: The performance of task co-location. (a) The tail latency and throughput of the LC task and (b) BE-task throughput versus request throughput. Note that the X-axis is in log scale.）

每个工作核配置 4、8 或 16 个工作 threadlet 时，网络最大吞吐变化小于 10%。

网络性能对工作 threadlet 数量的敏感性（Figure 12: Sensitivity of networking performance with 4, 8, and 16 worker threadlets per worker core.）

阻塞锁评测使用四个核、一个共享锁、32 个线程或 threadlet，临界区为 10 µs。对照是 Linux 内核互斥锁、Argobots 阻塞锁和 MCS-B（MCS 锁的阻塞版本）。LoomOS 的平均等待延迟分别比三者低 28.5、17.1 和 26.5 倍，吞吐分别为三者的 2.17、1.67 和 1.93 倍。

共享锁性能（Figure 13: Lock performance with one shared lock and a 10 µs critical section. (a) Throughput; higher is better. (b) Latency; lower is better.）

四核、四线程的锁交接分解中，LoomOS 每次交接耗时 277 个周期，40.1% 的总延迟花在解锁以外的操作上。

系统调用测试用共享内存传递参数与结果，由用户态和内核态 threadlet 委派处理，减少同步陷入和双方忙等。LoomOS 的用户到内核、内核到用户两段延迟分别为 125 和 156 个周期，合计 281；传统 Linux 为 316 和 206 个周期，合计 522，LoomOS 低 46.2%。Linux 轮询版为 97 和 133 个周期，合计 230，LoomOS 比它多 51 个周期；LoomOS 的主要剩余开销是共享内存读写。

Loom 每核片上存储约 5.8 KB：寄存器文件增加 1.8 KB，线程策略表占 1.2 KB，地址监控表占 2.8 KB。Vivado 报告片上功耗增加 5%，关键路径仍在 Rocket 的数据 TLB（data translation lookaside buffer，DTLB）和一级数据缓存访问逻辑；LoomOS 实现 9,517 行代码。
