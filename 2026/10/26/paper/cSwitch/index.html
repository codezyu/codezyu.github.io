cSwitch：面向 I/O Chiplet Wall 的 Linux 线程调度

论文：Scheduling Linux Threads under I/O Chiplet Wall Using cSwitch，Seunghyun An、Joontaek Oh、Ming Liu，Association for Computing Machinery（ACM）Symposium on Operating Systems Principles（SOSP）2026。数字对象标识符（DOI）：10.1145/3830418.3843889。实现：cSwitch。

TLDR： 芯粒处理器将内存和设备流量汇入共享 I/O chiplet 与片外互连；动态争用使 CPU 空闲度和拓扑亲近度不能代表到内存或设备的可用路径带宽。cSwitch 用 I/O 芯粒负载映射（I/O Chiplet Loading Map）和芯粒流量标签（Chiplet Traffic Label）估计通道负载并关联线程请求流（cFlow），再按加权最大最小公平份额调节超额 cFlow 对应线程的请求注入速率；若限速后入口仍拥塞，则迁移对拥塞贡献较大的线程。cSwitch 将需要协同执行的线程组合为协同流量组（MegaCFlow），再由 cFlow 调度器按组调度。在关闭 SMT 和 Turbo Boost 的 AMD EPYC 9634 上，12 个应用的 I/O chiplet 负载评测中相对 EEVDF 加速 1.2–2.7×；负载升高时，PageRank 比 Caladan+ 快 3.9×。

一、背景：芯粒处理器的共享片外路径

1.1 芯粒处理器的片外资源互连架构

芯粒处理器把 CPU 核心和缓存分布在多个计算 chiplet（compute chiplet，CC），并将内存控制器、相干路由和 PCIe（Peripheral Component Interconnect Express）等系统接口集中到 I/O chiplet。AMD EPYC 9634 有 12 个计算 chiplet，每个包含 7 个 CPU 核心，并由一个 I/O chiplet 汇接内存与设备接口。

访问片外资源时，请求从计算 chiplet 经 CC–I/O 链路、封装内互连和跨芯粒接口进入 I/O chiplet，再到达 DRAM（动态随机存取存储器）、CXL（Compute Express Link，计算快速互连接口）内存或设备。封装中介层（interposer）上的互连网络称为 NoI（network-on-interposer，芯粒间封装互连网络）；计算 chiplet 内部还通过 NoC（network-on-chip，片上网络）转发请求。内存、设备以及部分芯粒间一致性流量共用这些有限带宽、有限缓冲的路径。

二、现状：Linux 调度器依赖 CPU 与拓扑信号

2.1 Linux 调度器的放置与负载均衡信号

Linux 默认调度器 EEVDF（Earliest Eligible Virtual Deadline First，最早合格虚拟截止时间优先）按任务的虚拟运行时间和虚拟截止时间选择任务，以实现按权重分配 CPU 时间。它为每个 CPU 维护独立运行队列，并周期性地在 CPU 间迁移任务；放置启发式主要考虑空闲核、缓存亲和和 NUMA（non-uniform memory access，非一致性内存访问）距离，Linux 也提供 sub-NUMA clustering（SNC，子 NUMA 聚类）等拓扑划分。

这些放置与负载均衡信号不反映计算 chiplet 到内存或设备路径的动态可用带宽。唤醒者–被唤醒者关系等启发式依赖操作系统可见的同步行为，也难以发现异步或内存密集型线程之间的流量关系。结果是调度器既看不到线程经过哪些 I/O 路径，也无法判断拥塞发生在哪里。

ARCAS 结合拓扑感知放置与硬件引导的内存分配；Caladan+ 使用微秒级监控和负载感知放置。论文指出，两者同样没有建模动态 I/O chiplet 争用。

三、问题：I/O 路径争用打破拓扑调度假设

3.1 共享芯粒间 I/O 路径的性能瓶颈

论文把这条共享的芯粒间通信路径所形成的性能限制称为 I/O Chiplet Wall。它不是单一内存控制器的瓶颈：请求在 I/O chiplet、NoI、内部路由和芯粒接口上竞争，影响时延、总带宽和不同线程间的干扰。

首先，穿过 I/O chiplet 会增加访存时延。与非 chiplet Intel CPU 相比，AMD EPYC 9634 在 64B 随机读下的平均停顿周期（stalled cycles）是 Intel CPU 的 1.58×；I/O chiplet 负载升高时，停顿周期最高达到 Intel CPU 的 2.0×。即使背景流量尚未达到测得饱和点的 39%，只共享 CC–I/O 链路也会使受害应用性能下降 9.5%；若再共享下游 I/O–DIMM 路径，下降幅度为 13.3%。

其次，共享路径限制了总内存带宽。增加活跃核心后，EPYC 9634 的内存带宽在约 330 GB/s 饱和；应用时延仍继续上升，最高为 15% 应用负载下基准时延的 2.4×。超过路径容量后，请求排队只会加重争用，不能带来更多有效带宽。

第三，I/O 侧拥塞会通过 credit-based flow control（下游缓冲区有空位才授权上游发送的流控机制）回传到核心。NoI 和 NoC 只有在下游缓冲区归还发送额度后才能继续注入请求；内存端拥塞使额度返回变慢，继而限制请求注入并增加核心停顿。DuckDB 执行 TPC-H（决策支持基准）时，将内存分布到 12 个 DIMM（双列直插式内存模块）、而不是 1 个，可使应用时延降低 77.3%，核心停顿周期占比降低 29.2%。

第四，固定带宽的 CC–I/O 链路使单核可用带宽随同一计算 chiplet 上的并发线程增加而下降。EPYC 9634 上，使用全部 14 个逻辑 CPU 时，四种 DRAM 工作负载的单核带宽下降 1.7–2.4×；访问 CXL 内存时下降 1.6–2.5×。

最后，I/O chiplet 和内存控制器没有按线程隔离或限速机制，主要依靠 best-effort（尽力而为）仲裁。请求注入强度、到达时序、内存控制器的调度和行缓冲命中都会影响带宽分配；争用因而会扩散到同时使用相关链路的应用。

3.2 芯粒系统中的四类调度失配

上述路径特性在调度层具体表现为四类失配：

可用核心不等于可用带宽。 两个空闲核可能连接到负载不同的 CC–I/O 链路。PageRank 测试中，链路负载变化时，EEVDF 和 chiplet-affinity（优先在同一计算 chiplet 内放置线程）策略的性能低于 oracle（获知链路状态的理想调度器）：有空闲核时，前两者的性能分别下降 35.1% 和 24.4%；核心繁忙时，分别下降 53.2% 和 58.0%。

拓扑亲近可能加重争用。 当 I/O chiplet 负载超过 80% 时，优先放到同一核心或同一 chiplet 的策略分别出现最高 4.3× 和 4.5× 的性能下降。缓存或 NUMA 距离因此不能单独代表当前的访存性能距离。

拥塞会扩大受害范围。 内存通道过载时，即使线程不共享数据、核心或 chiplet，回传的拥塞仍会降低其他线程的性能。论文测得受影响核心、计算 chiplet 和内存层级的性能分别下降 1.7×、1.2× 和 1.4×；完全没有路径重叠的线程不受影响。

CPU 负载均衡可能恶化内存负载。 只按 CPU 利用率迁移线程，会把内存密集型任务集中到同一路径。作为对照，作者构造的 oracle 同时考虑核心、I/O chiplet 与内存进行端到端负载均衡；内存通道偏斜增加时，它比 EEVDF 和 chiplet-affinity 分别快 13.6% 和 17.9%。在同步密集型多线程 skiplist 上，该 oracle 的吞吐高出 20% 以上。

这四类结果表明，在单插槽芯粒系统中，CPU 忙闲、缓存或 NUMA 亲和度都不能稳定代表当前的端到端 I/O 带宽；EEVDF 也无法识别具体的拥塞路径及其施害流、受害流。

四、方案：cSwitch 联合调度线程位置与流量

cSwitch 将 I/O chiplet 抽象为连接计算 chiplet 与内存、设备的数据交换节点，把线程在核心上发起的请求表示为 cFlow，并联合决定线程位置和请求注入速率。针对路径状态不可见的问题，I/O Chiplet Loading Map 与 Chiplet Traffic Label 分别估算通道负载、描述流量归属；针对空闲度与拓扑信号失准，cFlow 调度器按路径容量计算公平份额，并调节超额 cFlow 对应线程的请求注入速率；若限速后入口仍拥塞，则把对拥塞贡献较大的线程迁移到剩余带宽较高的入口通道。cSwitch 将需要协同执行的线程组合为协同流量组（MegaCFlow），再由 cFlow 调度器按组调度。设计目标是在提升性能和资源利用率的同时减少无谓拥塞，并在多租户之间实现 max-min fairness。

4.1 cSwitch 的软件交换机与虚拟队列

针对硬件队列状态无法直接暴露给操作系统的问题，cSwitch 把 I/O chiplet 抽象成连接计算 chiplet 与内存、设备的交换机：入口（ingress）接收来自计算 chiplet 的流量，出口（egress）通向内存控制器和设备，流量管理器（traffic manager）决定各 cFlow 经过交换机的速率与顺序。它不在硬件路径上添加缓冲，而使用 phantom queues（虚拟队列）：将虚拟队列阈值设在硬件容量以下，并结合停顿周期和服务时延推断拥塞，在实际硬件队列饱和前调整调度。

系统由内核调度组件和用户态控制组件协作。内核采集硬件性能计数器并应用时间片、优先级和迁移计划；用户态调度计划器（planner）结合遥测状态计算计划。这个抽象将 CPU 调度转成数据流调度，使调度器能够同时考虑线程位置和它产生的流量。

4.2 I/O Chiplet Loading Map 推断通道映射

由于硬件不直接暴露入口到出口的映射，I/O Chiplet Loading Map 按调度周期采样硬件计数器，记录入口和出口的请求、响应计数。入口侧还记录 LLC（last-level cache，末级缓存）未命中的请求、返回 LLC 的响应、数据服务时延及活跃 cFlow；出口侧则根据响应服务时延估算内存或设备通道的拥塞程度。

硬件没有直接暴露每个入口到各出口的映射。cSwitch 比较连续快照中的请求增量，构造入口–出口二分图；一对一或一对多关系可据增量匹配。多个入口汇入同一出口时，它再用入口时延膨胀作为权重，估计各入口对出口负载的贡献。该映射由计数器间接推断；原论文第 5.7 节报告，入口带宽估算误差约为 10%。

4.3 Chiplet Traffic Label 描述 cFlow 状态

为把路径遥测归属到具体线程请求流，一个 cFlow 表示某线程在一个核心上向内存或 I/O 设备发出的请求；一个线程可以对应多个 cFlow。Chiplet Traffic Label（芯粒流量标签）为每个 cFlow 记录三类状态：通信路径（入口、出口及目标）、性能属性（请求数、完成数、服务时延和带宽需求）以及拥塞影响程度（核心停顿周期和服务时延）。

cSwitch 使用每核性能计数器持续更新标签，并以 EWMA（exponentially weighted moving average，指数加权移动平均）平滑历史值，再用双阈值迟滞减少瞬时波动造成的反复调度。标签把线程行为与 I/O Chiplet Loading Map 中的通道负载关联起来，供后续限速和迁移使用。

4.4 cFlow 的出口限速与入口迁移

cFlow 调度器回应两类失配：可用核心和拓扑亲和度不能表示路径剩余带宽，按 CPU 利用率负载均衡则可能加重内存路径偏斜。

cFlow 调度器按调度周期同时决定线程在哪个核心运行、以多大速率注入请求。新线程先尝试放到父线程所在计算 chiplet 的空闲核心，以保留缓存局部性；没有可用核心时，再选择全局利用率较低的核心。初始运行后，cSwitch 根据计数器填充并更新每个 cFlow 的 Chiplet Traffic Label。

每个调度周期中，调度器先检查出口。它将有效带宽与链路容量比较，并结合平滑后的服务时延和双阈值迟滞判断拥塞；未拥塞时交给默认调度器处理。出口拥塞时，cSwitch 根据各 cFlow 的估计需求和通道容量计算加权 max-min 公平份额，超额流量通过缩短对应线程的 CPU 时间片、必要时降低其运行队列优先级来限速。

若出口限速后入口仍拥塞，cSwitch 会把拥塞通道上带宽需求高且贡献较大的 cFlow 标记为可迁移。随后，调度器按需求、优先级和入口剩余带宽做贪心匹配，把这些 cFlow 对应的线程迁移到剩余带宽更高、与已有高流量重叠更少的入口通道对应的核心；带宽相近时优先选择拓扑距离较近的核心，以控制迁移成本并保留局部性。全局 I/O 路径都已饱和时，迁移空间会减少，但限速仍可控制过载和负载偏斜。

4.5 MegaCFlow 协调线程组流量

对需要协同执行的线程，cSwitch 提供受网络调度中的 coflow（协同流量组）抽象启发的 MegaCFlow。应用可以显式提供分组提示，系统也可以根据相关流量模式（例如 Linux lockstat 工具记录的同步行为）识别线程组。MegaCFlow 汇总组内 cFlow 的标签，并用带宽消耗最大的入口和出口表示主要通信路径。

若组内总需求不超过这两个通道中较小的可用容量，调度器将组内线程作为一个整体，优先放到共享主入口路径对应的核心上；按各线程对该组流量的贡献分配时间片，并为整个 MegaCFlow 施加共享速率上限。若需求超过通道容量，cSwitch 则将 MegaCFlow 拆成多个 cFlow，按剩余带宽分散到其他路径，再由普通 cFlow 逻辑限速和迁移。

4.6 sched_ext 与 eBPF 策略接口

cSwitch 基于 Linux sched_ext（可扩展调度类）和 eBPF（extended Berkeley Packet Filter，可扩展 Berkeley 包过滤器）分离策略与执行机制。用户态 planner（调度计划器）读取内部状态并给出时间片调整、线程迁移和优先级更新；内核负责落实计划。应用可以替换调度策略，同时复用 I/O Chiplet Loading Map 和 Chiplet Traffic Label。论文将 ARCAS 和 Caladan+ 移植到该接口，保留它们的策略逻辑并使用 cSwitch 的遥测。

cSwitch 保留 CPU affinity（线程可运行的 CPU 亲和约束）、cpusets（CPU 与内存节点集合限制）和 cgroups（control groups，控制组）约束，并与其他 Linux 调度类（scheduler class）共存；当前设计面向单处理器插槽内的 chiplet 互连，不改变既有 NUMA 策略或内存放置。扩展到跨处理器插槽的 NUMA 需要补充相应拓扑信息。

五、结果：路径感知调度改善拥塞下的性能

评测平台与负载。 主要平台是 Supermicro 服务器中的 AMD EPYC 9634，配有 1 TB DDR5 和四个 256 GB Micron CZ120 CXL 内存模块。评测关闭同步多线程（SMT）和 Turbo Boost，运行 Ubuntu 22.04.5 LTS（长期支持版）与 Linux 6.19.6。研究 I/O chiplet 与非 chiplet 架构差异时，另用配有 Intel CPU 和 256 GB DDR5 的服务器。

工作负载覆盖数据库、数据分析、机器学习和高性能计算，包括 RocksDB、OrientDB、Elasticsearch、DuckDB、PageRank、llama.cpp、Filebench 等；应用请求由 Yahoo! Cloud Serving Benchmark（YCSB）、Memtier 和 TPC Benchmark H（TPC-H）产生。比较对象为 Linux EEVDF、ARCAS 和 Caladan+。论文报告应用时延与吞吐，并采集核心停顿周期及内存、I/O 带宽；背景流量由顺序读线程产生，通过读循环中的 nop（空操作）指令控制速率。

5.1 多类拥塞场景下的调度性能

论文在 12 个应用上改变 I/O chiplet 负载，并以 EEVDF 为基线。在负载较低时，cSwitch 平均比 EEVDF 快 1.2×、比 Caladan+ 快 1.9×。注入背景流量后，cSwitch 相对 EEVDF 的加速为 1.2–2.7×，平均比 ARCAS 快 1.4×、比 Caladan+ 快 1.7×。这些差异主要来自 cSwitch 对共享路径负载的感知：它据此按可用带宽迁移线程或调节请求注入速率；ARCAS 和 Caladan+ 没有相同的 I/O chiplet 拥塞视图。

I/O chiplet 负载变化时的调度器加速比（Figure 10: (a)/(b) report the speedup of cSwitch, ARCAS, and Caladan+ over the Linux EEVDF when the I/O chiplet is unloaded/loaded. RDB=RocksDB. ODB=OrientDB. ES=ElasticSearch. BC/PR∈GAPBS. NRS|NRL∈Node Replication Library. FileS|WebP|WebS|VAR∈Filebench.）

空闲与繁忙核心上的线程放置。

在 llama.cpp、PageRank 和 File Server 的空闲与繁忙核心测试中，cSwitch 比 ARCAS、EEVDF 和 Caladan+ 分别快 1.4×、1.7× 和 2.0×；核心繁忙时，分别快 2.6×、1.4× 和 2.7×。它估算核心到内存的端到端可用带宽，避免将线程放到表面空闲、实际受链路带宽限制的核心。

空闲与繁忙核心上的调度器性能（Figure 11: (a) and (b) compare the performance of cSwitch, ARCAS, EEVDF, and Caladan+ running llama.cpp, PageRank, and File Server when there are heterogeneous free/busy cores as described in §3.2. We normalize the performance to the EEVDF case.）

CC–I/O 链路拥塞下的调度性能。

当共享 CC–I/O 链路的背景负载超过 60% 时，ARCAS、EEVDF 和 Caladan+ 的性能最多分别下降 82.3%、84.5% 和 66.7%；cSwitch 检测到拥塞后将线程迁到可用带宽更充足的入口通道。对整个 I/O chiplet 注入背景流量时，其他调度器的性能下降均超过 60%。ARCAS 依赖 LLC miss 信号，却看不到链路剩余带宽，可能持续把线程放在拥塞路径上。

CC–I/O 链路和 I/O chiplet 负载下的性能下降（Figure 12: (a) and (b) show the performance degradation when varying the traffic load of the compute-I/O chiplet link and the overall I/O chiplet under cSwitch, ARCAS, EEVDF, and Caladan+.）

PageRank 下的跨芯粒扩展性。

I/O chiplet 负载升高时，PageRank 中的 cSwitch 分别比 ARCAS、EEVDF 和 Caladan+ 快 1.4×、1.5× 和 3.9×。它按入口和出口的可用带宽分散流量；论文将 Caladan+ 在该实验中的性能下降归因于微秒级调度带来的上下文切换开销。

不同线程数和 chiplet 负载下的 PageRank 性能（Figure 13: (a) and (b) present the performance of PageRank when varying the number of threads under cSwitch, ARCAS, EEVDF, and Caladan+. We normalize the perf. to the single-thread case.）

回传拥塞下的时延改善。

对内存和 CXL 设备路径逐步增加负载时，cSwitch 相对既有调度器的时延改善最高为 1.7×。它先按出口拥塞对流量限速；若入口仍然拥塞，再将高需求线程迁到带宽较充足的路径，从而在回压传到核心流水线前降低请求压力。

5.2 机制验证、平台移植与运行开销

在十个顺序读线程、异构限速条件下，I/O Chiplet Loading Map 的入口带宽估算误差约为 10%；出口测试评估 cSwitch 在两个背景工作线程下识别针对特定内存控制器的干扰源线程的能力；在高负载周期中，它平均在 95% 的周期内识别正确。

将 cSwitch 移植到有两个计算 tile 的 Intel Xeon Gold 6530（Emerald Rapids）后，由于该平台对芯粒间路径的可观测性较弱，实验只启用出口限速；指针追逐（pointer chasing）测试中，4,096 次访问窗口的 P99（第 99 百分位）时延降低 33%。

消融实验中，启用入口迁移后，NAS Parallel Benchmarks（NPB）中的 CG（共轭梯度）、FT（快速傅里叶变换）和 PageRank 性能最高提高 1.5×，其中 CG 收益最大；启用出口限速后，指针追逐和 RocksDB 的 P99 时延分别降低 57% 和 88%。

入口迁移的性能提升与出口限速的 P99 时延变化（Figure 14: (a) shows the normalized performance improvement when ingress migration is enabled on NPB CG, FT, and PageRank. (b) presents the normalized P99 latency reduction when egress throttling is enabled on pointer chasing, Redis, and RocksDB.）

40 线程 GAP Benchmark Suite（GAPBS）PageRank 中，用户态调度器消耗 6.22 CPU 秒，占应用 179.60 CPU 秒的 3.46%；planner 计算消耗 1.75 CPU 秒，占应用 CPU 时间的 0.97%；其余 CPU 开销主要来自用户态调度运行时。在 84 个核心上，cSwitch 的内存开销约占系统内存的 0.01%。
