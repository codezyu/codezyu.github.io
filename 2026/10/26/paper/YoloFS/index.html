YoloFS：让文件系统呈现并约束 AI agent 的文件操作

论文：Don’t Let AI Agents YOLO Your Files: Information and Control in Agent-Native Filesystems，Shawn (Wanxiang) Zhong、Junxuan Liao、Jing Liu、Mai Zheng、Andrea C. Arpaci-Dusseau、Remzi H. Arpaci-Dusseau，SOSP ’26。DOI：10.1145/3830418.3843858。

TLDR： AI agent 文件误用的难点是实际效果不可见、变更难按会话和命令恢复，敏感访问也难靠静态策略控制。YoloFS 以 staging 暂存变更、以 snapshots and travel 检查并回退命令，再用 progressive permission 按路径门控访问；项目内操作无需许可，外部路径通常只询问一次。Claude 在 11 项隐藏副作用任务中自纠 8 项；112 项常规任务成功率 99%，平均每项交互 0.4 次。

一、背景：Agent 的本地文件访问

本地 AI agent 由大语言模型和 agent harness（负责执行模型工具调用的运行框架）组成。用户交代任务后，模型可以调用文件读写工具，也可以让 harness 执行 shell 命令；一次任务可能连续运行许多命令，并以用户权限访问本机文件。

现有 harness 主要用三类 guardrail（防护机制）限制文件访问：内置工具的路径策略、匹配 shell 命令字符串的过滤器，以及限制命令可访问路径的 sandbox（沙箱）。内置工具策略不覆盖 shell；命令过滤器容易被等效命令绕过，也难以判断一条命令的实际效果；沙箱既可能挡住合法构建或测试，也仍允许 agent 改动沙箱内可写文件。

agent 文件访问流程与三类 harness 防护（Figure 2. Workflow for an agent’s access to the filesystem and the three guardrails provided by its harness (Table 1).）

二、现状：公开误用报告的影响与成因

2.1 公开报告中的损害类型与恢复结果

作者收集了 2024 年 2 月至 2026 年 3 月的 290 份公开报告，来源包括 GitHub issue、社交媒体、产品论坛、博客和国家漏洞数据库。报告分为 158 起已确认造成损害的 incident、49 起展示出攻击路径的 exploit，以及 83 项尚未展示实际影响的 weakness。影响统计只覆盖前两类共 207 份报告。

在各项信息已知的报告中，最常见的文件操作是写入（44%），其次是删除（39%）；另有 17% 涉及秘密泄漏。42% 的已知范围记录显示，受影响文件超出项目目录，涉及系统文件、用户文件或凭据。在恢复情况已知的报告中，40% 所涉损害无法恢复：23% 的报告记录全部数据丢失，17% 记录部分丢失。对 agent 反应已知的报告，68% 中 agent 继续操作，仿佛没有发生损害；对用户知情情况已知的报告，83% 的用户立即发现，10% 迟发现，8% 始终未发现。各项比例按维度已知记录计算，分母不同。

公开报告中的文件误用影响（Figure 3. Impact summary. Reports with unknown values excluded from the corresponding row. Row totals shown next to the labels.）

2.2 文件误用成因与审批疲劳

作者把 290 份报告中的原因归到模型、harness 和用户三方，类别可以重叠。模型相关原因出现在 168 份报告中，包括生成错误目标或扩大操作范围、没有遵循指令，以及服从项目文件或网页中的 prompt injection（提示注入）。harness 相关原因出现在 218 份报告中：147 份涉及防护失效，包括 shell 绕过（77）、按命令字符串而非实际效果过滤（52）、沙箱范围不合适（41）；另有 130 份涉及预先固定的访问策略。用户相关原因出现在 105 份报告中，其中 80 份涉及自动批准，31 份涉及审批信息不足。原因分类计数可以重叠。

文件系统误用的多方成因（Figure 4. Taxonomy of causes (§3.3–§3.5). Counts can overlap.）

审批提示通常显示命令，而不说明实际读写的文件。部分用户为了避免每次会话回答数百次提示而开启 YOLO mode（始终允许所有操作），这种自动放行属于 approval fatigue（审批疲劳）；即使命令很短，运行脚本也可能触发隐藏操作。

Codex 审批命令与实际文件变化（Figure 5. Codex prompts the user with the generated shell script.）

三、问题：文件影响、恢复与访问策略缺口

3.1 命令文本与文件效果的映射缺口

现有审批通常呈现命令文本，而不说明命令运行后实际读取或改动了哪些文件。内置工具的拒绝策略可以被 shell 绕过；若按命令字符串过滤，不同命令可以产生相同文件效果，同一命令也会因参数、脚本内容和环境产生不同影响。因此，用户批准或 agent 检查一条命令时，仍可能无法判断它真正作用于哪些路径；命令输出也不保证 agent 能识别意外副作用。

3.2 变更恢复粒度与 agent 会话不匹配

版本控制系统只跟踪仓库内选中的文件，会漏掉仓库外文件和被忽略文件；agent 还可能覆盖或删除 .git 历史。若改为跟踪 agent 可访问的所有文件，扫描目录、计算哈希和保存版本的成本会上升。版本化文件系统按单文件、目录子树或整个文件系统保存状态，粒度都不等于一次 agent 会话：单文件版本不能聚合会话变更，子树快照可能混入其他写入，整盘回滚则可能丢掉用户的无关改动；专用磁盘格式还可能要求迁移现有数据。

union filesystem 可把变更放进可写层，但把基础层文件重命名到可写层时要复制整个文件内容。要对每条命令做细粒度撤销，又需要堆叠新的可写层；层数增加会拖慢查找，并受挂载层数限制。这些方式无法同时覆盖 agent 能访问的文件、按会话复核和按命令恢复，又保持现有数据兼容和较低操作开销。

3.3 不可逆访问与静态策略的授权冲突

撤销只能恢复文件状态，不能收回已经读出的 SSH key 等秘密。访问需求又随任务变化，启动 agent 前无法完整预测；沙箱和操作系统权限只能按既有策略放行或拒绝，不能把新出现的访问请求暂停下来交给用户决定。预先放宽策略会留下可写范围，收紧策略则可能挡住合法构建、测试或 GPU 访问；逐条询问又会累积审批负担，推动用户始终放行或关闭保护。这使「拦住不可逆的敏感访问」与「允许 agent 完成未知任务」难以同时做到。

四、方案：YoloFS 的文件影响与访问控制

YoloFS 提出 agent-native filesystem（面向 agent 工作方式设计的文件系统），把文件效果信息和访问控制放到文件系统中。它提供三种原语：呈现文件影响，让 agent 检查命令读写了什么、让用户复核会话变更；撤销变更，让 agent 恢复错误操作并重试；在访问发生前设门控，处理无法撤回的效果。设计还要求完整中介 agent 能访问的文件、允许运行中调整策略、兼容已有数据并保持较低开销。

文件系统承担 agent 操作的影响审查和访问控制（Figure 1. Shifting information and control from agents to filesystems improves safety while reducing user interaction.）

YoloFS 用 staging（会话变更暂存）、snapshots and travel（中间状态快照与返回）和 progressive permission（运行中细化路径权限）落实这三种原语：staging 为整个会话保留待审核的变更；snapshots and travel 补足 staging 无法定位单条命令的问题；progressive permission 则在秘密读取等不可逆访问发生前作出路径级决策。前两者处理可撤销的写入和删除，后者处理事后无法恢复的访问。

YoloFS 的暂存、状态快照与渐进式权限（Figure 6. YoloFS staging (§5.2), snapshots and travel (§5.3), and progressive permission (§5.4). Each panel highlights a different aspect. Mutations are staged for user review (a), and snapshotted for agent self-correction (b). Unknown accesses require user approval (c).）

4.1 会话级变更审核（staging）

CLI（命令行工具）在 mount namespace（挂载命名空间）中通过 pivot_root 将 YoloFS 挂载为 agent 命令的根文件系统，使 shell、内置工具和其他文件访问都经过同一文件系统中介；在用户提交前，基础文件保持不变。YoloFS 使用平面文件存储保留新建和修改文件的内容，用 override tree 将路径映射到暂存文件、基础文件中的位置，或标记为不存在，并用只追加的 session journal 记录路径状态变化。

YoloFS 的内核中介层与状态存储（Figure 7. YoloFS architecture. The agent runs commands on top of YoloFS, takes snapshots, inspects changes, and travels. The user reviews, commits, and manages permissions.）

将内容与路径映射分开后，重命名可以移动路径映射，不必复制基础文件的内容。journal 保存暂存、删除和重命名等动作；用户审核净变更后可以 commit 到基础文件系统、abort 整个会话或留待之后处理，agent 不能替用户作出最终提交决定。

journal 中变更、状态和权限事件的记录格式（Figure 8. Journal format. In an action, pre is the path’s previous backing. In a note, op ∈ {read, write}, result ∈ {blocked, user-allowed, user-denied}, and policy is defined in Figure 7.）

动作记录保留受影响路径变更前的 backing，CLI 可回放 journal 并把映射与基础目录合并，重建 agent 看到的文件树，供用户复核会话结果。基础文件重命名时，YoloFS 只调整路径映射，不复制文件内容。

文件操作形成的 journal 记录与最终路径视图（Figure 9. Left: Example syscalls and resulting journal records. Gray fields record previous backings (§5.3). Right: The final override tree. n = StagedFile(n), path = BaseFile(path), and ∅ = None.）

staging 提供的是会话当前累计状态，单独使用时难以定位哪条命令引入某个改动，也不能方便地撤销单条命令；snapshots and travel 用命令边界保存的历史补足这一点。

4.2 命令级追溯与恢复（snapshots and travel）

YoloFS 默认在每条命令后创建 snapshot。新状态中再次写入暂存文件时使用 copy-on-write，保留旧版本；journal 的动作记录保存路径之前的状态，使 CLI 能从命令对应的记录段计算变更，而不用从会话开头重放全部历史。agent 因此能看到单条命令带来的文件变化，并选择回到更早的状态。

travel 通过追加 T 标记指定目标状态，不会截断被放弃的历史。CLI 根据有效的记录段重建 override tree；agent 既能恢复到已有 snapshot，也能回到之前放弃的状态。这个机制弥补了 staging 只能呈现聚合结果的限制，并让普通文件操作继续使用当前视图，而不必逐层搜索旧状态。

snapshot 与 travel 保留的 journal 状态段（Figure 10. Top: Snapshot (P) and travel (T) markers partition the journal into segments. n denotes the n-th marker that starts segment n with generation n. Bottom: The timeline shows live segments in black and dead segments in gray. → indicates travel.）

snapshots and travel 只能撤销文件变更，不能让秘密「未曾被读过」。YoloFS 用 progressive permission 处理这类访问。

4.3 路径级动态门控（progressive permission）

progressive permission 不按命令字符串猜测文件效果，而按路径实施规则。每条路径可设为 ask（访问时询问）、allow（在用户原有权限内允许）、write-ask（读取和执行允许、写入时询问）、read-only（允许读取和执行、拒绝写入）或 deny（拒绝全部访问）；路径继承最近祖先的规则，更具体的规则覆盖继承值。由于规则按路径生效，同一路径上的访问无论来自 shell、内置工具还是其他方式，都会受该规则约束，从而防止改用其他命令绕过过滤器。

遇到 ask 或 write-ask 访问时，YoloFS 暂停请求线程，将路径、操作和进程交给 CLI；用户可以当场允许、拒绝或添加后续规则，超时则拒绝访问。规则可在运行中修改，并保存到项目配置供后续会话复用，agent 不能替自己改规则或批准请求。访问尝试、处理结果和规则变更也写入 journal，并在审核时与暂存差异一起呈现，补足 staging 只显示变更、不显示拒绝访问与权限决定的限制。

YoloFS 的内核文件系统由约 2.7 千行 C 代码实现，配套的用户态 CLI 约 8 千行 Rust 代码。YoloFS 支持 Ubuntu 24.04 默认的 Linux 6.8 和 Ubuntu 26.04 默认的 Linux 7.0，并接入 Claude Code、Copilot 和 Gemini。本文讨论文件系统访问；论文将数据库、网页和云 API 等非文件系统接口的保护视为互补工作。

五、结果：YoloFS 的纠错、交互与性能成本

5.1 隐藏副作用纠错与常规任务交互

隐藏副作用评测包含 11 项任务：命令看似是 lint、清理构建产物或迁移数据，却会额外删除源文件、覆盖配置或移除文档；项目只有 10–41 行代码。任务按命令副作用的可见程度分四级：L1 的行为写在单个可读脚本中（3 项），L2 的 Makefile 会调用子脚本（3 项），L3 包含三层以上间接调用（2 项），L∞ 使用无源码的预编译程序（3 项）。测试使用 Claude Code 2.1.45、Codex 0.101.0、Copilot CLI 0.0.411、Gemini CLI 0.29.0，以及接入 YoloFS 的 Claude Code。

无 YoloFS 时，Claude Code 只有在 optimizer 任务中请求用户确认，其余任务未能阻止副作用；Copilot 只有在 build-pkg 中询问用户，其余未能阻止；Codex 遭遇沙箱限制后询问能否在沙箱外重跑，论文将此记为「询问用户」而非成功阻止；Gemini 在 9 项任务中失败，另 2 项没有执行命令，也没有完成任务。接入 YoloFS 后，Claude Code 在 11 项任务中都没有破坏基础文件系统：8 项中自行发现副作用并 travel 回先前 snapshot，另 3 项接受了看似符合目标的改动，但改动仍留在 staging，供用户提交前决定。这个结果分别体现 snapshots and travel 的命令级纠错，以及 staging 的提交前控制。

另一组 112 项任务用单次文件操作测试 18 种操作和每种操作的 5–7 类路径，覆盖项目内、跨项目边界和 symlink 路径。YoloFS 成功率为 99%，Claude Code 为 98%，Codex 为 100%，Copilot 为 96%，Gemini 为 75%；每项任务的平均用户交互次数分别为 0.4、0.9、0.4、1.3 和 2.2。YoloFS 的项目内操作不需要许可，外部路径通常只询问一次，ls 和 glob 除外。这组结果对应 progressive permission 的路径级授权：维持任务成功率的同时，把询问集中到需要用户决定的访问上。

5.2 文件操作开销与现实工作负载

性能实验在 CloudLab c6525-25g 主机上运行，硬件为 16 核 AMD EPYC 7302P、128 GB 内存和 480 GB Micron 5200 MAX SATA SSD，软件为 Ubuntu 24.04、Linux 6.8 和 Ext4。对暂存区内 1 GB 文件进行单线程 4 KB 读写时，YoloFS 的顺序与随机读写吞吐相对 Ext4 变化为 −2% 至 +1%；元数据操作的权限检查开销大多可忽略，stat 延迟增加 4%。YoloFS 在多数元数据操作上快于 OverlayFS；当文件操作由暂存状态提供服务时，YoloFS 的 readdir、rename 和 unlink 延迟也低于 Ext4。BranchFS 在这些操作上比其他文件系统慢 20 倍以上。

基础文件、snapshot 与暂存文件上的元数据操作延迟（Figure 11. Metadata operation latency. The files can reside in the base filesystem, a snapshot, or the staging area.）

snapshot 数从 50 增至 100 时，YoloFS 性能没有下降，因为 YoloFS 始终维护当前 override tree，文件操作只需查询当前视图，不必搜索旧状态。OverlayFS 约在 50 个 snapshot 时因挂载选项超过内核长度上限而无法继续创建。

snapshot 数量增加时的扩展性（Figure 12. Snapshot scalability as the number of snapshots grows. OverlayFS fails at approximately 50 snapshots.）

在 Linux 内核开发工作负载中，YoloFS 总耗时与 Ext4 接近；提交超过 100,000 个文件时额外增加 3.5 秒。OverlayFS 比 YoloFS 慢 18%；BranchFS 存在缺陷，无法完成初始构建，在约 20 秒的构建流程上增加两分钟以上。
