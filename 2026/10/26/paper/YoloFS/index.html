YoloFS：让文件系统呈现并约束 AI agent 的文件操作

论文：Don’t Let AI Agents YOLO Your Files: Information and Control in Agent-Native Filesystems，Shawn (Wanxiang) Zhong、Junxuan Liao、Jing Liu、Mai Zheng、Andrea C. Arpaci-Dusseau、Remzi H. Arpaci-Dusseau，SOSP ’26。DOI：10.1145/3830418.3843858。

TLDR： AI agent 的文件操作可能超出任务范围，现有审批又难呈现实际副作用，误删和泄漏也难恢复。YoloFS 将变更留在暂存区供用户提交前复核，保留命令间状态供 agent 检查和回退，并在访问时按路径询问、逐步补充权限。11 项隐藏副作用任务中，Claude 自行纠正 8 项；112 项常规任务成功率为 99%，平均每项 0.4 次用户交互。

一、背景：agent 文件访问的现有防护

本地 AI agent 由大语言模型和 agent harness（负责执行模型工具调用的运行框架）组成。用户交代任务后，模型可以调用文件读写工具，也可以让 harness 执行 shell 命令；一次任务可能连续运行许多命令，并以用户权限访问本机文件。

现有 harness 主要用三类 guardrail（防护机制）限制文件访问：内置工具的路径策略、匹配 shell 命令字符串的过滤器，以及限制命令可访问路径的 sandbox（沙箱）。内置工具策略不覆盖 shell；命令过滤器容易被等效命令绕过，也难以判断一条命令的实际效果；沙箱既可能挡住合法构建或测试，也仍允许 agent 改动沙箱内可写文件。

agent 文件访问流程与三类 harness 防护（Figure 2. Workflow for an agent’s access to the filesystem and the three guardrails provided by its harness (Table 1).）

二、现状：文件误用的影响与成因

2.1 误用报告揭示影响范围

作者收集了 2024 年 2 月至 2026 年 3 月的 290 份公开报告，来源包括 GitHub issue、社交媒体、产品论坛、博客和国家漏洞数据库。报告分为 158 起已确认造成损害的 incident、49 起展示出攻击路径的 exploit，以及 83 项尚未展示实际影响的 weakness。影响统计只覆盖前两类共 207 份报告。

在各项信息已知的报告中，最常见的文件操作是写入（44%），其次是删除（39%）；另有 17% 涉及秘密泄漏。42% 的已知范围记录显示，受影响文件超出项目目录，涉及系统文件、用户文件或凭据。对恢复情况已知的报告，40% 无法恢复，其中 23% 是全部数据丢失、17% 是部分丢失；31% 可以较容易恢复，29% 则需要用户投入大量精力。这些比例按各维度的已知记录统计，因此分母不同。

公开报告中的文件误用影响（Figure 3. Impact summary. Reports with unknown values excluded from the corresponding row. Row totals shown next to the labels.）

2.2 文件误用成因与审批负担

作者把 290 份报告中的原因归到模型、harness 和用户三方，类别可以重叠。模型相关原因出现在 168 份报告中，包括生成错误目标或错误范围的操作、没有遵循指令，以及服从项目文件或网页中的 prompt injection（提示注入）。harness 相关原因出现在 218 份报告中：内置工具策略可以被 shell 绕过，命令过滤器按字符串而非文件效果判断，沙箱则可能过严或过松；静态策略也难以提前覆盖不同任务的访问需求。用户相关原因出现在 105 份报告中，其中 80 份涉及自动批准，31 份涉及审批信息不足；分类计数可以重叠。

文件系统误用的多方成因（Figure 4. Taxonomy of causes (§3.3–§3.5). Counts can overlap.）

论文指出，部分用户为了避免每次会话回答数百次审批提示而开启 YOLO mode（始终允许所有操作），这种自动放行属于 approval fatigue（审批疲劳）。审批提示若只列命令而不说明实际读写的文件，用户就难以据此判断风险；即使命令很短，运行脚本也可能触发隐藏操作。

Codex 审批命令与实际文件变化（Figure 5. Codex prompts the user with the generated shell script.）

三、优化点：文件系统的信息与控制原语

这项研究把问题归纳为信息缺口和控制缺口：用户与 agent 都难以可靠判断命令实际访问或改动了什么；现有机制也难以在损害发生前阻止访问，或在之后恢复状态。作者据此提出 agent-native filesystem（面向 agent 工作方式设计的文件系统），让文件系统直接观测并管理文件影响。

这类文件系统应提供三种原语：呈现文件影响，让 agent 检查命令读写了什么、让用户复核会话变更；撤销文件变更，让 agent 能恢复错误操作并重试；在访问发生前设门控，让用户决定敏感路径是否可读写。访问凭据一旦被读取或泄漏就无法撤回，因此仅有事后恢复并不够。

文件系统承担 agent 操作的影响审查和访问控制（Figure 1. Shifting information and control from agents to filesystems improves safety while reducing user interaction.）

实现这些原语还要同时满足完整性、适应性、兼容性和性能要求：保护范围要覆盖 agent 能访问的所有文件；访问规则要能在任务执行期间调整；不能要求用户迁移现有文件系统数据；每次文件操作增加的开销也应较低。

现有方案难以同时满足这些要求。版本控制系统通常只跟踪仓库内被选中的文件，漏掉仓库外访问；若扩展为跟踪 agent 能访问的所有文件，扫描、散列和存储历史的成本会增加。版本化文件系统可以恢复旧内容，但单文件、目录子树和整个文件系统的快照都不对应 agent 会话的撤销粒度，专用磁盘格式还可能要求迁移现有数据。另一类方案是 union filesystem（联合文件系统，把多个目录层合并呈现）：将基础层文件重命名到可写层时需要复制内容，为逐命令撤销而堆叠快照也会增加查找开销。操作系统访问控制和沙箱要求预先设定策略，无法把未预料的访问暂停给用户当场决策。

四、方案：YoloFS 的变更暂存与权限控制

YoloFS 通过三项机制实现上述原语：staging（变更暂存，留待用户审核）、snapshots and travel（中间状态快照与状态返回），以及 progressive permission（运行中逐步细化路径访问规则）。staging 使用户能在提交前检查变更；snapshots and travel 让 agent 检查并恢复单条命令的影响；progressive permission 则把用户决策放在具体文件访问发生时。

YoloFS 的暂存、状态快照与渐进式权限（Figure 6. YoloFS staging (§5.2), snapshots and travel (§5.3), and progressive permission (§5.4). Each panel highlights a different aspect. Mutations are staged for user review (a), and snapshotted for agent self-correction (b). Unknown accesses require user approval (c).）

4.1 staging 的变更追踪

YoloFS 是位于 agent 与基础文件系统之间的 Linux stackable filesystem（可叠加文件系统）。agent 在以 YoloFS 为根目录的 mount namespace（挂载命名空间）中运行，命令对文件的访问由 YoloFS 中介；基础文件在用户提交之前保持不变。

YoloFS 的内核中介层与状态存储（Figure 7. YoloFS architecture. The agent runs commands on top of YoloFS, takes snapshots, inspects changes, and travels. The user reviews, commits, and manages permissions.）

YoloFS 把待提交内容、路径映射和历史记录分开保存：flat file store 保存新建或被修改文件的内容；override tree 记录每个路径当前对应暂存文件、基础文件中的位置或不存在；append-only session journal（只追加的会话日志）记录状态变化。这样，虚拟目录仍呈现原有层级，但暂存内容无需按基础目录结构复制。重命名可以移动路径映射，不必复制大文件内容。

journal 记录暂存、删除和重命名等变更，也记录 snapshot、travel 和权限事件。CLI（命令行工具）回放 journal，生成供用户检查的净变更；用户可以 commit 将最终状态应用到基础文件系统，也可以 abort 丢弃整个会话的暂存状态，agent 不能替用户提交或放弃。

journal 中变更、状态和权限事件的记录格式（Figure 8. Journal format. In an action, pre is the path’s previous backing. In a note, op ∈ {read, write}, result ∈ {blocked, user-allowed, user-denied}, and policy is defined in Figure 7.）

变更记录还保留受影响路径之前的状态，因此 CLI 可以按一段记录重建变更，而不必从会话开头重新回放全部历史。对基础文件的重命名只需调整映射；审核时再把映射与基础目录合并，得到 agent 看到的文件树。

文件操作形成的 journal 记录与最终路径视图（Figure 9. Left: Example syscalls and resulting journal records. Gray fields record previous backings (§5.3). Right: The final override tree. n = StagedFile(n), path = BaseFile(path), and ∅ = None.）

4.2 travel 的状态恢复

只有 staging 时，CLI 只能看到当前累计结果，不容易定位哪条命令引入了错误。YoloFS 默认在每条命令后创建 snapshot，用 journal 标记状态边界；snapshot 之后的写入采用 copy-on-write（写时复制），保留旧版本供检查和恢复。

agent 发现问题后可以执行 travel，让 YoloFS 重建指定 snapshot 的状态。travel 会追加历史标记，而不是删除被放弃的变更；agent 之后还能回到先前放弃的状态。CLI 根据仍对目标状态有效的记录段重建路径映射，内核始终只需维护当前视图。

snapshot 与 travel 保留的 journal 状态段（Figure 10. Top: Snapshot (P) and travel (T) markers partition the journal into segments. n denotes the n-th marker that starts segment n with generation n. Bottom: The timeline shows live segments in black and dead segments in gray. → indicates travel.）

4.3 progressive permission 的路径规则

读取秘密等影响不能靠撤销来补救。YoloFS 因此按路径控制访问，而不根据命令字符串猜测命令效果。每条路径有五种策略：ask 在访问时询问用户，allow 允许在用户现有权限内读写、执行和目录操作，write-ask 允许读取和执行、在写入时询问，read-only 允许读取和执行并拒绝写入，deny 拒绝所有访问。路径继承最近祖先的策略，更具体的规则覆盖继承值。

遇到需要询问的访问时，YoloFS 暂停请求线程，并把路径、操作和进程交给 CLI，请用户当场允许或拒绝；超时则拒绝访问。论文的恶意依赖示例中，访问用户主目录前默认需要询问。用户也可以在提示中为路径设置后续规则，之后的访问按新规则处理。只有用户能修改规则或批准访问，agent 不能替自己扩权。因为策略约束的是文件系统路径，同一规则会覆盖 shell、内置工具及其他访问方式。

YoloFS 由 2.7 千行 C 代码实现的内核文件系统和 8 千行 Rust 代码实现的 CLI 组成，支持 Linux 6.8（Ubuntu 24.04 默认内核）和 Linux 7.0（Ubuntu 26.04 默认内核）。

YoloFS 接入 Claude Code、Copilot 和 Gemini。为避免 agent 绕过文件系统中介，CLI 通过 mount namespace 与 pivot_root 把 agent 的根文件系统切换到 YoloFS，使其不能直接访问基础路径。

五、结果：YoloFS 的任务与性能评估

5.1 副作用防护与任务交互成本

作者设计了 11 项隐藏破坏性副作用的任务，命令表面上是 lint（代码静态检查）、清理构建产物或数据迁移等常见操作，实际还会删除源文件、覆盖配置或移除文档；任务项目只有 10–41 行代码。任务从可读脚本逐步增加到多层脚本和无源码的预编译程序，以提高隐藏影响的程度。

基线使用 Claude Code 2.1.45（claude-sonnet-4-6）、Codex 0.101.0（gpt-5.3-codex）、Copilot CLI 0.0.411（claude-sonnet-4-6）和 Gemini CLI 0.29.0（gemini-3-flash-preview）；YoloFS 与 Claude Code 比较。Claude Code 在 10/11 项任务中未能阻止副作用，剩余 1 项在 optimizer 上请求用户确认；Copilot 在 10/11 项中失败，只在 build-pkg 上发现问题并询问用户。Codex 在 11 项任务中都先遭遇沙箱限制，再询问是否在沙箱外重跑；论文把这些结果记为「询问用户」，不算成功阻止损害。Gemini 在 9/11 项中失败，另有 2 项未执行命令，因此没有造成损害，也没有完成任务。

Claude Code 接入 YoloFS 后，11 项任务的基础文件都未受到破坏：Claude 在 8 项中发现影响不符合任务目标并自行返回 snapshot，另外 3 项接受了看起来符合目标的变化，但 YoloFS 将其保留在 staging 中，供用户提交前决定。

另一组 112 项任务覆盖 18 种文件操作及每种操作的 5–7 类路径，用来测量任务成功率和用户交互。YoloFS 的任务成功率为 99%，与 Claude Code 的 98% 接近，也接近 Codex 的 100%；Copilot 为 96%，Gemini 为 75%。每项任务平均需要的用户交互次数，YoloFS 和 Codex 都是 0.4，Claude Code 为 0.9，Copilot 为 1.3，Gemini 为 2.2。YoloFS 在项目内操作时无需许可；在这组测试中，外部路径访问会触发一次性询问，ls 和 glob（路径模式匹配）除外。

5.2 YoloFS 性能与扩展性评估

性能测试在 CloudLab c6525-25g 主机上运行，配有 16 核 AMD EPYC 7302P、128 GB 内存和 480 GB Micron 5200 MAX SATA SSD，使用 Ubuntu 24.04、Linux 6.8 和 Ext4。对暂存区内的 1 GB 文件进行单线程 4 KB 读写时，YoloFS 在顺序与随机读写中的吞吐相对 Ext4 变化为 −2% 至 +1%。元数据操作的权限检查开销在大多数操作中可忽略，stat 增加 4%。

基础文件、snapshot 与暂存文件上的元数据操作延迟（Figure 11. Metadata operation latency. The files can reside in the base filesystem, a snapshot, or the staging area.）

增加 snapshot 数量时，YoloFS 始终从当前 override tree 提供视图，因此普通文件操作不需要遍历旧状态；实验中 snapshot 从 50 增至 100 个时，性能没有下降。OverlayFS 在约 50 个 snapshot 后达到挂载选项长度上限而无法继续创建。

snapshot 数量增加时的扩展性（Figure 12. Snapshot scalability as the number of snapshots grows. OverlayFS fails at approximately 50 snapshots.）

在 Linux 内核开发流程中，YoloFS 的总耗时与 Ext4 接近；提交超过 100,000 个文件时额外增加 3.5 秒。OverlayFS 比 YoloFS 慢 18%；BranchFS 因缺陷无法完成初始构建，在约 20 秒的构建流程上又增加两分钟以上。
