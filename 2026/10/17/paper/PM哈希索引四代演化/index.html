持久内存哈希索引：共享候选空间与局部重哈希

TLDR： 这类设计通过共享候选空间减少冲突搬移；支持扩容的方案只重哈希受影响的局部层，不迁移全表。Path Hashing 让树路径共享 cell，Level Hashing、Clevel 和 GPHash 则通过多层桶共享空间。

一、哈希索引操作与写入开销

哈希索引通过哈希函数将 key 映射到桶或槽，再按计算出的候选位置查找条目。不同 key 可能映射到相同位置，因此插入时要处理冲突；条目增加到容量上限后，还要扩容。冲突处理和扩容都可能增加查找或写入工作。

不同冲突处理方式带来的写入量不同。链式哈希在插入、删除时修改指针；线性探测删除时可能要搬移后续元素，才能保持探测链可达；Cuckoo Hashing 通过驱逐腾出位置，装载因子较高时一次插入可能触发多次驱逐。这些做法会把一次逻辑更新扩展成多次数据或元数据写入。

降低搬移也有代价。2-choice hashing 只给每个 key 两个候选位置，额外写入少，但空间利用率可能受限。如果为少写而缩小可用位置，索引可能更早装满，或让查找变慢。

容量增长也会带来额外工作。out-of-place resizing 同时保留新旧两张表，迁移期间查找要检查两张表；全表重哈希则要搬动大量条目。索引设计需要控制冲突处理和扩容引入的写入，同时维持有界查找和较高空间利用率。

二、存储介质模型对哈希索引的要求

考虑这样一种存储介质模型：写入成本高于读取，写入耐久度有限，原子写粒度有限，崩溃可能中断多步写入。

存储介质特性对哈希索引的要求
写入成本高、耐久度有限冲突处理和扩容时减少额外写入，尽量避免搬动已有条目
原子写粒度有限不依赖整条 key/value 记录原子更新；有效状态等控制信息应能单独原子发布
崩溃可能中断多步写入安排数据与有效状态的写入顺序，使恢复时能识别未完成的操作

三、Path Hashing：写入友好的静态索引

2017：Path Hashing 的特性与结构

论文：A Write-friendly Hashing Scheme for Non-volatile Memory Systems，Pengfei Zuo、Yu Hua，MSST 2017。实现：github.com/Pfzuo/Path-Hashing。

背景

该工作研究非易失内存（non-volatile memory，NVM）上的哈希索引。本文将其中可持久化、可按字节寻址的内存简称为 PM（persistent memory）。

这类介质的写入延迟高于读取，写入耐久度也有限。论文指出，写延迟可能是读的 3–8 倍；PCM（phase-change memory，相变内存）的耐久度约为 10^7–10^8 次写入。这些约束使冲突处理产生的额外写入成为索引设计需要控制的成本。

现状

在写入成本高的存储模型中，链式、线性探测和驱逐式方案会因冲突处理而改写已有条目或相关指针。Path Hashing 为后续工作提供了一个写入友好的参照结构。

优化点

Path Hashing 用共享备用位置吸收冲突，不搬动已有条目，并把候选查找范围限定在一条或两条树路径内。它是静态结构，不支持动态扩容，也没有崩溃一致性协议或并发控制。

方案

倒置二叉树与共享备用位置

Path Hashing 将存储格（cell）逻辑组织成倒置完全二叉树。只有叶层 cell 能由哈希函数直接寻址；哈希值确定叶子后，叶子到根的路径就是该 key 的探测路径。叶子被占用时，插入沿路径向上找第一个空 cell。内部节点由多个叶子共享，越靠近根共享它的叶子越多，因此冲突条目可以使用共享备用位置，而不必搬动已有条目。论文将此机制称为 position sharing。

路径节点的地址由叶子编号和层级决定，不依赖表内当前内容。查找沿相同路径进行，删除只把目标 cell 标为空，无须回移后续元素。

Double-path hashing 用两个彼此独立的哈希函数生成两个叶子，提供两条路径，增加冲突项可用的位置。

Path Hashing 的双哈希探测路径（Figure 3: An illustration of path hashing (L = 3) with two hash functions.）

双路径增加了可用位置，但每条路径仍由多个树层组成，查找需要读取路径节点。Path shortening 减少参与探测的层数：删除倒置二叉树底部的若干层、只保留顶部若干层后，查找只读取保留层中的节点，读节点数随之减少。

Path shortening 缩短探测路径（Figure 4: An illustration of path hashing (L = 4) with path shortening.）

存储时，保留的树层按层连续映射到一维数组；给定叶子，路径节点的下标由层级和数组偏移计算。

每个 cell 保存 <key, value, token>，token 表示空或非空。插入只写新项所在 cell，删除只将 token 清零，不为冲突处理写日志。

若两条候选路径都满，插入失败项进入暂存区（stash）；论文将暂存区设为全表规模的 1%，查找时还需额外扫描暂存区。

四、新增约束下的索引设计演进

2018：Level Hashing 的一致性与扩容

论文：Write-Optimized and High-Performance Hashing Index Scheme for Persistent Memory，Pengfei Zuo、Yu Hua、Jie Wu，OSDI 2018。实现：github.com/Pfzuo/Level-Hashing。

背景

Level Hashing 面对的持久化约束包括有限的原子写粒度：在论文的 64 位处理器模型中，单次原子写的粒度最多为 8 字节。条目数据与有效状态分开写时，必须规定持久化顺序。

现状

Path Hashing 控制了冲突写入，但容量静态，且没有崩溃恢复机制。另一种 PCM 友好哈希表（PCM-friendly hash table，PFHT）将驱逐次数限制为一次，并把无法插入的条目放入暂存区；这样减少写入，却限制装载因子，查找暂存区还需线性扫描。

优化点

Level Hashing 要在控制冲突写入的同时，支持崩溃一致性和动态扩容；扩容期间查找仍只需访问同一张表。

方案

两层桶与有限搬移

每个桶有 4 个槽。每个 key 计算两个顶层候选桶，插入优先进入负载较低者，使条目分散到两个候选桶，降低单个桶先满的机会；另有 N/2 个底层桶，由顶层桶共享。每个 key 最多检查两个顶层桶和对应的两个底层桶，即 4 桶、16 槽，查找范围有上界。

两个顶层候选桶都满时，算法选取其中一个桶里的元素，尝试将该元素移到该元素对应的另一个顶层候选桶；若无法移入，再把新项放入共享底层。one-step movement 允许索引在少量搬移已有项的前提下，提高可用位置的灵活度。

Level Hashing 的双层桶与 one-step movement（Figure 1: The hash table structure of level hashing with 4 slots per bucket. (In these tables, “TL” indicates the top level, and “BL” indicates the bottom level.)）

Token 状态与写入顺序

每个槽有一个 token 表示有效状态，桶内 token 集中在桶头区。桶头区小于 8 字节时，可用一次原子写更新状态。插入先写数据，再执行 MFENCE（memory fence，内存栅栏）指令，确保先前写入完成后才将 token 从无效改为有效；如果在发布 token 前崩溃，未完成数据不会被识别为有效项。删除只将 token 清零。

扩容重哈希时，先向新位置写副本，再更新新旧 token；崩溃可能留下重复项，但不会因先使旧项失效而丢失数据。该过程无须日志。

更新时，若桶内有空槽，可把新值写到空槽并一次原子更新相关 token；没有空槽时才退回日志。

并发实现使用细粒度锁，每槽一把锁，插入最多锁两个槽。

中间层重哈希与表内扩容

原表有 N 个顶层桶和 N/2 个底层桶。扩容时在顶层增加 2N 个桶，旧顶层保留为新表的第二层，旧底层的 0.5N 个桶暂作 interim level。算法只将 interim level 重哈希到上面两层，完成后回收这批临时桶。重哈希量是原表 1.5N 个桶的三分之一；扩容后新顶层与原顶层合计 3N 个桶，正好是原表容量的两倍。扩容期间的查找始终访问同一张表。

Level Hashing 的原地扩容过程（Figure 3: The cost-efficient in-place resizing in the level hashing. (“IL” indicates the interim level.)）

连续扩容可能让底层变满，偶数次扩容时装载因子下降；论文称为 B2T（在顶层与底层之间重新分配条目）的策略可改善后续扩容时的最大装载因子。

扩容后约三分之二的条目位于底层，而静态查找仍先查顶层。动态查找按各层条目分布，优先查条目较多的一层，以减少固定查找顺序带来的额外探测。

2020：Clevel 的无锁并发与后台迁移

论文：Lock-free Concurrent Level Hashing for Persistent Memory，Zhangyu Chen、Yu Hua、Bo Ding、Pengfei Zuo，USENIX ATC 2020。实现：github.com/chenzhangyu/Clevel-Hashing。

背景

该论文指出，PM 的读延迟约为 DRAM 的 3 倍，写带宽约为 DRAM 的 1/6；崩溃一致性所需的 cache-line flush（将修改过的缓存行写回持久内存）和 fence 若位于关键路径，也会增加延迟。

现状

Level Hashing 的槽操作使用细粒度锁，扩容仍是单线程并由全局锁保护。持久化写入需要 flush 和 fence，若锁在这些操作期间持有，其他线程的等待时间会增加；锁竞争和扩容停顿限制多核可扩展性。

优化点

Clevel 要让操作在扩容期间继续并发，同时支持崩溃恢复。

方案

分层桶布局

Clevel 将两层结构推广为动态 level list：至少两层，相邻上层桶数是下层的两倍；第一层桶数最多，末层最少。每桶从 4 槽增至 8 槽，8 个 8 字节指针正好占 64 字节，即一条 cache line。

指针槽与 key/value 管理

槽保存指针，实际 key/value 对象由 PMDK（Persistent Memory Development Kit）的持久化原子分配器管理，因此可支持变长 key/value。

多槽桶与装载因子

Clevel 取消 one-step movement，以 8 槽桶增加每桶可容纳的位置，不再依靠插入时搬移来提高装载因子。

CAS 与 tag

Clevel 用比较并交换（compare-and-swap，CAS）实现无锁查找、插入、更新和删除。它把由 key 哈希导出的 16 位 tag 放入 x86_64 指针未使用的高位，先比 tag，匹配后才读取完整 key。

并发迁移正确性

迁移期间，同一 key 可能暂时有多个副本，Clevel 保留更靠近第一层的副本。查找按迁移方向从末层向第一层进行（bottom-to-top search）；若未找到条目，线程会比较本地 context 与全局 context 指针。指针不同表示 level list 在查找期间发生变化，此时重试。

插入使用 context-aware scheme：扩容期间不向末层插入；若插入后表开始扩容，且条目已写入末层，则不检查重复项，使用指向该条目的同一指针重新执行插入。

更新使用 rehashing-aware scheme：当表正在扩容、目标桶在末层且桶号落在两次进度快照之间时，补做查找和更新，避免后台线程删除正在更新的副本。

Clevel 扩容迁移与并发更新的冲突（Figure 4: The update failure. (“T1”: an update thread, “T2”: a rehashing thread, “t1-t4”: timestamps, “p”: pointer to the old item, “p0”: pointer to the updated item.)）

后台扩容与持久化进度

扩容分为 expansion 和 rehashing。Expansion 在当前第一层上方增加一层，新层桶数为原第一层的两倍；新层挂入 level list 后，用写时复制（copy-on-write，CoW）与 CAS 更新全局 context，并设为新的第一层。Rehashing 由后台线程从末层向第一层逐桶迁移。

Clevel 的多层索引与线程本地 context（Figure 2: The clevel hashing index overview.）

论文将全局 context 计为 17 字节：两个 8 字节指针和一个 1 字节布尔标志。context 只有在增加或删除层时才更新。

持久化时，数据 store 后执行 flush 和 fence，并持久化依赖的元数据。后台线程每完成一个桶，就在 PM 中记录进度；崩溃恢复后从下一个未完成桶继续。

PMDK 对象管理

PMDK 持久化原子分配器与每线程 persistent buffer 配合管理对象，避免泄漏。

隔离级别与缩容边界

论文采用 read uncommitted（读未提交，即查找可能读到尚未提交的更新）隔离级别，不支持缩容；作者指出缩容的搬移方向与扩容相反，并发下难以让所有线程保持统一查找方向。

2025：GPHash 的 GPU 执行与缓存机制

论文：GPHash: An Efficient Hash Index for GPU with Byte-Granularity Persistent Memory，Menglei Chen、Yu Hua、Zhangyu Chen、Ming Zhang、Gen Dong，FAST 2025。实现：github.com/LighT-chenml/GPHash。

背景

该工作讨论 GPU with persistent memory（GPM，即 GPU 与 PM 组合的系统）：统一虚拟寻址（UVA）将 PM 映射到 GPU 地址空间，GPU kernel 可直接按字节 load/store。

现状

CPU 哈希索引的执行方式不能直接套用 GPU：warp（GPU 协作执行的线程组）内线程走不同分支会产生分支分歧（divergence），不连续访存难以合并。PM 与 GPU 显存的带宽差距也会限制并行索引操作；NVIDIA V100 显存读取带宽可达 900 GB/s，而 6 个 Optane DC PMM 的 PM 读、写带宽分别为 39.6 GB/s 和 13.8 GB/s。

优化点

GPHash 面向 GPU 调整操作单位和 key 布局，并通过热点数据缓存减少 PM 访问。

方案

Warp 协作与 key 布局

GPHash 将多哈希位置、跨层共享和多槽桶结合起来：哈希函数只寻址顶层桶，其余层的桶由顶层桶共享；发生冲突时可在哈希位置及其共享桶中选择位置。

定长 key 直接存于槽中，value 存指针，使同一桶的 key 连续排列，便于 warp 合并访存；变长 key 仍以指针保存。

GPHash 以 warp 而非单线程作为一次操作的协作单位：ballot 找出尚未完成操作的线程，选择编号最小者为 active thread，再用 shfl 广播参数，由整个 warp 协作完成一个操作。这种执行方式可显式处理线程束内的分支分歧。

GPHash 的分层桶、共享位置与 key 布局（Figure 2: The hash table structure of GPHash (using 2 hash locations and 4-level buckets with 4-way associativity as an example).）

槽状态与崩溃恢复

槽状态和指纹放在 8 字节字段中，以 atomicCAS（原子比较并交换）转换状态。插入先将槽置为 INSERT，再写 key 和 value 指针，最后写入指纹；崩溃后可识别并清空遗留的 INSERT 状态。删除通过 CAS 将槽置为 EMPTY，更新通过 CAS 更换 value 指针。该状态机制用于避免每次操作都写日志。

GPHash 的无锁、无日志插入状态转换（Figure 3: The illustration of lock-free and log-free insertion (using the logical structure of a slot for easy understanding).）

BktCache 与显存缓存

BktCache（frozen-based bucket cache，冻结式桶缓存）按桶缓存热点数据到 GPU 显存。该设计让相邻两次加载之间的缓存成员保持不变，查找线程因此不必并发修改链式缓存元数据，降低了缓存管理争用。为减少加载过程对正在执行的索引操作的干扰，GPHash 用另一个 GPU stream（执行流）并发加载：先将旧映射设为 NOT_CACHED，等待目标桶引用计数归零，再复制新桶，并用 CAS 更新映射；缓存替换采用 LFU（least frequently used，最少使用频率优先）。

BktCache 的并发取桶过程（Figure 4: The overview of concurrent fetching mechanism.）

并发扩容限制

空间不足时，GPHash 新增一层，并以数千个线程并行扫描底层、重哈希条目；它不支持与普通操作并发扩容，因为论文认为同时维护 BktCache 和扩容期间的一致性较困难。

变长 key/value 支持

变长 key/value 还需要 GPU 上的高效并发变长分配器，论文将其留作未来工作。

五、实验设置与结果

Path Hashing（2017）的模拟评测与空间利用率

实验设置

论文使用 gem5 full-system simulator 配合 NVMain 模拟 PCM，而非真实 PM 硬件；配置为 4 核、2 GHz、16 GB，读延迟 75 ns、写延迟 150 ns。数据集包括 RandomNum、DocWord 和 Fingerprint。

结果

三个数据集上的空间利用率约为 95%；Fingerprint 上，25 层树保留 9 层时超过 92%，保留 11 层时接近完整树的利用率。论文还用归一化修改项数（normalized number of modified items）和平均写入缓存行数（average number of written cache lines）衡量写入量；Path Hashing 与 2-choice hashing 的这两项开销不随装载因子增长，而若干搬移型方案会增长。

不同方案的空间利用率（Figure 8: Space utilization ratios of hashing schemes.）

Level Hashing（2018）的性能与装载因子

实验设置

Level Hashing 用 Quartz 在 DRAM 上模拟 PM 延迟和带宽，并与真实 DRAM 实现对照。测试平台为 4 颗、每颗 6 核的 Xeon E5-2620（2.0 GHz）、32 GB DRAM，负载为 100M 个条目（约 3.2 GB），key 16 字节、value 不超过 15 字节。对手包括桶化 Cuckoo Hashing（bucketized cuckoo hashing，BCH）、PFHT 和 Path Hashing；论文也为对手补上其一致性机制。

结果

论文报告，只有约 1.2% 的插入触发 one-step movement。消融实验中，只有多槽桶时装载因子为 2.2%；依次加入双哈希位置、共享底层和 one-step movement 后，分别为 47.6%、82.5% 和 91.1%。最大装载因子对比中各方案均超过 90%；Path Hashing 的单项桶实现达到 94.2%。91.1% 来自消融实验，94.2% 来自方案对比，二者不是同一实验口径。

不同哈希表的最大装载因子（Figure 8: Maximum load factors of hash tables. (# in the NAME-# indicates the number of slots per bucket.)）

相对最强对手，Level Hashing 的插入加速为 1.4–3.0 倍、更新加速为 1.2–2.1 倍、扩容加速超过 4.3 倍；并发吞吐相对 libcuckoo 高 1.6–2.1 倍。

Clevel（2020）的实机并发评测

实验设置

论文在真实 Intel Optane DC 持久内存模块（persistent memory module，PMM）上评测：6 个模块共 1.5 TB、128 GB DRAM、24.75 MB L3，配置为 App Direct 模式并挂载 ext4-DAX 文件系统（DAX 指 Direct Access，即直接访问）。测试使用 36 个线程并固定在一个非一致性内存访问（NUMA）节点，软件为 PMDK 1.6；微基准包含 16M 个条目，宏基准包含 64M 个条目，key/value 各 15 字节。默认使用 1 个重哈希线程、35 个插入线程，并将层数控制在 4 层以内。

结果

论文报告装载因子为 86%，并称与 4 槽版 Level Hashing 相当；但两篇论文的硬件、key/value 大小和负载不同。相对 RECIPE 转换出的持久化 Cache-Line Hash Table（P-CLHT），吞吐最高提升 4.2 倍；正向查找的延迟加速比为 1.2–5.0×，负向查找为 1.4–9.0×；插入吞吐相对 pmemkv 的 concurrent_hash_map（cmap）高 1.4 倍。这些最大值来自各自对应的比较项。

GPHash（2025）的性能与消融分析

实验设置

评测平台为 NVIDIA Tesla V100、768 GB Intel Optane DC PMM（6×128 GB）、192 GB DRAM，CUDA 11.4。默认配置为 2 层、2 个哈希位置、每桶 8 槽，BktCache 占 20%，批大小 2^12；工作负载包括 Yahoo! Cloud Serving Benchmark（YCSB，Zipf 参数 θ=0.99，含 A、B、C、D、F 和 LOAD；LOAD 为 100% 插入）、Deep Learning Recommendation Model（DLRM）和 PageRank，测试 8 字节及 32 字节 key、128 字节 value，装载阶段为 16M 个条目。

结果

相对 CPU-assisted 数据管理方案，GPHash 最高快 27.62 倍；相对 GPM 哈希索引最高快 17.42 倍，最大装载因子为 92%。消融实验显示，warp-cooperative execution 可使吞吐最高提升 104.1%，定长 key 原位存储最高提升 13.7%。倾斜负载下 BktCache 提升最高为 40.9%，其中 YCSB A 为 17.6%、YCSB B 为 35.5%；较均衡的 YCSB D 与 LOAD 为 7.6%。这些数值对应论文各自的消融对照和负载。

六、存储介质特性如何落实为索引设计

写入成本高、耐久度有限，意味着索引必须控制冲突处理和扩容产生的额外写入。Path Hashing 通过共享备用位置吸收冲突，不搬动已有条目，并把查找限定在一条或两条树路径内；但它是静态结构，路径用尽后还要查暂存区。Level Hashing 通过 one-step movement 换取更高装载因子，代价是插入时可能改写已有条目。

原子写粒度有限，要求状态更新落在可原子写入的范围内；崩溃可能中断多步写入，则要求数据与有效状态按可恢复的顺序持久化。Level Hashing 将 token 集中在小于 8 字节的桶头区，先写条目再发布有效状态，并在扩容时先写新副本再更新新旧 token。它在单表内重哈希原底层的临时桶，避免迁移期间查找两张表。细粒度锁与全局扩容锁仍会限制并发；Clevel 因此用 CAS 处理无锁操作，并将重哈希移到后台、持久化逐桶进度，使崩溃后能从未完成处继续。

GPU 直接访问 PM 时，索引还要满足 warp 执行与访存合并的要求。GPHash 以 warp 为操作单位，将定长 key 直接放入槽以便合并访存，并用 BktCache 缓存热点桶、减少 PM 访问；槽状态仍由 8 字节原子操作维护。并发扩容和变长 key/value 管理仍有限制：它不支持与普通操作并发扩容，变长 key/value 需要专用分配器。
