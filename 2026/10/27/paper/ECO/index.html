ECO（Engine for Code Optimization）：用 LLM 优化 Google 生产代码效率

论文：ECO: An AI-Driven Code Efficiency Optimizer for Warehouse Scale Computers (Operational Systems)，Hannah Lin*、Martin Maas*、Maximilian Roquemore、Arman Hasanzadeh、Fred Lewis、Yusuf Simonson、Ameya Shringi、Hongwen Dai、Patrick Musau、Tzu-Wei Yang、Amir Yazdanbakhsh、Deniz Altinbüken、Florin Papa、Maggie Nolan Edmonds、Aditya Patil、Don Schwarz、Satish Chandra、Chris Kennelly、Milad Hashemi、Parthasarathy Ranganathan，20th USENIX Symposium on Operating Systems Design and Implementation（OSDI 2026）。Hannah Lin 与 Martin Maas 并列共同第一作者；作者来自 Google 和 Google DeepMind。论文：USENIX OSDI 2026。

TLDR： ECO 要解决 LLM 代码优化进入生产环境时的两项难题：从庞大代码库中找出值得优化的位置，以及确认自动生成的修改正确且确实有效。系统把 Google Wide Profiling（GWP）的全机群性能数据与历史优化样本结合，用 embedding-based search（先把代码映射为向量，再检索相似函数）找出高成本函数中的候选，再由经过 fine-tuning（用目标代码样本继续训练模型）的 LLM 生成修改。修改依次经过构建和相关测试、LLM 自审、负责相应代码的审核者（code owner）审核，以及部署后的性能监控。论文报告，一年的生产部署期内，ECO 成功落地 6,400 多个 commit、改动超过 25,000 行生产代码；摘要称 99.5% 的已提交 commit 没有因上线性能回归而触发回滚，正文报告比例高于 99.5%。作者把节省量概括为数十万 normalized CPU cores（NC）；论文将 1 NC 定义为特定硬件平台单核提供的 MIPS（million instructions per second），不能直接当作实际 CPU 核数。

一、背景：代码优化的长尾成本

Google 的代码库包含数十亿行代码，覆盖超过 100,000 个 package 和数千个项目。数据中心中的大量 CPU cycles 消耗在 long-tail workloads 上，也就是单项规模小到不值得投入工程师手动优化的工作负载。自动化优化因此有机会覆盖人工工作顾不过来的代码。

传统工具难以覆盖这些优化。编译器优化必须证明变换保持语义，因此不能利用程序员根据上下文判断安全的语义改写。静态分析工具则依赖预先写好的规则和有限的语法模式。例如，Clang-Tidy 可以为简单循环中的 vector<T>::push_back 建议添加 reserve，但难以处理跨多个循环、条件分支或 helper function 的向量填充，也缺少判断特定领域 API 语义所需的上下文。

ECO 的性能优化示例：消除冗余 map 操作和预留 vector 空间（Figure 3: Examples of ECO performance optimizations.）

LLM 能从少量示例中识别语法不同但意图相似的代码，也能结合周边代码和注释推断开发者意图。这让它有机会处理静态规则覆盖不到的优化；代价是模型生成代码的成本和错误风险都高。ECO 论文关注的正是如何让 LLM 在大型生产代码库中找到可改之处，并把生成的修改接入现有工程流程。

二、现状：生产代码效率优化挑战

此前的 LLM 代码优化研究主要在编程竞赛数据或小型基准上验证生成能力。它们没有充分覆盖大型代码库中的候选定位、code owner 审核、渐进式部署和效果归因。把 LLM 用到每一行代码既昂贵，也会产生大量低质量候选，让人工审核难以承受。

ECO 使用 LLM 生成针对 Google 生产代码的效率修改；论文讨论的对象是用 LLM 优化代码效率，不是优化 LLM 模型自身或 LLM 推理代码的效率。论文当前实现以 C++ 代码库为目标，但作者说明整体方法并不从根本上受限于 C++。

生产环境还要求区分“代码能通过测试”和“代码提高效率”。构建与单元测试可以发现部分错误，但测试覆盖并不完备，多数测试也不测量性能。即使补丁正确，性能变化仍可能依赖实际流量、硬件和部署进度；只看离线基准，无法证明它在 Google 的生产负载中产生了预期收益。

三、问题：opportunity localization 与 reliability

论文把两项相互独立的系统问题称为 opportunity localization（从大规模代码库中找出高影响优化位置）和 reliability（确保生成的变更正确且能改善效率）。前者要从数十亿行代码中定位高影响候选。只依赖性能热点，会得到大量需要人工判断的函数；只按历史代码模式搜索，又会忽略某个候选是否真的消耗了足够资源。ECO 需要同时利用运行时成本和历史优化形态。

后者要求生成的修改既正确又能改善效率。语法正确不代表语义正确，测试通过也不代表性能变好。若变更进入生产后引发回归，可能造成事故；若监控不能把观测到的指标变化关联到具体 commit，工程师也难以及时判断是否应回滚。因此，系统必须把自动验证、人工审核和上线后的持续监控接成一条流程。

四、方案：ECO 的优化流水线

ECO 首先从历史 commit 和人工整理的性能资料中构建优化样本。研究团队用关键词、提交说明、性能相关文档和内部整理的资料寻找已有改进，再把可重复的低效代码形态及对应修复整理为 performance anti-pattern database。论文列出 Copy、Map、Vector 等类别；Appendix A 说明，这些类别可以随时间扩展。团队会按出现频率和预期节省量选择要处理的类别，并维护对应的 prompt recipes（按优化类别准备的提示配置）。

从历史 commit 和整理资料中挖掘性能 anti-pattern 的流程（Figure 11: The approach and processing pipeline used to mine performance anti-patterns from our repository’s commit history and a number of curated additional data sources.）

论文使用几十年的历史代码变更训练模型；用于 fine-tuning 的专有数据集约含 55,000 个 commit，并包括源代码、提交元数据、代码修改及性能样本。论文中的评测使用 Gemini Pro 1.0；作者强调系统架构不绑定某个模型，也说明论文没有比较不同 LLM 的能力高低。

为了给历史样本找出现实候选，ECO 用 Clang 解析 C++ 文件，提取函数及其 AST（abstract syntax tree）派生的类型信息，并将每个函数整理为 IR（intermediate representation，供检索使用的函数表示）。GWP 周期性采样所有运行中应用的 program counter（采样到的执行位置）、调用栈和性能计数器，再把 profile 聚合到全局数据库。ECO 将 CPU 使用、内存分配和 LLC（last-level cache，即缓存层级中的最后一级）misses 等成本关联到函数；对调用树做剪枝，并把共享库函数的成本归到更适合修改的调用者。作者以每个 binary（可执行文件）的总 cycles 为参照，把候选函数成本阈值设为 C_min = 0.1%（下限）和 C_max = 25%（上限），由此得到超过 1,000 万个候选函数。

检索阶段先把历史样本和候选函数映射为向量，再用 ScaNN 的 approximate nearest neighbor（ANN）搜索取回每个 query 的前 500 个候选。论文比较了 Bag of Words（BOW）、通用 deep text embedding 和 deep code embedding；deep code embedding 使用 10 亿参数的双编码器，并以 2,500 万个相似函数对和代码修改样本进行 fine-tuning。检索后，系统还会根据 BLEU、ROUGE-L 两种文本相似度分数、类型重合和控制流关键词相似度排序。最终候选既要与已知优化形态相似，也要位于 profiler 标出的高成本代码中。

ECO 的代码向量检索与候选排序流程（Figure 6: ECO’s code retrieval approach. Source code is represented as vectors and ScaNN [15] is used to find nearest neighbors in the vector space. After retrieving nearest neighbors, we optionally rank code by similarity; these steps are marked by (*).）

候选确定后，ECO 用经过 fine-tuning 的 LLM 生成代码变更。工程师可以按优化任务选择 zero-shot（不提供示例）、few-shot（提供少量示例）、Chain-of-Thought（CoT，让模型按步骤生成分析和答案）或 ReAct（让模型在思考、执行和观察之间循环交互）prompting；论文没有发现某一种策略在所有任务上都最好。生成的修改先进入自动验证：Google 的持续集成系统运行受影响的构建、单元测试和集成测试；简单错误可自动修复，较复杂的失败会交给 LLM 尝试修正，仍失败的修改则放弃。通过测试后，LLM 再按常见错误、优化目标和具体 anti-pattern 的检查项进行自审。

ECO 使用的 prompting 策略模板（Figure 7: Templates for different prompting strategies used by ECO.）

ECO 生成的代码优化示例（Figure 8: Code optimization samples generated by ECO.）

LLM 自审通过也不等于自动合入。Google 的 code owner 仍负责最终审核，Rosie 工具会批量生成 commit 并定位需要审核的 code owner。变更进入生产后，GWP 继续观测对应 binary 的部署覆盖与性能指标；由于各服务渐进发布，ECO 将 commit 在 binary 中的采用情况与指标变化关联。若监控发现性能回归，Google 的生产工具可以自动回滚变更。

五、结果：生产部署与资源节省

检索评测包含 63 组成对的函数和已知优化（Copy、Map、Vector 各 21 对），另加入 1,740 个没有已知目标优化的函数，组成 1,803 个函数的候选库。论文以 mean average precision at 5（MAP@5，前五个结果的平均检索精度）衡量排序质量。deep code embedding 的 MAP@5 从未做第二阶段排序时的 0.1945 提高到排序后的 0.2036；deep text embedding 的 MAP@5 则从 0.0259 提高到 0.1633。结果表明 embedding-based search 结合后续排序能缩小候选范围，但这些分数来自论文构造的 63 个正例，不是生产命中率。

生成质量评测从真实代码库选取 48 个历史性能改进 commit；这些 commit 未用于 fine-tuning。四种 prompting 各生成五个样本，共 960 个候选修改，由人工按“正确且提高性能”为 1、“部分符合”为 0.5、“不符合”为 0 打分。zero-shot 和 ReAct 的平均质量分最高，分别为 0.531 和 0.510；CoT 平均为 0.344。CodeBLEU 按代码 n-gram 比较生成修改与历史修改；它与人工质量分总体同向，但改变量名或格式等非性能内容仍可能得到高分，加入大量文档说明的有效改动则可能得分偏低。受控 microbenchmark 使用 Copy、Map、Vector 三个手写 C++ 基准，这些基准不在模型训练集内；每个 prompt 抽样五次，温度设为 0.3，每个接受的改动测量十次，speedup 以未优化代码为 baseline（对照代码）。人工优化的 speedup 基线为 Copy 3.59×、Map 1.22×、Vector 1.82×。生成样本中，Copy/ReAct 的最佳值为 5.90×，高于该项人工基线；Map 与 Vector 的最佳值分别为 1.07× 和 1.35×，低于各自人工基线。作者总体判断专家仍优于模型；ECO 的价值在于覆盖更多代码。

这些生成候选的数量不能与整套系统的生产提交数混为一谈。论文报告 ECO 在一年的生产部署期内成功落地超过 6,400 个 commit，改动超过 25,000 行生产代码；摘要称 99.5% 的已提交 commit 没有触发回滚，正文报告超过 99.5% 无需回滚，Section 7.4 报告回滚率低于 0.5%。论文中的回滚是上线后因性能回归撤销变更，不是所有被测试或审核拒绝的候选。Figure 10 的横轴刻度至 350 天；正文只给出一年的统计期，没有列出日历起止日期。

生产性能由 GWP 观测。论文说明各服务会渐进部署，因此将某 commit 在 binary 中的采用情况与关键性能指标变化关联；但没有给出逐 commit 的精确对照窗口、反事实 baseline、MIPS 参考值或完整的节省计算公式。作者将 NC（normalized cores）定义为特定硬件平台上单核提供的 MIPS，并把全系统节省概括为数十万 normalized CPU cores。Table 5 对 Copy、Map、Vector 分别列出 331k、125k、618k NC Savings，但没有说明这些类别值是否可相加或如何与全系统 headline 汇总；因此不把它们自行合成为新的总数，也不将 NC 说成实际安装的 CPU 核数。

作者还估算了推理成本：按写作时 Gemini 3.1 Pro Preview 的价格区间，假设每次调用 10,000 个 token、其中 90% 为输入、每个 commit 调用十次，生成 10,000 个 commit 约需 3,000 美元。这是按当时价格和假设计算的估值，不是论文披露的生产账单。作者称人工审核和基础设施开销合计低于 Google 总资源的 0.1%，但没有公开精确数值；论文的节省量则是持续运行中获得的效率收益。
