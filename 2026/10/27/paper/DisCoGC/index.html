DisCoGC：分布式 Log-Structured Storage 中的 discard-based garbage collection

论文：Discard-Based Garbage Collection for Distributed Log-Structured Storage Systems in ByteDance，Runhua Bian 等，USENIX FAST ’26（24th USENIX Conference on File and Storage Technologies，2026）。论文页面。本文将 garbage collection 译作「垃圾回收」，后文用 GC；DisCoGC 是作者方案名，展开为 Discard-and-Compaction combined Garbage Collection。论文研究 ByteDrive 与 ByteStore 组成的存储栈。

TLDR： ByteStore 通过 compaction 把有效数据写入新 LogFiles，再删除旧文件；这种 GC 会增加 NAND flash 写入，而失效数据仍占据 SSD 空间。DisCoGC 将 discard 用于回收 LogFile 中的失效范围，减少有效数据搬移，并扩展相邻 discard 范围、对齐 Erasure Coding（EC，纠删码）stripe、合并请求并限制发送速率，以处理跨层分配单位错位和请求开销，再由低频 compaction 整理碎片。在 ByteDance 生产集群中，space amplification 从 1.37 降至 1.23，logical write amplification（LWA）降低 32%，physical write amplification（PWA）最多增加 10%，总 write amplification 降低 25%，Total Cost of Ownership（TCO）降低 20%；作者报告，相较 compaction-only GC，前台 latency 和每 TiB volume 带宽受影响可忽略，但未报告具体变化幅度。

一、背景：ByteStore 通过 LogFile 提供 append-only 存储

ByteStore 是 ByteDance 的分布式存储底座，通过 LogFile 向上层提供 append-only 接口，数据写入 LogFile 尾部而不在原位置覆写。论文聚焦 ByteDrive 与 ByteStore：ByteDrive 为计算实例提供虚拟 volume，并把上层随机写转换为 ByteStore 上的追加写。ByteStore 也支撑其他上层存储服务。

ByteDance 的分层存储栈（Figure 2: Hierarchical storage stack in ByteDance.）

ByteDrive 与 ByteStore 的关键层次如下。ByteDrive 的 Volume Layer 接收 4 KiB 粒度的读写和 trim 请求，并把 Logical Block Address（LBA）空间分到不同 Segment；Segment Layer 压缩数据、添加 block header，再追加到 LogFile，并用 log-structured merge-tree（LSM-tree）记录每个 LBA 最新数据的位置。ByteStore 将 LogFile 映射到 chunk，chunk 副本分布在不同 ChunkServer 上。

ByteDrive Segment Layer压缩 block 并追加到 LogFile；LSM-tree 保存每个 LBA 到 ByteStore 最新数据位置的映射。

这个栈中相邻层采用的分配单位不同。ByteDrive 的请求可从任意 4 KiB 边界开始，ByteStore 的 LogFile 接受任意长度追加，而 UFS 按 cluster 管理空间；启用 EC 时，discard 还要满足 stripe 的完整性要求。

论文在 ByteDrive Volume API 中把 4 KiB 范围释放接口称为 trim；其脚注则约定，软件栈各层之间传递的范围操作称为 discard，提交到 SSD 硬件的命令称为 trim。下文按这一约定区分两者。

二、现状：compaction 增加写入量，失效数据占据空间

BlockServer 会扫描 Segment 的 LSM-tree，计算每个 LogFile 的 garbage ratio（GR）；GR 超过阈值时，系统把有效数据从旧 LogFiles 复制到新 LogFiles，再删除旧文件。这个 compaction-only GC 回收了失效数据占用的空间，但复制有效数据会增加写入量。compaction-only GC 的 GR 为 1 − Valid Data / Total Data。

compaction 的回收过程（Figure 6: Compaction process.）

论文把 compaction 产生的上层额外写入称为 logical write amplification（LWA）；SSD 内部 GC 和 wear leveling 产生的额外写入称为 physical write amplification（PWA），总 write amplification 为 WA = LWA × PWA。失效数据留在 SSD 上会提高 space amplification。更激进的 compaction 能减少这类空间占用，却会增加 LWA、加快 SSD 磨损，并与前台 I/O 争用。作者称，write amplification 与 space amplification 使 ByteDance 每月承担数百万美元的额外 TCO。

三、问题：discard 受跨层边界、元数据和设备能力约束

discard 可以告知下层某段数据已无效，使系统释放其占用的空间，而不必把仍有效的数据复制到新 LogFiles。不过，多层存储的分配边界不一致会造成 boundary loss：失效数据位于范围边界时，可能因单位错位而无法释放。启用 EC 时，ByteStore SDK 需要按完整 EC stripe 处理 discard；UFS 则只能释放完整 cluster。EC 的 stripe packet 通常是 4 KiB 的倍数，但一个 cluster 包含 4 × 4,064 B data，并非 4 KiB 的整数倍，所以两层都可能留下无法回收的边界数据。论文的示例中，EC 对齐后仍有 200 KiB 范围中的 36% 留在边界；UFS 侧 4.03 个 cluster 中只能释放 3 个，另有 25.6% 未回收；两层合计损失超过一半。

discard 请求的 boundary loss（Figure 12: Boundary loss of a discard request.）

频繁的小范围 discard 还会反复修改 UFS 的 MetaPage，并消耗 CPU 和 SSD 的 I/O operations per second（IOPS）额度；在一次 LSM-tree 扫描中大量发出请求，会与前台 I/O 争用。discard 在 LogFile 和 chunk 中留下稀疏空洞，也会增加 LogFile、chunk 索引及 MetaPage 的管理量。

最后，只有 SSD 收到 trim 后，设备才会尽快获知相应 LBA 已无效。不同 SSD 的最大 trim IOPS 不同；trim 过慢会推迟空间释放，使 UFS 空间承压，并让 SSD 内部 GC 搬移更多失效数据，进而影响前台服务。因此，DisCoGC 必须同时处理跨层范围残留、discard 元数据开销、碎片增长和设备 trim 能力不足。

四、方案：DisCoGC 结合 discard 与 compaction

4.1 失效范围的异步 discard 回收路径

DisCoGC 在高层识别失效范围，再异步向下层提交 discard。BlockServer 扫描每个 Segment 的 LSM-tree，找出尚未 discard 的 LogFile 范围；随后经 ByteStore SDK 把这些范围映射到 chunk 及其副本；UFS 再定位对应 cluster、修改 MetaPage 释放空间。请求完成后，BlockServer 记录已成功处理的范围，避免重复提交。新追加数据可以复用已释放的 cluster。

这条路径跳过了 compaction 中读取旧 LogFiles 的有效数据并将其写入新文件的过程，目标是在不增加有效数据搬移写入的前提下，回收失效范围。作者将单个 discard 范围的回收描述为 constant-time 操作。

discard 的执行流程（Figure 11: Discard execution flow.）

4.2 EC 与 UFS 分配单位错位

EC 要按完整 stripe 处理相应数据范围，UFS 要按完整 cluster 释放空间。任意大小的 discard 请求与这两种单位都可能不对齐；因此，即使 LogFile 中的某段数据已经失效，范围边界处仍可能有数据无法回收。单独追踪 EC 与 UFS 两层未回收的边界数据，需要 BlockServer 在扫描 LSM-tree 时额外判断，还可能为每个 EC stripe 中的多个子范围维护大量状态。

4.3 boundary extension 与 EC stripe 对齐

BlockServer 检查新 discard 范围是否邻接先前已经 discard 的范围；如果邻接，就把当前范围朝既有范围扩展，这一机制称为 boundary extension。论文将扩展幅度描述为「最多数 MiB」，没有给出固定数值上限；两次操作因此轻微重叠。discard 对同一范围可重复执行，因此重叠不会妨碍重试；扩展既能回收旧请求留下的边界数据，也能避免当前请求再留下无法回收的边界数据。

扩展 discard 范围以消除 EC loss（Figure 13: Extend discard range to eliminate EC loss.）

在 EC 层，DisCoGC 把 stripe unit 配置为 n × 4 × 4,064 B，使其与 UFS cluster 的 data 容量对齐。这样可以消除 EC stripe 与 cluster 之间的 cluster loss；LogFile 接受任意长度请求，因此该配置不要求上层写请求也按相同单位对齐。

面向 discard 的 EC stripe 对齐（Figure 14: Discard-friendly EC stripes eliminate cluster loss (sector headers are omitted).）

4.4 discard 批处理与 IOPS flow control

UFS 把指向同一 LogFile 的多个 discard 范围合并为一个请求，从而减少 MetaPage 更新次数。每批范围数可配置为 1 到 64。BlockServer 按 Segment 生成 discard task，限制并发数 P，并优先选择可回收范围最大的 top-k Segment；k 根据 P 和正在执行的 task 数量计算。

若可回收范围很多，批处理后仍可能集中产生请求。BlockServer 因此限制 discard 请求的 IOPS，避免 discard 抢占过多前台资源。论文的部署经验是将批大小上限设为 32 或 64，并把 discard IOPS 调到最坏情况下 CPU 开销增加不超过 2%；完成调优后，多数场景的批大小约为 10，DisCoGC 的平均 CPU 开销约为 1.2%，常见值约为 1%。

4.5 discard 与 compaction 的分工

discard 与 compaction 承担不同任务：高频 discard 作为主要回收方式，避免搬移有效数据；低频 compaction 则合并被打散的 LogFile 和 chunk，并回收边界残留及较小的不可 discard 碎片。DisCoGC 将 Valid Data 定义为仍被 Segment 索引引用的数据，将 Total Data 定义为 LogFile 中所有尚未 discard 的数据；计算 GR 时，论文将未回收的边界数据计入 Total Data。LPB（loss per boundary）取 EC stripe 长度的一半，公式为 GR = 1 − Valid Data / (Total Data + LPB × Boundaries)。BlockServer 通常按分钟级间隔调度 compaction：LogFile 数量未超过阈值时，优先选 GR 最高的 top-k Segment；超过阈值后，改为选择 LogFile 数量最多的 Segment，以压低元数据开销并整理碎片。k 由并行度控制机制管理。

碎片增加会使 SSD 内部操作变多，DisCoGC 的 PWA 因而比 compaction-only GC 高 2%–10%；但 discard 减少了回收过程中的数据搬移，论文报告总 NAND 写入量仍会下降。

4.6 SSD trim 的过滤与合并

trim 到达 SSD 后，flash translation layer（FTL）先在前台记录 trim log、使 SSD 内部写缓存中的相应数据失效，再异步更新 LBA-to-PBA table。论文观察到，SSD Model A 的 trim 范围小于 128 MiB 时，trim latency 小于 1 ms；更大的 trim 可能需要先 flush 写缓存，因而提高前台 latency。

UFS 的 trim filter 只提交至少 128 KiB 的范围；trim merger 则把 LBA 上相邻的小范围合成较大的 trim 请求。128 MiB 是论文观察到的 Model A 延迟阈值示例，128 KiB 是评测使用的 filter 阈值，两者对应不同机制。未达到 filter 阈值且未与相邻范围合并的请求不会发给 SSD 执行 trim；论文指出，这些未 trim 的小范围会在后续 SSD GC 中引起额外写入。filter 和 merger 用于减少 trim 请求数、适应设备最大 trim IOPS；具体阈值需要按目标 SSD 的 trim 能力调节。

4.7 discard 状态持久化与运行监控

DisCoGC 先在 offline 集群渐进启用，再按 volume 扩大部署。canary 阶段使用 mock discard：只在内存记录状态，不实际释放数据，用于检查软件正确性和数据安全。

discard 状态由 BlockServer 管理。每个 Segment 有一份 discard LogFile，使用 write-ahead log（WAL）持久化状态：扫描后记录已发出的范围，discard 成功后再记录成功范围。重启时比较 issued 与 successfully discarded 范围，重试中断的操作。对每个被回收的数据 LogFile，BlockServer 用 bitmap 按未压缩数据的 4 KiB block 跟踪范围；成功范围可由 issued bitmap I 和 failed bitmap F 推得，S = I & (~F)。Roaring bitmap 可将连续位压缩，使 bitmap 大小减半；由于失败范围通常较少，只记录 F 还能使总 bitmap 空间再减少 25%–45%。

监控在 discard ratio（已成功 discard 的范围总大小 / 可 discard 数据总大小）连续 10 分钟低于 80%、且 SSD 空间使用率超过 85% 并继续上升时告警。若 I/O utility 低于 70%，运维提高 discard 并发度和最大 IOPS；论文没有定义 I/O utility 的统计口径。若集群仍有 offline workload，则可对其限流；若负载已高且不能限流，运维会增加备用 ChunkServer 或迁移 volume。

五、结果：生产 TCO 降低 20%

5.1 生产集群与离线评测结果

生产集群使用混合 online、SAR 和 offline workload；每台服务器配有双路 24 核、48 线程 CPU、256 GiB DRAM、200 Gbps 网络和 16 块 SSD。离线 testbed 为 10 台相同配置的服务器，回放上述三类 trace 和 Flexible I/O Tester（FIO）benchmark；除非特别说明，评测使用 SSD Model A。Model A 使用 PCIe 5.0、容量 7.68 TiB、读写带宽 13.0/9.0 GiB/s、读写 IOPS 2,800 K/400 K、trim IOPS 160 K；Model B 使用 PCIe 4.0、容量 7.5 TiB、读写带宽 6.5/3.5 GiB/s、读写 IOPS 900 K/200 K、trim IOPS 6 K。

生产监控中，compaction-only GC 与 DisCoGC 的 space amplification 分别为 1.37 和 1.23；DisCoGC 的 LWA 降低 32%，PWA 最多增加 10%，总 write amplification 降低 25%，估算 TCO 降低 20%。

超过 90% 的 LogFile 失效范围大于 128 KiB，超过 70% 大于 1 MiB，说明生产混合负载中存在大量适合 discard 的较大范围。作者报告，相较 compaction-only GC，前台 latency 和每 TiB volume 带宽受影响可忽略；正文没有给出具体变化幅度。

5.2 机制贡献、trim 约束与资源代价

在固定 space amplification 的 factor analysis 中，online、SAR、offline 分别设为 1.2、1.05、1.2。相对 compaction-only GC，加入 discard 和 flow control 后，LWA 降低 8.4%–13.9%，discard ratio 为 0.45–0.88；批大小设为 64 后，LWA 再降 2.7%–11.7%，discard ratio 接近 1；加入 boundary extension 后，LWA 再降 5.5%–16.1%。作者报告这些配置下前台带宽和 latency 保持稳定，但没有给出变化幅度。

DisCoGC 各机制的 factor analysis（Figure 19: Factor analysis.）

在 offline trace、space amplification 固定为 1.2 的 SSD 空间使用率实验中，空间使用率从 60% 提高到 80% 会增加 PWA；作者报告 LWA 和前台 latency 不随空间使用率改变，但没有给出具体幅度。

在 space amplification 为 1.5 的重负载 FIO 实验中，提高 discard IOPS 上限会降低 LWA；作者同时报告限速上限提高会使前台 latency 变差，原因是 discard 与前台任务争用 CPU，正文未给出变化数值。

不同 discard IOPS 限制下的性能（Figure 21: Performance with different discard IOPS limit.）

论文定义的 delete latency 是 compaction 期间删除一个 chunk 的平均时间；一个 chunk 可能包含多个需要在 SSD 上 trim 的范围。这与 4.6 节中针对单次 trim 的 trim latency 不同。trim 评测使用 8 MiB 粒度的随机写、每次 64 KiB block，并启用 boundary extension。Model A 上，只启用 trim 时 PWA 从 1.4 降至 1.3，delete latency 增加约 600 μs；此时 trim IOPS 约为 5 K，低于设备 160 K 的上限。增加 128 KiB filter 后 PWA 为 1.35，filter 进一步限制了实际 trim；再加 merger 后 PWA 为 1.33，仍高于 trim-only，因为有些小范围无法合并，另一些范围在被合并和 trim 前已多次搬移。Model B 的 trim IOPS 为 6 K，trim-only 会达到设备上限；正文称此时 PWA 和 delete latency 较高，但未给出数值。启用 128 KiB filter 后，PWA 为 1.74、trim IOPS 为 2.8 K、delete latency 为 34 ms；再加 merger 后 PWA 降至 1.65，trim IOPS 和 delete latency 略有增加，正文未报告增量。论文没有评测 Model B 完全不使用 trim 的情况，因为该设备的 SSD 内部 GC 能力不足。

两款 SSD 上 trim 相关优化的影响（Figure 22: The impact of trim-related optimizations across different SSD models.）

在 offline trace、SSD 空间使用率 60%、space amplification 为 1.25 的资源测试中，DisCoGC 的 CPU 使用量为 compaction-only GC 的 82.9%，memory 使用量为其 102.9%。CPU 降低来自 compaction 次数减少；memory 略增来自 discard bitmap。
