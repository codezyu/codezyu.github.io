Bidaw：面向交互式 LLM 服务的计算—存储双向感知

论文：Bidaw: Enhancing Key-Value Caching for Interactive LLM Serving via Bidirectional Computation–Storage Awareness，Shipeng Hu、Guangyan Zhang、Yuqi Zhou、Yaya Wei、Ziyan Zhong、Jike Chen，USENIX FAST ’26（2026）。USENIX 论文页

TLDR： 交互式 LLM 服务每轮推理前都要读取历史 key–value tensors（键和值张量，简称 KV）。OPT-13B、200 GB performance layer（性能层）的测试中，该层平均容纳 40.1% 的 KV 时，现有淘汰策略命中率仍约为 20%；KV 加载时延的变异系数超过 90%。Bidaw 按 KV 所在层和大小调度请求，用前一轮回答长度预测下一次 KV 访问，并缓存单位空间能节省更多计算的历史张量。论文在 A800、200 GB host memory（主机内存）和 1.5 GB/s SSD 配置下报告：相较现有方案，OPT-13B 响应时延改善最高为 3.58×；多模型测试中，相较现有方案，在相近时延下支持的用户到达率提高 1.43–1.83×。ShareGPT 测试中，相较 FlashGen，在时延相近时支持的用户到达率提高 1.40×。

一、背景：多轮对话需要复用历史 KV

交互式 LLM 服务由用户和模型轮流发言。模型生成每一轮回答时，需要读取该用户此前对话产生的 key–value tensors（键和值张量，简称 KV）；本轮推理也会生成供后续轮次使用的 KV。GPU 内存有限，历史 KV 因而放在由主机内存和 SSD 组成的 two-tier storage（双层存储）中：主机内存作为性能层，SSD 作为 capacity layer（容量层）。新请求到来后，计算引擎要先把需要的历史 KV 加载进 GPU，再开始推理。

每一轮 LLM 回答都使用此前对话轮次的 key–value tensor（KV）（Figure 1: Each round’s LLM answer is generated using key–value tensor(s) from previous conversation rounds.）

如果不保留历史 KV，服务就得在新一轮到来时重新计算此前对话。论文使用的 interactive conversation workload（交互式对话工作负载）包含超过一百万轮对话，平均每个用户有 22.4 轮；重复计算最高可占总计算量的 93.1%。缓存历史 KV 能省去这部分重复计算，但主机内存装不下所有用户的 KV，SSD 读取又会进入请求的关键路径。

交互式 LLM 服务的双层 KV 缓存架构（Figure 2: Caching KVs of history conversations in the two-tier storage for interactive LLM serving.）

二、现状：现有缓存命中率约 20%

现有系统 CachedAttention 和 FlashGen 都把历史 KV 放在双层存储中。CachedAttention 使用 queue-enhanced（队列增强）淘汰策略，并尝试提前把等待请求需要的 KV 从容量层加载到性能层；FlashGen 根据 GPU 内存是否能容纳请求来调度，并采用包含式缓存，在 SSD 中保留性能层 KV 的副本以便快速淘汰。论文指出，已有公开 LLM 服务工作负载通常缺少对分析 KV 访问所需的时间戳或用户级信息；论文因此还使用了包含真实交互时间信息的服务工作负载。

该工作负载的平均用户问题长度为 36 个 token（词元），平均模型回答长度为 45 个 token；每段对话的平均轮数、中位数和第 90 百分位数分别为 22、18 和 45。多轮对话持续期间，用户会间隔一段时间再发送下一问，多个用户的历史 KV 因而同时留在存储中。

用户对话时长与交互轮数分布（Figure 4: The CDF of 1) duration, and 2) interaction rounds, of user conversations.）

论文只分析重复计算消除后可由一台 80 GB A800 承担的用户到达率，以免引入计算瓶颈。OPT-13B 测试中，性能层为 200 GB，约为 GPU 内存的 2.5 倍；并发 KV 总量最高达到性能层容量的 3.91 倍。

并发缓存 KV 大小与用户数随用户到达率的变化（Figure 5: The sizes of concurrently cached KVs and the number of concurrent users with increasing user arrival rates.）

即使性能层容纳了平均 40.1% 的 KV，CachedAttention 的 queue-enhanced 淘汰策略、FIFO（first in, first out）和 LRU（least recently used）的命中率仍只有约 20%。在 30 个新用户/分钟的 OPT-13B 设置下，80% 的 KV 访问 weighted reuse distance（加权重用距离，即两次访问同一用户 KV 之间其他不同 KV 的总大小）超过 200 GB 性能层容量。

KV 访问的 weighted reuse distance 与命中率（Figure 6: The poor temporal locality and the low hit rate of KV accesses.）

请求间的 KV 加载时延也相差很大。差异来自历史对话长度造成的 KV 大小差异，以及主机内存与 SSD 之间的带宽差距。论文按不同到达时间窗口统计 KV 加载时延，报告其变异系数超过 90%；即使只比较 5 秒内到达的请求，作者仍观察到较大差异。对于按到达顺序调度请求的系统，较早发出的 SSD 读取会占住队列，使后到且只需从主机内存读取 KV 的请求也可能等待。

不同到达时间窗口下 KV 加载时延的变异系数（Figure 7: The large coefficient of variation, of KV loading times among requests arriving within different time intervals. Requests arriving even within a very short time interval (e.g., 5s) have greatly varying KV loading times.）

各请求加载的 Key/Value 大小（Figure 8: Wide variation of loaded Key/Value sizes.）

在 A800、OPT-13B、200 GB 主机内存和 1.5 GB/s SSD 带宽设置下，论文把 CachedAttention 与 FlashGen 和「所有 KV 都能从主机内存加载」的模拟理想方案比较：现有系统的响应时延最高为理想方案的 3.8 倍，吞吐最高只有理想方案的一半。这里的吞吐对比按相近响应时延下每分钟可服务的用户数计算。

现有双层缓存相对理想缓存方案的服务性能差距（Figure 3: Big serving performance gap between existing works with two-tier storage and the simulated ideal caching solution with all KVs loaded from the performance layer.）

三、问题：计算引擎与存储缺少双向感知

低效来自计算引擎与双层存储缺少双向信息。计算引擎调度请求时，不知道每个请求的 KV 位于主机内存还是 SSD，也不考虑其大小对应的读取时间；存储侧淘汰 KV 时，则只根据过去的 KV 访问和排队信息，拿不到计算引擎观察到的用户对话节奏。

这两种信息缺失造成不同的问题。计算引擎若先调度一个需要长时间读 SSD 的请求，GPU 必须等它的 KV 加载完成，后续只需从主机内存读取 KV 的请求也会排队。SSD 读取通常需要数百毫秒，而 GPU 计算只能与首轮、持续几十毫秒的推理迭代重叠，因而无法靠简单的计算与输入/输出（I/O）重叠消除等待。存储淘汰若只依赖过去访问，在用户长时间间隔发问的工作负载上又难以预测下一次 KV 访问，导致性能层命中率低。

Bidaw 要把这两类信息连起来：计算侧用存储层级和 KV 大小安排请求；存储侧利用计算引擎生成的回答预测用户下一次访问，并据此决定把哪些 KV 留在主机内存。

四、方案：Bidaw 的双向感知机制

Bidaw 的计算侧把 KV 的位置和大小交给调度器，存储侧接收每个用户最新一轮的模型回答长度。系统据此减少慢 I/O 对可运行请求的阻塞，并估算每个用户下一次访问性能层 KV 的机会。计算侧采用 I/O-aware request scheduling，存储侧采用 previous-answer-based eviction strategy。

Bidaw 系统架构（Figure 9: System overview.）

4.1 双队列式 I/O-aware request scheduling

每个新请求到达时，计算引擎检查它的 KV 所在层。KV 已在主机内存的请求进入 ready queue；KV 在 SSD 的请求进入 preparing queue，等待读入主机内存后再提升到前一队列。GPU 只从 ready queue 取请求做推理，因此 SSD 读取不会挡住只需较快主机内存读取的请求。若队首请求不适合当前剩余 GPU 内存，调度器会跳过它，继续找能放入 GPU 的请求。

ready queue 按请求最初到达时间排序，避免请求在 SSD 队列等待后因提升时间较晚而被排到队尾。对 preparing queue，Bidaw 使用 disk-HRRN（Highest Response Ratio Next 的定制策略）按读取优先级发出 SSD I/O；策略同时考虑 KV 大小与请求等待时间。其响应比为：

优先读取较小的 KV，可以让短 I/O 尽快完成；等待时间持续增加又会逐步提高大 KV 请求的优先级，避免长期饥饿。双队列与该优先级策略共同减少 SSD 读取造成的队头阻塞。

4.2 基于 hit potential 的 KV 淘汰策略

hit potential 是对用户下一次 KV 访问命中率的估计，按各个 weighted reuse distance 区间的访问概率和该区间命中率加权计算。交互式对话中，用户要花时间阅读或收听模型回答，再理解内容并组织下一问；回答越长，下一次访问通常越晚，中间更可能出现其他用户的 KV 访问，因此 weighted reuse distance 的下界也越大。

论文分析 8:00–20:00 不同时段采集的十分钟 trace（访问轨迹），并测试不同用户到达率；观测按回答长度分组后，用 IQR（interquartile range，按四分位距筛选）方法去除离群值。12 组测试中，前一轮模型回答长度与 weighted reuse distance 下界的 Spearman 秩相关系数为 0.94–0.98。Bidaw 因此由计算引擎记录每个用户最近一轮的回答长度，再结合历史访问统计，预测该用户下一次 KV 访问的 weighted reuse distance 下界。

前一轮回答长度与 weighted reuse distance 下界的相关性（Figure 12: The weighted reuse distance and the previous round’s model answer length for requests with different times and difference user arrival rates. Each dot represents a KV access corresponding to one request. The lower bound of the weighted reuse distance is marked in red. There exists positive correlation between the lower bound of the weighted reuse distance and the previous round’s model answer length.）

只有预测距离还不能直接决定淘汰对象。论文先用后台 ghost cache 回放过去的访问 trace，并按 Belady 最优淘汰策略估算不同距离区间的命中率，作为未来命中机会的上界。距离小于性能层容量的区间命中率设为 1；中间的 promising reuse distance 再切成多个细粒度区间；超过最优策略也无法命中的 extreme reuse distance 区间命中率设为 0。随后，系统根据每个用户历史 weighted reuse distance 分布估计下一次访问落入各区间的概率，并用回答长度预测的下界排除不可能的较小距离区间。加权计算各区间的概率和命中率得到该用户的 hit potential；论文在公式中将该值记为 Overall_potential：

4.3 Cost efficiency 驱动的历史张量选择

GPU 推理会产生多种供后续轮次使用的中间张量，它们大小不同，重新计算所需的浮点运算量也不同。Bidaw 定义 Cost efficiency（缓存效率）为可节省的计算量与所需存储空间之比：

在 OPT-13B、2048 个 token 的历史对话设置下，论文测得 tensor 6（normalized activation）的 Cost efficiency 为 51.0 GFLOPs/MB（每 MB 空间节省 51.0 十亿次浮点运算），高于 KV 张量的 30.5 GFLOPs/MB。对 MHA（multi-head attention，多头注意力）模型，Bidaw 缓存该 storage-efficient tensor；读取后再将它转换为推理所需的 KV。转换放在低优先级 CUDA stream 中，与其他请求的正常推理并行。论文观察到，历史缓存减少重复计算后，仍有超过 30% 的 GPU streaming multiprocessors（SMs）空闲，可用于这项转换。对 GQA（grouped-query attention，分组查询注意力）模型，KV 本身较小，论文改为直接缓存 KV。

各中间张量的存储大小、节省计算量和 Cost efficiency（Figure 14: The size (per decoder layer), saved computing amount (per decoder layer) and cost efficiency (saved computing amount / size) when caching each intermediate tensor for OPT-13B model with a 2048-token history conversation.）

4.4 连续批处理中的请求与 KV 管理

系统采用 continuous batching：批次中先完成推理的请求会立即释放 GPU，系统可以接纳新请求。淘汰时，Bidaw 保留等待队列请求所需的数据；容量层已有性能层 KV 的副本，因此淘汰时只需移除主机内存中的副本。

4.5 双粒度 GPU 内存块管理

传统 PagedAttention 为提高 GPU 内存利用率会分配许多不连续的小内存块。Bidaw 的设计目标是提高 CPU-GPU 传输带宽利用率，因此为历史对话和已知长度的用户问题分配 256 个 token 的大块，为长度未知的回答分配 16 个 token 的小块。大块可以拆成小块，小块也能合并回大块，以减少 GPU 内存碎片。

五、结果：端到端收益与开销

5.1 多模型与多工作负载评测

实验使用一台配备 80 GB A800 GPU、200 GB 主机内存的服务器；容量层由 4 块 SATA（Serial ATA） SSD 组成 RAID-5，带宽为 1.5 GB/s。测试的模型包括 OPT-6.7B、Qwen-7B、OPT-13B、Qwen-14B 和 OPT-30B。对照方案为 vLLM、CachedAttention、FlashGen，以及假设所有 KV 都能从主机内存读取的模拟理想方案。工作负载包括论文从产业合作方采集的百万级交互式对话工作负载，以及公开 ShareGPT 多轮对话；ShareGPT 没有真实时间戳，论文按 Poisson（泊松）分布模拟请求到达时间。

在交互式对话工作负载中，Bidaw 相比现有方案在 OPT-13B 上的响应时延改善最高为 3.58×；跨不同模型的平均响应时延最高降低 83.9%。在相近响应时延下，Bidaw 相比现有方案支持的用户到达率提高 1.43–1.83 倍。

不同模型下每条请求的平均响应时延（Figure 15: The average response latency for each request across different models.）

将主机内存从 120 GB 调整到 200 GB 时，Bidaw 仍能在相近时延下支持现有方案 1.75–2.19 倍的用户到达率。

不同主机内存容量下每条请求的平均响应时延（Figure 16: The average response latency for each request with varying host memory sizes.）

论文通过从主机内存复制 KV 并注入额外时延来模拟 5 GB/s SSD。带宽从 1.5 GB/s 提高到 5 GB/s 后，FlashGen 的吞吐从 15.18 增至 20.23 用户/分钟；Bidaw 从 27.81 增至 30.35 用户/分钟。提高 SSD 带宽能改善 FlashGen，但仍未消除 I/O 瓶颈，Bidaw 在这组设置下仍支持更多用户。

ShareGPT 的 OPT-13B 测试中，FlashGen 和 Bidaw 的平均响应时延分别为 9.09 秒和 8.70 秒；在相近时延下，Bidaw 支持的用户到达率是 FlashGen 的 1.40 倍。相对 vLLM、CachedAttention 和 FlashGen，Bidaw 的响应时延最高分别降低 69.8%、65.8% 和 56.9%。提升幅度小于交互式对话工作负载，论文将其归因于 ShareGPT 缺少真实时间戳：模拟到达时间下，previous-answer-based eviction strategy 没有降低 miss rate（缓存未命中率）。与交互式对话工作负载相比，ShareGPT 单轮回答 token 数更多，因此平均时延略高；每位用户的对话轮数较少，因此整体吞吐略高。

公开 ShareGPT 工作负载下每条请求的平均响应时延（Figure 17: The average response latency for each request on public ShareGPT workload.）

论文将 Bidaw 称为响应准确率无损的方案。它不采用丢弃部分 KV 的有损选择；MHA 模型会把缓存的 storage-efficient tensor 转换为推理所需 KV。I/O-aware request scheduling 只改变不同用户请求的先后顺序，不改变单个请求内部生成回答的计算顺序。

5.2 命中率、调度开销与尾延迟

在 OPT-13B、每分钟 30 个用户的测试中，Bidaw 的 I/O-aware request scheduling 把请求平均排队时间从 5.76 秒降到 2.45 秒，降低 57.5%。

请求排队时间的 CDF（Figure 19: CDF of the request queuing time.）

论文在 OPT-13B 上改变主机内存大小和用户到达率来评估性能层 miss rate；previous-answer-based eviction strategy 相较 queue-enhanced 最多降低 57.6%，相较 LFU（least frequently used）、LRU 和 FIFO 等通用策略最多降低 69.9%。

不同淘汰策略下的性能层 miss rate（Figure 18: The performance layer miss rate with different eviction strategies.）

Bidaw 每次调度平均耗时 0.62 ms；后台淘汰平均耗时 0.35 ms，ghost cache 中的 Belady 最优淘汰耗时 2.86 ms。把 storage-efficient tensor 转为 KV 要几十毫秒，论文称相较数百或数千毫秒的响应时延影响很小；转换在低优先级 CUDA stream 中运行。

调度、淘汰与 KV 转换开销（Figure 20: Overhead analysis. (a) The CDF of the scheduling operation cost. (b) The average time of each eviction operation under our previous-answer-based eviction strategy and the optimal eviction strategy. (c) The execution time for transforming the storage-efficient tensor into the KV tensor.）

在 OPT-30B 消融实验中，加入 I/O-aware request scheduling 后，平均响应时延相对基础版本最高改善 1.58×；再加入 previous-answer-based eviction strategy 后，吞吐提高 1.25 倍；加入 storage-efficient tensor 缓存后，吞吐进一步提高 1.10 倍。

各项技术的消融结果（Figure 21: Effects of individual techniques.）

OPT-30B 的尾延迟测试中，Bidaw 相比 CachedAttention 和 FlashGen 的 P90（第 90 百分位时延）分别降低 52.96% 和 66.63%，P95（第 95 百分位时延）分别降低 49.30% 和 62.64%，P99（第 99 百分位时延）分别降低 47.03% 和 56.81%。
