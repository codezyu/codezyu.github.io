论文：Strata: Hierarchical Context Caching for Long Context Language Model Serving，Zhiqiang Xie（Stanford University and NVIDIA）、Ziyi Xu（Shanghai Jiao Tong University）、Mark Zhao（University of Colorado Boulder）、Yuwei An（Carnegie Mellon University）、Vikram Sharma Mailthody（NVIDIA）、Scott Mahlke（NVIDIA and University of Michigan）、Michael Garland（NVIDIA）、Christos Kozyrakis（NVIDIA and Stanford University），OSDI ’26（2026）。论文 PDF。

TLDR： 长上下文服务要把 KV cache（模型为已处理 token 计算并保存的 key、value 状态）从 CPU 内存或 SSD 装入 GPU HBM（high-bandwidth memory，GPU 上的高带宽内存）；Qwen2.5-14B 的 LooGLE 测试中，page size 32 的 I/O 曲线显示，朴素 CPU offload 最多有 74% 的 prefill（处理新输入与上下文的阶段）时间耗在 KV 传输上。Strata 在 SGLang 中以 GPU-assisted I/O（由 GPU kernel 并行搬运数据）分离 GPU 计算布局与主机、SSD 传输布局；cache-aware scheduler（按缓存状态和加载开销组批的调度器）会延后首个 cache miss（缓存未命中）尚在解析时到达的同上下文请求，以抑制 delay hit（首个 cache miss 尚未完成时，同一上下文的后续请求也被记录为 cache miss），平衡加载量与计算量，并用互补任务填补加载停顿。在 H200 上，Llama-3.1-70B-Instruct（4 张 GPU 张量并行，128K 上下文窗口）处理 LooGLE 时，平均输入长度为 21,613 tokens；在相同平均 Time To First Token（TTFT，从请求到首个输出 token 的时间）下，Strata 的输出 token 吞吐最高分别达到 vLLM v0.8.5 + LMCache v0.2.1 的 5 倍和 TensorRT-LLM-HiCache v0.17.0 的 3.75 倍。论文称该系统已集成进 SGLang，并部署于多家 AI 公司的生产环境。

一、背景：长上下文的 KV cache 层级存储

LLM 推理分为 prefill 和 decode。prefill 处理用户新输入及需要复用的上下文，并生成后续计算要用的 KV cache；decode 则逐 token 自回归生成输出，不必为每个新 token 重算此前所有层的注意力。上下文越长，prefill 计算和 KV cache 占用都越大，decode 阶段还会继续扩展 KV cache。

KV cache 的复用有两种范围：同一请求内，后续 token 继续使用已有状态；不同请求之间，系统可以按共同前缀复用已计算状态。后者常称为 context caching 或 prefix caching，可减少重复 prefill。但 GPU HBM 容量有限：论文举例，40 GB HBM 对 Llama-8B 约能容纳 30 万 tokens，少量长文档或几百轮对话就可能占满。缓存因而向 CPU 内存、SSD，乃至远端内存池扩展；命中这些较慢层后，系统仍须把 KV cache 加载回 GPU 才能计算。

分层缓存能增加可复用数据的容量，却将数据移动引入请求关键路径。长上下文负载因此同时受计算、缓存容量和层间带宽影响；是否命中 GPU HBM 以外的层，会改变 prefill 所需的加载时间。

二、现状：小 page 降低传输效率

PagedAttention 将 KV cache 切成可动态分配的 page，允许逻辑相邻的 token 分散存放，减少为连续大块内存预留空间造成的浪费。推理内核可以高效处理这些小 page，但跨 CPU、GPU 或存储层移动时，page 太小会形成大量小 I/O。论文指出，TensorRT-LLM、vLLM 和 SGLang 常见 page 大小分别为 32、16 和 1 token；单个 token 的 KV 状态可能从几十 KB 到数 MB，现有 GPU cache 布局还会让一个逻辑 page 分散在多个 layer。

I/O 吞吐受并发数、单次传输大小和延迟共同限制。论文用 Little’s Law 写作 (C=\lambda L)，其中 (\lambda) 是 I/O 到达率、(C) 是平均并发数、(L) 是平均延迟；若单次传输平均大小为 (S)，稳定状态下吞吐 (X=\lambda S=C S/L)。当应用并行度、驱动队列和硬件队列限制了并发时，提高单次传输大小更实际。要达到 PCIe 5.0 理论带宽的 75%–80%，论文指出通常需要 1–2 MB 的传输。

然而，增大 page 会使缓存匹配变粗，降低 cache hit rate（缓存命中率），因为缓存匹配按 page 进行。论文在 H200 上用 Mistral-24B 和 ShareGPT 将 page 从 1 增至 512 tokens；最大 page 下，平均 TTFT 增至最多 2 倍，第 90 百分位 TTFT（P90）增至最多 2.9 倍。细粒度与大传输之间存在直接取舍。

增大 page size 后 cache hit rate 下降、TTFT 上升（Figure 2: Large page sizes decrease cache hit rate and increase TTFT, benchmarked on H200 for Mistral-24B using the ShareGPT dataset.）

长上下文缓存基准也显示，小 page 会让传输带宽闲置。CPU 到 GPU 加载 Llama-3.1-8B 的 8,192-token KV cache、page size 为 32 时，现有方式只达到 PCIe 5.0 理论带宽的约 22%；Grace Hopper 上最低约为 5%。

以 Qwen2.5-14B 在 LooGLE 上运行的基准为例，page size 32 时朴素 CPU offload 有 74% 的 prefill 时间阻塞于 KV 加载；原文另报告吞吐最多退化 4×，但这一段未说明该倍数的比较基线。即使换成能达到 PCIe 理论带宽 75% 的 I/O 机制，prefill 时间仍有最多 24% 被加载停顿占用。

三、问题：加载停顿与 delay hit

已有层级缓存方案常逐层加载：在计算第 (N) 层时，异步搬运第 (N+1) 层的 KV cache，假设前一层计算足以覆盖加载时间。长上下文但新增 token 较少时，计算量不足以覆盖大批 KV 数据传输；重新计算历史上下文又随长度增长而变得昂贵。结果是，prefill 从计算受限转为 PCIe 带宽受限。

问题不仅是 I/O 速度。GPU 的 layer-first 布局按层连续存放所有 token，因此一个 token 跨层的 KV 数据分散为 (L) 段；page-first 布局则把一个 page 对应的各层 KV 数据连续存放，便于传输，却会让注意力内核增加地址间接寻址。仅增大 page 也会牺牲 cache hit rate，因此系统需要在保留细粒度缓存的同时合并传输。

调度器若只按 GPU 计算和显存需求组批，就可能把需要大量加载、但新增计算量很少的请求放在一起，造成 batch 长时间等待数据。另一项风险是论文引用的 delay hit [8]：首个 cache miss 尚未处理完时，同一上下文的后续请求到达；由于首个请求还没有把数据写入缓存，后续请求也被记录为 cache miss，从而重复计算长上下文。异步调度会在当前 batch 结束前准备下一批，扩大这种重复工作的窗口。论文分析的 Mooncake Tool-Agent trace 中，38% 的请求与另一条在 1 秒内到达的请求共享至少 6K-token 前缀（不含 system prompt）；作者据此认为，高吞吐服务中 delay hit 很可能发生。

四、方案：GPU-assisted I/O 与缓存感知调度

Strata 包含管理数据移动的 Cache Controller 和负责组批的 Scheduler。它扩展 SGLang 的 RadixTree 为 HiRadixTree，用 token ID 查找缓存前缀，并保存 page 位置、层级与临时请求状态。请求入队后，调度器估计其加载量和计算量，选出下一批，并同时发起 KV 加载；prefill 执行到某层前，通过 CUDA event 确认该层数据已就绪。系统在同一 GPU 上交替执行 prefill、decode batch，沿用 SGLang 优先执行 prefill、以较大 batch 执行 decode 的策略。SGLang 的核心调度器以 Python 实现，Strata 将这些调度策略补充为 C++ 实现以减少开销。论文称 Strata 已集成进 SGLang，并在多家 AI 公司的生产环境部署。

4.1 GPU-assisted I/O 与分层缓存策略

CPU 逐个提交小型异步 memcpy 时，传输可能受主机调度、驱动队列和小请求开销限制。Strata 改用 GPU kernel 发起 GPU-assisted I/O：数千个 GPU 线程各自从 GPU 全局内存或注册并锁定（pinned）的 CPU 内存读取小块数据，经寄存器写入目标内存。GPU 的并行度可以同时推进大量小数据块；论文称多数架构上 GPU-assisted I/O 的传输粒度可低至 128 bytes，这一粒度足以覆盖 KB 级的单 page KV cache，无需为带宽而增大缓存 page。

GPU kernel 本身也会与模型计算争用 Streaming Multiprocessor（SM，GPU 内的并行计算单元）、寄存器和执行周期。Strata 用少量较大的 CUDA block，让 GPU 硬件调度器尽可能将 I/O kernel 放到少数 SM；低层指令绕过 cache，以减少污染。H200 上的并发微基准分别使用 prefill batch（2 个请求，每个输入 4K tokens）和 decode batch（Llama-3.1-8B，16 个请求，每个输入 4K tokens）。两个各含 1,024 个线程的 I/O block 达到 48 GB/s，prefill 性能下降不到 5%，decode 下降 10%。因此，CPU 到 GPU 的关键加载路径默认使用两个 block；GPU 到 CPU 的备份路径默认使用一个 block，以减少干扰。论文也提供 ROCm 后端。

GPU-assisted I/O kernel 对并发 prefill 与 decode 的干扰（Figure 5: Performance interference vs. resources allocated to the KV-cache I/O kernel. Measurement on concurrently running Strata's I/O kernel with a prefill pass (batch of two requests with 4k input each) and a decode pass (Llama-3.1-8B, batch of 16 requests with 4k input each), respectively.）

Strata 保持 GPU 端的 layer-first 布局，并让主机内存和 SSD 使用 page-first 布局；I/O kernel 读取后只需对目标偏移增加一次地址计算，就能在传输中转换布局。这样 GPU 计算不必增加额外的 layer 间接寻址，主机侧又可以用大块连续数据传输。

Layer-first 与 page-first 内存布局（Figure 6: Layer-first vs. Page-first layouts）

SSD 命中时，Cache Controller 会在请求排队期间尽力将数据预取到主机内存；调度器选中请求时，若预取尚未结束，就终止未完成的预取并使用当前已在主机或 GPU 的缓存。部署方还可以配置为等预取完成，或最多等到指定超时。对 KV cache 备份，Strata 提供三种策略：write-back 在 page 即将逐出时才备份；write-through 在新 KV 生成时就备份；默认的 selective-write-through 为 HiRadixTree 节点累计访问次数，超过阈值才备份，默认阈值为 2。各层默认使用 LRU（least recently used，按最近使用情况选择淘汰对象）策略。

4.2 加载约束下的分阶段请求调度

调度分三步。第一步通过 HiRadixTree 的 transient node（暂存未完成请求状态的节点）追踪还未入缓存的上下文：in-queue 表示有排队请求引用新上下文，in-flight 表示对应缓存正在计算。若后续请求匹配到正在解析的前缀，且匹配 token 数超过默认阈值 100，调度器将其延至下一轮并放到等待队列前端，等首个请求生成缓存后再复用。

第二步组建计算量能覆盖加载量的 prefill batch。调度器按请求累计 load / compute 比率判断是否会令 batch 进入 loading-bound（按该系统阈值判定的加载受限 batch）；默认数值阈值为 100，即 load / compute 比值超过 100 时判为 loading-bound。该阈值可按硬件与模型单独 profile。超出阈值的请求暂存到降优先级队列，先挑选不会令 batch 变成 loading-bound 的请求。若多个请求能在同一 batch 共享上下文，调度器还会优先合并它们，称为 bundle hit，以减少 GPU cache 占用和设备侧带宽压力。若队列扫描完后 batch 仍有空间，再按原顺序补入降优先级请求，避免饥饿。

第三步在 batch 仍受加载限制时用有用计算填充停顿。Strata 可先运行 decode batch，再继续等待 KV 加载；decode 主要占用 HBM 带宽，加载主要占用 PCIe 带宽，二者可以并行而较少竞争。对 prefill/decode 分离部署，也可以用另一个 prefill batch 填充空档。

五、结果：端到端吞吐与消融评估

5.1 Strata 端到端吞吐与时延评测

论文报告平均 TTFT（Time To First Token，从请求到首个输出 token 的时间）和输出 token 吞吐。主测试平台是 8 张 H200 GPU 的节点，GPU 之间使用 NVLink，主机为 Intel Sapphire Rapids、配有 1.6 TB DRAM；每张 GPU 通过 PCIe 5.0 x16 连接 CPU，单向峰值带宽 64 GB/s。Llama-3.1-8B-Instruct 和 Qwen2.5-14B-Instruct-1M 各用一张 GPU，Llama-3.1-70B-Instruct 使用四张 GPU 张量并行；三者上下文窗口分别为 128K、1M、128K。

基线包括 vLLM v0.8.5 与 LMCache v0.2.1（chunk size 256、page size 32），TensorRT-LLM v0.17.0 的 HiCache（page size 32），以及 SGLang v0.4.5 的 SGLang-HiCache。SGLang 与 Strata 使用 page size 1，SGLang-HiCache 使用 32。没有逐条请求时间戳的数据集按 Poisson 分布模拟请求到达；ReviewMT 和 ShareGPT 保留多轮对话依赖；ShareGPT 的后续请求在模型回复后延迟 60 秒，以模拟用户思考时间。最大并发在途请求数为 128，这不是固定 batch 大小。主机缓存使用 1 TB pinned DRAM（GH200 上为 400 GB）；ShareGPT 测试另将 GPU cache 限制在约 50 万 tokens。除 H20-storage 上的专门磁盘实验外，多数基准未使用 SSD 层，因为基线对磁盘支持有限。

5.2 机制评估与适用边界

除特别注明外，机制分析使用 H200、Qwen2.5-14B 和 LooGLE。将 Strata-Schedule-Only 与 Strata-IO 分别叠加到 SGLang-HiCache，峰值吞吐最高提升 1.8× 和 2.3×；低请求率时调度作用更大，请求率升高、I/O 成为主要瓶颈后，GPU-assisted I/O 更关键。Strata-IO 在高请求率下也优于采用 CUDA kernel 的 vLLM-LMCache 和 TRT-LLM-HiCache。只用最长前缀匹配增加设备侧复用，在高请求率和频繁逐出时不能持续获益。

I/O 与调度组件的吞吐分解（Figure 9: Breakdown of I/O and scheduling of Strata.）

不同 page size 的对比显示，SGLang-HiCache 的吞吐随 page 增大先提升、随后因 cache hit rate 下降而回落；其最优设置 page size 512 的峰值吞吐仍只有 Strata-IO 的 93%，cache hit rate 低 2.4%。论文据此指出，Strata-IO 不必依赖增大 page 才能获得高传输吞吐。

不同 page size 下 Strata-IO 与 SGLang-HiCache 的对比（Figure 10: Performance comparison between Strata-IO and SGLang-HiCache with different page sizes.）

cache distance 指同一上下文的请求在队列中相隔多远。逐步消融以 SGLang-HiCache 为基线，并比较各机制加入后的峰值吞吐变化：最短距离负载中，delay hit 缓解使峰值吞吐提高 42%；shuffle 与最大距离负载中，I/O 优化分别提高 76% 和 95%，随后加入平衡组批再分别提高 11% 和 12%，加入停顿填充再分别提高 8% 和 3%。最大距离负载由相同上下文查询均匀分散在请求队列中，shuffle 则沿用原始 LooGLE 顺序。

不同 cache distance 下各优化机制的峰值吞吐贡献（Figure 11: Breakdown of Strata’s optimization attributions on different workload patterns.）

cache resolve time（从请求触发 cache miss 到对应 KV cache 可用的时间）越长、请求到达率越高，delay hit 导致的 cache miss 越多。论文将每 1K 输入 token 的典型 cache resolve time 描述为数百毫秒到数秒，具体取决于模型和硬件；模拟使用近乎无限的缓存来排除逐出影响，因为测试平台无法持续承受足够高的请求吞吐。

不同 cache resolve time 与请求吞吐下的 delay hit 影响（Figure 12: Delay hit impact for the Mooncake Tool-Agent trace under varying cache resolve times and throughputs. Different throughputs are achieved by scaling query timestamps.）

SSD 测试单独运行在 H20-storage 节点（8 张 H20 和 Intel P5510 NVMe SSD，磁盘读取峰值 7 GB/s）。DeepSeek-V3、8 张 H20、page size 32、请求率 12 req/s 时，page-first 布局相对原始布局将平均 TTFT 从 5.03 s 降至 2.42 s，生成吞吐从 27.43 增至 36.41 tokens/s，即分别改善约 2.1× 与 1.3×。论文没有在这段实验说明中给出具体数据集或输入长度，因此不把它归到 LooGLE 等负载上。

DeepSeek-V3 上 page-first 布局的端到端效果（Figure 13: End-to-end performance improvement of the decoupled memory layout for DeepSeek-V3 on 8×H20 GPUs, with page size 32 and request rate 12 req/s.）

在 GH200 上的测试使用 Llama-3.1-8B 和 LooGLE。GH200 将一张 H100 GPU 与 64 核 NVIDIA Grace CPU 集成，提供 464 GB LPDDR5X，CPU 侧内存带宽最高 384 GB/s。Strata-IO 将主机到 GPU 的持续传输带宽从约 40 GB/s 提升到约 150 GB/s。在输出吞吐与平均 TTFT 的比较中，Strata-IO-GH 尚未超过 H200 上的 Strata-IO；加入感知带宽的调度后，Strata-GH 的表现接近模拟无限 CPU-GPU 带宽的 Strata-Oracle。

PCIe 5.0 与 Grace Hopper 平台的吞吐—时延对比（Figure 14: A zoomed-in comparison between benchmarks on PCIe-5.0 and Grace-Hopper platform.）

持续传输带宽对比（Figure 15: Sustained Bandwidth comparison.）

作者讨论了几项边界。GPU-assisted I/O 以少量 SM 竞争换取小块数据的传输效率；H200 上 cudaMemcpyBatchAsync 将多个小型复制请求合并为一次主机驱动提交，吞吐为 38 GB/s，低于 GPU kernel 的 48 GB/s，但它不占用 SM，适合不在关键路径上的 GPU 到 CPU 备份。当前调度策略优先提高整体计算与 I/O 利用率，仍可能导致单请求资源分配不均并造成服务级目标（Service-Level Objective，SLO）违约。现有策略主要覆盖主机 DRAM 到 HBM 的加载时延；SSD 预取则只与请求排队时间重叠，论文提出还可为更慢存储层的预取留出调度余量。Strata 面向标准 dense attention 产生的 KV cache，尚未覆盖 sparse 或 linear attention 等 hybrid 模型。论文还指出它运行在单个计算实例内，可与 Mooncake 等跨节点缓存设计的传输引擎集成，但不依赖高速网络等专用硬件来获得本文所述收益。
