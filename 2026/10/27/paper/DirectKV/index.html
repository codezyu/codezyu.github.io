DirectKV：长上下文 LLM 推理的 zero-copy（零拷贝）卸载

论文：No Buffer, No Bottleneck: Efficient Zero-Copy KV Cache Offloading for Long-Context LLMs（KV cache 指缓存历史 token 对应的 key 和 value 张量），Shutian Luo、Haiying Shen，University of Virginia，OSDI ’26（20th USENIX Symposium on Operating Systems Design and Implementation，2026 年 7 月 13—15 日，Seattle，论文集页码 39—54）。论文 PDF。

TLDR： 长上下文推理中的 KV cache 随序列长度增长；swap-based offloading 要用 GPU staging buffer（GPU 暂存缓冲区）换入 CPU 中的 KV 块，朴素 zero-copy 虽去掉 buffer，却会反复跨 CPU–GPU 链路读取 KV。DirectKV 让 CUDA kernel 直接访问固定（页锁定）主机内存（pinned host memory）中的 KV，并以 CPU-memory-aware tiling（面向 CPU 内存的分块）、key/value projection 与 attention 融合、warp-level pipelining（warp 级流水）减少重复取数和访存等待。在 GH200 上，CPU-memory-aware zero-copy 相比 naive zero-copy 的 CPU–GPU 传输量最多减少 50%（组件实验覆盖 Llama-8B、OPT-13B、OPT-30B）；在 1K—32K 上下文长度的服务评测中，论文报告平均加速比为 1.2×，并在 GH200 的多模型、多长度平均显存比较中比 Neo、Pie、FlexGen 低约 43%。这三项结果来自不同比较：传输量基线是 naive zero-copy，显存基线是几种卸载系统，1.2× 则是按每个上下文长度可运行的系统进行比较。

一、背景：KV cache 的容量压力

Transformer attention 将输入投影为 query（Q）、key（K）和 value（V）。生成每个新 token 时，Q 都要与此前缓存的 K、V 计算 attention；保留 KV cache 可以避免重新计算历史 token 的 K、V，但缓存大小会随序列长度和模型维度线性增长。论文指出，十亿参数级 LLM 在 128K token 上下文下，仅 KV cache 就可能需要数百 GB，超过 GPU HBM（high-bandwidth memory，GPU 侧高带宽内存）容量。

推理包含 prefill 和 decode 两个阶段：prefill 并行处理输入序列并初始化 KV cache；decode 逐 token 生成，每个新 query 都要访问已有缓存。长上下文和并发请求因此会让 KV cache 成为 GPU 显存容量的主要压力之一。

GH200、GB200 等 CPU–GPU superchip 通过 NVLink-C2C 提供最高 900 GB/s 的双向带宽，为 CPU 内存扩展 GPU 可用的 KV 容量提供了条件。DirectKV 的评测主要在 GH200 上进行；论文也以 GB200 作为适用平台示例，并未在 GB200 上给出这组评测结果。

二、现状：swap 和 naive zero-copy 的代价

swap-based offloading 把 KV 块保存在 CPU 内存，需要使用 GPU copy engine（GPU 数据复制引擎）将即将参与 attention 的块复制到 GPU staging buffer，再由 kernel 计算。系统可以让复制与计算重叠，但 staging buffer 占用 HBM；layer-by-layer 换入、换出还会增加 CPU–GPU 链路流量。动态 KV 块地址也可能迫使 CUDA Graph 更新或重新捕获，削弱图重放的收益。论文给出的带宽背景是：PCIe（PCI Express）约 40—60 GB/s，而 HBM 可达 3—4 TB/s；矩阵乘案例中使用的 PCIe Gen5 标称值为 64 GB/s。

zero-copy 允许 GPU kernel 直接访问 CPU 侧内存，不再先把 KV 复制进 GPU staging buffer。为比较这两种卸载方式，论文用矩阵乘法 C = A × B 做案例分析：三个方阵边长均为 10,240，每个矩阵约 400 MB。Baseline 把 A、B 都放在 GPU；Swap 把 B 放在 CPU，并使用 200 MB 的 GPU buffer 分块换入；Zero-Copy 则让 B 留在 CPU，由 GPU 直接访问。实验分别使用通过 PCIe Gen5 连接的 H100，以及通过 NVLink-C2C 连接的 GH200。

swap-based offloading 与 zero-copy 的 KV cache 路径（Figure 1: KV cache offloading via swapping and zero copy.）

Swap 借助异步复制把额外时延开销控制在 PCIe 上不到 10%、NVLink-C2C 上约 5%。naive zero-copy 则因矩阵计算重复读取 CPU 侧 B，在 PCIe 上的运行时延为 1,122 ms，而 GPU 内存中的 Baseline 为 56 ms；在 GH200 上，Zero-Copy 为 106 ms，Baseline 为 52 ms。它省去了 buffer：GPU 内存用量比 Baseline 少 50%，比 Swap 少 33%，但直接访问 CPU 内存并没有自动消除性能损失。

三种矩阵乘法配置的时延与显存占用（Figure 2: Comparison among three mechanisms for matrix multiplication.）

GH200 上的访存指标进一步显示，Baseline 和 Swap 的 L2 cache hit rate 都约为 77%，HBM 到 L2 的流量为 21.1 GB；Zero-Copy 的 CPU 到 GPU 流量为 22.7 GB，L2 hit rate 降至 32.3%。因此，链路带宽受限与 L2 局部性下降会共同拖慢朴素 zero-copy。

不同配置的数据获取量与 L2 cache 命中率（Figure 3: Data fetching and L2 cache hit rate.）

三、问题：CPU 常驻 KV 的重复访存瓶颈

GH200 的 NVLink-C2C 总双向带宽最高 900 GB/s，即每个方向最高 450 GB/s；HBM 带宽约 4 TB/s。长上下文 attention 的访问通常是粗粒度的：一个 streaming multiprocessor（SM，流式多处理器）读取约 100 KB 的 KV tile，100 多个 SM 可以同时取数，CPU 到 GPU 的聚合流量达到 MB 级，持续带宽比单次远端读取时延更关键。即使换成 NVLink-C2C，反复访问 CPU 常驻 KV 仍会把链路变成瓶颈。

根因在 kernel 的数据复用顺序。常规矩阵乘 tile 以 GPU HBM 中的 A、B 为输入，迭代时分别取入两个 tile，并让输出 C 留在寄存器或 SMEM（shared memory，共享内存）。若 B 在 CPU 内存中，B tile 会随计算被反复取回；较低的 CPU–GPU 带宽又无法像 HBM 一样承受这种重复访问。只移除 staging buffer 不会改变这一访存模式，因而 DirectKV 需要同时改变内存放置和 kernel 的循环顺序。

四、方案：让 CPU 常驻 KV 参与 attention kernel 设计

4.1 CPU-memory-aware tiling 的访存权衡

DirectKV 采用 CPU-memory-aware tiling（面向 CPU 内存的分块），针对 CPU 与 GPU 内存带宽不对称调整矩阵乘的数据复用。对 C = A × B，传统 tiling 在每个 k 步读取 A、B tile，并累计 C；DirectKV 则将 CPU 内存中的 B tile 读入 SMEM 后，固定该 tile，遍历多个 A、C tile 后再换下一个 B。这样每个 B tile 只需按 (k, j) 组合从 CPU 取一次，在矩阵乘模型中把 B 的取数规模从 O(n³) 降到 O(n²)。

代价是 C 不再跨 k 步一直驻留：每一步都要从 HBM 读取并写回 C，使 C 的 HBM 流量从传统 tiling 的 2 · O(n³) 增至 3 · O(n³)。DirectKV 把重复访问从较慢的 CPU–GPU 链路转移到带宽更高的 HBM，以此换取更少的远端 KV 读取。

4.2 prefill 与 decode 的 KV 遍历顺序

prefill 一次处理多个 query。DirectKV 逐 tile 生成 K、V；按模型配置，可对 K 应用 rotary positional embeddings（RoPE，按 token 位置对 Q、K 做旋转变换），再将新 KV 写入 CPU 固定内存。当前 K、V tile 同时留在 SMEM，直接用于 attention，不再为刚生成的 KV 先写回 CPU 再读回 GPU。attention 阶段固定 KV tile、遍历存放在 HBM 的 Q tile，使用 streaming softmax（按 KV tile 逐步更新 softmax 状态）累积结果。这样可以复用跨链路取回的 KV，但需要反复读写中间输出 O 和 softmax 状态。

decode 每次只有一个新 query，DirectKV 改为遍历 KV：producer warp 从 CPU 内存取入 KV tile，consumer warp 计算 attention，二者流水重叠。attention 输出可留在寄存器中累积；当前 token 的 K、V 投影完成后追加到 CPU 中的 KV cache，再参与本轮 attention。每个已有 KV tile 只需遍历一次，避免为单 token 的 query 重复读取输出状态。prefill 与 decode 的循环顺序不同，是因为前者要尽量复用昂贵的 CPU 常驻 KV，后者则可以用单个 query 顺序扫过 KV。

4.3 K/V projection–attention 融合与 warp-level pipelining

DirectKV 将 K/V projection 与 attention 融合进 CUDA kernel。分开的 kernel 会把投影生成的 K、V 写入 CPU KV cache，随后 attention 再从 CPU 读回；融合后，刚生成的 tile 留在 SMEM 供 attention 立即使用，减少这次冗余读取。持久化所需的 KV 仍写入 CPU cache，因此融合去掉的是当前计算路径上的往返读取，不是 KV cache 的保存。

KV projection 与 attention 的融合方式（Figure 9: KV Projection and attention fusing.）

在 Hopper GPU 上，DirectKV 以 warp-level pipelining 让不同 warp group 分担取数、计算和写回。prefill 使用 producer、consumer、storer 三组 warp：producer 预取下一 tile，consumer 计算当前 tile，storer 处理写回；默认两级流水以隐藏访存等待。decode 只有新生成的 KV 需要写回，因此用 producer 和 consumer 两组 warp，不另设 storer。论文还利用 Hopper 的 Tensor Memory Accelerator（TMA）执行异步数据移动。

4.5 固定主机内存中的 KV cache 管理

KV Cache Manager 使用 cudaHostAlloc 分配固定主机内存，让 GPU 通过设备可见指针直接访问 CPU 常驻 KV；生成后 KV 留在该内存中供后续 decode 重用。DirectKV 不依赖 GH200 的 Unified Page Table（UPT）或平台专用一致性机制：论文的设定中，CPU 不会并发更新这些 KV 块，因此使用固定内存和设备可见指针即可。

五、结果：GH200 上的容量与性能

5.1 长上下文服务的时延与显存

端到端评测在 NVIDIA GH200 上运行，GPU 配有 96 GB HBM3，CPU 使用 LPDDR5X 内存；互连对比另外使用 PCIe Gen5 的 H100。系统使用 CUDA 12.4、PyTorch 2.3 和 CUTLASS 3+ CuTe。模型为 Llama-3.1-8B、OPT-13B、OPT-30B；负载来自 ShareGPT 和 Alpaca，因数据集没有请求时间戳，论文按 Poisson process（泊松过程）生成请求到达。主评测的请求率最高 30 req/s、上下文长度为 1K—32K，并另加更高请求率、更长上下文的压力负载及 batch size 变化。

比较对象包括 SGLang（KV cache 留在 HBM）、Pie（使用 NVLink-C2C 和 GPU staging buffer 换入 KV）、Neo（CPU–GPU 异构流水并把部分 attention 卸载到 CPU）和 FlexGen（在 GPU、CPU、磁盘间分层放置 tensor，并使用 4-bit compression）。

Figure 10 的请求率测试中，横轴为 10、20、30 req/s，图中指标是逐 token 时延。30 req/s 时，Llama-3.1-8B（图中标为 Llama-8B）的 DirectKV 时延为 0.75 s，其他卸载系统为 1.55—2.95 s；OPT-13B 上 DirectKV 同为 0.75 s，其他卸载系统为 1.55—3.95 s。此时 SGLang 在 OPT-13B 上因显存不足而 OOM（out of memory）；在 OPT-30B 上它只支持较低请求率，而 DirectKV 可扩展到 30 req/s。Figure 10 的文字没有给出这些请求率曲线对应的具体上下文长度，因此不能把这组数值与下段的上下文长度 sweep 混为一组。

不同请求率下各模型的逐 token 时延（Figure 10: Per-token latency under varying request rate for different models.）

论文摘要把端到端性能概括为相对现有方案最高 1.2×。正文的上下文长度实验覆盖 1K—32K，并将每个长度下 DirectKV 与能够运行该长度的系统比较，报告平均加速比为 1.2×；正文没有把这个平均值拆成逐模型、逐长度的数值。在 16K token 时，DirectKV 比 Neo 和 Pie 约快 1.3×，比 FlexGen 约快 1.7×，但原文没有在这一句指明模型；到 32K 时 Neo、Pie 和 SGLang OOM，FlexGen 仍可运行。长上下文下的收益来自少用 GPU buffer、减少 CPU–GPU 往返；该平均加速比不代表 DirectKV 在 HBM 足够时一定快过 SGLang。

显存比较是在 GH200 上跨模型和序列长度测量平均值：SGLang 使用 92 GB，Neo 86 GB，Pie 88 GB，FlexGen 74 GB，DirectKV 47 GB。相对三种卸载系统（Neo、Pie、FlexGen）的平均用量，DirectKV 的 GPU 显存使用量降低 43%；这个百分比不是相对 GH200 的 96 GB 总容量，也不是相对 SGLang。

5.2 组件优化与互连条件下的性能

组件评测中，CPU-memory-aware zero-copy 相对 naive zero-copy（不是 swap-based 系统）的比较覆盖 Llama-8B、OPT-13B 和 OPT-30B。论文报告 CPU–GPU 传输量最多减少 50%，对应的推理时延最多降低 70%。§7.4.1 的文字和 Figure 12 没有给出这组数据对应的单一序列长度或 batch size，因此这里不把它绑定到某个上下文长度。
