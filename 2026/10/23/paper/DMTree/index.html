DMTree：面向分离式内存的计算侧协作树索引

论文：DMTree: Towards Efficient Tree Indexing on Disaggregated Memory via Compute-side Collaborative Design，Guoli Wei、Yongkun Li（通讯作者）、Haoze Song、Tao Li、Lulu Yao、Yinlong Xu、Heming Cui，FAST ‘26（24th USENIX Conference on File and Storage Technologies，2026）。Guoli Wei、Yongkun Li、Tao Li、Lulu Yao、Yinlong Xu 来自中国科学技术大学；Yongkun Li 与 Yinlong Xu 还隶属于该校的安徽省高性能计算重点实验室。Haoze Song、Heming Cui 来自香港大学。代码：GitHub/muouim/DMTree。

TLDR： DMTree 将 fingerprint table（指纹表）定位与叶节点加锁交给计算侧，缓解内存侧 IOPS。微基准 insert 较 dLSM 至多快5.7×；YCSB 搜索/写入较 Sherman、ROLEX 快 3.8×–9.7×。

一、背景：分离式内存中的 RDMA 资源

分离式内存（disaggregated memory，DM）将计算资源与内存资源放入独立资源池。计算服务器有较多 CPU、但内存有限；内存服务器有大容量内存、但 CPU 核较少。两类服务器通过 RDMA 通信。单边 RDMA（one-sided RDMA）允许计算服务器直接访问远端内存，不消耗内存服务器的 CPU。

计算池和内存池通过 RDMA 互连（Figure 1: Architecture of disaggregated memory.）

RDMA 资源主要分为两类：

  • IOPS：网卡每秒能处理的 RDMA 操作数，影响精确查找、加锁等小规模访问。
  • 带宽：链路每秒可传输的数据量，影响宽叶节点读取和批量扫描。

多台计算服务器访问同一内存服务器时，请求会汇聚到内存侧网络。论文观察到，内存服务器网络更容易成为瓶颈，而计算服务器之间的 RDMA 资源通常尚未饱和。

二、现状：范围索引的网络资源权衡

范围索引既要支持点查和写入，也要支持范围扫描。论文按数据在叶节点中的组织方式，分析了几类分离式内存索引。文中的 expected search 指一次 RDMA 读取一条键值对（key-value，KV）、没有读放大（read amplification）；expected insert 按一次 RDMA 查找空槽再一次写入计算，expected update 按一次读出 KV 再一次写回计算。

  • 连续叶节点存储：B+-tree（B+ 树）和 learned index（学习型索引，如 Sherman、ROLEX）在宽叶节点中连续存放多条有序 KV。点查单条 KV 时仍可能读出整个叶节点；例如叶节点含 32 条 KV 时，读放大约为 32×。实验中，Sherman 和 ROLEX 的 search 吞吐只有 expected search 的 16.3%–18.8%。
  • 精确定位：ART（Adaptive Radix Tree，如 SMART）每个叶节点只存一条 KV，避免点查读放大；但 scan 要为多个小叶节点发起 RDMA，insert 也更频繁地更新内部树。SMART 的 scan 吞吐只有 Sherman 的 35.5%，insert 吞吐只有 expected insert 的 35.8%。

B+-tree 与 ART 的搜索路径和叶节点定位（Figure 2: Exploring range indexes on DM: ①B+-tree uses "key-pointer" along the search path to ultimately locate a range leaf node; ②ART uses "segment key" along the path and locates a precise entry.）

  • LSM-tree：Log-Structured Merge tree（LSM-tree）的 dLSM 将随机写转为顺序块写，减少网络访问；但 compaction 需要处理大量远端数据。将 compaction 卸载到 CPU 资源有限的内存服务器后，insert 吞吐只有 expected insert 的 14.9%–41.4%。
  • 混合索引：CHIME 在 B+-tree 叶节点中使用 hopscotch hashing 定位 KV；FP-B+-tree 则为叶节点增加 fingerprint table（指纹表，FPT），每条 KV 对应一个 1 字节指纹。两者保留连续叶节点，也能定位到目标 KV；search 吞吐比 Sherman、ROLEX 高 2.2×–4.5×，scan 吞吐比 SMART 高 2.5×。不过，读取或更新 FPT、处理哈希冲突（hash collision），以及叶节点加锁和解锁仍需要额外 RDMA。FP-B+-tree 的 search 吞吐比 expected search 低 57.3%；CHIME 和 FP-B+-tree 的 insert 吞吐只有 expected insert 的 23.9%–45.4%，update 吞吐只有 expected update 的 48.1%–61.8%。

FP-B+-tree 的内部节点与带指纹表的叶节点结构（Figure 4: Structures of FP-B+-tree.）

现有范围索引在点操作和范围操作上的吞吐权衡（Figure 3: Performance trade-offs of existing range indexes for point and range operations on DM. Experiments use the default configuration of six compute servers and one memory server, with one billion preloaded key-value entries and 100 million operations per test (detailed in §5.1).）

三、优化点：降低内存侧定位与加锁 IOPS

混合索引已经减少点查的读放大，但精确定位和并发写入仍会产生 FPT 与锁操作的额外 RDMA 请求，这些请求继续汇聚到内存服务器。论文要优化的是内存侧这部分 IOPS 消耗，同时保留连续叶节点的点查和扫描效率；计算服务器之间尚未饱和的 RDMA 资源为此提供了空间。

FP-B+-tree 插入时计算服务器与内存服务器的 IOPS 和带宽消耗（Figure 5: RDMA resource consumption of FP-B+-tree during inserts (C1-C6 for compute servers, M1 for the memory server).）

四、方案：计算侧协作设计

DMTree 沿用 FP-B+-tree 结构：叶节点连续存放 KV，并在旁边维护 FPT，用指纹确定目标 KV 在叶节点中的槽位。这样，点查可以只读取目标 KV，scan 仍可连续访问叶节点。DMTree 再用计算侧协作缓存承担数据定位，并把叶节点锁操作安排在计算侧。

4.1 计算侧缓存与指纹表协作存储

每台计算服务器私有缓存内部树（internal tree）的最底层节点，并在本地重建上层节点。只有叶节点分裂或合并时，底层内部节点才需要更新；以 32 个 KV 槽位的叶节点为例，写满并分裂前需要 32 次 insert，因此内部树更新较少，缓存不易频繁失效。

FPT 采用协作存储：每张表在一台计算服务器上保存 primary（主副本），也可缓存在其他计算服务器上；primary 的归属按 FPT offset 做 consistent hashing（一致性哈希）。叶节点对应的内部树条目保存 primary FPT 的指针。查询时，计算服务器扫描本地或对端缓存的指纹以确定 KV 槽位；写入时只同步更新 primary，其他缓存副本异步更新。这样，FPT 的读取和同步流量从内存服务器转移到计算服务器。

4.2 指纹副本与内部树缓存的一致性

FPT 副本异步更新，可能暂时过期。若缓存指纹指向的 KV 与请求 key 不同，或缓存中缺少请求的指纹，DMTree 就读取 primary FPT、校验结果并刷新本地副本。

叶节点分裂、合并或范围变化也可能使内部树缓存过期。叶节点和内部节点记录 Kmax、Kmin 及右兄弟指针，用于判断节点范围和定位后继节点。DMTree 还在内部条目、叶节点 KV 条目和 FPT 中加入 8B version ID（版本号）；三处记录同一叶节点的版本，叶节点创建时版本置为 0，范围变化时递增。读取 FPT 或 KV 后，计算服务器将返回数据中的 version ID 与缓存内部条目的 version ID 比较；若不一致，就使缓存失效并重新遍历远端内部树。

内部节点、KV 条目和叶指纹表中的一致性字段（Figure 8: Structures of DMTree designed for consistency.）

4.3 计算侧协作锁与读写冲突校验

DMTree 对写写冲突（write-write conflict）使用悲观锁。叶节点的 lock field 与 primary FPT 一起放在计算侧；计算服务器通过跨服务器 RDMA_CAS 将锁从 0 改为 1。相较于基本 FP-B+-tree，DMTree 在 update 路径上把 5 次 RDMA 中的 3 次从内存侧移到计算侧；内存服务器侧只保留必要的 KV 读写。

更新操作中的计算侧协作锁（Figure 9: Compute-side collaborative locking in write operations.）

insert 更新 FPT 时，DMTree 将 lock field 放在 FPT 末尾，并把解锁合并到 FPT 的 RDMA_WRITE 中；网卡按顺序写入，因此解锁发生在 FPT 写完之后。update 不改 FPT，解锁仍需单独执行 RDMA_WRITE。

对读写冲突（read-write conflict），DMTree 使用 8B CRC（cyclic redundancy check，循环冗余校验）校验读写单元。读出的树节点、KV 条目或 FPT 若 CRC 不匹配，就重新读取；写入后则重新计算 CRC。小于 64B 缓存行（cache line）的 KV 条目不需要额外 CRC，因为 RDMA 对缓存行粒度的读写具有原子性。

4.4 操作路径与 RDMA 优化

scan 时，DMTree 用 FPT 过滤空槽，避免读取尚未写入的 KV。计算服务器还会将并发 search 和 write 请求合并成批次；超过批量阈值的请求直接执行，以限制排队时延。

通过指纹表过滤叶节点中的空槽（Figure 10: Filter empty entries through fingerprints during scans.）

  • Search：通过内部树缓存找到叶节点和 FPT，匹配指纹后读取候选 KV 并核对 key。若 KV 的 key 不符，或缓存中没有匹配指纹，DMTree 就读取 primary FPT 校验并刷新缓存；确认不存在后返回 NULL。
  • Write：定位叶节点和 primary FPT，并通过 RDMA_CAS 加锁。更新已有 KV，或将新 KV 和指纹写入空槽；FPT 满时分裂叶节点与 FPT，并更新内部树指针。
  • Delete：将 KV 条目标记为 NULL，逻辑删除并释放槽位。叶节点中的 KV 全部删除后，与相邻叶节点合并；后台线程回收空节点。
  • Scan：定位起始叶节点，读取 FPT 并过滤空槽，再读取有值的 KV；若当前叶节点不足以满足扫描长度，就沿右兄弟继续扫描。

五、结果：吞吐、时延与系统开销

5.1 实验设置与吞吐表现

实验集群有 6 台计算服务器和 1 台内存服务器。每台机器配备 2 颗 40 核 Intel Xeon Gold CPU、128GB DRAM 和 100Gbps Mellanox ConnectX-6 RNIC（RDMA network interface card，RDMA 网卡），并通过 100Gbps 以太网交换机互连。内存服务器只使用 1 个 CPU 核；每台计算服务器默认可使用 25GB 内存。

论文运行 search、insert、update、scan 四种 Micro-benchmark（微基准），以及 YCSB（Yahoo! Cloud Serving Benchmark）A–F：A（50% update、50% search）、B（5% update、95% search）、C（纯 search）、D（5% insert、95% search）、E（5% insert、95% scan）、F（50% read-modify-write、50% search）。两类测试均使用 uniform 和 Zipfian（coefficient 0.99）分布，预加载 10 亿条 32B KV（24B key、8B value），每项实验执行 1 亿次操作。默认最大 scan 长度为 100。基线包括：

索引类型
ShermanDM B+-tree
dLSMDM LSM-tree
ROLEXDM learned index
SMARTDM ART
CHIMEtree + hash hybrid index

默认配置中，Sherman 和 CHIME 的 span size 为 32；ROLEX 的 span size 和 model prediction error 均为 8；dLSM 的有序字符串表（Sorted String Table，SSTable）为 64MB；DMTree 的 span size 为 32，叶节点约 1.3KB。

Micro-benchmark。 在 search-only 测试中，DMTree、SMART 和 CHIME 接近 expected search 性能。DMTree 比 Sherman、ROLEX 快 4.5×–5.2×，比 dLSM 快 2.8×–3.1×。在 insert-only 测试中，DMTree 比 Sherman、ROLEX 快 3.7×–4.3×，比 SMART、CHIME 快 2.3×–3.5×，比 dLSM 快 2.1×–5.7×；论文将这一结果归因于减少读放大、内部树更新、hash collision 处理，以及移到计算侧的 FPT 和锁操作。

uniform update 下，DMTree 比所有基线快 1.4×–4.3×。Zipfian update 下，SMART、CHIME 和 DMTree 都通过聚合热点请求减少阻塞，DMTree 再凭计算侧加锁比 SMART、CHIME 快 1.1×–1.5×。在 scan-only 测试中，DMTree 比 SMART 快 3.2×，比 Sherman、CHIME 快 1.1×–1.3×；ROLEX 由于叶节点较小，scan 性能与 DMTree 接近。

Uniform 分布下各范围索引在微基准操作中的吞吐（Figure 11: Throughput comparison of range indexes on DM under Micro-benchmarks with Uniform distribution.）

Zipfian 分布下各范围索引在微基准操作中的吞吐（Figure 12: Throughput comparison of range indexes on DM under Micro-benchmarks with Zipfian distribution.）

YCSB。 在搜索或写入密集的 A、B、C、D、F 工作负载中，DMTree 比 Sherman、ROLEX 快 3.8×–9.7×，比 dLSM 快 1.4×–8.6×（D 的 insert 占比较高，差距更明显），比 CHIME 快 1.1×–1.7×。在 scan 密集的 E 中，DMTree 比 SMART 快 3.2×，与 Sherman、ROLEX 的性能相近。

YCSB 各工作负载下的索引性能对比（Figure 14: Performance comparison under YCSB-benchmarks.）

5.2 时延、资源开销与参数敏感性

P99 时延。 P99 指第 99 百分位时延。默认每台计算服务器运行 72 个 client thread。由于 SMART、ROLEX、CHIME 的 scan 尚不支持 coroutine（协程），测 scan 时所有索引都关闭 coroutine。search 时，DMTree 比 Sherman、ROLEX 的尾时延最多低 64%；在 Zipfian 分布下，比 SMART、CHIME 低 26%–31%，论文将其归因于 DMTree 限制聚合队列长度。insert 时，DMTree 比 Sherman、ROLEX、SMART、CHIME 低 28%–80%。Zipfian update 下，Sherman 的尾时延可达 20ms；dLSM 有超过 99% 的写入在本地结构中处理，因此 insert 和 update 的尾时延较低，但远端 flush 或 compaction 若受内存服务器 CPU 限制，时延可能超过 600ms。scan 时，DMTree 的尾时延比 SMART 低 70%，比 Sherman、CHIME 低 10%–19%。

不同操作下各索引的尾时延对比（Figure 13: Tail latency comparison of different operations.）

计算与内存开销。 search 中，指纹遍历占总时延的 5%；write 中，指纹遍历与同步合计占 19.4%。默认配置下，每台计算服务器需要 5.4GB：内部树缓存 2.3GB，协作指纹存储 3.1GB。对照方案中，Sherman 约需 2.1GB，SMART 22.5GB，ROLEX8（span size 为 8）5.6GB，ROLEX16（span size 为 16）1.5GB，CHIME 4.5GB。

在单独的计算侧内存敏感性测试中，可用内存从 20GB 降到 2.5GB。SMART 吞吐最多下降 72%；论文报告 DMTree 在这组配置下的 search 吞吐保持稳定。论文将 CHIME 在低缓存测试中的表现归因于 hotness-aware cache（感知访问热度的缓存）。

不同计算侧缓存配置下的 search 性能（Figure 15: Search performance with varying cache sizes.）

内存服务器上，DMTree 为 32B KV 增加 8B version field；KV 大于 64B 时再增加 8B CRC。存放 10 亿条 32B KV 时，Sherman 使用 54.2GB，DMTree 使用 60.1GB，空间增加约 10.9%。

消融。 相对基础 FP-B+-tree，RDMA 优化使 scan 提升 1.3×；计算侧协作缓存使 search 和 write 提升 1.2×–1.9×；计算侧协作并发控制又使 insert 和 update 提升 1.5×–1.6×。

逐项启用 DMTree 设计技术后的吞吐变化（Figure 16: Effectiveness of the design techniques.）

IOPS 利用率。 insert 测试中，DMTree 将计算服务器的 RDMA IOPS 利用率从 17.5% 提高到 32.9%，同时缓解内存服务器的 IOPS 瓶颈。

插入操作中 FP-B+-tree 与 DMTree 的 IOPS 资源消耗（Figure 17: IOPS resource consumption of FP-B+-tree and DMTree during inserts (C1-C6 for compute servers, M1 for the memory server).）

参数敏感性。 在 KV 大小测试中，因内存限制，预加载条数从 10 亿降到 1 亿。YCSB A（Zipfian）中，KV 从 16B 增至 128B 时，DMTree 比 Sherman、ROLEX 快 3.3×–13.5×。scan 测试中，KV 为 16B 时 DMTree 比 SMART 快 4.8×；增至 128B 后，带宽成为主要瓶颈，两者性能接近。

不同 KV 大小下 update-intensive 与 scan-dominant 工作负载的性能（Figure 18: Performance with different key-value sizes.）

最大 scan 长度从 10 增至 1000 时，SMART 因 RDMA 请求增加而明显变慢；长度为 1000 时，DMTree 比 SMART 快 3.5×–3.9×。不同 scan 长度下，DMTree 也持续比 Sherman 快 1.1×–1.2×，原因是 FPT 会过滤空槽。

不同最大 scan 长度下 scan-only 与 scan-dominant 工作负载的性能（Figure 19: Scan performance with different scan lengths.）

六、讨论：故障恢复与 CXL 适配

论文讨论了计算服务器故障时的元数据恢复方案：通过监控 RDMA 请求失败、探测服务器存活状态等轻量机制发现故障后，将失效服务器移出成员列表，从剩余副本中选举新的 primary；新 primary 可根据远端 KV 数据校验并重建 FPT。论文将其描述为与轻量故障检测和恢复协议兼容的设计。

DMTree 的设计原则也可适配 CXL（Compute Express Link）系统。论文认为，DMTree 依赖的单边远端访问可由 CXL 的 load/store 指令实现；计算服务器之间的协作则可由 CPU 间共享内存支持。论文指出，高并发下 CXL 内存侧仍可能成为瓶颈；更低时延和更高带宽可能降低 DMTree 的相对收益，并使并发控制等软件开销在 IOPS 或 PCIe 带宽饱和前成为瓶颈。将 DMTree 部署到 CXL 环境仍需相应适配。
