FastLanes：数据并行压缩布局与文件格式

论文：The FastLanes Compression Layout: Decoding >100 Billion Integers per Second with Scalar Code，Azim Afroozeh、Peter Boncz，PVLDB 16(9)，2023。后续文件格式论文：The FastLanes File Format，Azim Afroozeh、Peter Boncz，PVLDB 18(11)，4629–4643，2025，DOI：10.14778/3749646.3749718。实现：2023 版、2025 v0.1。

TLDR： FastLanes 用 1024 位交织和 04261537 转置并行解码轻量编码，峰值 70 值/周期，单列求和每值约 24 位胜过未压缩数组；2025 v0.1 以表达式编码和分段布局支持级联、多列压缩与部分解码。

一、背景：轻量压缩与向量化执行

分析型系统采用列存有两个理由：查询按需跳过整列，节省网络、磁盘与内存带宽；列存配合压缩，比行存更紧凑。广泛采用的向量化执行（源自 MonetDB/X100 的设计）按 1024 个值一批处理：表扫描先把压缩数据从 RAM 解码成一个含 1024 个值的未压缩向量，交给查询流水线；该向量装入 L1/L2 缓存，处理期间一般不再回 RAM。解码因此发生在内存与 CPU 之间，压缩数据可减少内存、网络与磁盘流量。

在这一执行模型下，解码端面对的是四类轻量压缩（lightweight compression，LWC）：字典编码（DICT）用短码替换重复值；基准帧编码（Frame of Reference，FOR）保存相对基准值的偏移；差分编码（DELTA）保存相邻值的差；游程编码（RLE）以（值，长度）对表达连续重复值。四者的位级表述都依赖位打包（bit-packing，按实际值域宽度截去前导多余位），并可配异常处理（Patching）容纳超出位宽的少数值。

硬件侧的事实也是前提：x86 的单指令多数据（single instruction, multiple data，SIMD）寄存器在 25 年里翻倍三次，MMX 64 位、SSE 128 位（1999）、AVX/AVX2 256 位（2008）、AVX-512 512 位（2015）；GPU 与 Apple CPU 已按 1024 位缓存行（cache line）粒度处理数据。本文把「下一种宽度」直接设定为虚拟的 1024 位寄存器。

二、现状：解码端的数据并行困境

Parquet 是开源数据湖格式中使用最广的一个。它对每列固定实施 DICT，码流再以可变长游程中的位打包或 RLE 表达；论文指出，这种逐块可变尺寸的自适应编码本身妨碍快速向量化解码，而且它的位打包采用顺序布局、RLE 采用经典双循环，二者都不为数据并行留机会。

解码顺序位打包数据需要 PERMUTE 或 BITSHUFFLE 之类的跨 lane（数据通道）指令。Schlegel 等提出 k-way 交织布局（interleaved layout），把 k 个连续打包值分摊到 k 条 lane，避免跨 lane 操作。既有 4-way、8-way、16-way 实现分别面向 128、256、512 位寄存器，布局仍绑定硬件宽度。1024 位交织布局在 AVX2、AVX-512 上的解包吞吐分别为 4-way 的 2×、4×（Figure 13）；BitWeaving 的垂直位打包（Vertical Bit Packing，VBP）布局利用 SIMD 寄存器的位并行性加速过滤扫描，但它本身没有快速解码方案；Polychroniou 等为 VBP 实现 SIMD 解包后，吞吐约为 1024 位交织布局的 1/30。

两类编码还有更深的依赖。DELTA 解码是链式加法：不处理布局时，相邻值落在相邻 lane，加法跨 lane。已有应对各自付出代价：D4、DM 按批次构造差分，间距增至 4 倍时位宽多 2 bit；four-cursor 布局多存基值（base），只能利用宽发射标量核的指令级并行（instruction-level parallelism，ILP），不能用于 SIMD；垂直计算（vertical computation）与 tree 方案依赖聚集/散布（gather/scatter）指令，采用非顺序访问；论文报告这两种方案并未加快解码。RLE 解码是嵌套循环，每遇到一个短游程就切换路径，分支误预测频繁；SIMD 指令集架构（instruction set architecture，ISA）没有控制流指令可用。

软件维护也有负担：二进制分发的软件很难为每代 x86 SIMD、ARM NEON 和可伸缩向量扩展（Scalable Vector Extension，SVE）分别手写、维护平台专用的 SIMD 内建函数（intrinsics）。此前研究多在单个编码内实现 SIMD 化，文中列出的五个问题没有一个方案同时解决。

三、优化点：数据并行来自位布局

2023 年论文引用了作者 2020 年的硕士论文 Towards a New File Format for Big Data: SIMD-Friendly Composable Compression。论文提出的 FastLanes 优化对象不是新编码，而是压缩数据的位布局：重新安排位的排布，使四类 LWC 的解码在 8、16、32、64 的任意 lane 宽度、任意在役 ISA 以至纯标量代码上都暴露充分的独立工作。验证目标有两项：位解包超过每周期 40 个值（实测峰值 70，Figure 8）；单列求和中，压缩列扫描应在比标量解码更低的压缩程度下胜过未压缩数组。

四、方案：虚拟 1024 位寄存器与统一转置布局

4.1 面向所有 SIMD 宽度的交织位打包

FastLanes 设定一个尚不存在的 1024 位寄存器 FLMM1024：寄存器由 T 位 lane 组成，T 取 8、16、32、64，lane 数 S=1024/T（128、64、32、16）。不取 2048 或 4096 是保守选择：块内最大值域决定位打包宽度，块变大可能提高所需位宽；扫描的最小访问粒度也随之增大。

交织规定逻辑位置为 p 的 W 位值进入第 p mod S 条 lane（Figure 1）。lane 内的位保持连续；一个 1024 位字装不下时，位的接续发生在相邻两个字之间（W=3、S=128 时，位置 256 的值前 2 位落在第一个字，其余接续到第二个字），而不会跨 lane。任何 (S,T) 组合都有满 lane 的独立工作；窄寄存器的 ISA 用多条相同指令加工相邻内存，即可凑足 1024 位宽度。

1024 位交织位打包布局：逻辑相邻的位打包值轮流进入各 lane（Figure 1: The 1024-bit interleaved layout. B = 3 adjacent FLMM1024 words (red boxes, shown top-down) store 1024 values. Black bars indicate bit-packed values with their logical positions in the column: logically subsequent W = 3-bit encoded values are round-robin spread into S = 128 lanes of T = 8-bits. In the first word, only the first two bits (yellow,pink) of the value at position 256 fit, so it is continued in the second word (blue bit). The value at position 640 is also split. This happens in all lanes.)

解码内核不手写：对 1≤W<T、T∈{8,16,32,64} 的全部组合做静态代码生成，共 116 个预编译解码函数，每个一次交付 1024 个值。W=3、T=8 的内核（Figure 3）用 10 条指令解出前 384 个值；AVX-512 平台上该内核最高每周期 70 个值，折合 2GHz 单核每秒 1400 亿，而 3 位编码的输入流需要 52GB/s，已接近该平台的内存带宽上限。论文据此估计，查询流水线比解包内核慢约 100×，因此扫描的解码开销可忽略。

4.2 异构 ISA 的标量路径

FLMM1024 的指令集（Listing 1）只有九种运算：LOAD、STORE、AND、OR、XOR、ADD、SET，以及把掩码与移位合并的 AND_LSHIFT、AND_RSHIFT。AND 与 SHIFT 的融合不只是省指令：标量执行时，对 uint64 直接移位会把位搬进相邻 lane（SIMD 指令不会），先按调整过的常量掩码做与再做移位，跨 lane 泄漏被零成本堵住；ADD 也有跨 lane 位泄漏的风险，掩码挡不住，但 SIMD 指令集不做溢出检测，采用 SIMD 加法本就要求防溢出编码保证正确，因此 ADD 直接假设溢出不发生。

标量 Scalar_T64 路径把一个 uint64 变量当作准 SIMD 寄存器：64 位分成 64/T 条 T 位 lane，16 个这样的变量恰构成 1024 位（struct { uint64 val[16]; }）。关闭自动向量化实测：对 8 位值，SIMD 比朴素标量快 40–70×；开启自动向量化后，标量路径相对手写 intrinsics 的性能损失为 0（Figure 8）。论文由此建议使用者直接采用标量路径：内核随编译器与 ISA 一起演进，不新增平台代码，只有 32 位寄存器的低端 CPU 也在支持范围内。

4.3 统一转置布局

DELTA 的链式加法要求相邻两值沿同一条 lane 相接。转置把列切成寄存器大小的块竖向堆叠：T 行 × S 列的矩阵中，每条 lane 持有一条互不相干的 DELTA 链（Figure 4）。每条链需要一个基值，向量头存放全部基值；基值之间再做 DELTA 时，存储开销为 (W+log(T)+1)/T bit/值，如 T=64、W=7 时多 0.21 bit/值（约 3%）。

新的问题：转置后的取值顺序依赖 T，而同一次扫描的多列必须产出同序元组流。统一办法以 8×16 tile（数据块）为基本单元：1024 值切成 8 个 tile；T=64 时一个 tile 独占一行，T=32、16、8 时分别两、四、八个 tile 并作一行（Figure 6）。tile 排列被证明唯一：起点必须为 0（64 位解码逐 tile 推进，表头也只存 tile 0 的基值）；对 16 位类型，偶数 tile 必须全在前半、奇数 tile 在后半，两半各自成链；对 32 位类型，两块一行的组合若从 02 起步，第二轮需要 24 而 tile 2 已被占据，从 06 起步则处理完 8 个 tile 后没有后继；于是第一对固定 04，第三对必须是 15，由此锁定第二对 26 与末对 37，全序 04261537。配套的处理序列：T=64 为基值→0→1→…→7；T=32 为基值→04→15→26→37；T=16 为基值→0426→1537；T=8 为基值→04261537 一次处理 8 个 tile。

统一转置布局及 04261537 tile 次序（Figure 6: Unified Transposed Layout: (a)-(c) idea of order unification, (d) how our unified approach arrives at the 04261537 order (blue) of 8x16 tiles (green) and the final value order (green), (e) how it provides data-parallelism for all possible lane-widths. Notably, FastLanes does not only store each sequence of 1024 tuples permuted in this reordering, but the individual columns are usually also encoded with some LWC scheme (DELTA, FOR, DICT, RLE), which involves bit-packing using 1024-bit interleaving (Figure 1). So the eventual bit-sequences stored are humanly hard to grasp. However, decoding the values requires only regular and astonishingly fast calculations that are completely data-parallel.)

关系代数按集合语义处理元组，乱序通常不影响结果；即便查询结果或算子语义要求保留原序，也可以恢复顺序或用选择向量（selection vector）记录原位。置换局限于单个 1024 向量内部，因此局部重排不改变跨向量次序。对于不会报错的简单算术算子，若所有参数使用相同选择向量且仍有较多元素参与，向量化执行器可以跳过选择向量，按顺序处理完整输入。

4.4 FastLanes-RLE 的字典与索引表示

经典 RLE 以（值，长度）游程对表示数据，解码需外层遍历游程、内层重复写值。SIMD 化 RLE 把游程值广播到寄存器的全部 lane，再连续 STORE；游程短于一次寄存器写入容量时，下一条 STORE 会覆盖前一条写入的大部分值。FastLanes-RLE 改用另一种表示：游程值（Run Values，可重复）作为 in-flight（不预先物化）的字典；引入 Index Vector（索引向量），它在每个新游程起点加一，单调递增，DELTA 编码后每值只需 1 位。16 位索引用于短游程密集的向量，8 位索引用于长游程；8 位场景的基值用 3 位打包，每值加 0.375 位，平均游程长度不超过 12 时压缩率即胜过经典 RLE；更长的游程交给 0 位 DELTA 变体（索引全零，原本为 1 的位作为异常值保存）；这一异常处理方案留作后续工作。解码产物不做全量展开，保持为紧凑、可随机访问的部分压缩向量。

五、结果：解码微基准与端到端

5.1 六个平台的解码微基准

测试覆盖六个平台（Table 2）：Ice Lake 8375C（AVX-512）、Zen3 EPYC 7R13（AVX2）、Zen4 Ryzen 9 7950X（AVX-512）、Apple M1（NEON）、Graviton2 与 Graviton3（NEON）。Graviton3 虽也支持 SVE，但论文因其在该平台上慢于 NEON 而未将 SVE 用于测试。每个向量重复解码 3000 万次，数据常驻 L1，指标为每值周期数。

在位解包基准中，1024 位交织布局的标量解码周期/值与顺序布局相同（Figure 9）；Scalar_T64 利用交织布局把 8 位类型的标量解码提速 8×。T=8、W=1 时，峰值为每周期 70 值（单列解码中即 70 元组/周期；Figure 8）。

Zen4 的 AVX-512 指令由两个 256 位单元执行，解码吞吐不高于 Zen3；按主频归一后，M1 的 Scalar_T64 每值周期数低于 Ice Lake。Graviton3 的 SVE 每值周期数高于 NEON，所以论文实验使用 NEON。8 位 DELTA 在较快平台上仍超过每周期 40 值。

融合位解包与解码内核可省去中间一次 STORE 和一次 LOAD（Figure 11）；DICT 与 FOR 的解码本身就是位解包，论文未单独测这两类。

当平均游程长度短于 333 值（每个 1024 值向量内超过 3 个游程）时，FastLanes-RLE 的周期/值低于标量和 SIMD 化 RLE（Figure 16）。后两种方案在新游程处发生分支误预测，SIMD 化 RLE 还会因下一条 STORE 覆盖前一条写入的大部分值而未用满寄存器宽度。

5.2 压缩列扫描的反超点

在向量化执行器 Tectorwise 中构建单列表 TAB：10×2^28 个 uint32，共 10GB，查询为 SELECT SUM(COL)，平台 Ice Lake；对照三种数据来源：未压缩数组、标量解码的压缩列、FastLanes 解码的压缩列。值域均匀取自 [0,2^W)（Figure 12）。以每值位宽观察反超点：标量解码要把 uint32 压到约 8 位（压缩比 4:1）才胜过未压缩数组；FastLanes 每值约 24 位（比未压缩的 32 位节省约 25%）时即反超。线程数增加后，RAM 带宽更紧张，反超点右移；8 线程时，FastLanes 扫描比未压缩数组扫描快 7×、比标量解码快 4×。归因与背景一致：压缩节省的内存带宽超过新增的解码 CPU 成本。

六、FastLanes 文件格式 v0.1

6.1 背景：数据并行工作负载

2025 年论文 The FastLanes File Format（PVLDB 18(11)）发布开源 FastLanes v0.1。它面向 CPU 架构多样化、GPU 计算和分析/AI 工作负载增长的环境；向量化查询引擎也开始直接处理压缩向量，因此文件格式需要支持数据并行解码和细粒度访问。

6.2 现状与优化点

Parquet、ORC 等列式格式形成于通用压缩和较粗访问粒度主导的时期，Parquet 常将轻量编码与 Snappy、Zstd 等通用压缩组合。BtrBlocks 能级联轻量编码，但按行组解码且不能充分利用数据并行。2023 年论文解决了编码布局和解码问题，却将完整文件格式留作后续工作；v0.1 的目标是把可组合编码、多列压缩和向量级部分读取纳入文件格式。

6.3 方案：表达式编码

表达式编码（Expression Encoding）把编码表示为可组合的算子链。每个算子以一个 1024 值向量为单位，将当前表示变换为下一种表示；例如先用 DICT 生成字典码，再用融合位打包的基准帧编码（FFOR）压缩码流。文件用逆波兰式（Reverse Polish Notation，RPN）分别保存算子和操作数。读取时沿表达式自底向上解码；如果查询算子可以直接处理当前压缩向量，就在该表示处停止，不必完全展开为 SQL 类型。算子池覆盖整数、浮点、字符串和跨列处理；异常处理算子 PATCH 将异常值分离存储，并与其他编码组合。

6.4 方案：分段页布局与表达式选择

分段页布局（Segmented Page Layout）将文件组织为行组（rowgroup）、列块（column chunk）和段（segment）；v0.1 默认每个行组含 64 个 1024 值向量。相同类型、在表达式中承担相同作用的数据放进同一段，例如基值、位打包码或字典数据。段内有入口点数组，记录每个向量对应的数据位置；段描述符保存入口点和数据区的偏移与大小。文件由二进制数据区和文件尾部（footer）组成，footer 用 FlatBuffers 序列化列的编码表达式、段位置和最小值/最大值（Min/Max）等统计量，可与数据区分开读取；读取器据此只取相关列或向量，并跳过范围不匹配的行组。

表达式检测分两阶段。规则阶段先识别常量列、相等列、字符串或浮点到数值类型的转换、较窄整数类型和一对一列映射；采样阶段再从候选表达式池中选取编码。三点采样（three-way sampling）检查每个行组的首、中、末三个 1024 值向量；在 Public BI 上，论文报告这三个样本的压缩率选择准确度超过 99%。

多列压缩（Multi-Column Compression，MCC）利用列间相关性。相等列可以存储对另一列的引用；一对一映射可以复用另一列的字典；包含数字的字符串列也可以拆成字符串和整数子列，再分别编码。统一转置布局（Unified Transposed Layout，UTL）在 v0.1 中是可选项：它能加速 DELTA 和 RLE，但会改变向量内的元组顺序；需要原序时可用选择向量恢复。

6.6 局限与后续工作

FastLanes v0.1 的编码路径尚未优化：Table 4 的编码总耗时为 81,341.63 ms，高于 Parquet 和 DuckDB，低于 BtrBlocks。该论文重点评估文件压缩、解码和随机读取，没有完成接入查询引擎后的端到端评测；作者将 DuckDB 读写器列为下一步工作，并把模式演进（schema evolution）、嵌套数据类型和更广泛的机器学习数据支持留作后续。

七、思考：回看 2023 年论文

为什么是 1024：更大块可能扩大块内值域、提高位打包宽度，也会增加扫描的最小访问粒度；因此论文选择 1024，而放弃 2048 和 4096。

元组乱序是否破坏查询：关系代数按集合语义处理，通常顺序无关；需要时还原顺序或用选择向量标记原位，置换局限于单个 1024 向量内部，列内大体顺序保留；至于对单个 1024 向量内部的定点访问，论文没有展开做法。

标量 uint64 为什么能当 SIMD 用：AND 与 SHIFT 融合并配合调整常量掩码，阻止位跨 lane 传递；ADD 的进位风险由防溢出编码兜底，因为 SIMD 本身没有溢出检测。

局限：实验以微基准和单列求和为主；论文把完整系统的端到端评测留作未来工作。FastLanes-RLE 的 0 位 DELTA 异常处理、级联压缩（多个 LWC 方案堆叠）和完整开源文件格式集成也列为后续研究；GPU、TPU 扫描尚未评估。SIMD 相对标量的加速比从 8 位类型的 40–70×降至 64 位类型的 3–4×。

论文的收尾观点是，若要利用 SIMD 硬件，需要从数据存储层重新设计布局；长期目标是减少大数据格式对 zstd、Snappy、LZ4 等通用压缩方法的依赖。
