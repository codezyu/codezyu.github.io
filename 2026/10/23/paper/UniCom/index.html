UniCom：面向现代计算机系统的通用高性能 I/O 完成机制

论文：UniCom: A Universally High-Performant I/O Completion Mechanism for Modern Computer Systems，Riwei Pan、Yu Liang、Sam H. Noh、Lei Li、Nan Guan、Tei-Wei Kuo、Chun Jason Xue，USENIX FAST ’26（2026）。论文：USENIX PDF，源码：GitHub/MiKoLab/UniCom。

TLDR： UniCom 在内核集中完成 I/O，以标签调度降低睡眠唤醒开销，并绕过大部分内核 I/O 栈。Optane 上 4 KB 读较 ext4 高 43.5%；RocksDB 64 B 吞吐较 ext4 高 24%。

一、高性能 SSD 的 I/O 栈开销

面向低时延的 SSD 已能提供每秒百万级 I/O 次数（IOPS）和亚 10 µs 时延；下一代 Compute Express Link（CXL）SSD 还可能进一步提高带宽、降低时延。设备变快后，软件 I/O 栈开销在端到端时延中的占比上升：在 Optane P5800X 上处理 4 KB 读取时，这部分开销约占一半。

二、现有 I/O 完成机制的性能边界

论文比较了 ext4 的中断机制、BypassD 的轮询机制，以及 io_uring 的 SQ_POLL 模式。实验使用 4 KB 和 128 KB 多线程随机读，并在部分测试中加入 16 个计算线程（C-threads），考察 I/O 与计算负载共用 CPU 时的表现。

  • 中断（ext4）：没有 C-threads、I/O 线程数不超过 8 时，ext4 的平均 IOPS 为 BypassD 的 62.9%。4 KB I/O 达到设备饱和点（1,550k IOPS）后，两者差距缩小。与 16 个 C-threads 共存时，ext4 的 I/O 性能低于无计算负载时；I/O 线程增加后，C-threads 的性能逐步下降，原因是两类线程争用 CPU。
  • 轮询（BypassD）：低 CPU 利用率下，I/O 线程以忙等（busy-wait）方式检测完成状态；但 128 KB I/O 达到设备饱和后，线程会在块队列中等待并持续忙等，忙等时间从 1 个 I/O 线程时的 36 µs 增至 32 个线程时的 587 µs。与 16 个 C-threads 共存时，4 KB I/O 性能比 ext4 下降得更快；I/O 线程增至 32 个时，C-threads 的性能只有 ext4 的 39.1%。
  • io_uring（SQ_POLL）：专用提交线程集中轮询，减少了每个 I/O 线程各自忙等的开销，但有三项限制：同步 I/O 应用要改用异步 I/O 范式，通常需要较大幅度修改源码；per-instance 接口使多个进程难以共享轮询线程，各自运行提交线程时会相互干扰；提交线程只负责转发请求，I/O 完成仍由底层机制处理，因此共享实例也无法消除底层完成机制的限制，论文测试中的吞吐量只与 ext4 相当。论文分别测试了每进程各用一个实例的 io-uring-proc，以及多个线程共享一个实例的 io-uring-shared；前者的线程间干扰也会降低 C-threads 性能。

现有 I/O 完成机制的性能趋势示意；不代表精确数值或尺度（Figure 3: General performance trends of existing I/O completion mechanisms. The depicted results are illustrative only; they do not represent exact values or scales, but rather high-level trends.）

三、混合负载下的完成目标

论文的目标是在不同 CPU 利用率下保持较高 I/O 性能，同时支持主流应用的同步 I/O。同步 I/O 的一项约束是降低睡眠与唤醒开销：ext4 上一次 4 KB O_DIRECT（直接 I/O，绕过页缓存）读取的平均时延为 8,730 ns，其中将任务移出运行队列（deactivation）耗时 710 ns（8%）、上下文切换耗时 980 ns（11%）、唤醒并将任务重新加入运行队列（reactivation）耗时 1,240 ns（14%），三项合计约占 33%。

跨进程集中处理也有约束：各进程的地址空间相互隔离，完成线程无法直接截获其他进程的请求；通过进程间通信（IPC）转发会引入同步开销。此外，直达 SSD 需要与睡眠唤醒和集中处理配合，并保留内核中的文件权限检查。

四、UniCom 的内核完成方案

论文的关键观察是，系统调用引起的用户态与内核态切换在测试平台上约需 150 ns，约占表中 4 KB 读取时延的 1.7%，相较设备 I/O 时延可以忽略。UniCom 因而在内核实现完成机制：利用内核调度设施处理睡眠与唤醒，以系统级完成线程服务多个进程，并通过内核直达路径 SKIP（Shortcut Kernel I/O Path）绕过大部分内核 I/O 栈。

4.1 TagSched 标签调度机制

TagSched 在进程控制块（Process Control Block，PCB）中加入 2-bit 调度标签，标记线程处于 IO-WAIT 或 IO-NORMAL 状态。线程初始标签为 IO-NORMAL（值为 0）；提交 I/O 前，标签减一并转为 IO-WAIT，随后线程让出 CPU。调度器跳过处于等待状态的线程，但保留其在运行队列中；I/O 完成时标签加一并恢复为 IO-NORMAL，线程便可重新参与调度。这样无需频繁将任务移出运行队列再重新插入。

标签更新不是原子操作。若 I/O 在提交线程设置 IO-WAIT 前已经完成，完成路径会先将标签加一，提交路径随后减一，两次更新相抵。调度器把标签值大于或等于 0 的线程按普通任务处理，因此线程不会因更新竞争而永久停在等待状态。

TagSched 标签更新机制（Figure 5: TagSched tag-update scheme.）

混合负载下，I/O 线程完成后可能要等正在运行的 C-thread 用完毫秒级时间片，才能再次被调度。TagSched 根据线程是否执行过 I/O 区分 I/O 线程与 C-threads；I/O 完成时向目标 CPU 发送处理器间中断（IPI），触发立即选择下一个任务的操作，使已完成的 I/O 线程无需等待整个时间片。

TagSched 保留原有调度公平性和虚拟运行时间（vruntime）计算，行为类似线程反复调用 sched_yield。运行队列沿用红黑树；任务数从 1 增至 100 时，任务选择延迟只增加 28 ns。

4.2 TagPoll 集中轮询机制

TagPoll 在内核运行专用的 I/O 完成线程，为多个 I/O 线程及进程集中轮询硬件 NVMe（Non-Volatile Memory Express）队列。完成时，完成线程通过对应 PCB 的标签更新 I/O 状态，并结合运行队列负载选择完成方式：由专用线程通知调度器，或在目标 I/O 线程独占 CPU 时让其自行轮询，以避免不必要的线程切换。

一次完成处理约需 550 ns，包括更新标签、发送 IPI 和检查调度器状态。单个专用完成线程的最高完成速率约为 1,820 KIOPS（千 IOPS）；论文将支持多个完成线程作为后续工作，以扩展到多块 SSD 或更高 IOPS。

4.3 SKIP 内核直达路径

SKIP 由内核模块 UnIDrv 和用户态库 Ulib 组成。它在内核中管理 NVMe 队列，并让 TagPoll 的完成线程直接轮询这些队列。商用 SSD 的硬件队列数量有限：论文测试的 Optane P5800X 支持 135 个队列，Kingston NV3 支持 31 个。BypassD 将队列直接映射给应用进程，静态分配可能造成队列浪费，也可能让多个 I/O 线程共用一个队列而相互竞争。UnIDrv 在内核维护队列池，并按进程标识符（PID）哈希将队列分给 I/O 线程。

SSD 请求需要物理块地址。UnIDrv 为每个文件维护一棵 per-file extent tree，将文件偏移映射到物理块地址（physical block address，PBA）。每条 extent 记录一个文件偏移范围到连续物理块区间的映射，占 12 字节：块对齐偏移、PBA 和块长度各占 4 字节。打开文件时，UnIDrv 遍历 ext4 磁盘上的 extents 建树，并将树指针存入 ext4_inode_info；ext4_ext_map_blocks 和 ext4_truncate 等操作会沿用 ext4 的锁机制同步更新它。

该结构替代 BypassD 的 fmap：后者在用户态页表中静态保存偏移到 PBA 的映射，并依赖定制 I/O 内存管理单元（IOMMU）硬件；映射查询会增加 PCI Express（PCIe）往返和地址转换时延，页表内存约占文件大小的 0.2%。

SKIP 方案：左侧为现有用户态方案，右侧为 UniCom 方案（Figure 8: SKIP scheme. The left side indicates the current user-space approach, while the right side shows UnICom solution.）

Ulib 通过动态链接器的 LD_PRELOAD 预加载机制拦截应用文件操作，再用 ioctl 接口 user_io_submit 将文件描述符、偏移、用户缓冲区和长度等参数交给 UnIDrv。内核完成文件权限检查后，直接向 NVMe 提交请求。UniCom 支持文件空间预分配（fallocate）、截断（truncate）和追加写入，并即时更新 extent tree；由于绕过页缓存，它只处理直接 I/O。缓冲 I/O 等其他操作仍走 POSIX（Portable Operating System Interface）接口。

4.4 UniCom 原型实现

原型基于 Linux 6.5.1 和 ext4 实现。用户态 Ulib 有 1,089 行代码，内核模块 UnIDrv 有 3,250 行；为支持 TagSched，论文修改了 Linux CFS（Completely Fair Scheduler）调度器 71 行代码。sched_entity 增加 2-bit I/O 标签和 1-bit I/O 线程标志，sched_class 增加动态更新标签的函数，TagSched 逻辑接入 pick_next_entity。它只在选中 IO-WAIT 任务时触发，以控制对其他任务的调度开销。为避免 I/O 线程和完成线程并发访问 NVMe 队列槽位造成缓存伪共享，共享数据结构按缓存行对齐。

文件打开、关闭、删除等元数据操作仍使用传统 POSIX 接口。论文称，这让 UniCom 与 ext4 的回写日志（writeback journal）模式及 BypassD 一样，能够保持元数据的崩溃一致性。

五、UniCom 的性能评估

实验在 Ubuntu 20.04、Linux 6.5.1 上进行，平台为 24 核 Intel Core i9-14900K（8 个性能核（P-core）、16 个能效核（E-core））、32 GB 内存、400 GB Intel Optane SSD 和 1 TB Kingston NV3。实验只使用 16 个 E-core，关闭超线程与睿频，所有 I/O 均为直接 I/O，结果取五次实验的平均值。UniCom 将一个 E-core 留给专用完成线程，应用使用其余 15 个；其他方法可使用全部 16 个 E-core。对照方法包括 ext4（中断）、BypassD（轮询）和仅用于微基准的 io_uring（SQ_POLL）。微基准中的 C-threads 性能按所有计算线程的计数器值总和衡量。

5.1 微基准与设计代价

不含 C-threads 的随机 I/O。 在 1 GB 文件上，UniCom 的 4 KB 随机读、写 IOPS 分别比 ext4 高 43.5% 和 34.9%；论文称其小 I/O 吞吐略高于 BypassD，归因于 per-file extent tree 降低了映射开销。单线程读取时，UniCom 的平均时延较 ext4 在 4 KB 下低 42%、128 KB 下低 17.4%；设备饱和（32 个线程）时，4 KB 读取的 99 百分位时延（P99）仍低 31.2%。128 KB 读取下，BypassD 和 io-uring-proc 的 P99 时延分别达到 16,175 µs 和 16,233 µs，ext4 与 UniCom 则约为 593 µs；这是因为非抢占轮询会让等待设备完成的 I/O 线程阻塞整个调度时间片。

与 C-threads 共存。 固定 16 个 C-threads 并增加 I/O 线程时，UniCom 的 4 KB IOPS 平均比 ext4 和 BypassD 高 39.4% 和 88.8%。专用完成线程占用一个 E-core，使 C-threads 性能相对 ext4、BypassD 低约 7.5%；I/O 线程增至 32 个时，该完成线程得到充分利用，C-threads 性能转而分别高 35.8% 和 26.4%。在 128 KB 读取下，C-threads 性能比 BypassD 和 io-uring-proc 高 39.3% 和 43.3%；但相较 ext4 和 io-uring-shared 仍低约 15%，主要因为可供应用使用的核心少一个，且大 I/O 时专用核心利用率较低。固定 16 个 I/O 线程并增加 C-threads 时，UniCom 的 4 KB IOPS 平均比 ext4 高 33.2%；有 32 个 C-threads 时，比 BypassD 高 82.7%。

在消费级 Kingston NV3 上，UniCom 的 4 KB IOPS 只比 ext4 高 5.3%，因为瓶颈主要是设备 I/O 时延；但比 BypassD 高 79.4%，原因是较长的设备等待会放大忙等对 CPU 的浪费。

组件、资源与公平性。 I/O 线程数不超过 8 时，自适应完成策略让线程在独占 CPU 时自行轮询，使 IOPS 比关闭该策略时平均高 13.8%。BypassD 只分配一个 NVMe 队列时，应用峰值 IOPS 比使用全部队列低约 20%；增加队列可缓解这一限制，但会减少其他应用可用的队列。UniCom 的内核队列池按需分配，缓解了固定分配带来的取舍。

extent tree 的映射查询时延比 fmap 低 71.2%；其中 syscall 开销约 150 ns，树搜索约 80 ns。打开文件时构建树会增加冷打开时延：基线约 7 µs，有 4、9、186 条 extent 的文件分别约为 28、57、146 µs；热打开时，这部分额外开销可以消除。

公平性测试在 32 个 I/O 线程和 16 个 C-threads 的 4 KB 随机读负载下，按线程记录 IOPS 和 C-thread 计算量。论文在图 15 中报告：I/O 线程分布走势与 BypassD 相似，C-thread 分布走势与 ext4 更接近；前者都将 I/O 线程保留在运行队列并沿用 vruntime 更新，后者都在 I/O 完成时抢占 C-threads。

5.2 应用工作负载评估

destor 与 stress-ng。 论文将多线程文件恢复程序 destor 与矩阵计算负载 stress-ng 同时运行。CPU 轻载时，UniCom 与 BypassD 的恢复带宽差值接近 0，且在设备饱和前比 ext4 高至多 32%；此时 ext4 和 BypassD 下 stress-ng 的每秒操作数（operations per second，OPS）高于 UniCom，差异来自专用完成线程占用的核心。CPU 高负载时，16 个 stress-ng 线程占满实验使用的 16 个 E-core，UniCom 的恢复带宽不低于 ext4，平均比 BypassD 高 52.3%。stress-ng OPS 在 16、32 个恢复线程下分别比 BypassD 高 22.5%、45.7%，但低于 ext4。

RocksDB 与 YCSB。 实验以 Yahoo! Cloud Serving Benchmark（YCSB）对 RocksDB 进行测试，加载 5 亿组键值对，键（key）长 32 B，值（value）长 64 B 或 200 B；每种负载执行 1,000 万次操作，线程数为 1、8 或 32。相较 ext4，UniCom 在 64 B 值上的平均吞吐量高 24%；单线程、200 B 值时高 28%。数据库争用使高并发下的收益收窄：32 个线程时，64 B 和 200 B 值的吞吐量分别高 9% 和 18%。相较 BypassD，单线程时两种值的吞吐量均高 3%；32 个线程时分别高 34% 和 56%。

六、论文结论与后续工作

论文将 UniCom 总结为一套结合集中轮询、标签调度和内核直达 I/O 的完成机制，目标是在不同 CPU 利用率下兼顾轮询的响应速度与中断的 CPU 效率，并保留同步 I/O 接口。评估覆盖微基准、混合负载和 RocksDB；作者将支持多个完成线程列为后续工作。
