WSBuffer：高带宽 SSD 时代的缓冲 I/O 重构（write-scrap buffering）

论文：Rearchitecting Buffered I/O in the Era of High-Bandwidth SSDs，Yekang Zhan、Tianze Wang、Zheng Peng、Haichuan Hu、Jiahao Wu、Xiangrui Yang、Qiang Cao（通讯作者）、Hong Jiang、Jie Yao。除 Hong Jiang（德克萨斯大学阿灵顿分校）外，其余作者来自华中科技大学。论文发表于 FAST ’26（第 24 届 USENIX Conference on File and Storage Technologies，2026）。论文：USENIX PDF，报告：FAST ’26 presentation。

TLDR： 高带宽 SSD 下，page cache 全量缓冲、页管理锁竞争和部分页读回是瓶颈。WSBuffer 缓冲小写及未对齐部分，大块对齐写直达 SSD，并异步回填、写回。测试中吞吐最高达基线 3.91×，时延加速比最高 82.80×。

一、背景：高带宽 SSD 改变 I/O 成本

缓冲 I/O 通过内核 page cache 接收不同偏移和大小的请求，并可在内核中合并写入、处理对齐、预取数据，再由后台线程刷新脏页。Direct I/O 绕过 page cache，能更直接地利用 SSD 带宽，但请求的偏移、大小和用户缓冲区地址都受对齐约束，增加了应用编程复杂度；同时，SSD 的访问时延仍高于内存，因此缓冲 I/O 仍广泛使用。

NVMe SSD 的带宽随设备内并行度和多盘部署持续增长：写带宽从 PCIe 3.0 时代的不到 3 GB/s 增至 PCIe 5.0 时代的 10 GB/s 以上，作者预计 PCIe 6.0 还会翻倍。内存与高速 SSD 的带宽差距因此缩小到一个数量级以内；SATA SSD 和 HDD 时代的差距则有两到三个数量级。多盘阵列还会进一步提高聚合带宽，使软件栈管理开销更容易成为写路径瓶颈。

二、现状：page cache 写路径的三类瓶颈

C1：全量缓存的管理成本限制写带宽。 作者在 8 块 Samsung 990 PRO PCIe 4.0 SSD 组成的 RAID0（总带宽约 55 GB/s）和约 200 GB/s DDR4 内存带宽的平台上，用 FIO 执行顺序 2 MB 写。测试提供充足内存，并关闭后台刷新。所有线程数下，Direct I/O 的写吞吐都比缓冲 I/O 高 1.10×–4.46×。尽管内存带宽约为 SSD 阵列的 3.6 倍，页分配、查找、状态维护及 LRU（Least Recently Used，最近最少使用）老化和回收的成本仍抵消了带宽优势。传统缓冲 I/O 把所有写入放在 page cache 中处理，因而无法随 SSD 带宽扩展。

8 块 SSD 与 8 个 DDR4 DRAM 下的写入吞吐（Figure 1: Maximum performance of direct I/O via a RAID0 array with 8 PCIe4.0 SSDs [51] (about 55GB/s total bandwidth) and buffered I/O via 8 DDR4 DRAM (about 200GB/s total bandwidth) under different thread counts.）

C2：页管理锁竞争加重内存依赖。 作者用 16 个线程执行 4 KB 整页写入，每个线程访问独立文件，并从实验开始启用页面刷新，以排除并发文件访问带来的锁竞争。当可用内存容量只有写入总量的 70% 时，除受自身并发问题影响的 BTRFS 外，文件系统写吞吐比内存充足时最多低 54%。内存不足会加快页替换，空闲页插入和干净页删除都要更新 Linux 内核 page cache 的 XArray 索引树。XArray 更新由不可扩展的 xa_lock 自旋锁保护；每个脏页刷新时都要经历 dirty（脏）、writeback（写回中）、clean（干净）状态转换并更新树节点 tag，因而反复争用这把锁。增加后台刷新线程不能消除这类锁竞争。

内存供给比例对缓冲 I/O 写吞吐的影响（Figure 2: The write throughput of file systems via buffered I/O under different memory supplies (i.e., the ratio of available memory capacity to the amount of written data). Page flushing is enabled throughout the entire process.）

C3：未命中缓存的部分页写需要先读盘。 缓冲 I/O 的部分页写若未命中 page cache，会先触发 page fault（缺页异常），从 SSD 读回整页，再更新其中一部分；这一步称为 read-before-write（先读后写）。作者在单线程、内存充足的条件下比较整页写与部分页写；后者时延是相应整页写的 1.51×–84.37×。现代 SSD 虽有较高带宽，但小访问时延仍高，也难以利用 SSD 内部并行度；因此，这部分额外时延主要来自读盘。

整页写与部分页写的时延对比（Figure 3: Full-page writes vs. partial-page writes.）

三、现有方案与设计目标

现有方案主要从优化 page cache 或绕过 page cache 两个方向处理写路径问题。

  • 优化 page cache。 ScaleCache 通过 ccXArray 提高页索引、更新和刷新的并行度；StreamCache 面向高强度扫描优化页状态维护、回收和分配；Uncached buffered I/O 在访问后回收相应内存页，并及时刷新脏页。这些方案降低了页管理开销，但缓冲 I/O 仍在写关键路径上缓存所有写入，难以充分利用高速 SSD。
  • 绕过 page cache。 BeeGFS 按固定阈值在缓冲 I/O 和 Direct I/O 间切换；Lustre AutoIO 根据 I/O 大小、文件锁竞争和内存约束动态选择模式。OrchFS 用非易失性内存（NVM）承接未对齐写，并对齐后通过 Direct I/O 写入 SSD；SPDK（Storage Performance Development Kit）等用户态 I/O 框架则绕过内核提交 I/O。这类方案减少了内核缓存路径的参与，但会增加应用修改和维护成本，也限制了对 legacy 应用的适用性与可移植性。

WSBuffer 重构缓冲 I/O 的写路径：让大部分缓冲处理退出前台写关键路径，同时保留 page cache 的读路径和缓冲 I/O 接口。其目标是：G1，尽量减少进入缓冲区的用户写入，让 SSD 承接更多大块写；G2，让脏数据平稳刷新并尽快回收写缓冲内存，减少后台刷新对前台写入的阻塞；G3，在避免部分页写读盘的同时，保持页数据管理简单。 WSBuffer 不改 POSIX I/O 接口，也不要求应用修改；它与既有 page cache 优化正交，可与 ccXArray 等方案集成。

四、WSBuffer 的设计

WSBuffer 在 POSIX 缓冲 I/O 接口下重构写路径，把写缓冲与读缓存分开：前台写入可直达 SSD，page cache 继续服务读请求。

WSBuffer 总体架构（Figure 4: WSBuffer overview.）

4.1 Scrap-page 结构与写入机制

scrap buffer 是 WSBuffer 专门承接写入的缓冲区，基本单元为 scrap-page。每个 scrap-page 由 128 B 元数据区（header）和默认 256 KB 数据区（data-zone）组成。header 包含有效字节数（4 B）、数据段数量（1 B）、目标 SSD 标识（SSD-id，2 B）、刷新状态 tag（1 B），以及 15 个索引项（每项 8 B，记录一个 data-segment，即连续数据段，在 data-zone 中的偏移和大小）。超过 95% 的 scrap-page 使用不到 15 个索引项。

data-zone 大小取 SSD 通道数与 SSD-page 大小乘积的整数倍。评估平台有 8 个通道、SSD-page 大小为 16 KB，因此默认 data-zone 为 256 KB，即 8 × 16 KB 的两倍。较小的 data-zone 便于灵活分配；较大的 data-zone 可使单位数据量对应的页索引和管理操作更少。后台刷新按一个 data-zone 为处理粒度，较大的粒度也提高了处理效率。

若把 128 B header 和 data-zone 放进同一分配块，header 会造成内存碎片，也会让一次 scrap-page 访问落到多个分散的内存区域。WSBuffer 因而每次分配 32 个 scrap-page，将 header 和 data-zone 分开放在 4 KB 与 8 MB 的区域中。

写入时，WSBuffer 按 scrap-page 边界拆分请求，直接把数据写入对应 data-zone，不先读回旧页；随后合并地址重叠的 data-segment，并更新 header。scrap-page 填满后，WSBuffer 更新状态 tag，将其加入写回队列。

写入请求合并到 scrap-page 的过程（Figure 5: A scrap buffer write example.）

4.2 Buffer-Minimized Data Access：写入分流与一致性

WSBuffer 的 Buffer-Minimized Data Access（缓冲最小化数据访问机制）负责在 scrap buffer、page cache 和 SSD 之间路由读写请求，并维护这些位置之间的数据一致性。写入分流使用请求大小阈值，评估平台的默认值为 1 MB：在该平台上，1 MB 及以上请求中可对齐的部分直接写入 SSD，比缓存在 scrap buffer 更快。

小于阈值的写入全部进入 scrap buffer，偏移不受限；较大的写入则拆成 data-zone 边界处的未对齐部分和中间对齐部分。未对齐部分进入 scrap buffer，对齐部分直接写入 SSD。对齐粒度是 data-zone（例如 256 KB），而不是内存页（例如 4 KB）。SSD 据此按完整 data-zone 分配对齐的大块空间，使其最小存储单位不再继续碎片化；每个 scrap-page 在 SSD 上也对应一段连续地址，便于后台刷新处理。阈值越高，进入 scrap buffer 的写入越多。

大块写入直达 SSD 后，WSBuffer 会回收被覆盖的旧 scrap-page 和 page cache 中的 memory-page（供读路径缓存的内存页）；小写进入 scrap buffer 后，也会回收相应的 memory-page。这些回收在后台执行。读取时，WSBuffer 先查找 scrap buffer，因为其中的数据始终是最新的；剩余部分再由 page cache 提供，未命中时才从 SSD 读取。

一致性依靠脏数据与干净缓存分开管理：scrap-page 保存尚未写回的最新数据，memory-page 始终保持干净，只供读路径缓存。因此，同一数据不需要在两个可写副本之间同步。

4.3 OTflush：SSD 忙碌感知的两阶段刷新

OTflush（机会主义两阶段刷新）用两阶段队列处理未填满 scrap-page 的回填和满页写回，并避免把后台 I/O 集中发往繁忙的 SSD。每块 SSD 都维护一个 Bcount（在途字节数），记录尚未完成的 I/O 字节数：提交 I/O 前增加计数，I/O 完成后递减。默认以 4 MB 为忙碌阈值，因为论文认为单次 4 MB 写入已接近打满单盘带宽；该阈值可以调整。

Stage-1：回填。 未填满的 scrap-page 加入 Queue-1。线程取出页面时，若它已被前台写满，就丢弃该队列项；若其对应 SSD 不忙，则从 SSD 异步读入缺失部分，再把页面放入 Queue-2；若 SSD 正忙，则把页面重新排到 Queue-1 队尾。

Stage-2：写回。 线程从 Queue-2 取出页面后，先检查页面是否仍有效；若它已因覆盖而失效，就丢弃队列项。若 header 中的 SSD-id 为 0，说明尚未分配 SSD 空间，OTflush 采用 delayed allocation（延迟分配），选择当前最空闲的 SSD 分配空间并写回；若已有关联 SSD，则在该 SSD 空闲时写回，忙碌时重新排队。写回完成后，WSBuffer 立即回收 scrap-page。两个阶段默认各使用一个队列和一个线程；由于 scrap-page 之间没有依赖，队列可拆成多个子队列并增加线程。

4.4 SXArray 与 Scrap-page 级锁

SXArray 是 WSBuffer 为 scrap-page 管理改造的 XArray；它只维护索引，不维护页状态。插入沿用常规更新；删除时，SXArray 在索引项级锁保护下先将索引项置为 NULL，再把树节点的级联删除延后到文件负载较轻时或文件关闭时执行。延迟执行树结构更新会使高负载时树暂时偏大；论文认为影响有限，因为 scrap-page 粒度较大、大写多数直写 SSD，每个文件中的 scrap-page 数量较少。被延迟删除的节点之后也可供新 scrap-page 复用。

page cache 的 XArray 继续管理只读 memory-page；这些页不再经历 dirty、writeback、clean 状态切换。page fault 引起的树更新只影响当前读线程，不会阻塞其他读线程。

scrap-page 状态由逐页独立的细粒度锁（per-scrap-page lock）保护。前台写入和 OTflush Stage-1 只需持有对应页锁，不修改树结构；Stage-2 写回时持有页锁，完成后再用 SXArray 的索引项级锁更新索引。scrap-page 插入仍需常规 XArray 锁，但大粒度页减少了锁竞争；该管理方式也能与 ccXArray 等 XArray 优化配合。

4.5 实现与文件系统集成

作者在 Linux 6.8 上基于 XFS 实现约 4,500 行代码的内核模块。scrap buffer 与文件系统的交互方式类似 page cache；所有缓冲 I/O 读写由 WSBuffer 的 data access 接管。论文称，该实现沿用并扩展 XFS 的元数据维护流程，不损害文件系统完整性。

fsync 会先查找相关 scrap-page，再由专用线程按 OTflush 流程刷新；memory-page 不需要参与。由于许多 scrap-page 已填满或正在刷新，剩余页面也能较快写回。持久性和崩溃一致性仍由底层文件系统（例如日志机制，journaling）保证，与传统 page cache 的做法相同。

WSBuffer 的架构不依赖 XFS 特性，scrap buffer 和并发页管理可直接用于其他文件系统；data access 和 OTflush 则需要针对各文件系统的数据结构与处理逻辑进行集成。

五、实验评估

5.1 WSBuffer 性能评估

实验设置。 测试机为双路 Intel Xeon Gold 6348（2.60 GHz、28 核）和 256 GB DDR4，存储为 8 块 PCIe 4.0 Samsung 990 PRO，单盘标称读带宽 7 GB/s、写带宽 6.9 GB/s。SSD 通过 Linux 软件 RAID（mdRAID）组成 RAID0，stripe size（条带大小）为 512 KB。除 ScaleCache 使用 Linux 5.4 外，实验运行于 Ubuntu 22.04 LTS、Linux 6.8；线程绑核、关闭 CPU 频率调节，并在每次运行前清理内核缓存，结果至少取 5 次平均。基线包括 EXT4、F2FS、BTRFS、XFS，以及部署在 XFS 上的 ScaleCache（ScaleCache-XFS）。论文指出，ScaleCache-XFS 的旧内核缺少后来并入主线的 folio 批量分配与刷新、delayed logging（延迟日志）、批量 inode 激活等 XFS 优化，因此部分测试中甚至慢于 Linux 6.8 的 XFS。

微基准。 在关闭后台刷新、提供充足内存的 FIO 单线程随机整页写测试中，写偏移按 scrap-page 边界对齐。WSBuffer 的平均写入时延加速比为 1.03×–3.29×：小于 1 MB 时为 1.03×–2.84×，收益来自批量分配、连续内存布局和较少的页索引；1 MB 及以上的写入直接落盘，时延加速比为 1.14×–3.29×。

同一微基准中的部分页写请求采用偏移变化 ±10% 的设置。WSBuffer 的时延加速比为 1.70×–82.80×；小于 1 MB 时为 2.11×–82.80×，主要因为 scrap buffer 消除了前台 read-before-write。对于 1 MB、2 MB 和 4 MB 请求，分别有 32.4%、82.3% 和 91.1% 的数据直接写入 SSD，时延加速比仍为 1.70×–4.06×。

不同写入偏移和大小下各文件系统的平均写时延（Figure 8: Average write latency of file systems under different write offsets and sizes.）

与 XFS Direct I/O 和在 XFS 上按 AutoIO 原则实现、采用 1 MB 阈值的混合 I/O 方案（XFS-AutoIO）相比，WSBuffer 快 1.59×–231.28×。Direct I/O 需要对未对齐写执行读改写；AutoIO 的小写和大写也分别受部分页写、读改写影响。论文说明，这项比较没有计入额外的应用编程成本。

WSBuffer 与 Direct I/O、混合 I/O 方案的对比（Figure 9: Comparison with direct I/O and hybrid I/O.）

多线程和 Filebench。 FIO 随机写请求大小为 4 KB–4 MB 时，WSBuffer 的吞吐比基线高 1.21×–3.91×，且随线程数增加得更快。Fileserver 混合读写负载（读写比 1:2）下高 1.19×–2.51×。峰值吞吐受约 55 GB/s 的 SSD 总带宽和内存拷贝限制：内核需把未对齐用户缓冲区中的数据复制到适合内核 submit_bio() 接口提交的对齐内存区域。只读负载下，WSBuffer 与 XFS 的性能接近。

随机写与 Fileserver 负载下的多线程性能（Figure 10: Multi-threaded performance. (a) Random writes with bsrange=4k-4m. (b) Fileserver load with read/write=1/2.）

Filebench 在内存充足、关闭页面刷新，并分别使用单线程和 16 线程的条件下测试三种负载。写密集的 Fileserver 中，WSBuffer 吞吐高 1.23×–2.51×，XFS 排第二；读密集的 Webproxy 中高 1.08×–1.65×，但略低于 XFS。关闭 OTflush 后，scrap-page 留在缓冲区，请求需分别查询 SXArray 和 XArray，页管理也要更新两棵树。开启 OTflush 可写回并回收 scrap-page；增加刷新线程能加快回收，因此 WSBuffer 的表现更接近 XFS。元数据密集的 Varmail 中，WSBuffer 高 1.06×–2.84×；该负载超过 60% 的时间用于 fsync，较大的 scrap-page 和更简单的页状态维护缩短了页定位、块 I/O 请求组装和刷新过程，F2FS 排第二。

内存受限测试对 Fileserver 和 Webproxy 开启页面刷新，并将内存供给设为写入量的 10%–50%；WSBuffer 每阶段各用一个 OTflush 线程，ScaleCache-XFS 无法在严格内存限制下运行。Fileserver 中，WSBuffer 吞吐高 1.23×–4.48×；Webproxy 中高 1.07×–4.37×。此时前台写入消耗内存的速度仍高于 OTflush 的释放速度，因此增加内存供给仍能提高性能；增加 OTflush 线程也可加快回收。Webproxy 下基线文件系统的锁竞争比 Fileserver 少，XFS 还能利用 folio 提供的批量分配与刷新优化。WSBuffer 的优势来自降低写入占用并减少页管理锁竞争，腾出的内存可用于 page cache 读缓存。

LevelDB 的访问以小请求为主，前台写入都缓存在内存中。图计算的收益还包括读性能的间接改善；作者将这部分与大块、对齐的 SSD 写入联系起来。内存分析另指出，减少写缓冲占用后，释放的内存可供 page cache 缓存读取。

CPU 利用率。 在内存充足的 4 KB–4 MB 随机写测试中，WSBuffer 的 CPU 利用率比基线低 3.2%–28.4%。论文将此归因于超过 80% 的写入数据直接交给 SSD，由直接内存访问（DMA）完成传输；WSBuffer 自身的 CPU 开销主要用于维护 scrap-page header 和 OTflush 队列。

内存占用。 默认 1 MB 阈值下，整页写中小于 1 MB 的数据全部进入内存，1 MB 及以上的整页写不进入内存；基线文件系统则将所有写入缓存在内存。图计算和 Nek5000 的前台写入内存占比分别为：LiveJournal 0.59%、Twitter 1.45%、Friendster 0.34%、Nek5000 1.67%。这些负载中的小写通常只有几 KB 到几十 KB，后续大写覆盖后会被回收；因此 WSBuffer 为读缓存留出了更多内存。

敏感性。 RAID stripe 大小变化不影响 WSBuffer 的性能优势。增加 SSD 数量时，WSBuffer 吞吐随总带宽提升；XFS 则未能从新增的 SSD 带宽中获得同等收益。

六、结论

WSBuffer 把缓冲 I/O 的写入按大小和对齐方式分流：scrap buffer 承接小写与未对齐部分，大块对齐数据直接写入 SSD；page cache 继续服务读请求。OTflush 异步回填未满页并择机写回，SXArray 与页级锁降低并发页管理开销。在 Linux 6.8 的 XFS 实现和论文测试中，WSBuffer 相对基线的吞吐最高达 3.91×，时延加速比最高为 82.80×。它保留缓冲 I/O 接口，但 data access 与 OTflush 移植到其他文件系统仍需针对性集成。
