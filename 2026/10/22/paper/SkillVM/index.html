SkillVM：面向异构 Agent 目标的 skill 编译与运行时

论文：Skill VM: Write Once, Run Everywhere Efficiently，Le Chen、Erhu Feng、Yubin Xia、Haibo Chen，上海交通大学并行与分布式系统研究所（IPADS），SOSP 2026。开源：github.com/SJTU-IPADS/SKVM。实现 36,200 行 TypeScript；论文将系统写作 SkillVM。

TLDR： 11.8 万个 skill 的测量显示，原样注入上下文会造成模型、harness 与环境错配。Skill VM 在安装期为目标编译变体，运行期按执行反馈重编译，并处理依赖绑定、并发抽取、代码固化与资源调度。评测中平均任务完成率提高 15.3%，对可完成任务的 token 消耗最多减少 40%；PDF 提取的代码固化提速 19–50 倍，并发最高提速 3.16 倍。

一、背景：skill 生态与执行模型

Skill 是可分发、自包含的知识包，可补充基座模型不具备的能力，也可将 agent 约束到特定工作流。例如，有的 skill 教模型用 pdfplumber 而非已弃用的 PyPDF2 提取字段。Skill 通常由三部分组成：metadata（名称、描述、触发条件，供运行时发现 skill 并匹配任务）、instructions（正文中的多步工作流、工具引用和任务指导）、bundled resources（脚本、参考资料和模板）。与裸 prompt 相比，metadata 让运行时可以按任务选择 skill；与微调相比，skill 不改模型权重，而是在 prompt 层发挥作用，因此分发轻量、可组合。Claude Skills、Cursor、Coze、Copilot 等平台已采用这一抽象。论文从 clawhub.ai 收集 28,990 个 skill、从 skills.sh 收集 89,280 个，合计超过 11.8 万；两个平台上的下载量都呈长尾分布，skills.sh 上 89% 的 skill 下载量不足 86 次。

Agent 按 ReAct（reasoning and acting，推理与行动）循环工作：先推理，再调用工具（如读文件、执行命令、发送请求），观察结果后继续推理。Agent 通过 agent harness（Agent 运行框架，以下称 harness）与外部世界交互；harness 管理大语言模型（LLM）的 API 连接、注册可用工具、分发调用，并控制哪些内容进入上下文窗口。Claude Code、OpenCode 和 OpenClaw 是常见 harness。Harness 提供的能力不同：有的具备文件系统和 web 搜索工具，有的只提供 read、write、exec；有的支持并发子 agent（sub-agent），有的只支持顺序执行。这些差异会决定 skill 中的操作能否执行。

论文对下载量超过 100 的 15,063 个 skill 进行大语言模型（LLM）辅助分类：工具参考占 52%（教模型操作 API 或 CLI，本质上是使用文档）、程序性指导占 28%（分步骤的工作流，如四阶段调试法）、内容生成占 20%（产出质量取决于模型自身能力）。在这批样本中，76% 含有显式程序结构（编号步骤、条件分支、步骤间数据依赖）；75% 含有代码片段（shell 命令、API 调用模式等），其整体结构会重复出现，变化的主要是输入参数。例如，天气 skill 可以复用同一组 curl 命令模板，只替换城市、日期或输出格式。这些结构为后文把 skill 当作代码处理提供了依据。

二、现状：三类错配与量化证据

当前系统把 skill 作为原始文本注入上下文，不针对执行目标进行改编。Skill 对模型、harness 和执行环境都有隐含假设；假设与目标不符时，会出现三类错配。

P1 模型错配。 Skill 假定模型能理解并执行其中的指令，但同一 skill 在不同模型上的表现差异明显。论文在 20 项任务中比较了 5 个模型与 3 种 harness；启用 skill 后，15% 的任务表现下降（Claude Opus 4.6 上为 7%，Qwen3-30B 上为 25%）；另有 17% 的任务没有提升（不计本就满分的任务），且至少有一个模型未从 skill 获益的任务占 87%。同类工作 SWE-Benchmark 的结果也显示，49 个 skill 中有 39 个未带来提升、3 个造成明显退步；token 增长 451%，通过率却没有变化。

模型与 harness 会显著影响 skill 表现；列为任务，行为模型，各子图对应一种 harness，格子颜色表示相对无 skill 基线的得分变化，格内数字为绝对任务得分（Figure 2. Skill performance across models and harnesses. Columns are tasks, rows are models, and each subplot corresponds to one harness. Cell colors indicate score deltas relative to the no-skill baseline, and cell labels show absolute task scores. Both model identity and harness choice significantly affect outcomes.）

pptx-creation skill 指导模型使用 JavaScript 库 PptxGenJS 生成 PowerPoint 演示文稿。Claude Opus 4.6 和 Gemini 3 Flash 使用该 skill 得满分；Devstral Small 在 OpenCode 中把 PptxGenJS 误当作 CLI，反复执行无效命令。不加载该 skill 时，Devstral Small 改用 python-pptx 得 95 分。这个案例表明，skill 假定模型能分辨库 API 与 CLI；论文观察到这一点对前沿模型（frontier models）成立，对较弱模型则不成立。

P2 harness 错配。 同一模型执行同一任务，换用不同 harness，结果也会变化。workday-scheduling 任务中，Gemini 3 Flash 使用原始 skill 在 BareAgent 上得 100 分，在 OpenCode 上却得 0 分。论文将失败归因于 skill 中一个畸形 JSON 键：BareAgent 只加入最小系统提示，OpenCode 则预置大量工具文档；更长的组合上下文诱发了格式错误。另一组实验中，使用原始 skill 时，OpenCode 与 OpenClaw 的得分差最多为 13 分，且差距随模型而异。

P3 环境错配。 Skill 可能依赖用户机器上没有安装的包、工具或配置。在 15,063 个分类样本中，53% 至少依赖一个外部包或工具；其中 19% 完全没有声明依赖，另有 40% 只列出实际所需依赖的一部分。即使列出了前置条件，skill 也常未说明操作系统、硬件、软件版本或包管理器状态等环境要求。在依赖缺失时，Qwen 模型的成功率下降 33–67%，失败的 workaround 会多消耗 2–4 倍输出 token；Claude Opus 4.6 虽仍能成功，每次运行的输出 token 仍增加 56–69%。因此，把依赖诊断和安装留给模型，会在每次遇到缺失依赖时增加执行成本。

要为不同目标改编 skill 有两项困难。第一，模型、harness、环境三轴独立变化，同一 skill 在不同组合下需要不同改法；弱模型配富 harness 的处理方式，未必适用于同一模型配最小 harness 的组合，因此适配空间是组合性的，固定改写规则难以覆盖。第二，skill 以自然语言编写，没有语法、抽象语法树（abstract syntax tree，AST）或可直接验证的性质；改编前必须先从散文中恢复隐含的工作流结构。

三、优化点：skill 编译与异构目标适配

论文以编程范式的演化作类比（汇编语言→高级语言→虚拟机）：skill 类似 agent 时代的程序，LLM 是异构处理器，harness 则提供各自的执行接口。现有 agent 直接把 skill 原文交给模型解释执行，没有为不同目标适配内容的机制。Skill VM 在这一执行路径中加入编译层，分为安装期 AOT（ahead-of-time，预先编译）和运行期 JIT（just-in-time，即时编译）优化。

AOT 编译器在安装 skill 时分析目标（模型、harness 和宿主环境），经过三个 pass 生成优化变体：基于能力的编译（§4.1）处理模型与 harness 错配，环境绑定（environment binding，§4.2）处理环境依赖，并发抽取（§4.3）识别并行机会，再映射到目标 harness 支持的并发原语。运行时保存这些变体；新任务到来时，按当前模型与 harness 选择变体，并通过渐进披露（progressive disclosure）机制加载内容——先读 metadata，再加载全文。加载全文前，运行时执行环境绑定脚本，检查依赖是否满足。Skill VM 对 agent 隐藏变体选择过程。JIT 优化器则处理静态编译时难以预见的问题：例如并发 sub-agent 争用资源，或只有多次执行后才能观察到的能力缺口。自适应重编译和代码固化负责这些运行期优化；资源感知调度器根据运行时资源状况安排已识别的并行任务。每个 skill 与目标组合只需进行一次 AOT 编译，之后可复用编译结果。

Skill VM 架构：AOT 编译器在安装期通过三趟编译生成优化变体，运行时在执行期间管理变体选择、JIT 优化和资源感知调度（Figure 5. SkillVM architecture. The AOT compiler produces optimized skill variants at install time through three passes. The runtime manages variant selection, JIT optimization, and resource-aware scheduling during execution.）

四、方案：安装期 AOT 编译

4.1 基于能力的编译

第一趟编译处理模型和 harness 的能力差距。由于目标种类繁多，编译器无法为每个目标编写专属逻辑，因此 Skill VM 使用 primitive capability（原生能力）描述 skill 的最低需求。原生能力由需求侧定义，不依赖具体模型，并遵循三项原则：可组合——skill 中的具体任务可表示为能力组合；通用——同一能力会出现在多种 skill 中，以控制编译器的工作量；语义独立——能力描述结构正确性，不判断输出质量。

作者先从 50 个代表性 skill 中借助 LLM 提取 19 个初始能力，再由人工逐项校验；随后用 15,063 个 skill 验证这套集合，仅在语料中出现比例至少为 1% 的新能力才会纳入。最终集合包含 26 个原生能力，覆盖 95% 的 skill 需求。每项能力分为 L1、L2、L3 三个熟练度层级：L1 要求最低，L(n+1) 级任务不能由 L(n) 能力完成。例如，gen_code（代码生成能力）从基本命令扩展到含 awk 的复杂管道；follow_procedure（流程遵循能力）从单步操作扩展到循环与验证。为检查层级边界，作者为每项能力、每个层级生成微基准并跨模型评测；若模型通过高级用例却未通过低级用例，就调整层级定义并重新测试。

用户配置 agent 时，系统离线测量目标模型的能力画像：逐项运行原生能力微基准，根据通过结果确定能力层级，并缓存画像，供该模型的各个 skill 编译复用。编译时，编译器把 skill 拆成具体任务，映射到所需能力，再与目标画像比较，按差距选择变换（transform）。Compensation（补偿）用于目标具备相应能力但熟练度较低的情况：增加示例、明确指令或加强任务约束，同时保留 skill 原意，优先采用此方式。Substitution（替代）用于目标缺少某项能力或差距过大时：改用其他能力实现同一目标的路径。例如，目标的 gen_code.python 只有 L1，而 gen_code.sql 达到 L2，编译器可将 Python 路径替换为 SQL 路径；这些可互换的实现路径构成等价类。

4.2 依赖探测与环境绑定

第二趟处理 P3 环境错配。编译器从第一趟产物抽取外部库、CLI 工具和系统服务等依赖，但不把抽取结果视为完整清单：依赖声明可能缺失或不完整，因此静态列表不足以决定特定主机上的安装动作。编译器先对清单中的每项运行轻量探针（如 pip show、which）；已满足的依赖无需处理，无法判断的项目则进行系统感知探测。随后生成幂等的 env-binding 脚本，在 skill 执行前检查并修复依赖。若环境发生变化或脚本执行失败，执行流程转由模型处理，脚本输出作为附加上下文提供给模型。

4.3 工作流 DAG 的并发抽取

第三趟从 skill 的工作流中提取并行性。多步工作流常以顺序散文描述，实际并非每一步都依赖前一步。编译器用 LLM 辅助分析拆分工作流，标出每步消费的输入和产生的输出，再构造有向无环图（DAG）：若步骤 B 消费步骤 A 的输出，就在 A 和 B 之间连边。编译器在输出 DAG 前检查有无环路和悬挂节点；验证失败时，受影响的步骤保持顺序执行。

Skill VM 按并发发生的位置区分三个层级。脚本级并发是在单一步骤内对多个独立数据项执行相同操作，例如对 15 个 CSV 文件运行同一分析；编译器用与实现语言相符的并发原语改写该步骤，如 shell 并行、Python multiprocessing 或 JavaScript Promise.all，不需要 harness 支持。工具级并发适用于多个互不依赖、各需一次工具调用的步骤，例如对同一项目运行几个独立分析脚本；编译器把相应 DAG 节点组成一个并行 stage，使模型在同一轮推理中发出多个工具调用，并标明各项输出应回填到哪些下游输入，要求 harness 支持批量工具分发。Agent 级并发适用于需要多轮推理的独立子任务，例如分别调用三个互不依赖的服务；编译器将每项任务改写为显式的 sub-agent 块，注明任务、输入上下文和预期输出，运行时在独立会话中启动 sub-agent，再按 DAG 合并结果，要求 harness 支持 sub-agent 分发。

如果目标 harness 不支持某一并发方式，编译器便保留顺序执行：或者改写指令，或者添加标注，将并行结构显式交给运行时处理。

这两类 AOT 改编方向受不同目标信息约束：能力编译按模型画像选择补偿或替代，并发抽取按工作流依赖与 harness 能力映射并行原语。

五、方案：运行期 JIT 优化

5.1 自适应重编译

运行时记录每次 skill 执行的结果，并区分任务特定失败与系统性失败。任务特定失败由某项任务的输入或约束引起；系统性失败则指同一原因可能在同一 skill 的其他任务中复现。只有系统性失败会触发自适应重编译：运行时把累积的失败日志和模型的自恢复轨迹交给编译器，由编译器针对问题施加补偿变换（compensation transform）。候选版本只有满足重编译契约中的得分与逐任务准入条件才会替代原版。

附录 A 给出重编译契约：每个任务独立运行 R=2 次，最多进行 K=3 轮，收敛阈值 τ=0.95；候选版本须提分至少 δ=0.1，或得分距基线不超过 δ 且成本降低至少 15%，才可准入。若任一基线任务的退步超过 ρ=0.09，或候选轮没有干净运行，则剔除该候选。

诊断由无交互界面的编码 agent（headless coding agent）执行，并遵循三项契约。C1（复现性）要求同一评测判据在一个任务的至少两次干净运行中失败，或在至少两个不同任务中失败；C2（通用性）要求修法不依赖失败任务中的字面值，且能帮助同一 skill 的其他合理任务。C1 与 C2 共同决定失败是否归类为系统性。C3（无权衡）要求评估修改对当前已通过任务的退步风险；若发现风险，需缩小改动、放弃，或说明为何不太可能造成退步。准入阶段再按 ρ=0.09 限制单任务退步。诊断证据既可来自基准评测，也可来自线上部署日志。

5.2 代码固化

代码固化（code solidification）把前文所述结构固定、仅输入参数变化的代码模式转为可执行函数，避免模型在调用中反复进行相同推理和工具循环。运行时连续 N 次匹配 AOT 预测的代码结构签名（code signature）后才会晋升；参数提取不完整、代码异常或执行失败时，则回到 LLM 路径。

代码固化流程：AOT 编译器分析 skill 代码片段并生成带代码签名与模板的 JIT 候选（阶段 1）；运行时在连续调用中检查模型生成的代码是否匹配预测签名（阶段 2）；晋升后由编译函数替代 LLM 推理（阶段 3）（Figure 8. Code solidification pipeline. The AOT compiler analyzes skill code segments and generates JIT candidates with code signatures and templates (Stage 1). The runtime checks that the model’s generated code matches the predicted signature across consecutive invocations (Stage 2). After promotion, a compiled function replaces LLM inference (Stage 3).）

附录 B 规定了晋升和降级门槛：连续 N=3 次匹配签名才晋升，任一次不匹配都会清零计数。服务时如果参数提取失败或模板仍有空缺，就交由模型处理；回退计数跨运行累计，达到 M=3 次后降级。模型还会在使用前校验结果的语义正确性；若模型拒绝输出，该次也计入回退，反复被拒的模板最终退役。

5.3 资源感知调度

编译期找出的并行机会能否转化为加速，还取决于运行期资源：CPU 占用、API 限流（HTTP 429）和可用内存。调度器监控这些状态；API 限流型工作流关注响应时延和 429 信号，计算密集型工作流关注 CPU 与内存。资源压力超过阈值时，调度器采取两种措施：限制新 sub-agent 的启动，避免进一步增加并发；对已运行的 sub-agent 选择性挂起其 agent 循环，并按资源用量或启动顺序选择，以减少资源竞争。

六、结果：完成率、token 消耗与编译成本

编译有效性。 评测使用扩展版 SkillsBench 和 PinchBench，覆盖 118 个任务；每项任务设置 5 个输入实例，每个实例运行 3 次，实验机器为 16GB 内存的 Mac Mini M4。论文评测 8 个模型，分为三档：SOTA（state of the art，前沿模型）为 Claude Opus 4.6 和 DeepSeek V3.2；中档为 Gemini 3 Flash、Qwen3.5-397B、Qwen3.5-122B 和 Claude 3.5 Haiku；小模型为 Qwen3-30B 和 Devstral Small。另在 Codex 上评测 GPT-5.6 Sol 与 GPT-5.4 Mini。四种 harness 分别是 BareAgent（只将编译后的 skill 注入系统提示）、OpenCode（支持批量工具分发）、OpenClaw（通用 Agent）和 Codex。三种对照基线为 No Skill（不加载 skill）、Original（原始 skill）和 Skill-Creator（使用 Claude Opus 4.6 优化的 skill）。

Skill VM 编译后的 skill 在每个模型-harness 组合上的得分都最高。与 Skill-Creator 基线相比，在 BareAgent 上 Qwen3-30B 的平均得分提高 25%，Devstral Small 提高 10%；与 No Skill 基线相比，只有 4.5% 的任务在使用编译版 skill 后完成率下降，原始 skill 对应比例为 15%。较弱模型获益较大，论文将其归因于非逻辑细节上的不足，如生成复杂 JSON 结构、处理环境依赖；能力细化等编译操作弥补了这些缺口。较强模型与 harness 已能处理多数任务，Skill VM 的收益更多体现为 token 与时延下降。DeepSeek V3.2 与 BareAgent 组合的 token 消耗减少近 40%；两个 Codex 配置分别提高 4.84 和 1.46 分，同时减少 10.5% 和 26.7% 的 token。论文把 token 节省归因于减少环境或工具报错后的 agent 往返重试。弱模型的部分任务则会因完成率提高、执行轨迹变长而多消耗 token。

Skill VM 编译效果：格内数字为优化后的任务完成率，颜色表示相对原始 skill 基线的得分提升（绿）或退步（红）（Figure 9. Skill compilation effectiveness. Cell values represent task completion rates after SkillVM optimization, while cell color indicates the score improvement (green) or regression (red) relative to original baseline skills.）

分阶段贡献与成本。 在 Qwen3-30B 与 BareAgent 的 14 类任务分解中，11 类任务使用原始 skill 的得分低于不使用 skill；AOT 编译后平均得分提高 88%；一轮 JIT 后有 8/14 类任务满分，三轮后为 10/14。JIT 也可能导致退步：Line Chart 任务中，编译器加入的示例文件过长，引发解析错误；依据此前失败日志定向修订三轮后才解决。

14 类 skill 的分阶段优化：每组展示无 skill、原始 skill、AOT 编译 skill 和三轮 JIT 优化共六个阶段（Figure 11. Staged optimization across 14 skill categories. Each group shows six stages: no skill, original skill, AOT-compiled skill, and three rounds of JIT optimization.）

成本评估使用 Claude Sonnet 4.6 作为编译器模型。目标能力画像测量消耗 1.15M token，成本 0.072 美元；AOT 编译每个 skill 平均消耗 90K token，成本 0.56 美元；三轮 JIT 的平均成本分别为 0.98、1.00 和 0.94 美元，对应 token 消耗 141K、172K 和 159K。能力画像测量开销为 0.55M–1.96M token，不随模型档次呈现系统性增长；对每个模型-harness 组合只需执行一次，最高成本为 7.92 美元。AOT 是一次性成本；JIT 虽可能多轮执行，但随着信息积累、skill 收敛，调用频率会下降。

三个机制的单独评测。 环境绑定实验使用 pdf-create 和 document-xlsx 两个 skill，比较完整环境、移除依赖和启用绑定三种设置。Claude Opus 4.6 能从缺失依赖中恢复，但会消耗更多 token；Qwen3.5-122B 在缺依赖时失败，环境绑定则使其得分恢复到完整环境基线，并显著减少 token 消耗。

环境绑定恢复任务完成率、token 效率和执行速度；从左到右依次是平均得分、平均 token 用量和平均时长（Figure 15. Environment binding restores task completion rate, token efficiency, and execution speed. From left to right: average score, average token use, and average duration.）

并发抽取在 9 个任务上最高提速 3.16 倍：脚本级并发平均提速 1.23 倍，因为可并行的数据处理不到端到端时延的 30%；工具级并发的平均加速最高，论文未给出具体倍数，其优势来自将独立工具调用合并到一轮，省去模型往返和工具调用时延；Agent 级并发平均提速 2.16 倍，但需等待最慢的 sub-agent，且因隔离上下文，平均减少 60% token。

九项任务中不同并行策略的表现；柱子表示顺序、脚本级、工具级和 agent 级执行（Figure 16. Performance of different parallelization strategies across nine tasks. Bars show sequential, script-level, tool-level, and agent-level execution.）

代码固化实验中，PDF 提取任务时延从 10,469–15,116 ms 降至 206–568 ms，提速 19–50 倍；weather-current 从 9,000 ms 降至 2,000 ms，提速 5 倍，受网络时延限制。weather-forecast 未能晋升：生成代码的结构偏离 AOT 预测的代码结构签名，8 次调用均由 LLM 生成代码；晋升门槛避免了不匹配的模板被用于执行。

四个案例中的代码固化：蓝色柱表示 LLM 推理时延，绿色柱表示固化执行，虚线标出晋升点。weather-forecast 从未晋升，因为运行时模型生成的代码模式偏离 AOT 预测，这也验证了晋升门槛的安全作用（Figure 14. Code solidification across four cases. Blue bars show LLM inference latency, green bars show solidified execution. The dashed line marks the promotion point. Weather-forecast never promotes because the runtime model’s code patterns diverge from the AOT prediction, validating the promotion gate as a safety mechanism.）

七、思考

成本模型更适用于高频 skill。 目标能力画像测量最高 7.92 美元，每个 skill 的 AOT 编译平均 0.56 美元，每轮 JIT 约 1 美元。要摊薄这些前期成本，skill 需要反复执行。

代码固化与并发抽取都依赖可辨识的任务结构。 代码固化将重复模式转为确定性代码，并发抽取将顺序散文转为 DAG；两者都要求系统能预先识别任务结构。weather-forecast 的代码模式未能匹配 AOT 预测的代码结构签名，因此运行时没有晋升模板，仍由 LLM 生成代码。Skill VM 分层处理 LLM 的非确定性：DAG 是否含悬挂节点、脚本是否通过语法检查等性质在编译期验证；运行期执行失败则通过降级和重编译处理；评测使用确定性测试判断机器可检查的性质，以大语言模型评审（LLM judge）评估开放标准，并通过多次运行取均值。
