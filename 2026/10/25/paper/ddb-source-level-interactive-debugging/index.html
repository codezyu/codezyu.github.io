DDB：面向分布式应用的源码级交互式调试

论文：DDB: Source-Level Interactive Debugging for Distributed Applications，Yibo Yan、Junzhou He、Seo Jin Park（University of Southern California），发表于 Symposium on Operating Systems Principles（SOSP ’26，操作系统原理研讨会；2026）。ACM DOI。

TLDR： RPC 处理函数命中断点时，单进程调试器只能显示当前进程的调用栈；逐进程设置的断点不会自动覆盖新加入、滚动重启产生或接收迁移计算的进程；人工暂停期间物理时间仍前进，系统超时可能到期并触发重试、选举或恢复流程。DDB 用 Distributed Backtrace（DBT，分布式回溯）重建同步 RPC 调用栈，Intent-Preserving Control Plane（意图保持控制平面）把断点安装到匹配进程并协调全局暂停，Pause-Erased Time（PET，暂停擦除时间）为每个进程提供不计入调试暂停的时钟视图。原型接入四种框架；122 个进程的响应性测试中，dbt 中位延迟为 13.3 ms。9 名参与者在每项限时 20 分钟的三类可复现 Raft 故障任务中，采用 DDB 的试次定位率为 100%，GDB 与 OpenTelemetry 基线合计为 38.5%。

一、背景：分布式程序的源码级调试需求

DDB 是一款面向分布式应用的源码级交互调试器。serverless（无服务器）平台、微服务、actor 模型框架和分布式运行时让应用代码越来越多地跨服务与机器执行，也降低了采用分布式编程的经验门槛，普通应用开发者因此开始编写这类程序。

分布式编程基础设施降低经验门槛并扩大开发者范围（Figure 1: Distributed programming paradigms and infrastructure have become much more accessible to ordinary application developers. The adoption of distributed programming has increased while the required expertise has dropped substantially.）

单进程调试器提供一个紧密的排查循环：设置断点、暂停执行、查看调用栈和变量，再根据运行时状态修正假设。分布式应用仍需要这种对真实执行状态的检查，只是请求状态分散在多个服务进程中。论文将 DDB 的适用场景限定在开发、测试和早期原型阶段的可复现问题；对于线上难以复现的故障，作者认为仍适合用可观测性工具和记录回放分析。

二、现状：分布式调试依赖局部工具与人工操作

2.1 单进程调试与分布式观测

单进程调试器 GNU Project Debugger（GDB）在断点处呈现当前进程的调用栈、参数和局部变量。分布式追踪与结构化日志记录请求路径和事件，帮助开发者定位异常服务、重建处理顺序；它们不提供断点处远端调用帧的实时变量。

当路径和事件记录不足以解释错误时，开发者需要逐层附加调试器，或增加日志、重新部署再复现。请求观测、局部变量检查和多进程控制因此分散在不同工具与人工操作中。

2.2 逐进程断点与物理计时

调试操作通常绑定具体进程：开发者需要选择副本、安装断点并分别控制进程。分布式系统则依据物理时间运行故障检测和超时；常规调试器暂停代码时，系统时钟仍前进，其他进程和外部服务也不会自动忽略这段时间。

三、问题：跨进程调试的三类缺口

3.1 RPC 断点处的调用方状态不可见

设请求经 RPC 依次到达服务 A、B、C，并在 C 的处理函数命中断点。本地调用栈只显示 C，开发者看不到 B、A 的调用帧、传入参数和运行时状态。逐层附加调试器还要求在每个进程的许多线程中找到对应请求的线程，人工工作量随调用深度增加。

Go 的 goroutine（用户级线程）会在操作系统（OS）线程之间重新调度。发送 RPC 的 goroutine 可能在远端断点命中前离开原 OS 线程，因此按发送时的 OS 线程 ID 展开调用方栈会得到错误帧。追踪即使保留 A→B→C 的请求路径，也不能恢复这些可检查的调用方状态。

3.2 动态部署中的断点覆盖缺口

论文举例的 socialnet 微服务基准部署有 36 个服务、每个服务 5 个副本，共 180 个进程。若断点绑定物理进程，开发者必须逐个识别相关副本；自动扩缩容会加入新副本，滚动重启会替换进程，支持计算迁移的运行时还会把计算移到其他进程。断点因此可能漏掉实际执行目标代码的实例。

3.3 调试暂停诱发超时级联

论文调查 LogCabin、RAMCloud 和 Nu 的超时后发现，阈值从 100 ms 的 RPC 重试到 500 ms 的选举计时器不等。开发者在断点处暂停数秒，超时便可能触发重试、领导者重新选举、事务中止或集群崩溃恢复。系统进入暂停前不存在的状态后，开发者检查到的就不再是原始故障路径。

跨进程交互调试的三项障碍（Figure 2: Three challenges of employing interactive debugging in distributed applications.）

四、方案：DDB 的跨进程调试机制

针对问题 3.1，Distributed Backtrace（DBT，分布式回溯）重建 RPC 调用方现场；针对问题 3.2，Intent-Preserving Control Plane（意图保持控制平面）按源码位置和逻辑范围，将断点安装到当前匹配的进程，并在拓扑变化后重新检查匹配关系。问题 3.3 由控制平面和 Pause-Erased Time（PET，暂停擦除时间）共同处理：控制平面向会话中其他已接入进程广播暂停命令，使它们在检查期间停止推进；PET 将累积暂停偏移从各进程返回的时间值中扣除。各进程实际暂停仍有时差；论文把低延迟网络列为部署假设，并未保证同步暂停。

在三节点 Raft 共识集群示例中，开发者在 follower（跟随者）的 AppendEntries 心跳 RPC 处理函数设置一个断点。两个 follower 命中后，DDB 暂停集群，并把调用栈从 follower 延伸到 leader（领导者）的 send_heartbeat 调用帧；开发者可以检查远端参数，再单步执行一个 follower，同时保持另一个暂停。

DDB 在三节点 Raft 集群中的调试界面（Figure 3: The DDB VS Code graphical frontend debugging a three-node Raft cluster (with one leader and two followers in the screenshot). Both followers have paused at the local AppendEntries RPC handler (middle). The Call Stack (top-right) displays a Distributed Backtrace extending to the leader’s remote calling frame. The DDB Sessions pane (bottom-right) and debugger control pane (top) allow granular per-process execution control while the rest of the cluster remains globally paused.）

调试流程与 DDB 的三项设计支柱（Figure 4: Overview of DDB’s three pillars. Distributed Backtrace (DBT) reconstructs cross-RPC call stacks for live inspection. The intent-preserving control plane automatically propagates debug operations across dynamic process sets and enables granular per-process control. Pause-Erased Time (PET) virtualizes each process’s clock to prevent debugger pauses from triggering timeout cascades.）

4.1 DBT 同步 RPC 调用栈回溯

DBT 回应问题 3.1。发送 RPC 时，DDB 捕获调用线程的寄存器上下文并写入 RPC 消息负载；被调方处理函数把元数据保存在注入的 extraction frame（元数据提取栈帧）中。元数据携带线程上下文而非 OS 线程 ID，因此用户级线程被调度到其他 OS 线程后仍可定位原调用栈。

RPC 元数据提取栈帧及其在调用栈中的位置（Figure 5: Illustration of the frame injection. Blue numbers on the left indicate the frame number, where 0 is the outermost frame and 4 is the innermost frame. Frame #2 is the injected frame. The local variable meta is inside the extraction frame.）

执行 dbt 时，DDB 先展开当前进程的栈，再读取 extraction frame 中的调用方上下文。中央控制平面联系远端 DKnot agent（进程内调试代理），取回栈所需内存；agent 恢复调用方上下文并使用 DWARF 调试信息展开远端栈。DDB 沿祖先调用链重复该过程，把被调方到调用方的栈帧拼成一个可导航的调用栈，并暴露远端局部变量、参数和堆对象。

DBT 要求调用方栈在回溯时仍有效，因此适用于同步阻塞 RPC；它不支持调用栈会立即释放或复用的事件驱动、异步或无栈并发模型。若调用方进程已退出，或链路经过未接入 DDB 的框架，回溯会在该处截断。控制平面只保存调试意图，不保存或重建已经释放的调用方栈帧。

4.2 调试意图传播与全局暂停

控制平面回应问题 3.2，并参与问题 3.3 的全局状态协调。DDB 把操作表示成 debug-intent（调试意图）：源码文件与行号、目标范围（如某服务的所有副本）以及断点、继续或表达式求值等命令。默认情况下，同一二进制的进程归入一个 logical group（逻辑组）；两级 source-map（源码映射）将源码路径映射到逻辑组，再映射到当前进程。

控制平面维持一项不变量：只要进程匹配意图的逻辑范围且加载的二进制包含目标源码位置，该意图就在该进程上生效。新进程会停在 attach-time barrier（附加屏障），待相关意图安装后才继续运行；进程退出时，调试状态被清理。因此，扩缩容或滚动重启改变进程集合后，控制平面会按意图范围重新检查匹配关系，并在匹配进程上安装断点；支持计算迁移的 Nu、Quicksand、ServiceWeaver 则由接收进程检查逻辑范围和源码映射后安装断点。

进程退出后，DDB 不会在替代进程恢复原有堆和栈；计算迁移时，调用方的堆也可能不在原进程，因此检查堆对象还需框架提供定位和恢复逻辑。控制平面只保留调试意图，不保存或恢复进程的运行时状态。

默认的 pause-the-world（全局暂停）策略在任一已接入进程暂停时，向会话中的其他进程广播暂停命令，以便检查程序实际到达过的全局状态。开发者可关闭全局暂停，只控制调试相关进程；此时其他进程继续运行，状态可能发生变化。DDB 的暂停式调试面向程序语义和状态错误，依赖精确线程交错的并发故障不在其范围内。

4.3 PET 的计时修正与适用边界

PET 回应问题 3.3 中由本地计时器和睡眠引起的超时。DDB 在每个被调试进程暂停时和恢复时分别记录时间戳，以两者之差计算该进程的暂停时长，并累加为该进程的暂停偏移；进程内 shim（用户态拦截层）通过 LD_PRELOAD（动态库预加载机制）拦截 POSIX（Portable Operating System Interface，可移植操作系统接口）时间 API（Application Programming Interface，应用程序接口），从 C 标准库（libc）或内核返回值中扣除该偏移。它覆盖读取当前时间、等待绝对截止时间和按相对时长睡眠。

仅修正 get_time 返回值仍会让暂停期间正在睡眠的线程在恢复后被内核提前唤醒。Virtual Deadline Enforcement（虚拟截止时间执行机制）为每个计时等待维护暂停擦除后的绝对截止时间；每次内核唤醒后，shim 检查虚拟时间，未到期就按剩余时间重新等待。因此，PET 提供的虚拟时间保持单调不减，计时等待只在虚拟截止时间到达后返回。

PET 对本地超时有效。对跨进程超时，只有暂停时差小于通信双方的剩余超时余量时，PET 才能避免误触发。论文假设控制平面与已接入进程之间的网络延迟足够低，但没有给出可量化的暂停时差上限，也不保证该条件。未接入集群的外部服务仍看到物理时间；当前 PET 也不拦截原始 rdtsc 或网卡硬件时间戳。

五、结果：调试效果与运行成本

DDB 原型运行于 Linux/x86_64，以 GDB 为主要调试后端，并实验性支持 LLVM 调试器（LLDB）；论文也报告了 aarch64 实验支持。Java 系统不在评测范围内，因为原型要求底层调试器能解释目标二进制。论文将二进制嵌入调试符号、降低编译优化等级列为源码级调试的构建设置。系统由 DCore 中央协调器、VS Code 扩展、每进程一个 DKnot agent、RPC 集成库 DConnector 和 PET shim 组成。

gRPC、Nu、Quicksand、ServiceWeaver 的接入分别约需 20、30、60、10 行代码，覆盖 C++ 和 Go。核心组件包括 DCore（Rust，14,867 行）、DKnot（Python，1,401 行）、DConnector（C/C++/Go，1,954 行）和 VS Code 适配器（TypeScript，约 700 行）。表 2 的 22,196 行总数还包括移植后的 socialnet 应用（Go，3,154 行），不含 libfaketime，并忽略空白和注释。

5.1 诊断效果与调试响应性

第一项用户研究招募 5 名有分布式系统经验的研究生。每名参与者分别尝试把 DDB 和 OpenTelemetry 接入同一个 C++ 代码库，每种工具的接入任务限时 20 分钟。成功条件有两项：沿线性调用关系从被调方回溯到调用方并查看局部状态（G1），以及观察一个调用同时发出多个下游请求的并发 fan-out（扇出）模式（G2）。5 名参与者都用 DDB 完成了两项目标，中位用时 400 秒；用 OpenTelemetry 时，1 人完成 G1，无人完成 G2。

DDB 与 OpenTelemetry 集成任务的成功率和完成时间（Figure 7: Left: Integration success rates for DDB vs. OpenTelemetry, where success requires viewing linear (G1) and concurrent (G2) caller–callee traces. Right: Completion time for successful DDB integrations (both G1 and G2). OpenTelemetry is not shown as no participant finished the full integration within the 20-minute time limit.）

第二项研究采用参与者内设计，招募 9 人比较 DDB、GDB 和 OpenTelemetry；三种工具顺序用 3×3 拉丁方部分平衡。参与者分别处理三个 Raft 共识故障：随机越界内存访问、网络分区恢复后旧 leader 未更新 term（任期）、并发选举导致的分布式死锁。每项任务限时 20 分钟，所有条件均可使用结构化日志和流量重放。使用 DDB 的试次中，参与者在 100% 的试次里定位到根因、在 89% 的试次里完成修复；GDB 试次的定位率和修复率分别为 44% 和 22%，OpenTelemetry 试次分别为 33% 和 11%。论文报告的两种基线工具汇总定位率为 38.5%；DDB 成功试次的定位时间中位数约 500 秒。三个故障均可复现。

总体定位、修复成功率与耗时分布（Figure 8: Aggregate reliability and diagnostic speed profiles across all trials. DDB reliably enabled participants to localize the root cause in 100% of trials, whereas baseline tools failed in the majority of cases and frequently reached the 1200-second timeout limit. Note that baseline boxplots may appear compact or low in certain cases; this reflects survivorship bias, as these distributions include only the few participants who localized the fault, while the majority timed out and are placed as failed cases.）

三类故障中的定位与修复耗时（Figure 9: Case-by-case comparison of time-to-localize and time-to-fix across different bug cases. Case 1: Random Segmentation Fault; Case 2: Logic Error; Case 3: Distributed Deadlock. The GDB outlier in Case 3 corresponds to a participant who resolved the fault based on prior intuition rather than systematic tool-guided diagnosis.）

屏幕记录显示，OpenTelemetry 参与者把较多时间用于配置埋点和在追踪、日志视图间切换；GDB 参与者难以管理多个进程和线程，时间敏感故障中的单进程暂停还会触发调用方 RPC 超时，迫使他们重启调试会话。记录呈现的三类困难是追踪埋点与视图切换、多进程线程管理、暂停造成调用方超时；DDB 的跨 RPC 检查、调试意图管理和全局暂停分别针对这些困难，但研究没有分别测量各机制的独立效果。

响应性测试在 Chameleon 的 24 台 compute_cascadelake_r 服务器上进行（每台 Intel Xeon Gold 6240R，24 核、2.4 GHz、187 GB 内存）。在 38、62、122 个进程规模下，dbt 中位延迟分别为 14.2、13.9、13.3 ms；122 个进程时 99 分位延迟为 160.1 ms。另一个按 RPC 跳数变化的测试中，2、3、4 跳回溯的中位延迟分别为 18.2、28.4 和 36.1 ms。continue 在三个规模下的中位延迟均不超过 4.8 ms；122 个进程暂停时，前端会并发发出 14,573 个 dbt 请求。

用户研究测量了整体诊断效果，规模测试测量了调试命令延迟；论文没有单独报告扩缩容、进程替换或计算迁移时的断点覆盖率，因此断点在动态拓扑变化后的覆盖属于论文提出的机制能力，并非这组评测直接测得的结果。

5.2 PET 时间修正与运行开销

PET 时间 API 和暂停跳变测试使用本地 Intel Xeon Gold 5420+ 服务器（28 核、2.00 GHz、256 GB 内存）；元数据嵌入与进程附加开销测试使用 CloudLab 的 12 台 c6525-25g 服务器（AMD EPYC 7302P，16 核、3.00 GHz、128 GB 内存、Mellanox ConnectX-5 网卡）。

启用 PET 后，常用时间 API 平均耗时为 86–95 ns；未启用时为 4–30 ns，单次拦截增加 60–82 ns。合成程序每轮运行约 50 μs，暂停到恢复的时长固定为 100 ms；程序观察到的时间跳变不超过 5 ms。5 ms 的观测上限至少比论文调查的最低较激进阈值 50 ms 小 10 倍；该阈值调查范围为 50–250 ms。

进程暂停与恢复时应用看到的 PET 时间线（Figure 10: The application-perceived time (PET) with multiple pauses (P) and resumes (R). The gray area shows the time jumps that the application perceives between an execution pause and resume.）

吞吐测试中，DDB 使 Nu 上 socialnet 吞吐下降 3.8%，ServiceWeaver 上下降 0.6%。在 gRPC Raft 上，DDB 下降 20.1%，附加 GDB 时下降 18.4%，两者相差 1.7 个百分点；调用上下文元数据每条 RPC 增加 52 字节。
