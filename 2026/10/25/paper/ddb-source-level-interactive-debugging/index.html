DDB：面向分布式应用的源码级交互式调试

论文：DDB: Source-Level Interactive Debugging for Distributed Applications，Yibo Yan、Junzhou He、Seo Jin Park（University of Southern California），发表于 Symposium on Operating Systems Principles（SOSP ’26，操作系统原理研讨会；2026）。ACM DOI。

TLDR： DDB 为分布式应用提供源码级交互调试：回溯跨进程调用栈，控制平面跟随动态副本，Pause-Erased Time（PET）扣除暂停时间。四种框架评测覆盖 122 个进程；9 人 Raft 研究中定位成功率为 100%，基线为 38.5%。

一、背景：分布式程序的源码级调试需求

DDB 是一款面向分布式应用的源码级交互调试器。无服务器（serverless）平台、微服务、actor 模型框架和分布式运行时让应用代码越来越多地跨服务与机器执行，也降低了采用分布式编程的经验门槛，普通应用开发者因此开始编写这类程序。单进程调试器提供一个紧密的排查循环：设置断点，暂停执行，查看调用栈和变量，再根据运行时状态修正假设。应用拆成多个进程后，附着在某一进程上的调试器只能看到本地执行现场，触发当前代码的远程调用方及其状态都不可见。

分布式编程基础设施降低经验门槛并扩大开发者范围（Figure 1: Distributed programming paradigms and infrastructure have become much more accessible to ordinary application developers. The adoption of distributed programming has increased while the required expertise has dropped substantially.）

日志和分布式追踪可以帮助开发者找出请求经过哪些服务、发生过哪些事件，但通常不能回答某个调用方当时传入了什么参数、运行时比较了什么值。开发者仍需加日志、重新部署并重复测试，逐步缩小问题范围。DDB 面向开发和测试环境，把源码级断点、跨进程调用栈与运行时状态检查带回这一交互式排查循环。

二、现状：跨进程调试的三类障碍

2.1 远端调用栈与状态不可见

假设一个请求经 RPC 依次经过服务 A、B、C，并在 C 的处理函数中触发断点。本地调试器只能显示 C 的调用栈，看不到 B 和 A 的调用帧、传入参数及运行时状态。开发者若逐层附加调试器，还要在每个进程的多个线程中找到与当前请求对应的线程，人工成本随 RPC 调用深度增加。

用户级线程又使线程标识不可靠。以 Go 的 goroutine（用户级线程）为例，发送 RPC 的 goroutine 可能在远端断点命中前被调度到其他操作系统（OS）线程；按原 OS 线程 ID 取栈可能得到错误的调用帧。

2.2 动态拓扑下的断点覆盖问题

实际部署的进程集合会随自动扩缩容、滚动重启和计算迁移而变化。论文以 socialnet 微服务基准的 180 个进程部署为例：如果逐个进程设置断点，开发者要先识别相关副本；新副本加入或计算迁移后，还要重新确认断点是否覆盖正在执行的代码。断点若绑定物理进程，就会随着拓扑变化失效或漏掉目标。

2.3 调试暂停触发分布式超时

分布式系统依赖超时检测故障。论文调查的系统中，RPC 重试阈值可低至 100 ms，选举计时器约为 500 ms；RAMCloud 的部分超时在 100–250 ms 范围内。开发者在断点处暂停数秒，就可能触发重试、领导者重新选举、事务中止或集群崩溃恢复。系统会进入暂停前不存在的恢复状态，开发者随后检查到的可能是调试动作制造出的执行路径，而不是原始故障现场。

跨进程交互调试的三项障碍（Figure 2: Three challenges of employing interactive debugging in distributed applications.）

三、优化目标：分布式交互调试的能力要求

分布式交互调试需要同时保留三项能力：从当前断点沿远程调用链检查远端调用帧及变量；把断点和调试命令关联到源码位置与逻辑目标，使其覆盖动态变化的进程集合；暂停执行时从应用可见时间中扣除调试暂停，避免本地计时器和超时因人工检查而提前到期。为让开发者看到一致的全局现场，DDB 默认在任一进程暂停时暂停所有已接入进程。

四、方案：DDB 的三项协同机制

DDB 将跨 RPC 调用栈重建、调试意图协调和时间虚拟化组合为一个调试会话。在论文展示的三节点 Raft 共识集群中，开发者只需在 follower（跟随者）的 AppendEntries 心跳 RPC 处理函数设置断点；两个 follower 命中后，DDB 暂停集群，调用栈从 follower 延伸到 leader（领导者）的 send_heartbeat 调用帧。开发者可以检查远端调用参数，再单步执行其中一个 follower，同时保持另一个 follower 暂停。

DDB 在三节点 Raft 集群中的调试界面（Figure 3: The DDB VS Code graphical frontend debugging a three-node Raft cluster (with one leader and two followers in the screenshot). Both followers have paused at the local AppendEntries RPC handler (middle). The Call Stack (top-right) displays a Distributed Backtrace extending to the leader’s remote calling frame. The DDB Sessions pane (bottom-right) and debugger control pane (top) allow granular per-process execution control while the rest of the cluster remains globally paused.）

调试流程与 DDB 的三项设计支柱（Figure 4: Overview of DDB’s three pillars. Distributed Backtrace (DBT) reconstructs cross-RPC call stacks for live inspection. The intent-preserving control plane automatically propagates debug operations across dynamic process sets and enables granular per-process control. Pause-Erased Time (PET) virtualizes each process’s clock to prevent debugger pauses from triggering timeout cascades.）

4.1 同步 RPC 调用栈回溯

Distributed Backtrace（DBT，分布式回溯）在 RPC 发送处捕获调用线程的上下文，即用于标识栈的寄存器值，并将其作为紧凑元数据写入 RPC 消息负载。只记录 OS 线程 ID 不够：用户级线程运行时可能在发送 RPC 后重新调度调用线程，原线程 ID 因而不再对应原调用栈。RPC 处理函数把收到的元数据保存在注入的元数据提取栈帧（extraction frame）中，供调试器之后读取。

RPC 元数据提取栈帧及其在调用栈中的位置（Figure 5: Illustration of the frame injection. Blue numbers on the left indicate the frame number, where 0 is the outermost frame and 4 is the innermost frame. Frame #2 is the injected frame. The local variable meta is inside the extraction frame.）

开发者执行 dbt 后，DDB 先展开当前进程的栈，再读取元数据提取栈帧中的调用方上下文。中央控制平面联系调用方进程的 DKnot agent（进程内调试代理），取回栈所需内存，并在调用方上下文中恢复寄存器，通过 DWARF 调试信息展开该进程的栈。随后 DDB 沿调用链重复这一过程，把被调方到祖先调用方的帧拼成一个连续调用栈；远端帧的局部变量、参数和堆对象仍可读取或修改。

只要同步阻塞 RPC 的调用方栈在回溯时仍然有效，并且相关进程仍在运行，DBT 就能为并发请求分别重建对应调用链。若调用方已退出或上游框架未接入 DDB，回溯会在该边界截断并说明原因。当前设计不支持事件驱动、异步或无栈并发模型，因为这些模型可能在请求发出后立即释放或复用调用栈。

4.2 动态拓扑下的调试意图管理

DDB 的 Intent-Preserving Control Plane（意图保持控制平面）把调试操作表示为 debug-intent（调试意图）：源码位置（文件与行号）、目标范围（例如某服务的所有副本或指定进程）和调试器命令（例如插入断点、继续执行或检查表达式）。默认情况下，同一二进制的进程归为一个 logical group（逻辑组）；DDB 维护两级 source map（源码映射），将源码路径映射到逻辑组，再映射到运行进程，因此开发者不必先找出源码由哪个二进制承载。

控制平面持续检查意图与进程拓扑的匹配关系。新进程加入后，会先停在 attach-time barrier（附加屏障），待适用的意图安装完成才继续运行；进程退出时，其调试状态被清理。断点因此可以覆盖自动扩缩容、重启以及分布式运行时 Nu、Quicksand、ServiceWeaver 支持的计算迁移。这里保持的是调试意图，不是进程运行状态：进程重启后，原有堆和栈不会恢复；计算迁移后的堆检查则需要运行时提供定位和恢复逻辑。

默认的全局暂停（pause-the-world）策略在任一已接入进程暂停时，向会话中的其他进程广播暂停命令。这样检查的是程序实际到达过的全局状态，而不是程序继续运行时收集的静态快照。开发者也可以关闭全局暂停，只暂停与调试操作相关的进程，但需要自行考虑其他进程继续运行造成的状态变化。

4.3 暂停擦除时间与虚拟截止时间

Pause-Erased Time（PET，暂停擦除时间）为每个已接入进程提供一个不计入调试暂停的时钟视图。DDB 在进程停止后和恢复前分别读取时间，累加暂停时长；进程内的 shim（用户态拦截层）通过 LD_PRELOAD（动态库预加载机制）拦截 POSIX（Portable Operating System Interface，可移植操作系统接口）时间 API（Application Programming Interface，应用程序接口）。shim 从 C 标准库（libc）或内核返回的时间中扣除累积暂停偏移。PET 覆盖读取当前时间、等待绝对截止时间和按相对时长睡眠三类语义。

仅修正 get_time 返回值仍不足以保证计时器正确。线程暂停期间，内核真实截止时间可能已经过去，并在恢复时立即唤醒线程。为此，Virtual Deadline Enforcement（虚拟截止时间执行机制）为计时等待维护暂停擦除后的绝对截止时间；每次内核唤醒后，shim 都检查 PET 是否已到截止时间，若尚未到达便按剩余时长重新等待。PET 因而保证单调时钟不倒退，且睡眠操作只有在虚拟截止时间到达后才返回。

本地超时由进程自己的时钟决定，PET 可直接屏蔽暂停时长。跨进程超时还取决于暂停传播的同步程度：若相关进程间的暂停时差超过超时剩余余量，仍可能误触发。论文将控制平面与进程位于低延迟网络、暂停时差远小于常见超时设为部署假设。PET 也无法改变未接入 DDB 的外部服务所见的物理时间；当前实现只拦截 POSIX 时间 API，不会改写应用直接读取的原始 rdtsc 或网卡硬件时间戳。

五、结果：交互延迟与诊断效果

5.1 四种框架上的集成与运行开销

DDB 原型运行于 Linux/x86_64，以 GNU Project Debugger（GDB）承担底层调试；论文也报告了 aarch64 的实验支持。系统由 DCore 中央协调器、VS Code 扩展、每进程一个 DKnot agent、RPC 元数据集成库 DConnector 和 PET shim 组成。核心实现包括 DCore（Rust，14,867 行）、DKnot（Python，1,401 行）、DConnector（C/C++/Go，1,954 行）和 VS Code 适配器（TypeScript，约 700 行）。对 gRPC、Nu、Quicksand、ServiceWeaver 的接入分别约需 20、30、60、10 行代码，覆盖 C++ 和 Go。表 2 所列 22,196 行总数还包括移植后的 socialnet 应用（Go，3,154 行）；统计不含 libfaketime，也忽略空白和注释。

DDB 中央协调、VS Code 前端与进程内组件的架构（Figure 6: The design overview of DDB. Components in gray are DDB components.）

评测使用 socialnet 微服务基准和一个 gRPC Raft 实现。响应性测试部署在 Chameleon 的 24 台 compute_cascadelake_r 服务器上，每台配 Intel Xeon Gold 6240R（24 核、2.4 GHz）、187 GB 内存和 Broadcom BCM57414 网卡；集群规模为 38、62 和 122 个进程。三个规模下，dbt 的中位延迟分别为 14.2、13.9 和 13.3 ms；在 122 个进程时，99 分位延迟为 160.1 ms。深度为 3 和 4 个 RPC 跳数的调用链，中位回溯延迟分别为 28.4 和 36.1 ms。continue 在三个规模下的中位延迟均不超过 4.8 ms。122 个进程时，前端会并发发出超过 14,600 个 dbt 请求；调用延迟主要随 RPC 调用深度增长。

PET 时间 API 和暂停跳变测试在本地 Intel Xeon Gold 5420+ 服务器上进行（28 核、2.00 GHz、256 GB 内存）；RPC 元数据嵌入与调试器附加开销测试使用 CloudLab 的 12 台 c6525-25g 服务器（AMD EPYC 7302P，16 核、3.00 GHz、128 GB 内存、Mellanox ConnectX-5 网卡）。

启用 PET 后，论文测得常用时间 API 的平均耗时为 86–95 ns；未启用 PET 时为 4–30 ns，折算后单次拦截增加 60–82 ns。合成程序以约 50 μs 的工作周期运行，实验把每次暂停到恢复的间隔固定为 100 ms，并反复注入暂停和恢复；程序观察到的时间跳变始终不超过 5 ms。论文调查的系统中，较激进的超时阈值为 50–250 ms；5 ms 的观测上限至少比其中最低阈值小 10 倍。

进程暂停与恢复时应用看到的 PET 时间线（Figure 10: The application-perceived time (PET) with multiple pauses (P) and resumes (R). The gray area shows the time jumps that the application perceives between an execution pause and resume.）

在应用吞吐测试中，DDB 使 Nu 上的 socialnet 吞吐下降 3.8%，使 ServiceWeaver 上的 socialnet 下降 0.6%。在 gRPC Raft 上，DDB 的吞吐下降 20.1%，附加 GDB 时下降 18.4%，两者相差 1.7 个百分点。调用上下文元数据为每条 RPC 增加 52 字节。

四种运行配置下 DDB 与 GDB 的吞吐保留率（Figure 11: The performance overhead when DDB metadata is embedded, and DDB is attached across Nu’s socialnet, ServiceWeaver (SW)’s socialnet, and gRPC-based Raft consensus implementation.）

5.2 分布式故障定位用户研究

第一项用户研究招募 5 名有分布式系统经验的研究生，让参与者在 20 分钟内分别接入 DDB 和 OpenTelemetry。任务要求查看线性调用方—被调方关系及局部状态（G1），并观察并发扇出（fan-out）模式（G2），即一个调用同时发出多个下游请求。DDB 的 5 名参与者都完成了两项目标，中位完成时间为 400 秒；OpenTelemetry 有 1 人完成 G1，没有人完成 G2。

DDB 与 OpenTelemetry 集成任务的成功率和完成时间（Figure 7: Left: Integration success rates for DDB vs. OpenTelemetry, where success requires viewing linear (G1) and concurrent (G2) caller–callee traces. Right: Completion time for successful DDB integrations (both G1 and G2). OpenTelemetry is not shown as no participant finished the full integration within the 20-minute time limit.）

第二项研究招募 9 名参与者，采用参与者内设计比较 DDB、GDB 和 OpenTelemetry，并用 3×3 拉丁方部分平衡工具顺序。参与者分别处理三个 Raft 故障：跨两个副本随机触发的越界内存访问、网络分区后旧 leader 未更新 term（任期）的逻辑错误，以及多个 leader 选举导致的分布式死锁；每项任务最多 20 分钟。所有参与者都可使用结构化日志和流量重放。DDB 在 100% 的试次中定位到故障，并在 89% 的试次中完成修复；GDB 的定位和修复成功率分别为 44% 和 22%，OpenTelemetry 分别为 33% 和 11%。两种基线工具合计的定位成功率为 38.5%。DDB 成功试次的定位时间中位数约为 500 秒。

总体定位、修复成功率与耗时分布（Figure 8: Aggregate reliability and diagnostic speed profiles across all trials. DDB reliably enabled participants to localize the root cause in 100% of trials, whereas baseline tools failed in the majority of cases and frequently reached the 1200-second timeout limit. Note that baseline boxplots may appear compact or low in certain cases; this reflects survivorship bias, as these distributions include only the few participants who localized the fault, while the majority timed out and are placed as failed cases.）

三类故障中的定位与修复耗时（Figure 9: Case-by-case comparison of time-to-localize and time-to-fix across different bug cases. Case 1: Random Segmentation Fault; Case 2: Logic Error; Case 3: Distributed Deadlock. The GDB outlier in Case 3 corresponds to a participant who resolved the fault based on prior intuition rather than systematic tool-guided diagnosis.）

屏幕记录显示，OpenTelemetry 参与者花费较多时间配置埋点并在追踪视图和日志间切换；GDB 参与者则要管理多个进程和线程。在时间敏感的故障中，暂停单个进程还会让调用方超时，迫使参与者重启调试会话。DDB 的全局暂停、断点传播和跨 RPC 状态检查共同减少了这些手工步骤。

这项用户研究的三个故障均可复现。作者将 DDB 定位在早期开发和原型阶段；它不解决故障重现问题，对线上不可重现故障，论文认为可观测工具和记录回放仍更合适。DDB 以 GDB 为底层调试器，并有实验性 LLVM 调试器（LLDB）支持；目标二进制需能由相应调试器管理，嵌入调试符号并降低编译优化时可获得更好的调试体验。依赖精确线程交错的并发故障不在 DDB 的暂停式调试范围内；论文把记录回放作为另一类工具，描述其目标是重放已记录的非确定执行。
