CrystalLLM：用少量 GPU 高保真仿真大规模 LLM 训练

论文：A Few GPUs, A Whole Lotta Scale: Faithful LLM Training Emulation with CrystalLLM，Shaoke Xi、ChonLam Lao、Boyi Jia、Jiaqi Gao、Zhipeng Zhang、Jiamin Cao、Brian Sutioso、Erci Xu、Minlan Yu、Kui Ren、Yong Li、Zhengping Qian、Ennan Zhai、Jingren Zhou，SOSP ’26（2026）。论文 DOI。实现：AlibabaResearch/CrystalLLM。

TLDR： CrystalLLM 用少量 GPU 采集、校准各 GPU 训练进程（rank）的执行图，目标 rank 跑真实代码，其余 rank 重放通信。Qwen3 混合专家（MoE）评测中，迭代时间平均误差为 0.58%，显存误差低于 0.01%。

一、背景：训练栈需要全规模验证

大语言模型（large language model，LLM）训练已运行在数千到数万张 GPU（图形处理器）组成的集群上。与模型规模同步增长的还有训练软件栈：工程师需要从训练遥测和故障中定位问题，在 Python 编排、分布式运行时、通信库和 CUDA（NVIDIA 的 GPU 并行计算平台）内核中实现改动，再用真实训练配置验证效果，最后在检查点等允许的时机部署。

这类迭代需要复现生产环境中的行为。通信与计算重叠、集合通信争用、同步异常和显存压力，都可能只在大规模下出现；小规模验证通过，并不能证明生产配置也有效。论文指出，生产集群的大部分 GPU 已投入训练，留给开发和调试的通常只有数十或数百张 GPU，而生产任务本身需要数千到数万张。若测试必须等待大规模集群腾出资源，系统迭代就会延迟。

二、现状：缩小配置改变性能条件

一种办法是用仿真器代替真实训练。仿真器根据运行轨迹、算子级性能剖析（profiling）数据或分析模型估算训练行为，不必为每个配置同时运行完整 GPU 集群，适合早期探索；但结果只覆盖模型显式表示的因素。GPU 内核调度和热降频无法直接从这类描述中得出；框架、编译器、内核、网络和硬件演进后，相关模型还要重新校验和维护。论文测得，PyTorch Profiler 会使一个 128-GPU Qwen3 训练任务的迭代时间增加最多 20.04%，而专为重放设计的表示可以避免记录不必要的算子细节。

另一种办法是在少量 GPU 上运行完整软件栈，同时缩小模型、批量大小或并行度。这保留了真实代码，却改动了运行配置。以观察流水线并行中的通信为例，GPU 数减少后，数据并行（data parallel，DP）、专家并行（expert parallel，EP）和张量并行（tensor parallel，TP）通常也要收缩，虚拟流水线并行（virtual pipeline parallel，VPP）度和全局批量大小随之调整。作者举例，缩小后若微批次数不足以驱动流水线调度，训练代码就需要特殊处理；原文称生产运行中不会出现这种情况。缩小规模还会改变每张 GPU 的工作量、显存布局和通信瓶颈，使诸如 CPU 激活值卸载（将激活值暂存到主机内存）的收益无法直接外推到生产环境。

三、优化点：逻辑规模与物理 GPU 解耦

工程师排查问题时，通常只需观察目标 rank 的一个子集；论文举例是 8 张 GPU。工程师可以检查这些 rank 的执行路径和显存，也可以观察最后完成一次迭代的 rank；其余 rank 仍需参与分布式通信，但不必同时执行真实计算。因此，本文要解决的问题是：在保留目标规模交互关系的同时，只用少量物理 GPU 运行需要观察的 rank。

四、方案：分片采集并重放执行图

本文把分布式训练中的每个工作进程称为 rank。CrystalLLM 分成两个阶段：先在少量 GPU 上采集目标配置中各 rank 的执行图，再让目标 rank 运行原训练程序、由虚拟 rank 重放其余执行。执行图记录计算、通信和跨 rank 依赖，重放时虚拟 rank 仍会与目标 rank 进行真实通信。

CrystalLLM 的图准备与混合仿真流程（Figure 1. System overview. Phase 1 (graph preparation, §4) collects the bare graph via context switching (Stage 1) and fills and calibrates timing (Stage 2) to produce the execution graph. Phase 2 (hybrid emulation, §5) runs the ranks of interest on sandbox GPUs while virtual ranks replay the graph on assistant GPUs.）

CrystalTrace 保留必要依赖

CrystalLLM 使用 CrystalTrace 表示训练执行图。图中的节点对应一段计算或一次通信事件，记录唯一标识和 GPU 侧持续时间；边记录节点间的依赖，包括同一 rank 内的先后关系，以及集合通信、匹配收发等要求多个 rank 同步到达的关系。采集粒度可以是一个微批次，使每个调度单元保留足以重放后续通信的依赖边界。

CrystalTrace 所示 1F1B 流水线调度的依赖关系（Figure 2. Snippet from CrystalTrace capturing dependencies of 1F1B.）

CrystalTrace 记录 CUDA 事件，不单独记录 CPU 时间戳。CPU 数据加载停顿或内核排队会表现为 GPU 事件之间更长的间隔，因此仍会进入重放时序。与面向性能分析的算子级 trace 相比，这种表示只保留重放所需的信息。

上下文切换采集裸图

采集阶段先得到不含准确时序的裸图（bare graph）。协调器维护所有逻辑 rank 的执行状态，在每张可用 GPU 上调度一个 rank 子集；rank 运行原程序，直到阻塞在集合通信等通信点。若参与同一操作的 rank 尚未全部就绪，协调器保存当前 rank 的通信输入和 GPU 上下文，换入能推进该操作的 rank。收齐所需输入后，CPU 集合通信执行器计算输出，解除等待的 rank，再继续调度。重复这一过程，就能逐步采集所有 rank 的操作和依赖。

用上下文切换采集执行图（Figure 3. Context switch to generate graph.）

因为每个 rank 都执行原始训练代码并使用真实张量，采集能够沿着实际数据相关的控制路径运行。对已知工作负载，也可以直接提供通信输入张量来绕开 GPU 上下文切换；通常权重和梯度只影响数值计算，而数据加载状态、词表索引和 MoE all-to-all（全到全）集合通信的切分大小则可能改变控制流或内存分配，需要提供有效输入。

GPU 上下文切换（context switching）的采集开销可能很高。论文以一个 235B 混合专家（MoE）模型、2048-rank 目标配置为例，使用 32 张 GPU 时，纯上下文切换采集约需 9 小时；提供通信输入后，采集变成约 64 轮、每轮约 1 分钟。数据并行副本的执行图结构相同，因此只需采集一个包含 32 个模型并行 rank 的副本；论文报告可进一步降至单轮、约 1 分钟。若并行度或集合通信元数据改变，需要重新采集；仅改变计算或显存行为时，可以复用图并重新校准时序。

切片实测与全局时序校准

上下文切换适合收集执行结构，但切换本身会扭曲持续时间。CrystalLLM 因此把训练任务切成多个 rank 子集，依次运行每个 slice（切片）：当前切片中的 rank 在沙箱 GPU（sandbox GPU）上执行真实计算和通信，其他 rank 依照裸图重放，作为通信对端。轮流运行后，每个 rank 至少有一次真实执行记录，得到切片内的准确时序。

各切片的时间线只在局部对齐。CrystalLLM 再利用跨切片依赖校准全局时间，例如约束后一切片中的 receive（接收操作）必须发生在前一切片对应 send（发送操作）之后，并沿依赖关系传播时间偏移。这样可以把切片内测得的时序组合成与目标规模一致的执行图。

执行图生成的采集与时序校准流程（Figure 4. Workflow for generating the execution graph for emulation. Block colors: light green = forward (F), yellow = backward (B), purple = send (S), dark green = receive (R).）

虚拟 rank 与目标 rank 实际通信

最终仿真只让指定的目标 rank 在沙箱 GPU 上运行原始程序，其余 rank 作为虚拟 rank，由辅助 GPU（assistant GPU）按校准后的执行图重放。虚拟 rank 到达计算节点时等待记录的持续时间，到达通信节点时则通过 NCCL 与目标 rank 进行真实通信。所需张量从采集记录或用户提供的数据中读取；运行时优先把后续通信需要的张量从磁盘预取到 GPU 缓冲区，GPU 空间不足时暂存在 CPU 缓冲区。论文给出的前提是 PCI Express（PCIe）预取带宽（例如 64 GB/s）高于消费这些数据的网卡（network interface card，NIC）带宽（例如每个 NIC 50 GB/s），从而使数据能及时到达。

若为所有虚拟 rank 建立完整的 NCCL（NVIDIA Collective Communications Library）通信组（communicator）和缓冲区，初始化会消耗大量资源。CrystalLLM 只实例化与目标 rank 所在组重叠的通信组；仿真 2000 个虚拟 rank 时，活跃 NCCL 通信组从 8617 个降至 82 个。辅助节点（assistant node）上的代表 rank（leader）代替被省略的 rank 完成初始化屏障与拓扑信息交换，保持训练程序看到的全局 rank 数（world size）不变。

运行时还会剪除不影响目标 rank 的虚拟通信。在 ring 或 tree 集合通信中，目标 rank 只与通信路径上的相邻 rank 直接交换数据，因此远离目标 rank 的虚拟 rank 可以省略。

ring 与 tree 通信路径上的相邻虚拟 rank（Figure 5. Runtime communication pruning: only vRanks adjacent to the sandbox on the ring (a) or tree (b) path participate.）

这种剪枝改变了原集合通信的参与者，但目标 rank 仍需得到与完整通信组相同的数值结果。对 AllReduce（先归约组内张量、再把结果分发给成员），CrystalLLM 调整边界虚拟 rank 的输入，使目标 rank 负责的数据块与完整通信组结果一致。

通信剪枝下 ring all-reduce 的数值正确性（Figure 6. Collective numerical correctness under pruning (ring all-reduce; sandbox Ranks 43–44, neighboring vRanks 42/45, pruned non-neighbors omitted). Each row is a chunk. (a) Reduce: the leftmost vRank pre-subtracts sandbox contributions (K−1, K−2) so sandbox-owned chunks accumulate correct full values (VAL); other chunks carry arbitrary values (ANY). (b) Broadcast: the leftmost vRank supplies full values for all chunks.）

执行图复用的适用范围

CrystalLLM 假设同一程序和训练配置会产生相同操作序列，数据并行副本的执行图具有对称性，并且数据预取能跟上网络消费速度。原型支持通过 NCCL 通信的 PyTorch 训练任务，论文以 Megatron-LM 工作负载评估。配置改变并导致执行图或通信元数据变化时，必须重新采集；目标硬件或待测代码尚不存在、运行时数据会改变控制流（例如部分强化学习后训练）、问题依赖所有 rank 长期共同计算、全局拥塞或瞬态慢节点分布时，固定图重放不能代替全规模运行。原型也尚不支持融合计算与通信的内核。

五、结果：时延精度与资源成本

端到端预测覆盖时延与显存

评测在一套 2048-GPU 测试集群上进行，每台机器有 8 张 GPU；训练实现采用 Megatron-LM 的 Qwen3 混合专家（Mixture of Experts，MoE）预训练代码。模型包括 235B-A22B、503B-A20B 和 1.01T-A43B，参数覆盖 94 或 62 层、64 或 32 个注意力头、128 或 256 个专家；TopK=8 表示每个 token 路由到 8 个专家。实验改变 TP、流水线并行（pipeline parallel，PP）、VPP、EP 和梯度累积步数，覆盖 512、1024 和 2048 GPU 目标规模。基线训练运行 85 个迭代，报告去掉预热后的中间 70 次迭代中位数；显存实验先预热 10 次，再测量 3–10 次。MoE 显存实验还分别测量均衡路由和通过模拟路由器（mock router）注入偏斜路由分数（logits）的情况。

跨模型、规模和并行配置，CrystalLLM 的迭代时间预测平均误差为 0.58%，最大误差为 1.98%。峰值 GPU 显存估计误差低于 0.01%，并能复现基线中的显存不足（out-of-memory，OOM）错误。内核级评估以同一 DP 组内 32 个基线 rank 的中位数为参照，并将 rank 间偏差视为硬件自然波动。在 1024-rank 配置中，CrystalLLM 的内核持续时间误差落在该波动范围内；以总迭代时间归一化的内核启动时刻最大误差为 3.64%。

扩展规模时的物理开销与用途

论文将 503B 模型的流水线并行度从 4 提高到 64，把目标规模扩展到 8192 GPU，同时保持数据并行度不变。随着流水线加深，增加 assistant 节点可并行测量流水线阶段；采用这一配置后，CrystalLLM 报告从 512 到 8192 GPU 的仿真时间均低于 80 分钟，图采集约 4 分钟。若不增加 assistant 节点，1024-GPU 配置需要顺序处理 8 个流水线阶段，仿真时间为 125 分钟，约为该配置按比例增加 assistant 节点时的 1.6 倍。

仿真耗时分解（Figure 9. Emulation time breakdown.）

8192-GPU 配置使用 16 台 sandbox 节点和 16 台 assistant 节点。这里有一处口径不一致：论文称这套物理部署使用的 GPU 少于目标 GPU 数的 0.4%；但表 3 标注每节点有 8 张 GPU，因此 32 台节点实际是 256 张 GPU，占 8192 张 GPU 的 3.125%。低于 0.4% 对应的是把 32 台节点除以 8192 张 GPU，单位并不相同。论文摘要另称所需 GPU 少于目标的 1%，也与表中节点数折算结果不一致。

虚拟 rank 初始化实验显示，标准 NCCL 为 512 个 rank 创建独立进程、CUDA context（GPU 执行上下文）和缓冲区时，会用掉 544.5 GB CPU 内存与 103.7 GB GPU 内存，耗时 756 秒；该基线在 1024 个 rank 及以上发生 OOM。CrystalLLM 初始化 8192 个 rank 用时 44.3 秒，每张物理 GPU 使用 5.4 GB 显存。通信剪枝也避免虚拟 rank 与目标 rank 争用流式多处理器（streaming multiprocessor，SM）、显存和 PCIe 带宽：32-rank 测试中，未剪枝方案的传输时延最高膨胀 148 倍，CrystalLLM 的最大误差为 0.2%。单 assistant 节点承载 128 个 rank 时，大消息仍会受节点内带宽限制；例如 32 GB AllReduce 为 267.42 ms，基线为 177.62 ms，作者通过横向增加 assistant 节点缓解这一瓶颈。

集合通信的传输时延开销（Figure 13. Latency overhead.）

上述评测衡量 CrystalLLM 自身的资源开销；论文还在各仿真器支持的配置范围内比较了预测精度。在 Phantora 支持的 Qwen3 4B、32-GPU、TP=4 测试中，序列长度为 4096 时预测误差约为 12%，降到 1024 时误差升至 64%。

CrystalLLM 与仿真器的预测结果比较（Figure 14. CrystalLLM compared with Simulators.）

在 235B MoE 模型和多个并行策略的比较中，SimAI 的迭代时间平均误差为 77.2%。附录汇总了不同规模和策略下的预测结果；论文将误差归因于 workload 文件未表达流水线并行中的通信气泡，也未计入 MoE 门控（gating）、张量重排（permute）、专家分发（dispatch）和结果合并（combine）等计算开销。SimAI 不支持显存分配模拟，因此没有参与显存对比。

CrystalLLM 与 SimAI 的迭代时间预测（Figure 15. End-to-end iteration time estimation results compared with SimAI.）

生产使用案例包括并行度和显存策略调优、显存分析与集群健康检查。作者报告，CrystalLLM 用 16–32 张 GPU 搜索配置，并在一次搜索中复用同一执行图评估 90 种策略；其生产实践中找到的配置比人工调优配置高 3–5% 模型 FLOPs 利用率（Model FLOPs Utilization，MFU）。针对 MoE 路由不均，模拟路由器可重放生产观测到的偏斜特征；作者报告，早期阶段的路由不均会使迭代时间延长超过 5%，显存波动最高达 20 GB。换用一个注意力（attention）内核后，最大可训练序列长度下降 13%；快照显示激活值变得细碎，小张量占据了此前可放置大块激活值的内存区段，使每个 rank 的保留显存高水位（reserved watermark）增加了该 GPU 显存的 9%。在另一次临时张量延迟释放问题中，reserved 指缓存分配器向 GPU 预留的显存，allocated 指当前张量使用的显存；问题修复后，reserved 与 allocated 的差值从每个 rank 显存的 19% 降到 8%。一次集群筛查中，某 sandbox 节点迭代时间为 6.40 秒，而其他配对节点中位数为 5.70 秒；检查发现其 GPU 因热降频运行在 900 MHz。CrystalLLM 提供的是正常训练行为的可重复基线，能帮助定位偏离基线的节点，但不会合成罕见故障本身。
